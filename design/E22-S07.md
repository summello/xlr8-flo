# E22-S07 — People have a display name: stored, copied at acceptance, returned beside every email

**Epic** E22 · **M3** · **migration/M** · tags: migration

> Operator decision, 21 Oct 2026: canvas DECISIONS **232**, amending **D-M2-16** ("people are shown
> by email"). People are shown by display name with the email as secondary text and as the fallback.
> Back end only; the UI is **E22-S09**.
> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (§O for the PATCH),
> `docs/author-traps.md`.

## Requirements (inlined)

- **USR-009** — Deactivating a user must block new sessions without deleting historical attribution.
- **USR-010** — Administrators must be able to inspect a user's effective access and the source of inherited permissions.
- **SEC-011** — Errors never leak a stack trace, query, path or internal hostname.

## Design

**Column.** `identity.display_name text NULL`, `CHECK (display_name IS NULL OR length(btrim(display_name)) BETWEEN 1 AND 200)`.
`identity` is not tenant-scoped (one person, many orgs), so this is one name per person.

**Backfill (in the migration).** For each identity with a null name, take `full_name` from its most
recent **used** invitation (`used_by = identity.id`, latest `used_at`) where `full_name` is not null.
Down drops the column. Data-preservation test: a backfilled name survives up→down→up as backfill again.

**Acceptance copies it.** `modules/identity/invitation.py` `mark_used` already stores `full_name` on
the invitation; in the same transaction, set `identity.display_name` **only when it is null**
(`COALESCE`), so a person who joins a second org keeps the name they already have.

**Editing.** `PATCH /api/v1/me` gains `display_name` (1..200 after trim, or `null` to clear), with
`If-Match` per §O, and one audit row `identity.display_name.set` in the **current** org (the
session's), since the identity is global. A person edits only their own name; administrators do not
edit names in M3.

**Returned beside every email.** Every response schema that carries a person's email for display
gains a sibling `*_name: str | None` read from `identity.display_name`: the approver picker, requester
and "on behalf of" fields, decision trails and explanations, delegation lists, vendor contacts that
link to an identity, user administration lists, and `GET /me`. Find them with
`grep -rn "_email" apps/api/src/flo/modules/*/schemas.py`; each gains the name in the **same query**
(a join, not a per-row lookup). Search that filters people by email prefix also matches a
case-insensitive name prefix.

## Acceptance

- [ ] Migration: up adds the column and backfills from the latest used invitation; down drops it; data-preservation assertion as above.
- [ ] Accepting an invitation with `full_name` sets the name when null and leaves an existing name unchanged (second-org case).
- [ ] `PATCH /me` sets, trims, rejects 0 or 201 chars (422) and clears with `null`; stale `If-Match` → 409; audited.
- [ ] A test lists every schema field ending `_email` that describes a person and asserts a sibling `_name` exists (so the next schema cannot forget it).
- [ ] People search matches `ali` against a display name `Alice Ng` and against `ali@…`.
- [ ] TEN-010: a name is visible only where the email already was (no new endpoint exposes identities across orgs).
- [ ] `flo check` green; the generated API client is regenerated.

## Plants

1. Overwrite an existing name at acceptance: the second-org test fails.
2. Remove `requester_name` from one schema: the sibling-field test fails.

## Files

One migration, `modules/identity/{invitation,service,schemas}.py`, the schemas that carry person
emails, `api/me.py` (or wherever `/me` lives), tests, the generated client, and `docs/m2-decisions.md`
(D-M2-16 marked amended by 232).
**Out of scope:** every UI change (E22-S09), administrator editing of names, and avatars.
