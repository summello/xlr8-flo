# E13-S26 — An issued purchase order stays immutable after it is closed or cancelled

**Epic** E13 · **M3** · **migration/S** · after **E13-S06**, **E13-S07**, **E13-S16** · tags: `migration`
Origin: M3 epic checkpoint E13 (codex-a finding 1, 8 Nov 2026).

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Migrations:** reversible, tested up/down against a seeded database; chain onto the current head.

## Requirements (inlined)

- **PO-011** — A change order must preserve the prior version, identify changed fields/lines, recalculate budget effects, and be reapproved when policy requires.
- **PO-013** — Cancelling or reducing a PO must release the unused commitment exactly once and must not erase its history.
- **PO-014** — Generated PO PDFs must be reproducible from the stored PO snapshot and template version.

## Defect

`migrations/20261029_0084_po_change.py` defines `purchase_order_immutable()` and `po_line_parent_immutable()`.
Both protect a row only while its parent status is `issued` or `superseded` (lines ~59 and ~98). The
`issued → cancelled` and `issued → closed` transitions are allowed (line ~53), and from then on the trigger
returns early: a raw `UPDATE`/`DELETE` of the header or its lines succeeds. The issued record of a closed or
cancelled PO is therefore not protected by the database, only by application code.

## Design

New migration (next number on the head at authoring time; today `20261102_0089` is the head) that
`CREATE OR REPLACE`s both functions. `downgrade` restores the 0084 bodies verbatim. Rules, in this order
inside `purchase_order_immutable()`:

1. **A terminal status is frozen, issued or not** (planner ruling, pre-flight 2): `IF TG_OP = 'UPDATE' AND
   OLD.status IN ('closed','cancelled') AND NEW.status IS DISTINCT FROM OLD.status THEN RAISE
   'issued_is_immutable: ...'`. Guard on `TG_OP = 'UPDATE'`: the trigger also fires on `DELETE`, where `NEW` is
   null (0084 line ~91). Both statuses are terminal in `purchasing/lifecycle.py` `TRANSITIONS` (no pair leaves
   either), so this enforces the existing table and adds no transition.
2. **An issued row leaves for `closed` or `cancelled` only stamped** (planner ruling, pre-flight 3): in the
   transition branch, additionally refuse when `NEW.status IN ('closed','cancelled') AND OLD.issued_at IS NULL`.
   Both application issue paths stamp in the same transaction as the transition (`issue.py` ~168-173,
   `changes.py` ~818-823), so no committed issued row is unstamped and no application path changes. This is
   what makes rule 3's predicate complete: every closed/cancelled row that was issued carries `issued_at`.
   The unstamped `issued` row the existing test builds (`tests/purchasing/test_changes.py` ~214-235) stays
   legal; it just cannot become terminal until stamped.
3. **Protected set** (every 0084 rule: no `DELETE`, no non-lifecycle column edit, stamp once, lines frozen) =
   `OLD.status IN ('issued','superseded')` (exactly as today, stamped or not) **or**
   `OLD.status IN ('closed','cancelled') AND OLD.issued_at IS NOT NULL`. For a protected terminal row the
   transition branch never applies (rule 1 already refused any status change); the no-transition branch
   refuses a version change and any stamp write (the stamp is already whole). Outside the set, return
   `CASE WHEN TG_OP = 'DELETE' THEN OLD ELSE NEW END` as today: a PO cancelled before issue
   (`issued_at IS NULL`) keeps today's column, line and `DELETE` behaviour; only rule 1 touches it.

`po_line_parent_immutable()`: the `frozen` lookup becomes `p.status IN ('issued','superseded') OR
(p.status IN ('closed','cancelled') AND p.issued_at IS NOT NULL)`; nothing else changes.

Exception texts keep the `issued_is_immutable:` prefix the database tests match on. The API never sees
them: the service refuses first (`purchasing/service.py` ~944 `_draft`: `issued_is_immutable` for
issued/superseded, `po_not_draft` for every other non-draft); a raw-SQL bypass surfacing as a 500 is correct.

**Application writes checked (planner, 8 Nov, against the milestone head):** every `UPDATE purchase_order` /
`po_line` write in `apps/api/src/flo/modules/` runs on a draft or approved PO or inside the issue / change-apply
transaction before the row is terminal (`service.py` ~882/996/1080/1142 draft edits, `issue.py` ~84/115/170,
`changes.py` ~812/820, `lifecycle.py` ~87 the transition itself). `cancel.py` and `transmission.py` write no
`purchase_order` or `po_line` column; resend and change-recipient write `po_transmission` only. Re-run the grep
before writing; if a new write on a closed/cancelled issued PO has appeared, stop and write `notes.blocked`, do
not widen the excluded-column list.

**Existing tests this changes (update them, in this diff):**
- `tests/purchasing/test_po_lifecycle.py` `setstatus` forces `issued` without a stamp, then
  `test_every_status_and_action_pair_moves_or_is_refused` and `test_close_needs_a_reason_...` close/cancel it
  through `transition()`: rule 2 now refuses with a `CheckViolation`. Make `setstatus` also write
  `issued_at = now(), issued_by = <db[3]>` when the target is `issued` (still under `session_replication_role =
  replica`).
- `tests/purchasing/test_cancel_notice.py` ~284 raw-updates a cancelled PO to `superseded`: rule 1 now refuses.
  Force it the way `test_po_lifecycle.setstatus` does (`SET LOCAL session_replication_role = replica` inside
  `tenant_transaction`).
- Run every file under `tests/purchasing/` and `tests/kernel/test_migrate.py`; any other raw transition out of
  a terminal status, or out of an unstamped `issued`, is forced the same way, never by loosening the trigger.

## Acceptance

- [ ] pytest (real Postgres): for an issued-then-closed and an issued-then-cancelled PO (issued through the
      service, so stamped), a raw `UPDATE` of a header money column, a raw status change, a raw version bump,
      a `DELETE`, and an `INSERT`, `UPDATE` and `DELETE` on its `po_line` each raise `issued_is_immutable`.
- [ ] pytest: an unstamped `issued` row (raw status + version bump, as `test_changes.py` ~214) refuses a raw
      transition to `closed` and to `cancelled` with `version = version + 1`; after the whole stamp is written
      the same transition succeeds and the row is then protected.
- [ ] pytest: a PO cancelled before issue (draft -> cancelled through `transition()`) can still have a
      non-status header column updated, a `po_line` updated, and be `DELETE`d (with its lines, lines first) as
      today; a raw status change on it raises `issued_is_immutable`.
- [ ] pytest: `test_the_issue_stamp_is_written_once_and_whole`, the close and cancel service paths, resend and
      change-recipient tests, and the whole of `tests/purchasing/` stay green (with the two helper changes above).
- [ ] Migration up, down, up on a seeded database (`tests/kernel/test_migrate.py`, beside
      `test_po_attachment_vendor_mark_migration_roundtrips_and_guards`): after down, an issued-then-closed PO
      is editable again (0084 behaviour); after up, refused; row data identical across the round trip.
- [ ] `flo check --light` green.

## Plants

1. Drop `closed` from the protected set: the issued-then-closed raw-update test fails.
2. Protect every cancelled PO regardless of `issued_at`: the cancelled-before-issue test fails.
3. Remove the `TG_OP = 'UPDATE'` guard from rule 1: the cancelled-before-issue `DELETE` test fails.
4. Remove rule 2: the unstamped-issued-to-closed test fails.
