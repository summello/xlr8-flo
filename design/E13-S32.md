## Requirements (inlined)

- **PO-007** — The lifecycle should support Draft, Approval Pending, Approved, Issued, Partially Delivered, Delivered, Accepted, Closed, Cancelled, and Superseded. E13-S06: a change order writes a new revision (same number, `revision + 1`) and the old row becomes `superseded`; E13-S12: a superseded revision is reached from the current PO's versions and history, and its page shows a notice with a link to the current one.
- **EML-003** — A hard-bounced or complained address must enter a suppression list and must not be retried silently; the PO must show as undelivered and be actionable (PO-015). E13-S10: a provider event moves `po_transmission.result`, and a hard bounce or complaint adds the address to `email_suppression`.
- **VEN-012** — A vendor that is inactive, suspended, expired, or not approved must not be invited or selected unless policy explicitly permits an authorized override. E11-S06: `pending_approval` is the status while a create request is in approval; the approver decides on the record as submitted.
- **SEC-011** — User-visible errors and API errors must not expose secrets, queries, stack traces, filesystem paths, or internal topology. Here: the webhook must not become an oracle for which message ids exist.

## 1. The PO list shows every superseded revision as its own purchase order

`modules/purchasing/service.py` `list_orders` (~457-560): `where` filters only `p.status <> 'deleted'`, so a PO with two applied change orders is three rows with one number and counts three in the `all` tab. The tab counts are computed from `where` alone, while the rows also apply `after` (the `q` search and the cursor), so with a search the counts and the rows disagree.

Fix:

- `where` becomes `p.status NOT IN ('deleted', 'superseded')`. A superseded revision stays reachable by id, through `versions()` and the history, exactly as today; only the list drops it.
- The counts apply the `q` condition and not the cursor. Split what is now `after` into the search condition and the cursor condition; counts use `where` + search, rows use `where` + search + tab + cursor. Do not change the page shape.

## 2. A delivery event that arrives before its route row is acknowledged and lost

`api/webhooks.py` `_apply` (~25-46): the org of an event comes only from `email_message_route`, which `OutboxStore.sent()` (`kernel/outbox/store.py` ~230-251) inserts after the provider call returns. An event that reaches the webhook before that commit finds no route, gets 200, and the provider never retries: a hard bounce is never suppressed and the transmission stays `sent`.

The webhook cannot simply refuse unknown ids: every non-PO email (invitations, approvals) has no route by design and would fail forever. Mark PO emails at send time instead, and retry only those.

Fix:

- **Send:** `kernel/adapters/resend.py` `send` (~75-100) adds `"tags": [{"name": "kind", "value": "po"}]` to the request body when the template name starts with `po-` (the same test `OutboxStore.sent()` uses at ~243-246; share one small predicate in `kernel/outbox/`, do not write the prefix twice). Resend's send API takes `tags` as an array of `{name, value}`, ASCII letters, digits, `_` and `-`, 256 characters at most. Other emails send no tags, as today. If `send` does not receive the template name today, pass it through from the dispatcher; do not parse the subject or body.
- **Webhook:** Resend's event payload carries the tags as an object map, `data.tags == {"kind": "po"}`, and the event time as top-level `created_at` (ISO 8601). In `_apply`, when `email_route` returns `None`:
  - `data.tags` is a dict with `kind == "po"` **and** top-level `created_at` parses and is less than `UNROUTED_RETRY_SECONDS = 3600` old (by `time.time()`, as the signature check does) → the route answers **503** with an empty body, so the provider retries. Log one line at warning level with the event id only (never the message id's org, never the body).
  - anything else (no tag, another kind, missing or unparsable `created_at`, older than the window) → 200 and nothing stored, as today.
- The signature check stays first: an unsigned request never reaches this branch, so the 503 is not an oracle for anyone who cannot already sign as the provider. Return the 503 as a plain `Response(status_code=503)`, not a `ProblemError` (no problem body on this route's non-2xx, as the 401 path decides; follow whatever the 401 does if it differs).
- `_apply` runs in `asyncio.to_thread`; have it return a bool (retry or not) rather than raise.

`# ponytail:` the window is one constant; if `sent()` fails for good after the email left, events for that message are retried for an hour and then dropped. A stored-unrouted-event table is the upgrade if that ever shows in the logs.

## 3. A `vendor.edit` holder can change a vendor while its create request is in approval

`modules/vendors/changes.py` `can_write_draft` (~121-140) is the gate for every name, contact, identifier, document and sensitive write (callers: `service.py` 386, 529, 701, 739, 767; `documents.py` 68, 205, 271). It returns `"edit"` for a `vendor.edit` holder in **every** status. While the status is `pending_approval` an approver is deciding on the record: a legal name, a bank account or the `receives_documents` contact can change between their read and their decision.

Fix, in `can_write_draft` only: after the lock, when `status == "pending_approval"` raise `conflict("pending_approval", "This vendor is awaiting approval. Withdraw the request or wait for the decision before changing it.")` for the `vendor.edit` branch, before returning `"edit"`. The requester branch already refuses with `not_draft` after submit; leave it. Every other status behaves as today.

Before changing it, read each caller. If any of them is a write the **approver** must make during approval (document verification is the candidate: `documents.py` ~205/~271), do **not** block that write: report it in `notes.blocked` with the file and line and stop on part 3 only (finish parts 1 and 2). Do not guess which approval-time writes are intended.

Out of scope for this part: changes to an `active` vendor's bank details or contacts without approval. That needs a new `vendor_change` kind, an approval route and a screen, and is recorded for the operator as a separate story.

## Acceptance

- [ ] **List:** a PO with one applied change order appears once in `all` and in `issued` (the live revision), and each count is 1; the superseded revision's `get` still works and `versions()` still lists both.
- [ ] **Counts with search:** two POs, `q` matching one number → rows 1, `all` count 1; the second page of a long list keeps the same counts as the first (the cursor does not shrink them).
- [ ] **Tag on send:** the Resend request body for a `po-…` template has `tags == [{"name": "kind", "value": "po"}]`; for any other template the body has no `tags` key (adapter test with the existing HTTP stub).
- [ ] **Webhook, unrouted:** signed event, unknown `email_id`, `data.tags == {"kind": "po"}`, `created_at` now → 503, nothing stored. Same event with `created_at` two hours old → 200. Same event without tags, or with `{"kind": "other"}`, or with `created_at` missing or `"nonsense"` → 200. Unsigned → 401 as today (before any of this).
- [ ] **Webhook, routed:** the existing delivered/bounced/complained tests stay green unchanged; an event with the tag whose route exists is applied and answers 200.
- [ ] **Late route:** an event answered 503, then `OutboxStore.sent()` writes the route, then the same signed event again (fresh timestamp header) → 200 and `po_transmission.result` moves; a hard bounce adds the suppression row.
- [ ] **Vendor freeze, per write (authorization test):** on a `pending_approval` vendor, a `vendor.edit` holder gets 409 `pending_approval` from name PATCH, contact create/update/delete, sensitive PUT (holding reveal too), document create and replace; the row and its children are unchanged. On `draft`, `active`, `suspended` and `rejected` each write behaves as before (existing tests green).
- [ ] The create request can still be withdrawn, approved and rejected while frozen (`tests/vendors` lifecycle tests green).
- [ ] TEN-010: no new endpoint; existing isolation cases green. `flo check --light` green.
