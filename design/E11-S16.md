- **VEN-005** — Vendor creation, activation, scope changes, suspension, and reactivation must support approval.

## Design

Five dialogs on `/vendors/:id`, each opened from a header action that renders only when the server
says the user may act:

| Dialog | Calls | Confirm label | Takes effect |
|---|---|---|---|
| `Suspend` (Destructive) | `POST /vendors/{id}/changes {kind:"suspend"}` | `Request Suspension` | after approval |
| `Reactivate` (Primary) | `…changes {kind:"reactivate"}` | `Request Reactivation` | after approval |
| `Change Availability` | `…changes {kind:"availability", payload}` | `Request Change` | after approval |
| `Disable Here` | `POST /vendors/{id}/units/{unit}/disable` | `Disable in <unit name>` | at once, no approval |
| `Enable Here` | `…/enable` | `Enable in <unit name>` | at once |

Each dialog has an intro, **consequence rows** (open RFQs and issued POs from the change evidence,
0 until E12/E13; whether approval is needed; whether it can be undone), a **required reason**
(except Enable Here), the **safe button focused** on open, focus trapped, and Escape to close and
return focus. `Disable Here` and `Enable Here` show only on a global vendor when the server says
local disable is allowed for the unit (the `vendor.allow_local_disable` setting and `vendor.edit`
there). Errors such as 409 `change_pending`, `workflow_not_set_up` and
`local_disable_not_allowed` are shown in the dialog in words (what happened, what was kept, how to
recover), and the reason text is kept.

After a request, the profile shows the pending change beside the unchanged status (`Suspension
requested by you, awaiting approval`). The status pill does not change.

## Amendment, 22 Oct 2026 (planner; canvas DECISIONS 238)

Review finding 1 (VEN-005) needs the caller's permitted vendor actions, and no non-admin endpoint exposes them.
Decided (no new rule, it exposes the routes' own checks):

- **Server (now in scope, vendors module + `VendorDetail` only):** `actions: list[str]` from the service, one entry per
  check the matching route makes: `edit`, `request_change` (`vendor.edit`, organization), `inactivate`,
  `verify_documents` (`vendor.approve`, organization). `local_disable_units: list[UUID]`: units where the caller holds
  `vendor.edit` on the unit target, empty when the vendor does not allow local disable. If E11-S13 has merged
  `sensitive_access` first, keep both fields side by side.
- **UI:** each header action and the Disable Here / Enable Here controls render only when listed; a view-only user
  sees none. The server still refuses a forced call (existing tests).
- Regenerate the API client.

Acceptance gains: API tests per role (vendor manager: edit, request_change; approver role with vendor.approve:
inactivate, verify_documents; requestor: none) and one for `local_disable_units` on a unit-scoped editor; the
view-only-user spec. Plants: return every action regardless of role, the requestor test fails; render the header
actions unconditionally, the view-only spec fails.
