## Screen `/sourcing/rfqs/:id/award`

Arrives from the comparison's `Start Award` with its basis (`?basis=<BasisName>` search param). E12-S10 merged
(`d8b6eb2b`) **without** the button: this story adds `Start Award` to the comparison's sticky award bar, replacing the
`ponytail:` comment at `apps/web/src/routes/sourcing/rfqs/comparison.tsx` ~93, and wires this route by hand in
`route-paths.ts` / `__root.tsx` as E12-S10 did. **Load or create:** the
route `GET`s `/api/v1/sourcing/rfqs/{id}/award`; on 404 with a `basis` param it `POST`s the same path with
`{basis}` (Idempotency-Key) and renders the 201 body; a 409 `award_exists` from that POST means another tab
created it, so it `GET`s again. Without a `basis` param a 404 shows the empty state with a link back to the comparison. Awarded lines show each line's vendor
and quantity (a line may split by quantity), and `Set All to Lowest` (the keyboard shortcut for the
common case, decision 156). Lines are saved with `PUT .../award/lines` (`If-Match`, §O). Each **not-lowest line** has a one-line `Justification`, marked Required
when the org setting is on (decision 157): the UI reads it from a new read-only `AwardRead.justification_required: bool`,
filled in `_read` from the same `effective_setting(unit_id, "sourcing.require_non_lowest_justification")` call `submit` makes
(`sourcing/awards.py` ~680); never from `/api/v1/org/...`, which needs `org.unit.read` the sourcing roles lack. A line that is **not** `not_lowest` but whose vendor is not the
comparison's `lines[].lowest.vendor_id` (a tied vendor other than the earliest submission) has a one-line
`Tie Override Reason`, always Required (the rule `submit` applies, `sourcing/awards.py` ~698); both fields go in
the line's `justification` / `tie_override_reason` (≤500). An **`Award Rationale`** text area (required, ≤2000)
above the action bar is saved with `PATCH .../award` `{rationale}` (`If-Match`). Submit's 422 `cannot_submit`
field errors (`rationale`, `lines/<rfq_line_id>/<vendor_id>`) map to those fields and the error summary. `Scope and Funds Check` shows, per requisition, the
scope, reserved funds, award amount and the result (server figures). The **verdict sits beside
`Total Awarded` and in the pinned action bar** (decision 156), so the deciding figure is never
carried from one place to another. The verdict is one selector over the server's `checks[]`: the first check
with a non-zero `over_scope_by` gives `Over scope by <figure> on <requisition>`, else the first with a non-zero
`over_funds_by` gives `Over reserved funds by <figure> on <requisition>`, else `Within scope and funds`. Zero is
tested on the decimal string (`/[1-9]/`), never by arithmetic in the browser. Over scope is refused **with the figure and the two ways out**
(change the selection; amend the requisition). Submit is never disabled. The released amount
(`<n> will be released and returned to <main project>`, decision 205) is a server figure, labelled
as what will happen on approval. **Server change in this story:** `RequisitionCheck`
(`modules/sourcing/awards.py`) gains `release: str` (`scope − award` when positive, else `0`, the exact `unused`
`_approved` passes to `release_unawarded`; `_approved` itself is **not** touched, this story adds a read-only field) and `main_project: str` (the number of the requisition's `project_id`, joined in the same `awarded` query
in `figures`). A check with `release` zero shows no release line. Add a test that, after approval, the amount posted by
`release_unawarded` equals the `release` the draft showed, and regenerate the API client.

**Permissions** mirror the server; the web has no client-side permission gate for sourcing (`RfqHeaderActions`
shows by status only): `GET` needs `rfq.view`, create / lines / rationale `rfq.edit`, Submit `rfq.approve`
(`api/sourcing.py` ~490–533). A 403 shows its problem detail inline and keeps the draft. `pages/sourcing.md` §1 lists
the route under `rfq.approve` only; the server is the authority, so record that drift in `notes.followup`.

With no published award workflow, a 409 shows: "No award workflow is published. Ask an
administrator to set one up. Your draft is kept." (decision 204). The button stays `Submit for
Approval`.
