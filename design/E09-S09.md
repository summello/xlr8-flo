# E09-S09 — Linked-record graph: RFQs, bids, awards, POs, approvals, notes, ledger entries

**Epic** E09 · **M2** · **api/M** · after **E09-S06**, **E09-S10** · tags: —

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (H registries) and `docs/author-traps.md`. Read `design/E10-S07.md` (`assert_current_approval`, latest instance). Screen consumer: the **Linked Records** card in `design-system/pages/requisitions.md` §2. It is a list, and the page spec says not to draw a graph ("The graph view is a gap"). This story serves nodes and edges so a later view can draw one, and the card lists the nodes.

## Requirements

- **REQ-009** — RFQs, bids, comparisons, awards, POs, approvals, notes, attachments, and budget entries must remain linked.
- **WF-001** — A downstream record must never be created from an unauthorized or stale upstream version.

## Design decisions (this packet)

- **Links are computed from the owning records, never stored twice.** Each kind of linked record has a provider that reads its own module's foreign keys. A link table would be a second copy that can drift. Providers are registered through `requisitions.service.register_link_provider(kind: str, provider: Callable[[Connection, Scope, UUID, ReadCheck], list[LinkedRecord]])`. M2 registers: `project` (the requisition's), `generated_project` (`projects.service.generated_for`), `approval` (each instance, through `approvals.service.instances_for`), `ledger_entry` (a new `budget.service.entries_for_source(conn, scope, "requisition", id)`), `note` and `attachment` (`collaboration.service` lists), and `revision` (E09-S08). M3 registers `rfq`, `bid`, `comparison`, `award` and `purchase_order` the same way. No M2 code mentions those kinds.
- **Each node is filtered by the caller's own access** to that record (a `ReadCheck` callable built from `kernel.authz.permits`): `project.read` for projects, `ledger.read` on the project for ledger entries, the adapter's `read_permission` (`requisition.view`) at the requisition's target for approvals (convention P), and the requisition's read for notes, attachments and revisions. A node the caller may not read is **omitted without a count** (a count would confirm existence).
- **Order** (closes `requisitions.md` open question 4 for M2): by `at` ascending, then kind in the order project, generated project, revision, approval, ledger entry, attachment, note. Every node is listed individually, not grouped. M3 decides PO grouping for itself.
- **The WF-001 guard lives here** because downstream creators will call into requisitions: `requisitions.service.assert_current_upstream(conn, scope, requisition_id, document_version) -> None`. It raises 409 `CONFLICT`, `checks.problem = "stale_version"`, with a WF-006 detail, unless the requisition is `sourcing_in_progress` or later and not terminal, has no pending amendment, its `version == document_version`, and `approvals.service.assert_current_approval(conn, scope, "requisition", id, document_version)` passes. M3's RFQ creation (E12-S01) calls it in its own transaction, after locking the requisition `FOR SHARE`.

## Contract

- `GET /api/v1/requisitions/{id}/links` — `requisition.view` (record) → 200 `{nodes: [LinkedRecord], edges: [{from, to, relation}]}`.
  - `LinkedRecord = {key: "<kind>:<id>", kind, id, label, state, state_tone, href, at}`. `label` is human: "Ledger entry LE-0318 · Reservation 196,000.00 USD", "Approval APR-00302 · Approved", "Project PRJ-0042 Plant 4 Line Retrofit". `state_tone` is one of the MASTER §2.3 tones (`neutral|info|success|warning|danger`), so the UI renders icon and words. `href` is the app route (`/projects/<id>`, `/projects/<id>/ledger?entry=<id>`, `/approvals?instance=<id>`).
  - `relation` ∈ `funds` (requisition → its project), `generated` (requisition → generated project), `reserves` / `releases` / `allocates` (requisition → ledger entry), `approved_by` (requisition → approval instance), `revision_of`, `attached`, `noted`. M3 adds `sourced_by`, `bid_on`, `compared_in`, `awarded_in`, `ordered_on`.
- Service exports: `register_link_provider`, `links(conn, scope, requisition_id, read_check)`, `assert_current_upstream`.
- `budget.service.entries_for_source(conn, scope, source_type, source_id) -> list[LedgerEntryRead]` (authorized addition, one query on `(org_id, source_type, source_id)`, served by the existing `ledger_source` index).

## Behaviour

1. `links` calls every registered provider, filters through `read_check`, sorts, and builds edges from the providers' `relation`. A provider that raises is logged with its kind, and its nodes are left out with `partial: true` added to the response (the UI's partial state, "Could not load linked records" per card). The other nodes are still returned.
2. No writes and no migration.
3. `COVERED` entry for the route.

## Acceptance criteria

- [ ] After submit, approve, an attachment and a note: nodes for the project, the generated project, the submission revision, the approval instance, the reservation ledger entry, the attachment and the note, with the edges above, in the stated order.
- [ ] After a withdraw following approval: a `releases` edge to the release entry, and the generated project's state reads Abandoned with tone `danger`.
- [ ] A caller without `ledger.read` on the project sees no ledger nodes and no count of them. A caller who cannot read the generated project sees no node for it.
- [ ] A test provider registered for kind `rfq` appears with its relation, which proves the M3 hook.
- [ ] A provider that raises gives `partial: true` and the other nodes.
- [ ] `assert_current_upstream` passes for an approved, unchanged requisition at its version, and raises `stale_version` for: an older version, a pending amendment (E09-S08), a `draft` or `approval_pending` requisition, a terminal one, and a superseded approval.
- [ ] Foreign tenant → 404. No grant → 404.

## Plants

1. Skip the per-node `read_check`: the no-`ledger.read` test fails.
2. Let `assert_current_upstream` ignore `pending_amendment_id`: the pending-amendment case fails.
3. Let one provider's exception propagate: the partial test fails.
