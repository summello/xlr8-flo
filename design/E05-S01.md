# E05-S01 — Organization and BU/OU with unique codes, settings precedence

**Epic** E05 · **M1** · **crud/M** · after **E02-S05** · tags: 

## Requirements

- **ORG-001** — An organization must support multiple Business Units and/or Operating Units, each with a unique code.
- **ORG-002** — Approval configuration must be definable organization-wide or per BU/OU, with a documented precedence rule.
- **ORG-012** — Authorized users must be able to determine which setting applies when organization and BU/OU configurations overlap.

## Design decisions (confirm on review)

- **D-M1-1 Settings precedence (ORG-002, ORG-012):** the nearest scope wins. Resolution order for a key at a BU/OU: that BU/OU, then each parent BU/OU up to the root BU/OU, then the organization default, then the built-in default. A BU/OU value never *merges* with its parent; it replaces it.
- BU/OUs form a tree (parent nullable), up to 5 levels (same cap as projects, PROJ-005).

## Contract

Schema (one migration, revision `20260826_0013`, `down_revision = "20260825_0012"`, reversible, RLS on every table via the existing tenant-policy pattern; an RLS-bypass planted test is required by the existing guard):

- `organization` already exists from E02? If the table exists, **extend**, do not recreate; otherwise create. Columns needed: `id uuid pk`, `name`, `base_currency char(3) not null` (FX-001), `created_at`.
- `org_unit(id uuid pk, org_id, parent_id uuid null fk org_unit, code text not null, name text not null, kind text check in ('bu','ou'), active bool default true, created_at)`; `UNIQUE (org_id, code)` (ORG-001); parent must share `org_id`; depth <= 5 enforced in the service with a recursive CTE, and by a trigger-free check constraint is not possible, so the service test covers it.
- `org_setting(id uuid pk, org_id, unit_id uuid null fk org_unit, key text not null, value jsonb not null, updated_by uuid, updated_at)`; `UNIQUE (org_id, unit_id, key)` using `NULLS NOT DISTINCT`.

Endpoints (router parses/authorizes only; logic in `modules/org/service.py`; permission codes `org.unit.manage`, `org.unit.read`, `org.setting.manage`, added to the existing permission catalog in the same migration):

- `POST /api/v1/org/units` (Idempotency-Key) → 201 `OrgUnitRead` | 409 `duplicate_code` | 422 depth > 5 / parent in another org→404
- `GET /api/v1/org/units` (tree flat list, cursor paging, filter by `kind`, `active`) → 200
- `PATCH /api/v1/org/units/{id}` (name, active; `code` is immutable once any setting or later project references it) → 200 | 404
- `PUT /api/v1/org/settings/{key}` body `{unit_id|null, value}` (Idempotency-Key) → 200
- `GET /api/v1/org/units/{id}/settings/{key}/effective` → 200 `{value, source: {scope: 'unit'|'org'|'default', unit_id, unit_code}}` (ORG-012: tells the user *which* setting applies)

## Behaviour

1. `org_id` from the session only. A foreign-tenant unit id returns 404, never 403.
2. Unit code uniqueness is case-insensitive per org (store upper-cased).
3. Deactivating a unit that has active child units is a 409 with the child codes in the problem detail.
4. Every write: audit entry (`org_unit.create|update|deactivate`, `org_setting.set`) in the same transaction.
5. Effective-setting resolution is one recursive CTE (unit → ancestors → org row → registry default). The registry of known keys and defaults is a module constant in `modules/org/settings.py` (`allow_negative_budget=false`, `funding_mode='roll_down'`, `fiscal_year_start_month=1`); unknown keys → 422.

## Acceptance criteria

- [ ] Two units in one org with codes `fin` and `FIN` → second returns 409
- [ ] Same code in two different orgs both succeed
- [ ] A sixth level returns 422 naming the depth limit
- [ ] A child BU value overrides the parent and org values; removing it falls back one level at a time; `effective` names the source scope each time (ORG-012)
- [ ] Foreign-tenant unit id → 404 on GET, PATCH, PUT-setting and effective (add all four to `tests/isolation/test_route_coverage.py` COVERED with real named tests)
- [ ] A user without `org.unit.manage` gets 403 on every write endpoint, including through the UI-hidden paths
- [ ] Replayed `Idempotency-Key` returns the first response and writes one audit row
- [ ] Migration up, down, and a data-preservation assertion (rows inserted at 0012 survive 0013 up/down)
