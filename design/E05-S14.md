## Why this story exists

E05-S13 delivers the API. Without a screen the email link opens nothing.

## Requirements

- **AUTH-003 / AUTH-004** — password follows NIST guidance, minimum 15 characters, paste allowed, no composition rules.
- **AUTH-007** — nothing on the screen reveals whether an account exists; every unusable link renders one message.
- **AUTH-006** — privileged roles continue to MFA enrolment after accept.
- **SEC-008 / TEN-010** — organization, role and scope shown come from the server record, never the URL.
- **A11Y-006** (AGENTS §3.4) — programmatic labels, field errors, summary, input preserved. **UX-004** loading/empty/partial/error states. **UX-005** errors say what happened, what was kept, how to recover.

## Contract

Route `/invite/:token`, outside the app shell, TanStack Router per existing conventions. On mount call `GET /api/v1/invitations/by-token` with the token in the `X-Invitation-Token` header; the token is read from the path **once**, then the URL is replaced with `/invite` via `history.replaceState` so it is not in history, and never goes to analytics, logs or error text. The document sets `Referrer-Policy: no-referrer` for this route (meta tag or header via the existing static-header mechanism; state which).

States, exactly as `invitation.md` §5: Checking · Form · Field errors · Server unreachable · Expired · Unavailable · Existing account (guarded, see notes) · Accepted. Left panel per §3 (aside only for form, field-errors, network and done; generic left panel for checking, expired, unavailable). Form per §4: read-only email (`readonly`, `aria-readonly="true"`, `--sunken`), full name (prefilled, editable, required), password (`autocomplete="new-password"`, Show/Hide with `aria-pressed`, at least 15, paste allowed), terms checkbox, `Accept and create account`. Validation, summary, focus and kept input exactly as `sign-up.md` §2 if that story exists; otherwise implement the same pattern from E05-S10's sign-in form and record `notes.followup`. Server password rejection clears the password and keeps everything else. After accept: **Accepted** state; the button goes to `/sign-in/mfa/enroll` for roles needing MFA, else `Continue to XLR8 FLO` to Home; lifetime text reads the server's expiry value, not a hardcoded 7.

The accept POST sends `Idempotency-Key` (one key per form submission, reused on retry). Tokens, passwords and the recovery data never appear in `console`, error boundaries or telemetry.

## Acceptance criteria

## Pre-flight amendments 2 (Opus, 9 Oct 2026, traced against merged E05-S12 and E05-S13) — authoritative

1. **API facts (generated client types).** `GET /api/v1/invitations/by-token` returns `{"state":"valid","org_name","tenant_label","inviter_name","inviter_title","role_name","access_words","expires_at","email","full_name"}` or `{"state":"expired"}`; `inviter_title` is **null today** (no profile field exists): render the inviter's name alone, with no separator, placeholder or the word "null" when it is null. `POST /api/v1/invitations/accept` takes the token in `X-Invitation-Token` and body `{full_name, password, accepted_terms}`, answers `200 {"next": "enroll"|"home"}`; a weak password is `422` with a field error on `password`; every other failure (`404`) means the link is no longer usable. `accept` ignores the `Idempotency-Key` (still send one per submission). No API change in this story.
2. **Existing-account state is entered only through the sign-in detour, never inferred.** The API deliberately does not say whether the invited email already has an account (AUTH-007). The screen shows the new-account form by default, with `Already have an account? Sign in to accept`. That link sets an in-memory flag `detour = true` (same module as the token) and navigates (SPA) to `/sign-in?return=%2Finvite`. Back on `/invite` with the token and `detour` set, the screen runs `probe()`; if it answers `verified` or `choose` the screen is in the existing-account state (subline shows the **invited** `email` from `by-token`) and `Accept and join` posts `{}`; any other outcome sends the person to the matching sign-in step with `return=/invite` (the memory survives SPA navigation). A `404` from that accept (wrong signed-in email, already a member, spent link) renders **Unavailable**. `Not now` clears the token and goes Home (`/`).
3. **`choose` must not trap the detour.** E05-S13's organization gate lets an unselected multi-tenant session read and accept, so on `/invite` treat `probe()` = `choose` as signed in (do not redirect to the chooser from this screen).
4. **Authorized edit to keep the token through the chooser.** After sign-in, a multi-tenant person is sent by `finish()` to `/sign-in/organization`, whose `select()` ends with `window.location.assign(back)`: a hard page load that would drop the in-memory token. Authorized change in `features/auth/OrganizationChooser.tsx` only: when `back` is exactly `/invite`, call `navigate(back)` (SPA) instead of `window.location.assign(back)`; every other `back` keeps the hard load (E05-S12 amendment 6: no tenant data in memory; `/invite` shows none). Playwright test: sign in as a two-tenant person on the detour, choose a tenant, land on `/invite` still holding the invitation (existing-account state). **Plant:** revert to `window.location.assign` and that test fails.
5. **MFA-pending session on accept.** The MFA gate answers `403`; `probe()` then reports `verify` or `enroll`, and the screen sends the person there with `return=/invite`. No special copy.
6. **Standing rule.** An unstated low-level detail (a class name, an id, copy that `invitation.md` already gives, a spacing token) is never a block: follow `invitation.md`, `sign-in.md` and the nearest existing component, and record one `notes.followup` line. Block only for an API gap, per item 8 of the first amendments.
