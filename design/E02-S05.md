# E02-S05 — RBAC: roles, permissions, org/BU/project/record/action scope, default-deny

**Epic** E02 · **M0** · **security/L** · after **E02-S02, E03-S02** · tags: `auth`, `security`

## Requirements

- **USR-001** — A user must be assignable globally or to one or more BU/OUs.
- **USR-002** — A user must be able to hold multiple roles, including different roles in different BU/OUs.
- **USR-003** — Access must support organization, BU/OU, module, record, and action scopes.
- **USR-004** — Project-specific view, create, edit, approve, and administrative permissions must be supported.
- **USR-005** — Server-side authorization must be evaluated for every protected request; hidden UI controls are insufficient.
- **USR-006** — Least privilege and default-deny behavior must apply to new roles and permissions.

## Deliverable

The authorization model every later module depends on. Get the shape wrong here and eleven modules inherit it.

## Model

```sql
role              (id, org_id, code, name, is_system)
permission        (code)                       -- 'project.approve', 'budget.transfer', …
role_permission   (role_id, permission_code)
user_role         (user_id, role_id, scope_type, scope_id)
                  -- scope_type: 'org' | 'bu' | 'project'
                  -- USR-002: the same user may hold different roles per scope
```

A grant is a triple: **(user, role, scope)**. Effective permissions for a request are the union of permissions from every grant whose scope contains the target record.

## Behaviour

1. **Default-deny (USR-006)** — the resolver returns deny unless an explicit grant matches. A new permission code is denied to every role until granted; a new role holds nothing. There is no implicit inheritance and no wildcard role.
2. **Scope containment** — `org` contains every `bu`; a `bu` contains its projects; a `project` grant contains that project and, for roll-down hierarchies, its descendants. Containment is computed by recursive CTE and is the only mechanism — no ad-hoc `if user.is_admin`.
3. **Enforcement point (USR-005)** — a single `require(permission, target)` dependency on every protected route. A route without it fails a CI check that enumerates routes and asserts each is either explicitly public or carries `require(...)`. Authorization is never expressed in the UI layer.
4. **Separation of duty (USR-007, deferred to E10-S04 for approvals)** — the model must already carry enough to answer "did this user create the thing they are approving"; expose `created_by` in the check context now so E10 does not need a migration.
5. Grants are **audited** with before/after (AUD-001) and take effect on the next request — no permission cache with a TTL, because a revoked permission that lingers is a security hole.
6. Eleven baseline roles are seeded from `requirements.md` §3.1 as `is_system` rows: Organization Administrator, Project Administrator, Requestor, Approver, Sourcing Specialist, Purchasing User, Vendor Manager, Budget/Finance User, Warehouse/Asset User, Executive/Viewer, Auditor. **Auditor is read-only by construction** — it holds no permission ending in `.create`, `.edit`, `.approve`, or `.delete`.

## Acceptance criteria

- [ ] A user with a `bu` grant can reach records in that BU and **404s** on another BU's record (ACC-004, and 404 not 403 per E03-S02)
- [ ] The same user holding Requestor in BU-A and Approver in BU-B gets exactly those permissions in each, and neither in the other
- [ ] A brand-new role grants nothing until a permission is explicitly attached
- [ ] A new permission code is denied to every existing role, including Organization Administrator, until granted
- [ ] A project grant reaches descendants in roll-down mode and does not leak to siblings
- [ ] CI enumerates every route and fails if one is neither marked public nor guarded by `require(...)`
- [ ] Revoking a role takes effect on the very next request
- [ ] Auditor holds no mutating permission — asserted by a test over the seeded permission set
- [ ] Every grant change writes an audit row with before and after
