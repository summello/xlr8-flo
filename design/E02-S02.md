# E02-S02 — Server sessions, httpOnly cookies, CSRF, idle and absolute timeout, revocation

**Epic** E02 · **M0** · **security/L** · after **E02-S01** · tags: `auth`, `security`

## Requirements

- **AUTH-009** — Session idle and absolute timeouts must be configurable, with reauthentication for sensitive actions.
- **AUTH-010** — Users must be able to view and revoke their active sessions where the identity solution supports it.
- **SEC-007** — Output must be contextually encoded; browser protections such as CSP, secure cookies, CSRF defense, clickjacking defense, and strict transport policy must be configured.

## Deliverable

Server-side sessions in Postgres with opaque tokens. **Not JWTs** — a JWT cannot be revoked before expiry, which makes AUTH-010 unimplementable and turns a compromised token into a guaranteed window.

## Contract

```
POST /api/v1/auth/login      {email, password}  → 204 + Set-Cookie: flo_session
POST /api/v1/auth/logout                        → 204, revokes the current session
GET  /api/v1/auth/sessions                      → 200 [{id, created_at, last_seen_at,
                                                        ip_prefix, user_agent, current}]
DELETE /api/v1/auth/sessions/{id}               → 204, revokes one
DELETE /api/v1/auth/sessions                    → 204, revokes all others
```

## Behaviour

1. **Token** — 256 bits from `secrets.token_urlsafe(32)`. The database stores only a SHA-256 **hash** of it, so a database read does not yield usable sessions.
2. **Cookie** — `HttpOnly; Secure; SameSite=Lax; Path=/`. `Lax`, not `Strict`, so an emailed deep link to an approval still works; and not `None`, because there is no cross-site embedding.
3. **CSRF** — double-submit token in a readable cookie plus an `X-CSRF-Token` header, validated on every unsafe method. `SameSite=Lax` alone is not sufficient for top-level POST navigations.
4. **Timeouts (AUTH-009)** — configurable idle (default 8 h, refreshed on activity) and absolute (default 12 h, never refreshed). Both stored on the row and enforced server-side on every request; a client clock is never trusted.
5. **Rotation** — the session id is regenerated on privilege change (login, MFA completion, password change) to prevent fixation.
6. **Revocation (AUTH-010)** — revoking marks the row and takes effect on the **next request**, with no cache to wait out. Revoked-then-reused tokens are audited as a security event.
7. **Headers (SEC-007)** — set on every response: `Content-Security-Policy` (no `unsafe-inline`; hashes or nonces), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security` with a one-year max-age.
8. Session listing shows a **truncated** IP (`/24` or `/48`) and a coarse user-agent — enough to recognize a device, not a location trail (PRIV-001).

## Acceptance criteria

- [ ] Session token never appears in a URL, a log line, or an audit record — only its hash is stored
- [ ] Cookie carries HttpOnly, Secure, SameSite=Lax; JavaScript cannot read it
- [ ] An unsafe request without a matching CSRF token is rejected 403
- [ ] Idle timeout expires an inactive session; activity refreshes it; the absolute timeout expires regardless of activity
- [ ] Session id changes on login, on MFA completion, and on password change
- [ ] Revoking a session from another device makes the next request from the revoked one fail
- [ ] "Revoke all others" leaves exactly the current session alive
- [ ] Reusing a revoked token writes a security audit event
- [ ] All seven security headers present; CSP contains no `unsafe-inline`
