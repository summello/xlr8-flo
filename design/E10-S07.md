# E10-S07 — Stale-version guard and material-change resubmission policy

**Epic** E10 · **M2** · **concurrency/M** · after **E10-S06** · tags: `concurrency`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (H, O) and `docs/author-traps.md`. Decisions: D-M2-13 (canvas `DECISIONS.md` 79).

## Requirements

- **APR-015** — A document changed in a material way after approval must be resubmitted according to policy.
- **APR-016** — Users must not approve a stale document version.
- **DATA-002** — Concurrent edits must use optimistic concurrency or equivalent version checks; stale writes must not silently overwrite newer data.
- **WF-001** — A downstream record must never be created from an unauthorized or stale upstream version.

## Contract

1. **Stale guard on every decision** (E10-S06's route): after locking the instance, read `adapter.snapshot(...).version`. If the body's `document_version` differs from it (the document's **current** version, never the version recorded at `start`), answer 409 `CONFLICT`, `checks.problem = "stale_version"`, detail "This document changed after you opened it. Reload it and review the current version." and write nothing. Comments are guarded too: a comment on a stale version is refused, so rationale always names what it judged. A non-material edit while an instance runs bumps the version and is **not** a reason to block the step: approvers reload and decide on the current version (pre-flight finding, 11 Oct).
2. **Material digest.** `DocumentSnapshot.material` (convention H) is a `dict[str, str]` of the document's material fields. `material_digest(snapshot) = sha256` of its canonical JSON (sorted keys, no whitespace), hex. E10-S05 already stores `approval_instance.material_digest` at `start`; this story also stores it at approval as `approved_material_digest` (one new nullable column, added in this story's migration).
   - For requisitions the material fields are **exactly** D-M2-13 (operator-accepted canvas 79): `amount` (the estimate as a decimal string with four places), `project_id`, `ledger_account_code`, `catalogue_items` (sorted, comma-joined catalogue entry ids of the lines, `-` for lines without one), `line_count`. Not configurable per workflow, with no builder setting. E09-S05 implements it in the adapter; this packet fixes the list.
3. **Service functions** (re-exported through `approvals/service.py`, `material_digest` included: E09-S08 computes the same digest for its pre-submit comparison, so there is one function):
   ```python
   def approval_state(conn, scope, document_type, document_id) -> ApprovalState
       # {status: "none"|"running"|"approved"|"rejected"|"returned"|"withdrawn"|"superseded",
       #  instance_id, approved_version, approved_material_digest, running_instance_id}
       # all read the IN-FORCE instance (item 3a); running_instance_id is a newer running one, else None
   def requires_resubmission(conn, scope, document_type, document_id) -> bool
       # True iff the latest instance is "approved" and the document's current material digest differs
   def supersede(conn, scope, document_type, document_id, actor_id, reason) -> None
       # marks the approved instance "superseded" (audited); the document must resubmit to be approved again
   def assert_current_approval(conn, scope, document_type, document_id, document_version) -> None
       # WF-001 guard for downstream creation: raises 409 stale_version unless the latest instance is
       # "approved", its approved_material_digest equals the current material digest, and
       # document_version equals the document's CURRENT version (the caller read what it builds from);
       # a non-material edit after approval keeps the approval in force (policy item 4)
   ```
3a. **The "in-force instance"** is what `approval_state`, `requires_resubmission` and `assert_current_approval` read. Order the document's instances by `(started_at, id)` and take the newest whose status is `running`, `approved` or `superseded`; an instance that ended `rejected`, `returned` or `withdrawn` is **ignored when an `approved` or `superseded` instance precedes it** (a failed amendment leaves the approved version in force). With no such preceding instance, a lone `rejected`, `returned` or `withdrawn` instance is the state itself (not approved). Consequences, all intended:
   - While an amendment of an approved document is pending (a newer `running` instance, E09-S08), the in-force instance is the running one, `assert_current_approval` fails with `stale_version`, and nothing downstream (an RFQ, E12-S01) can be created mid-amendment (WF-001). `running_instance_id` names it.
   - If that amendment is **rejected, returned or withdrawn**, the approved instance is in force again with its own `approved_material_digest`; `assert_current_approval` passes for the approved version, and E09-S08 can compare a proposed amendment against `approved_material_digest` for a later non-material amendment.
   - Once an amendment is approved, its instance is newest and carries the amended digest.
   (E10-S05's `resume_from` is separate: it concerns the newest instance overall and requires `returned`.)

4. **Policy (APR-015).** A document module that edits an approved document calls `requires_resubmission` inside the edit's transaction. When it is true, the module must either refuse the edit or call `supersede` and move the document back into its approval path. Which one is the document's rule: **requisitions go through E09-S08's amendment flow**, which keeps the approved version in force until the amendment is approved. Non-material edits never touch approval state.
5. **Concurrency:** `supersede` and decisions both lock the instance row `FOR UPDATE`. A decision racing a material edit either sees the new version (and is refused as stale) or completes first (and the edit then finds `requires_resubmission`). Never both.

## Acceptance criteria

- [ ] Approving with `document_version` one behind the document is 409 `stale_version`, with no decision row and the task still open.
- [ ] Two approvers on an `all` step: the document is edited (version bump through the fake adapter) between their decisions; the second is refused as stale.
- [ ] The digest is identical for the same material values in a different key order, and different when any one of the five requisition fields changes.
- [ ] `requires_resubmission` is false after a non-material change (justification) and true after a change to each material field.
- [ ] `assert_current_approval` passes for the approved version and after a later **non-material** edit (passing the new version), and raises `stale_version` for a version older than the current one, after a material edit, after `supersede`, and for a running instance.
- [ ] A non-material edit while an instance runs: a decision carrying the new version succeeds; one carrying the old version is `stale_version`.
- [ ] Approved, then an amendment instance is started and rejected (and again with returned, and withdrawn): `approval_state` still reports the original approved instance with its digest, `assert_current_approval` passes for the approved version, `running_instance_id` is None; while the amendment is running it fails `stale_version` and `running_instance_id` names it.
- [ ] A lone rejected instance with no earlier approved one is not approved and `assert_current_approval` fails.
- [ ] `supersede` and a concurrent decision on the same instance: exactly one wins (a two-connection test).

## Plants

1. Compare the decision's version only with the instance's version, not the current snapshot: the edited-between-decisions test fails.
2. Hash `str(material)` instead of canonical JSON: the key-order test fails.
3. Let `assert_current_approval` accept a superseded instance: its test fails.
4. Take the plain newest instance (no skipping of rejected amendments): the rejected-amendment case fails.
