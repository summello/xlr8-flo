# E22-S14 — The unit list follows the list-scope rule: a unit-scoped grant lists its units

**Epic** E22 · **M3** · **security/S** · after **E22-S13**, **E11-S05** · tags: `auth`, `security`
Origin: ACC-008 automated keyboard run, 21 Nov 2026 (result record on PR #22). Operator, 21 Nov 2026: fix before
the human walkthrough round.

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.

One route, one service method, their tests. No migration, no API shape change, no frontend change.

## Requirements (inlined)

- **USR-003** — Access must support organization, BU/OU, module, record, and action scopes.
- **ACC-004** — A user cannot access another BU/OU's record by guessing an identifier or changing a request.
- **ACC-008** — A complete project-to-PO workflow is operable without a mouse.
- **DECISIONS 234** (operator, 22 Oct 2026, E22-S06): list routes accept the read permission held at any scope and
  narrow rows to the caller's scopes.
- **E22-S13 decision 2** (operator, 8 Nov 2026): a caller holding the read permission nowhere gets an **empty 200**
  on every list route, never a 403.
- **DECISIONS 241** (E11-S05): `GET /org/units` admits `org.unit.read`, or else `vendor.request`; a
  `vendor.request`-only caller sees **active** units only.

## The defect

`GET /api/v1/org/units` (`api/org.py` ~67-89) authorizes through `unit_permission` against
`organization_target` only, and `OrgService.list_units` (`modules/org/service.py` ~286-317) re-checks both
permissions at organization scope (`_holds`, ~275-284). A user whose roles are granted on a business unit (the
normal case: the walkthrough seed grants every person on unit WALK-OPS) gets **403**. Every screen that lists units
for its user breaks for them: the project form's Business unit (`ProjectForm.tsx` ~50) — so a unit-scoped project
manager **cannot create a project** — the vendor request form, the vendor dialog and the projects list filter. It
also contradicts E22-S13 decision 2.

## Fix

**Route** (`api/org.py`): `list_units` takes two dependencies,
`read: Annotated[GrantedScopes, Depends(require_granted("org.unit.read"))]` and
`req: Annotated[GrantedScopes, Depends(require_granted("vendor.request"))]` (`kernel/authz.py` ~185), in place of
`require_resolved(unit_permission)`. Delete `unit_permission` if nothing else uses it (`grep unit_permission`).
`context.user_id` becomes `read.user_id`.

**Service** (`OrgService.list_units`): takes `read: GrantedScopes | None = None, req: GrantedScopes | None = None`.
Both `None` is the internal path (`vendors/service.py` ~228, `requisitions/lookups.py` ~95, no actor): unchanged,
unfiltered. Otherwise, in this order:

1. `read.org_wide` → today's `org.unit.read` behaviour: every unit, `kind`/`active` filters as asked.
2. neither `read` nor `req` truthy → `OrgUnitPage(rows=[], next_cursor=None)` **before any SQL**.
3. otherwise one query adds this row predicate (all in SQL, keyset paging unchanged):
   `id = ANY(%(read_units)s) OR (active AND (%(req_org)s OR id = ANY(%(req_units)s)))`
   with `read_units = list(read.bu_ids)`, `req_org = req.org_wide`, `req_units = list(req.bu_ids)`. The `kind`
   and `active` query filters still apply on top. So a unit where the caller holds `org.unit.read` shows even when
   inactive; a unit reached only through `vendor.request` shows only while active (DECISIONS 241, per unit).

`bu_ids` is exactly the granted BU/OU ids (E22-S13: units never roll down to units). **`project_ids` grant no unit**:
a project-scoped grant does not reveal its unit; such a caller with no unit grant gets the empty page. The `_holds`
helper stays if other methods use it; `list_units` stops calling it.

`org_id = %(org_id)s` stays on the statement (TEN-010).

## Plants

1. Restore the organization-target check (`require_resolved(unit_permission)`): the unit-scoped cases answer 403.
2. Drop `id = ANY(%(req_units)s)` narrowing (use `req` truthiness alone): unit B appears for the A-scoped caller.
3. Drop `active AND` from the `vendor.request` branch: inactive A2 appears for the `vendor.request`-only caller.
