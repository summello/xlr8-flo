> **Writes:** `PUT` takes **no `If-Match`**: the mark is not PO content, and `purchase_order.version` is the
> ETag that `transition` and `PATCH` check (`purchasing/lifecycle.py:64-87`, `api/purchasing.py:129-142`), so
> bumping it would 409 a concurrent issue, approve or cancel. This is the §O exception (`docs/m2-conventions.md`
> §O): `purchase_order.version` is untouched, last write wins, every change is audited. `Idempotency-Key` is
> not required: the middleware keys only `POST` and a `DELETE` pattern (`kernel/idempotency/middleware.py:235-240`)
> and a `PUT` of a value is idempotent. State both in the route docstring.
> **RLS:** the new table gets literal `ALTER TABLE <t> ENABLE ROW LEVEL SECURITY; … FORCE …; CREATE POLICY
> tenant_isolation ON <t> …` statements in the migration text, never generated by a helper or f-string.

## Requirements (inlined)

- **PO-017** — POs must support notes, terms, supporting attachments, and vendor-facing attachments.
  Internal-only content must never be included accidentally.
- **EML-005** — Vendor-facing email must never include internal-only notes or attachments; covered by an
  automated test (E13-S11's `test_nothing_internal_reaches_the_supplier_email_or_pdf`, extended here).

## Why

PO-017 asks for vendor-facing attachments. M3 sends none (scanning is E19-S04), but a user must be able to say
now which files are *meant* for the vendor, so nothing is re-triaged later and the in-app "Never sent to the
vendor" list (E13-S14, E13-S17) has a real source. The mark is **intent only**: it changes no email, no PDF and
no outbox row. The default is internal; a file is vendor-facing only after an authorised, audited, explicit act.

## Decided (operator, 1 Nov 2026, "use your defaults")

- **Q1 — who and when.** Same enforcement as shareable notes (E13-S11): `purchase_order.create` while the PO is
  `draft`, `purchase_order.amend` in every other status (`po_write`, `api/document_types.py:66`). The mark is
  allowed in every status **except `cancelled` and `deleted`**, which refuse with 409. `superseded` is allowed
  and resolves to the chain (D1 below); `closed` is allowed (intent only; the closed PO's snapshot is untouched).
- **Q2 — revisions.** The mark is **keyed to the file**, not to a PO revision, so it follows the file across
  change orders. There is nothing to copy forward: a change order creates a new `purchase_order` row and moves
  no attachment (`purchasing/changes.py:795-807`).
- **Re-uploaded bytes reset the mark.** The mark stores the `attachment_version_id` it was set against and reads
  `vendor_facing = true` only while that is the file's **latest** version. A new version via
  `POST /api/v1/attachments/{id}/versions` therefore reads `false` until someone marks it again.

## Design

### 1. Storage: one table, the RFQ precedent plus its integrity constraints

```
po_attachment_vendor_mark(
  org_id uuid NOT NULL REFERENCES organization(id),
  attachment_id uuid NOT NULL,
  po_id uuid NOT NULL,                       -- the revision the file belongs to (attachment.document_id)
  attachment_version_id uuid NOT NULL,       -- the file version the mark was set against
  vendor_facing boolean NOT NULL DEFAULT false,
  marked_by uuid NOT NULL REFERENCES identity(id),
  marked_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (attachment_id),
  FOREIGN KEY (org_id, attachment_id) REFERENCES attachment(org_id, id),
  FOREIGN KEY (org_id, po_id) REFERENCES purchase_order(org_id, id),
  FOREIGN KEY (attachment_version_id) REFERENCES attachment_version(id))
```

Modelled on `rfq_attachment_visibility` (`migrations/20261022_0068_rfq_content.py:37-48`) with both composite
FKs it carries (`attachment`, parent document) plus the identity FK. `attachment(org_id, id)` and
`purchase_order(org_id, id)` both have `UNIQUE (org_id, id)` (`20261009_0041_collaboration.py:27-31`,
`20261027_0078_purchase_order.py:38`). No column on `attachment` or `purchase_order`. Absence of a row means
internal. **Migration `0087`** (next free number after `0086_po_transmission`; renumber at merge if another
lane took it): the down migration drops the table and carries `# irreversible: drops every vendor-facing mark`
as `0068:88-89` does (AGENTS.md §3.3, Opus review). `tests/kernel/test_migrate.py:187-188` lists revisions:
add it.

### 2. Routes (both new; the generic collaboration `AttachmentRead` and routes are not changed)

- `GET /api/v1/purchase-orders/{id}/attachments` → `list[PoAttachmentRead]` (`id`, `display_name`, `version`,
  `scan_status` of the latest version, `uploaded_at`, `document_id` (the revision it sits on), `vendor_facing`).
  Dependency `ViewContext` (`api/purchasing.py:61`), so a foreign id is 404 before any 403. Lists the **whole
  chain** of `{id}` (that PO and every ancestor via `supersedes_id`, the recursive CTE shape of
  `purchasing/vendor_copy.py:111-114`), non-deleted files only, ordered `uploaded_at, id`. `vendor_facing` is
  true only for a mark row with `vendor_facing` set whose `attachment_version_id` is the file's latest version.
- `PUT /api/v1/purchase-orders/{id}/attachments/{aid}/vendor-facing`, body `{"vendor_facing": bool}`, response
  the `PoAttachmentRead` for that file.

Both routes are added to `tests/isolation/test_route_coverage.py` `COVERED` (PO rows, lines ~69-73), or that gate
fails; the TEN-010 case is a test in the PO routes isolation test they point at.

### 3. Authorization and the service

The router takes `ViewContext`, then calls `po_write(connection, current_scope(), id, context.user_id)`
**before** the service (the existing helper in `api/document_types.py:66`; `purchasing.service` cannot import
the api layer, D-15). `po_write` opens its own `tenant_transaction` and reads the status unlocked (its
ponytail), so the `cancelled`/`deleted` refusal is **in the service, under the `purchase_order` row lock**, not
in `po_write`. The service method `set_attachment_vendor_facing(id, aid, vendor_facing)`, one
`tenant_transaction`:

1. Read the PO scoped (foreign tenant → 404) and lock its row; refuse 409 (`conflict`, message "A cancelled PO's
   files can no longer be marked.") when status is `cancelled` or `deleted`.
2. Read the attachment: it must exist, not be deleted, and have `document_type = 'purchase_order'` and
   `document_id` in the chain of `{id}`; otherwise 404. A file of another PO or tenant is 404.
3. Read the file's latest `attachment_version.id`.
4. Upsert the row (`ON CONFLICT (attachment_id) DO UPDATE`) with `po_id = attachment.document_id`, that version
   id, the value, `marked_by`, `marked_at`. A request that leaves the stored effective value unchanged (same
   value against the same latest version) writes nothing and no audit row, and returns 200.
5. Audit `purchase_order.attachment.vendor_facing` with `{attachment_id, attachment_version_id, vendor_facing}`
   via `PurchaseOrderService._audit` (`purchasing/service.py:114-127`, target type `purchase_order`), once per
   actual change.

### 4. Nothing is sent, and the leak test proves it

`vendor_copy`, `transmission.enqueue`, `pdf.py` and the email context **do not read the table** and name no
file. Extend E13-S11's `test_nothing_internal_reaches_the_supplier_email_or_pdf`
(`apps/api/tests/purchasing/test_vendor_visibility.py:87`): over HTTP on the draft, before approve, mark
`INTFILE-9Z` vendor-facing; then after issue assert the email still has exactly one attachment (the PDF), the
email body and PDF bytes contain neither `INTFILE-9Z` nor `INTBYTES-5W`, and a recording `Storage` fake sees no
`get` of that file's `storage_key` during issue and dispatch. (`transmission.enqueue` holds no `Storage`
(`purchasing/transmission.py:71-99`), so the storage fake is the observable.) A future change that starts
sending marked files fails here until it also passes scanning (E19-S04).

### 5. Scanning

A mark may be set on a file whose latest `scan_status` is not `clean`. The UI (E13-S14/S17) shows "Not sent
until scanning is available"; this story stores intent only and adds no scan rule or quarantine behaviour.
E19-S04 alone decides whether a marked file is sendable, and it reads the mark only while the marked version
is the latest.

## Acceptance

- [ ] Migration `0087`: up creates the table with RLS enabled and forced, one `tenant_isolation` policy and the three FKs; down drops it (`# irreversible:` comment present); the data-preservation assertion and the revision list in `tests/kernel/test_migrate.py` pass.
- [ ] `PUT …/vendor-facing` `true` stores a mark and returns the file with `vendor_facing: true`, one audit row; the same call again → 200, no second audit row. `false` flips it back with one more audit row.
- [ ] Default: a file with no row reads `vendor_facing: false` on the list.
- [ ] After a change order, the old revision's file is listed under the new revision's id and `PUT` on the **new** id succeeds (404 on a file outside the chain); the mark persists across the revision.
- [ ] Uploading a new version of a marked file makes `vendor_facing` read `false`; marking it again reads `true`.
- [ ] Unknown, deleted, other-PO or foreign-tenant attachment id → 404; a foreign tenant's PO id → 404 on both routes; both routes are in `COVERED` and the isolation test passes.
- [ ] Authorization per role: a role holding `purchase_order.create` marks while `draft` (→ 200) and is refused after issue; a role holding `purchase_order.amend` marks after issue; `purchase_order.view` only → 403; `requestor` → 403.
- [ ] Status rule: `cancelled` and `deleted` → 409; `superseded`, `closed`, `issued`, `approved`, `approval_pending`, `draft` → 200 for an authorised role (one test per status).
- [ ] No `If-Match` is required; the call does not change `purchase_order.version`, and a concurrent `transition` is not 409'd by it.
- [ ] The extended leak test above passes with `INTFILE-9Z` marked vendor-facing.
- [ ] `flo check --light` green; the operator note `docs/ops/purchase-orders.md` (new) says the mark is intent only, nothing is sent until E19-S04, and a new file version resets it (SUP-005).

## Plants (prove each guard fails)

1. Default the column to `true`: the default-internal test fails.
2. Have `vendor_copy` or `transmission.enqueue` read the mark and attach the file: the extended leak test fails on the attachment count, the bytes and the `Storage` fake.
3. Skip the chain/ownership check on the attachment (accept any attachment id): the other-PO 404 test fails.
4. Drop `FORCE ROW LEVEL SECURITY` from the migration: the catalogue assertion on `relforcerowsecurity` in the migration/RLS test (pattern `tests/isolation/test_rls.py:66-82`) fails. An HTTP test will not fail here because the service filters `org_id`.
5. Drop one composite FK: the migration constraint-catalogue assertion fails.
6. Write an audit row on a no-op repeat: the idempotence test fails.
7. Skip `po_write`: the 403 tests fail.
8. Skip the `cancelled`/`deleted` refusal: the status test fails.
9. Read `vendor_facing` without the latest-version check: the re-upload test fails.
10. Bump `purchase_order.version` in the service: the version-untouched test fails.
