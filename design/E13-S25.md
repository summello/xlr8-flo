## Requirements (inlined)

- **PO-017** — POs must support notes, terms, supporting attachments, and vendor-facing attachments.
  Internal-only content must never be included accidentally.
- **EML-005** (carried from E13-S11) — Vendor-facing email must never include internal-only notes or
  attachments; covered by an automated test.

## Why

PO-017 asks for vendor-facing attachments. M3 sends none (scanning is E19-S04), but a user must be able to say
now which files are *meant* for the vendor, so nothing is re-triaged later and the in-app "Never sent to the
vendor" list (E13-S14, E13-S17) has a real source. The mark is **intent only**: it changes no email, no PDF and
no outbox row. The default is internal; a file is vendor-facing only after an authorised, audited, explicit act.

## Design

### 1. Storage: one table, the RFQ precedent

`po_attachment_vendor_mark(org_id uuid NOT NULL REFERENCES organization(id), po_id uuid NOT NULL,
attachment_id uuid NOT NULL, vendor_facing boolean NOT NULL DEFAULT false, marked_by uuid NOT NULL,
marked_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (po_id, attachment_id))`, modelled on
`rfq_attachment_visibility` (`migrations/20261022_0068_rfq_content.py:37`). Reversible migration (down drops
the table), literal RLS, and a data-preservation assertion in the migration test. **No column on `attachment`**
and none on `purchase_order`: the attachment is generic collaboration data; the mark belongs to the PO.
Absence of a row means internal. Marks are not versioned; each change is an audit row (item 3).

### 2. Route and service

`PUT /api/v1/purchase-orders/{id}/attachments/{aid}/vendor-facing`, body `{"vendor_facing": bool}`, response
the attachment list item with `vendor_facing`. The router parses, authorises and calls one
`purchasing.service` method (`set_attachment_vendor_facing`). In one `tenant_transaction`: read the PO scoped
(foreign tenant → 404), confirm the attachment exists with `document_type = 'purchase_order'`,
`document_id = <po id>`, `deleted_at IS NULL` (else 404), authorise per Open Q1, upsert the mark, audit.
A request that sets the value already stored is a no-op that writes no audit row and returns 200.
Reading: `GET /api/v1/purchase-orders/{id}/attachments` (or the existing collaboration list, whichever
E13-S11 left) gains `vendor_facing: bool` per file; the generic collaboration `AttachmentRead` is **not**
changed (it is shared by every document type).

### 3. Audit and the leak guard

Audit action `purchase_order.attachment.vendor_facing` with `{attachment_id, vendor_facing}` via the shared
audit helper, one row per actual change. `vendor_copy`, `transmission.enqueue`, `pdf.py` and the email context
**do not read the table** and name no file: the E13-S11 EML-005 leak test must still pass with a file marked
`vendor_facing = true` (the mark is intent; nothing is sent until E19-S04). This story adds that case to the leak
test, so a future change that starts sending marked files fails here until it also passes scanning.

### 4. Scanning

A mark may be set on a file whose `scan_status` is not `clean`. The UI (E13-S14/S17) shows "Not sent until
scanning is available"; this story stores intent only. When E19-S04 lands, it alone decides whether a marked
file is sendable; this story adds no scan rule and no quarantine behaviour.

## Open (decide before pre-flight; do not guess)

- **Q1 (authorization / state):** who may set the mark, and in which PO states? Planner recommends the same
  rule as shareable notes (E13-S11): `purchase_order.create` while the PO is `draft`, `purchase_order.amend`
  after, and the mark is allowed in every state except `cancelled`. Because it records intent only, an issued
  PO's mark may still change; the issued snapshot and `po_version` rows are untouched.
- **Q2 (revisions):** a change order creates a new PO revision. Do marks carry forward to the new revision
  (copy rows for the same `attachment_id`s), or does each revision start all-internal? Recommend carry forward,
  so a file the user already cleared stays cleared and nothing silently becomes vendor-facing.
  Depends on which row the attachment's `document_id` points at; the author confirms against
  `purchasing/changes.py` before coding and records the answer in `notes.followup` if it differs.

## Acceptance

- [ ] Migration: up creates the table with RLS enabled and forced and one `tenant_isolation` policy; down drops it; a seeded database keeps its data (reversible, data-preservation assertion).
- [ ] `PUT …/vendor-facing` with `true` stores a mark, returns the file with `vendor_facing: true`, writes one audit row; the same call again → 200, no second audit row.
- [ ] `false` flips it back; one more audit row.
- [ ] Default: a file with no row reads `vendor_facing: false`.
- [ ] Unknown, deleted or other-PO attachment id → 404; foreign tenant's PO or attachment → 404 (TEN-010 case added).
- [ ] Authorization per role per Q1: an allowed role → 200; a role with `purchase_order.view` only → 403; `requestor` → 403; each state boundary from Q1 has a test.
- [ ] **EML-005 leak test, extended:** with an attachment marked `vendor_facing = true`, the issued email still has exactly one attachment (the PDF), the email body and PDF bytes contain neither the file name nor its bytes, and `transmission.enqueue` makes no attachment read.
- [ ] A cancelled PO refuses the mark (Q1).
- [ ] If Q2 = carry forward: a change-order revision shows the same marks; if not, all-internal; either has a test.
- [ ] `flo check --light` green; `docs/ops/` operator note updated (SUP-005).

## Plants (prove each guard fails)

1. Default the column to `true`: the default-internal test fails.
2. Have `vendor_copy` or `transmission.enqueue` read the mark and attach the file: the extended leak test fails on the attachment count and the bytes.
3. Skip the PO-scope check on the attachment (accept any attachment id): the other-PO 404 test fails.
4. Drop `FORCE ROW LEVEL SECURITY` from the migration: the isolation test fails.
5. Write an audit row on a no-op repeat: the idempotence test fails.
6. Skip the role check: the 403 tests fail.
