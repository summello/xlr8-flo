## Design

Two parts, per MASTER §7.16 and DECISIONS 175: **the confirmation dialog on the PO is the commit;
`/purchase-orders/:id/issue` is the moment that follows** and has no `Issue` button of its own.

**1. Trigger (existing detail page).** In `routes/purchase-orders/detail.tsx`, when
`p.actions` includes `"issue"` (the server already offers it for `approved`, `service.py:696`),
show an `Issue` button in `.vendor-head-actions`. It opens a modal confirmation dialog listing:
recipient(s) (the vendor contacts the send will use), version (`p.revision`), template
(`po-issued-v1`), **what will be sent** (`GET /api/v1/purchase-orders/{id}/vendor-copy`: lines,
totals, shareable notes) and **what stays here** — a fixed client list per MASTER §7.16.4:
chartfields, budget figures, internal notes (never fetched; the vendor copy omits them by
construction). The commitment is a **client sentence** built from `GET …/budget-summary`
(`this_po` per project): "Issuing commits {this_po} {currency} against {project_code}." — reuse the
`HOLDS`/`sentSignal` wording style in `components/purchasing/api.ts`; no new server field.

**2. Issue request.** `POST /api/v1/purchase-orders/{id}/issue` with `writeHeaders()` (supplies
`X-CSRF-Token`), `If-Match: <p.version>` (as `components/requisitions/api.ts:29` does), and an
`Idempotency-Key` generated **once per dialog open** (held in a ref, overriding the per-call key
`writeHeaders()` makes), so a double click or retry returns the same result. While in flight the
button is disabled. 409 `stale_version` → field-level error "This order changed since you opened
it" with `Reload`; the dialog keeps its state. On 200, navigate to `/purchase-orders/:id/issue`.

**3. The moment (`/purchase-orders/:id/issue`).** Add the route to `routes/__root.tsx` beside the
detail match (`__root.tsx:73`, render at `:446`). It reads the PO and
`GET …/transmissions` and plays §7.16.2: `po-stage`, `po-doc` lifts on `--shadow-drag`,
`po-seal` (success tone), `po-trace` to `po-vendor` as the email is queued. Each step is a word
and a row in a Frames table whose selected row follows the frame. Plays once per session
(`sessionStorage` flag per PO id); later visits show the finished picture. Reduced motion: the
finished picture with a note, no animation. Below 760px the trace is dropped and the stage stacks.
After it ends: the result in words and a small table (recipient, version, result) using the
existing `sentSignal` labels (`Email Queued`, `Email Delivered`, `Email Bounced` — never bare
`Delivered`, DECISIONS 173).

**4. Failure observation.** Issue only enqueues; delivery is later. The page polls
`GET …/transmissions` while **any** row for the current revision is `queued` or `sent` (one row per
recipient, `transmission.py:62`); it stops when **every** row is terminal, or after the time cap
(then shows "Still sending — results will appear on the order" and stops). The frame shows a
failure as soon as any row is a terminal failure. Interval 5 s and cap 2 min are network timing
constants (`const` in the component, `ponytail:` comment), not visual tokens; the 760px stacking
breakpoint is MASTER §7.16.2's own value. On `failed`, `bounced`, `address_suppressed` or `complained` the
trace snaps back to `--status-danger` and recovery is focused:
- `bounced` / `address_suppressed` (hard): primary and focused `Change Recipient`, `Resend` second
  (DECISIONS 174). `Change Recipient` opens a picker of `GET /api/v1/vendors/{vendor_id}/contacts`
  and calls `POST …/transmissions/resend` with `{contact_ids}`.
- `failed` (soft): primary and focused `Resend` → `POST …/transmissions/resend` with no body
  fields. Both POSTs use `writeHeaders()`. `Resend` says it sends the same version and commits
  nothing more.

**Motion tokens:** each transition uses `--dur-fast`/`--dur-base`/`--dur-slow` (≤ 260 ms) and an
`--ease-*` token; `--dur-page` (320 ms) is not used, so every transition stays ≤ 300 ms.

## Acceptance

- [ ] Detail page: `Issue` shows only when `actions` includes `issue`; opens the dialog; Escape closes it and returns focus to the button.
- [ ] Dialog shows recipient, version, template, vendor-copy contents, the fixed "stays here" list, and the commitment sentence from budget-summary.
- [ ] Playwright: issue an approved PO; a double click sends **one** POST (assert the request log) carrying `X-CSRF-Token`, `If-Match` and one `Idempotency-Key`; lands on the moment page; result reads `Email Queued`.
- [ ] 409 `stale_version` → error in the dialog with `Reload`; nothing navigates.
- [ ] Stubbed `bounced` transmission → danger frame, focus on `Change Recipient`; stubbed `failed` → focus on `Resend`.
- [ ] Polling stops once every row is terminal (assert no further `transmissions` requests).
- [ ] Reduced motion: no running animations (`document.getAnimations()` empty) and the finished picture with words.
- [ ] Every duration and curve is a MASTER motion token, none `--dur-page`.
- [ ] axe in both themes on the dialog and the moment page; keyboard-only path; MASTER §8; tokens only; `flo check --light` green.

## Blocked

Pre-flight 2 (8 Nov 07, codex, 5 findings) raised three questions the planner must not answer
(authorization and a state's meaning). Operator to decide before this story starts:

1. **Budget summary vs issue right.** `issue` needs only `purchase_order.issue`; `GET …/budget-summary`
   needs `ledger.read` on every project and returns 403 otherwise. May an issuer without `ledger.read`
   issue with the commitment sentence omitted (e.g. "Budget figures are not visible to you"), or must
   the dialog refuse, or should the server widen the read?
2. **Change Recipient vs vendor view.** `GET /vendors/{id}/contacts` needs `vendor.view`; resend needs
   only `purchase_order.issue`. Offer `Change Recipient` only to issuers who also hold `vendor.view`,
   or add a PO-scoped contacts read on the server?
3. **`complained`.** Is a spam complaint a failure needing recovery (which action is primary and
   focused), or a terminal non-failure shown in words only?

## Plants

1. Generate a new Idempotency-Key per click: the double-click assertion fails.
2. Ignore reduced motion: the reduced-motion assertion fails.
3. Focus `Resend` on a `bounced` result: the hard-bounce focus assertion fails.
4. Keep polling after every row is terminal: the no-further-requests assertion fails.
