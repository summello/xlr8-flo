## Operator decisions (7 Nov 2026) — binding

1. **Issuer without `ledger.read`:** issuing proceeds. The commitment sentence is replaced by
   **"Budget figures are not visible to you."** No server change; budget-summary authorization is unchanged.
2. **`Change Recipient` is offered only to issuers who also hold `vendor.view`.** Others can still
   `Resend` to the current recipients. No new endpoint.
3. **`complained` is a failure needing recovery.** `Change Recipient` is the primary, focused action;
   resend to the same address is **not** offered.

## Design

Two parts, per MASTER §7.16 and DECISIONS 175: **the confirmation dialog on the PO is the commit;
`/purchase-orders/:id/issue` is the moment that follows** and has no `Issue` button of its own.

### 1. Trigger and dialog (existing detail page)

In `routes/purchase-orders/detail.tsx`, inside `.vendor-head-actions` (`detail.tsx:55`), when
`p.actions` includes `"issue"` show an `Issue` button. It opens a Radix modal dialog
(`@radix-ui/react-dialog`, already a dependency), built like
`components/purchasing/dialogs/CancelOrReduce.tsx` (overlay and content classes at `:94-95`, opener
ref so Escape returns focus to `Issue`, the `key` ref at `:32`). The dialog lists, in this order:

- **Recipients:** `p.recipients` as name and email. If empty: "No recipient is set. Issuing sends to the vendor's document contacts and stops if it has none."
- **Version:** `v{p.revision + 1}`.
- **Template:** email `po-issued-v1` (a client constant; the value of `TEMPLATE` in `modules/purchasing/transmission.py:30`) and document `{vendorCopy.template_version}`.
- **What will be sent:** from `GET …/vendor-copy`: the lines (line no, description, quantity and UoM, unit price, line total), the four totals and the shareable notes. Amounts render through `components/ui/Money.tsx` with `vendor_copy.currency`. A failed load shows "The vendor copy could not be loaded." with `Try again`; `Issue` stays available (the server builds the copy at issue).
- **What stays here:** a fixed client list per MASTER §7.16.4: chartfields, budget figures, internal notes. Never fetched.
- **The commitment:** from `GET …/budget-summary`, one sentence per project: "Issuing commits {Money(this_po, currency)} against {project_code} {project_name}." On **403**: exactly "Budget figures are not visible to you." (decision 1). On any other failure: "Budget figures could not be loaded." with `Try again`. In every case `Issue` stays available: the sentence is information, the server commits.

### 2. Issue request

`POST /api/v1/purchase-orders/{id}/issue` with `mutationHeaders(key.current, p.version)`
(`components/requisitions/api.ts:29`: `X-CSRF-Token`, the given `Idempotency-Key`, `If-Match`). The key is
generated **once per dialog open** (`crypto.randomUUID()` in a ref, set when the dialog opens) and reused
on every retry from that dialog, so a retry after a network failure returns the same result. A ref guard
plus `disabled` while in flight means a double click sends **one** POST. Outcomes:

- 200 → navigate to `/purchase-orders/{id}/issue`.
- 409 `stale_version` → an alert in the dialog: "This order changed since you opened it." with `Reload` (reloads the PO and closes the dialog; the next open gets a new key). Nothing navigates.
- Any other problem (the 409s in the table, 400, 403, network) → an alert in the dialog with `failure(problem, "Issuing the purchase order")` (`components/requisitions/api.ts`); the dialog keeps its state and its key.

### 3. The moment (`/purchase-orders/:id/issue`)

**Routing.** In `routes/__root.tsx` add `PO_ISSUE_PATH = /^\/purchase-orders\/([0-9a-f-]{36})\/issue$/`
beside `PO_PATH` (`__root.tsx:76-78`), a shell-route entry beside the `PO_PATH` one (`:287-290`; title
"Purchase Order Issued", breadcrumbs Organization › Purchase Orders › Purchase Order (link to the PO) ›
Issued), the match beside `:451-453`, and the render beside `:470`. The page component is
`routes/purchase-orders/issue.tsx` (the folder's naming: `detail.tsx`, `changes.tsx`, `edit.tsx`).

**Reads.** `GET /purchase-orders/{id}` and `GET …/transmissions` (use `useLoad`,
`components/requisitions/useLoad.ts`, as `PoCards.tsx:88`). If the PO is not `issued`: "This purchase
order has not been issued." with a link back to it, no stage. The rows that matter are the **current
send**: `po_id === id`, `template_version === "po-issued-v1"`, `attempt` = the greatest among those.

**The stage** plays §7.16.2: `po-stage`; `po-doc` lifts on `--shadow-drag`; `po-seal` (success tone);
`po-trace` runs to `po-vendor` (the vendor's `vendor_snapshot.trading_name`) as the email is queued.
Steps chain on each animation's `finished` promise: no delay constants between them. Each step is a word
and a row in a **Frames** table (`<table>` with a caption; the row of the frame on show has
`aria-current="step"`), so the table is the whole story without the drawing (A11Y-009, DECISIONS 179).
Plays once per session per PO (`sessionStorage` key `po-issue-played:<id>`, set when the play starts);
later visits show the finished picture. Reduced motion
(`matchMedia("(prefers-reduced-motion: reduce)")`): the finished picture with the note "Animation is
off: this is the finished picture.", no animation is created. Below 760px (MASTER §7.16.2's own value; the
same literal is already used as a container query at `styles/purchase-orders.css:22`; CSS media and
container queries cannot read custom properties) the trace is hidden and the stage stacks.

**Result** after the play: the outcome in words and a small table (recipient, version `v{revision + 1}`,
result) for the current send, the result rendered with `components/ui/Signal.tsx` and `sentSignal`.

**Transmission words (MASTER §2.3, DECISIONS 173).** `sentSignal` in `components/purchasing/api.ts:30-41`
today returns bare `Delivered`, `Queued`, `Complained` and a `warning` tone for `address_suppressed`,
which MASTER §2.3 forbids. Correct the `SENT` map to MASTER's closed set, in place, so the detail card,
the list column and this page say the same thing:
`queued` info `Email Queued` · `sent` info `Email Sent` · `delivered` success `Email Delivered` ·
`failed` danger `Email Failed` · `bounced` danger `Email Bounced` · `complained` danger `Email Complaint` ·
`address_suppressed` danger `Address Suppressed`. The date suffix stays (`Email Delivered 12 Oct`).
Update `components/purchasing/api.test.ts:6-9` to the new words; `tests/e2e/po-screens.spec.ts:19-20`
(`toContainText("Bounced")`, `"Delivered"`) still holds and is not edited.

### 4. Failure observation and recovery

Issue only enqueues; delivery is later. The page polls `GET …/transmissions` while **any** row of the
current send is `queued` or `sent`; it stops when **every** row of the current send is terminal
(`failed`, `address_suppressed`, `delivered`, `bounced`, `complained`), or at the time cap (then
"Still sending — results will appear on the order." and it stops). Polling stops on unmount.
`POLL_MS = 5000` and `POLL_CAP_MS = 120000` are network timing constants (`const` in the component with a
`ponytail:` comment naming the cap and that a push channel would replace it), not visual tokens.

The frame shows a failure as soon as **any** row of the current send is `failed`, `bounced`,
`address_suppressed` or `complained`: the trace snaps back to `--status-danger`, the failed recipients
are named in words, and the recovery is focused. The recovery set is a pure function
`recovery(rows, canChangeRecipient)` in `components/purchasing/transmissions/recovery.ts` (shared with
E13-S16, whose packet names `components/purchasing/transmissions/*`), where
`canChangeRecipient = po.vendor_status !== null` (decision 2):

| Failures in the current send | `canChangeRecipient` | Actions, primary first | Focused |
|---|---|---|---|
| any `complained` | true | `Change Recipient` only | `Change Recipient` |
| any `complained` | false | none | the failure message (`tabIndex={-1}`): "The vendor's address reported this email as spam. Someone who can view this vendor's contacts can change the recipient." |
| any `bounced` or `address_suppressed`, no `complained` | true | `Change Recipient`, `Resend` | `Change Recipient` (DECISIONS 174) |
| any `bounced` or `address_suppressed`, no `complained` | false | `Resend` | `Resend` |
| only `failed` | either | `Resend`, then `Change Recipient` when true | `Resend` |

- `Resend` → `POST …/transmissions/resend` with body `{}` and `mutationHeaders(key)` (no `If-Match`: the route takes none), its key held per recovery attempt so a double click sends one POST. Its text says: "Sends the same version again. Nothing more is committed."
- `Change Recipient` opens a Radix dialog listing `GET /api/v1/vendors/{vendor_id}/contacts` (path param `id` = `po.vendor_id`) as checkboxes (name, email, type), 1 to 20 chosen; its note says "The next send goes only to the contacts you choose." Submit `POST …/transmissions/resend` with `{contact_ids}` and `mutationHeaders(key)`. A 422 shows the field error on the list; a failed contacts load shows `failure(…)` with `Try again`.
- After either resend succeeds: the response replaces the rows, the new attempt becomes the current send, the stage shows the queued state again without replaying, and polling restarts with a fresh cap.
- A 409 `transmission_queued` (another recipient's send still queued) or any other problem shows `failure(problem, "Resending")` beside the actions; focus stays on the action. A 403 (the viewer lacks `purchase_order.issue`; the server is the authority and `PoRead.actions` carries no resend action for an issued PO) shows the server's detail the same way.

**Motion tokens:** each transition uses `--dur-fast`/`--dur-base`/`--dur-slow` (≤ 260 ms,
`tokens.css:178-180`) and an `--ease-*` token (`:182-185`); `--dur-page` (320 ms, `:181`) is not used, so
every transition stays ≤ 300 ms. Shadow `--shadow-drag` (`:89`, dark `:262`, `:341`), danger
`--status-danger`, success `--status-success`. New classes `.po-stage .po-doc .po-seal .po-trace
.po-vendor` go in `styles/purchase-orders.css`, tokens only; no value from `design-system/canvas*/xlr8flo.css`.

## Plants

1. Generate a new Idempotency-Key per click instead of per dialog open: the retry same-key assertion fails.
2. Drop the in-flight guard and `disabled`: the double-click one-POST assertion fails.
3. Ignore reduced motion: the reduced-motion assertion fails.
4. Focus `Resend` on a `bounced` result with the vendor visible: the hard-bounce focus assertion fails.
5. Offer `Resend` on `complained`: the complained assertion fails.
6. Offer `Change Recipient` when `vendor_status` is null: the decision-2 assertion fails.
7. Keep polling after every row is terminal: the no-further-requests assertion fails.
8. Restore the bare `Delivered` word in `SENT`: the `sentSignal` vitest fails.
