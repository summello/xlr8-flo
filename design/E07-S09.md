# E07-S09 — Nightly reconciliation job: recompute from ledger, report drift, never correct

**Epic** E07 · **M1** · **engine/M** · after **E07-S06**, **E03-S06** · tags: `money`

## Requirements

- **BUD-013** — Recalculation jobs must be idempotent and report discrepancies rather than overwrite posted history.
- **OBS-004** — Business monitoring must expose stuck approvals, unreconciled balances, expired vendor documents, and failed transmissions.

## Contract

A job registered with the Postgres job queue (existing `kernel/jobs`), schedule: nightly at 02:00 UTC via the existing cron-worker tick; manual trigger through an internal-only endpoint `POST /internal/jobs/budget-reconcile` guarded by the existing origin-secret dependency (same as the quota endpoints).

Migration (reversible): the next revision after the current head at story start (revision id `20260826_<next 4-digit number>`, `down_revision` = the head `python -m flo.kernel.migrate --check` validates today); stories merge one at a time, so there is no gap or fork: `balance_drift_report(id uuid pk, org_id, run_id uuid not null, project_id uuid not null, bucket ledger_bucket not null, ledger_total numeric(18,4) not null, balance_total numeric(18,4) not null, difference numeric(18,4) not null, detected_at timestamptz not null default now())` — **append-only by trigger, RLS**; `reconcile_run(id uuid pk, org_id, started_at, finished_at, projects_checked int, drift_rows int, status text check in ('ok','drift','failed'))` (same protections).

## Behaviour (BUD-013, D-11, OBS-004)

1. Per org, in one **read-only** transaction (`SET TRANSACTION READ ONLY`, repeatable read for a consistent snapshot): recompute `SUM(amount) GROUP BY project_id, bucket` from `ledger_entry`, join to `project_balance`, and write one `balance_drift_report` row for **every** (project, bucket) whose ledger total differs from the stored balance. The job **never updates `project_balance` or `ledger_entry`**; the only tables it writes are the two report tables (invariant 9: it reports, never corrects). A test asserts the balance table is byte-identical before and after a run that found drift.
2. Idempotent: running twice for the same snapshot produces two runs and the same drift rows per run keyed by `run_id`; neither run alters any balance (BUD-013).
3. `status='drift'` emits a structured ERROR log `business_monitor=unreconciled_balance` with `org_id`, `projects`, and the largest `difference` (this is the P1 alert; the OBS-004 monitor reads the latest run) — no amounts beyond the difference.
4. `GET /api/v1/budget/reconciliation/status` (permission `ledger.read` at organization scope) → 200 `{last_run_at, status, drift_rows}`; `GET .../reconciliation/drift?run_id=&cursor=&page_size<=50` → 200.
5. A single org's failure does not stop the others; its run row is `failed` with only the exception class.
6. Orgs are iterated by a service-role query allowed to list tenant ids (the same pattern the existing jobs use); each org's work runs under its own tenant scope.

## Acceptance criteria

- [ ] On clean data, a run writes a `reconcile_run` with `status='ok'`, zero drift rows, and an unchanged `project_balance`
- [ ] A test that manually edits `project_balance.allocated` (bypassing the service, as the owner) makes the next run record exactly one drift row with the right difference, status `drift`, and leaves the tampered balance **unchanged**
- [ ] Planted drift in two projects of two orgs is isolated per org (each org's report sees only its own rows; another tenant's `run_id` → 404)
- [ ] Running the job twice is safe and creates no balance changes
- [ ] Drift and run tables reject UPDATE/DELETE
- [ ] The drift ERROR log line is emitted and contains no secret or full amounts list
- [ ] One org raising mid-run produces a `failed` row for it and still processes the next org
- [ ] The internal endpoint without the origin secret → the shared 404; authenticated read endpoints without `ledger.read` → 403
- [ ] Migration up/down/data-preservation
