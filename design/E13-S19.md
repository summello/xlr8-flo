## Requirements (inlined)

- **PO-013** — Cancelling or reducing a PO must release the unused commitment exactly once and must not erase its history.
- **ACC-006** — Releases of unused commitment happen once and keep their history (corrections are new rows, never edits).

## Design

### 1. Back end: one read route and one alignment (in this story)

**Why a route:** the page spec requires the dialog to state the released figure before confirming
(§2), and no read supplies it: `released_amount` counts releases already posted, and `budget-summary`'s
`this_po` is the lines' share, not the open commitment (`service.py:620-648`).

`GET /api/v1/purchase-orders/{id}/cancel-preview` → `PoCancelPreviewRead`, gated by `AmendContext`
(the same gate as the command it describes; it shows the caller nothing beyond what cancel itself would
do with their permission). 404 for a foreign or unknown PO (via `service._row`, before anything else);
409 `invalid_transition` for any status cancel refuses (`cancel.py:115`: anything but `draft`,
`approval_pending`, `approved`, `issued`). Read only: it takes no lock and posts nothing.

```python
class PoCancelPreviewRead(BaseModel):        # schemas.py, beside PoCancelRead
    status: PoStatus
    released: str                 # the open commitment cancel would release; "0.0000" before issue
    released_currency: str | None # the commitment entries' currency; None when released is 0
    rereserved: bool              # issued, a live reservation, and released > 0 (cancel.py:160)
    requisition_number: str
    reservation_project: PoProjectRef | None  # the live reservation's project when rereserved
    main_project: PoProjectRef    # requisition.project_id: where "Also cancel" returns the money
```

`cancel_preview(conn, scope, po_id, actor_id)` lives in `modules/purchasing/cancel.py`. To keep the
figure identical to what cancel releases, **extract** the open-commitment query at `cancel.py:145-153`
into `_open_commitments(service, root) -> list[tuple[int, Decimal, str]]` (entry id, remaining,
currency; add `e.currency` to the select) and call it from both `_cancel_issued` (ignoring the
currency; behaviour unchanged) and `cancel_preview`. `released` is the sum of `remaining` for an
`issued` PO, else 0, formatted with `service._fmt` (`service.py:117`). The reservation is
`reservation_entry(conn, scope, requisition_id)` unlocked, and its project
`reservation_remaining(conn, scope, entry).project_id`; project refs from
`ProjectService(conn, scope).get(id)` (`.number` as `code`, `.name`), as `service.py:628-638` does.
Route in `api/purchasing.py` beside `po_budget_summary`; regenerate the client
(`npm run generate:api` in `apps/web`).

**Alignment:** `service.py:664` offers `cancel` on `approval_pending` to every amend holder, but the
command is creator-only there (`cancel.py:93`, operator decision `992efaff`). Change that tuple to
`("cancel", "amend", True)` so `actions` tells the truth. Nothing else in `with_access` changes.

### 2. The dialog: `components/purchasing/dialogs/CancelOrReduce.tsx`

**Trigger** in `detail.tsx`'s `vendor-head-actions`, rendered only when `p.actions` contains `cancel`:
label `Cancel or Reduce` when `p.actions` also contains `reduce`, else `Cancel PO`; `Prohibit` icon
(Phosphor, regular), class `vendor-destructive req-destructive`. On success the dialog closes and calls
`po.reload()`; nothing else on the page changes.

**Mode** (a radio group, only when `reduce` is offered; default `Cancel the Whole PO`):
`Cancel the Whole PO` · `Reduce Quantities`.

**Cancel mode.** On open, `GET …/cancel-preview` (loading: one skeleton row at final height; error:
the problem's words via `failure()` and a `Try Again` that re-fetches; the confirm button stays
enabled, and the server still refuses whatever is wrong). Then a `What happens` list, every money word
from the preview, never computed in the browser:
1. The money sentence, from `cancelConsequence(preview, alsoCancelLines)` (a pure function exported
   from `components/purchasing/api.ts`):
   - `status !== "issued"`: "Nothing was issued, so nothing is committed or released. The requisition keeps its reservation." (`approval_pending` adds "The approval request is withdrawn.")
   - issued, `released` is zero: "Nothing is left to release: the commitment is used."
   - issued, `rereserved`, box clear: "Releases <released> once and re-reserves it for requisition <requisition_number> on <reservation_project code name>, so another PO can order the reopened quantity without new approval."
   - issued, `rereserved`, box set: "Releases <released> once and returns it to <main_project code name>. The requisition lines are cancelled."
   - issued, not `rereserved`: "Releases <released> once. The requisition holds no reservation, so the money is available again on the project it was committed to." Box set adds "The requisition lines are cancelled."
   `<released>` is `<Money zero="value">` with `released_currency`.
2. What stays: "The PO, its lines, versions and history stay readable."
3. The vendor line (below).

Controls, **issued only** (cancel ignores both before issue, `cancel.py:108-118`, so they are not
shown and the defaults are sent): checkbox `Also cancel these requisition lines` →
`cancel_requisition_lines`, changing sentence 1 as above; checkbox `Tell the vendor this PO is
cancelled`, default on → `notify_vendor`. Before issue the vendor line reads "The vendor never received
this PO, so nothing is sent." Then `Reason (required)`, a textarea, `maxLength` 500, trimmed; empty →
field error "Give a reason." and focus moves to it, nothing is sent. Buttons: `Keep PO` (safe, focused
on open) and `Cancel PO` (`vendor-danger-confirm`, the only danger fill; busy label `Cancelling…`).
`POST …/cancel` with `mutationHeaders(key, p.version)`.

**Vendor checkbox.** The dialog is correct against the `notify_vendor` contract; the email behind it
is E13-S24's. Do not hide, reword or work around the checkbox, and do not touch
`notify_vendor_cancelled`. The e2e asserts the request body, not an email.

**Reduce mode.** A table of the PO's lines (`p.lines`): `Line`, `Description`, `Quantity` (current,
with `uom_code`), `New Quantity` (a text input, `inputmode="decimal"`, blank = unchanged, labelled
"New quantity for line <n>"), `Remove` (checkbox, labelled "Remove line <n>"; disables that row's
input). Client check before sending, per row, as a field error under the input: a value must match
`^[0-9]{1,14}(\.[0-9]{1,4})?$`, be above zero and below the current quantity ("Enter a quantity
between 0 and <current>; to drop the line, choose Remove."). Nothing changed → "Lower a quantity or
remove a line." and nothing is sent. Copy above the table: "Lowering quantities raises a change order
for approval. When it is approved, the unused commitment of the removed quantity is released once,
re-reserved for the requisition while it holds a reservation (DECISIONS 209), and the new revision is
sent to the vendor." (`changes.py:706-716, 683-688`). Same `Reason (required)` field. Buttons
`Keep PO` (safe, focused) and `Submit Reduction` (`vendor-danger-confirm`; busy `Submitting…`).
`POST …/reduce` with `mutationHeaders(key, p.version)` and `lines` holding only changed rows:
`{line_no, quantity}` or `{line_no, remove: true}`.

On 201 the dialog stays open on a result view: title `Change Order <number> Submitted`, "It is
waiting for approval." and the server's `budget_effect` as a list, one row per entry:
`<Money value={delta} currency={currency}>` (signed, parenthesised and coloured by `Money`) with its
`department_code` and `ledger_account_code`; a `Close` button (focused) closes and calls `po.reload()`.

Why reduce has no figure before submit: the reduce command creates and submits in one transaction
(`cancel.py:195-243`); drafting a change order first to preview it would leave an open draft that
blocks cancel (`change_in_progress`) when the user backs out. The figure the user sees is the
server's, on the submitted change order.

**Refusals** (both modes): the dialog stays open, the reason and entries are kept, and the
problem's words are shown in a `role="alert"` paragraph (`failure(problem, "Cancelling")` /
`"Submitting the reduction"`). A 409 (any label) or 403 is final: the next attempt uses a new
idempotency key. On 409 `stale_version` also show a `Reload` button that closes the dialog and calls
`po.reload()`. A network failure keeps the key (a retry replays).

**Keyboard and focus:** Radix focus trap; the safe button is focused on open; Escape and the close
button return focus to the trigger (ignored while busy); every control reachable by Tab; targets
`--touch-target` below 1024px as `vendor-head-actions` already does. **No new CSS is expected**; if
a rule is needed it goes in `styles/purchase-orders.css` with tokens only.

## Acceptance

- [ ] `GET /purchase-orders/{id}/cancel-preview`, real Postgres (`tests/purchasing/test_cancel_preview.py`): for an issued PO, `released` equals the total the following `POST …/cancel` releases (sum of its `release` ledger rows) in each of: re-reserved, no live reservation, after a partial release, after a change-order increase (two commitment entries); `rereserved` and the project refs match; a draft/approved PO gives `released` "0.0000" and `released_currency` null; a cancelled PO gives 409 `invalid_transition`; a caller without `purchase_order.amend` gets 403; the preview posts no ledger row.
- [ ] TEN-010: a named foreign-tenant test gives 404 for the preview, entered in `tests/isolation/test_route_coverage.py::COVERED`.
- [ ] `tests/purchasing/test_cancel.py` passes unchanged after the `_open_commitments` extraction.
- [ ] `with_access` on `approval_pending`: the drafting buyer with amend gets `cancel`; another amend holder does not (`tests/purchasing/test_po_reads.py`).
- [ ] vitest: `cancelConsequence` returns each of the five sentences above for its case.
- [ ] Playwright (`tests/e2e/po-cancel.spec.ts`, own fixture): cancel an issued PO: the released figure and the re-reserve sentence on screen are the stub preview's (odd figures, as `po-screens-fixture.ts` does); setting `Also cancel these requisition lines` switches to the returned-to sentence with the main project; the request carries `X-CSRF-Token`, `Idempotency-Key`, `If-Match: 3` and the body's `reason`, `cancel_requisition_lines`, `notify_vendor`; afterwards the detail shows the `Cancelled.` banner, `Released commitment` and the history entry.
- [ ] Playwright: a draft PO with `actions: ["cancel"]` shows `Cancel PO`, no mode choice and neither checkbox; a PO with no `cancel` in `actions` shows no trigger.
- [ ] Playwright: reduce one line and remove another; the body holds only those two rows; the result view shows `Change Order 2 Submitted` and the stub's signed `budget_effect`; a quantity at or above the current one is refused at the field and nothing is sent.
- [ ] Playwright: a 409 `stale_version` keeps the reason and offers `Reload`; an empty reason is refused at the field.
- [ ] Safe button focused on open; the danger fill only on the confirm button (computed `background-color`, as `tests/e2e/vendor-status-dialogs.spec.ts:210`); Escape returns focus to the trigger; the whole cancel path by keyboard only.
- [ ] axe in light and dark (`emulateMedia`, as `vendor-status-dialogs.spec.ts:232-240`) on the open dialog in both modes; MASTER §8 checklist; tokens only; `flo check --light` green.
