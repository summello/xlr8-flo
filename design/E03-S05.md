# E03-S05 — Idempotency middleware keyed on (org, key, body hash)

**Epic** E03 · **M0** · **concurrency/M** · after **E03-S03** · tags: `money`, `concurrency`

## Requirements

- **DATA-003** — Financial and workflow commands must accept an idempotency key where retries are plausible.
- **FIN-012** — Retries and duplicate submissions must not create duplicate financial effects.
- **WF-004** — Retrying a workflow command must return the existing outcome or safely continue; it must not duplicate records or amounts.

## Model

```sql
CREATE TABLE idempotency_key (
  org_id        UUID        NOT NULL,
  key           TEXT        NOT NULL,
  endpoint      TEXT        NOT NULL,
  request_hash  TEXT        NOT NULL,          -- sha256 of the canonical body
  state         TEXT        NOT NULL,          -- in_progress | completed
  status_code   INT,
  response_body JSONB,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  completed_at  TIMESTAMPTZ,
  PRIMARY KEY (org_id, key)
);
```

## Behaviour

1. Every state-changing `POST` accepts `Idempotency-Key`. It is **required** on money-path endpoints (approve, transfer, adjust, issue) and optional elsewhere; a money endpoint called without one returns 400.
2. **The key is claimed before the work runs**, inside the business transaction:
   ```
   INSERT INTO idempotency_key (…, state='in_progress') ON CONFLICT DO NOTHING
   ```
   Zero rows inserted means someone else holds it — read the existing row and branch on its state.
3. **Three outcomes on a repeat:**
   | Existing state | Same `request_hash` | Response |
   |---|---|---|
   | `completed` | yes | replay the stored status, body **and the follow-up headers** — see 3a |
   | `completed` | no | **422 `idempotency_key_reused`** — same key, different body is a client bug, and silently returning the old answer would hide it |
   | `in_progress` | any | **409 `request_in_flight`**, `Retry-After: 1` |
3a. **A replay must be usable, not merely equal.** Storing only status and body loses `Location`
   and `ETag`, and a client that retried *because it lost the first response* is exactly the client
   that needs them: without `Location` it cannot find the resource it just created. Persist those
   two headers alongside the body and set them on the replay. Nothing else — a stored `Set-Cookie`
   or `Date` replayed hours later is worse than absent.

4. The claim, the business work, and the completion update are **one transaction**. A crash mid-flight rolls the claim back, so the key is retryable rather than permanently poisoned.
5. `request_hash` is over a canonicalized body — keys sorted, insignificant whitespace removed — so a reserialized retry is recognized as identical.
6. Keys expire after 24 hours by a cleanup job (E03-S06). Expiry is long enough to cover any realistic client retry and short enough to bound the table on a 512 MB database.
7. Stored responses never contain a secret; they are the same bodies the client already received.

## Acceptance criteria

- [ ] The same key with the same body, sent twice, produces **one** ledger effect and two identical responses
- [ ] The same key with a **different** body returns 422, and creates no second effect
- [ ] Two concurrent requests with the same key: one succeeds, the other gets 409 with `Retry-After`
- [ ] A crash between claim and completion leaves the key reusable, not stuck `in_progress`
- [ ] Bodies differing only in key order or whitespace hash identically
- [ ] A money endpoint without `Idempotency-Key` returns 400 naming the header
- [ ] Replayed responses carry the original status code, not 200
- [ ] Keys older than 24 h are removed by the cleanup job
