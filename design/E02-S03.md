# E02-S03 — Password reset: single-use short-lived tokens, no account enumeration

**Epic** E02 · **M0** · **security/M** · after **E02-S02** · tags: `auth`, `security`

## Requirements

- **AUTH-007** — Authentication errors must not reveal whether an account exists.
- **AUTH-008** — Password reset tokens must be single-use, short-lived, securely generated, and invalidated after use.

## Contract

```
POST /api/v1/auth/reset-request  {email}              → 202 always, body identical
POST /api/v1/auth/reset          {token, password}    → 204 | 400 invalid_or_expired
```

## Behaviour

1. **`reset-request` returns 202 with an identical body and comparable timing whether or not the account exists.** No "we sent you an email" versus "no such account" distinction anywhere — not in the body, not in the status, not in a header, not in the response time. When the account does not exist, do the same work minus the send.
2. Token: 256 bits from `secrets.token_urlsafe(32)`. Only its SHA-256 hash is stored. The plaintext exists exactly once, in the email.
3. TTL 30 minutes, configurable. **Single use** — consumed atomically:
   ```sql
   UPDATE password_reset SET used_at = now()
    WHERE token_hash = :h AND used_at IS NULL AND expires_at > now()
   RETURNING identity_id
   ```
   Zero rows returned means invalid, expired, or already used — all three answer with the same error.
4. Requesting a new reset invalidates all outstanding tokens for that identity.
5. On success: set the new password (through the E02-S01 policy check), **revoke every session** for that identity, and audit. A reset is the remedy for a compromise; leaving other sessions alive defeats it.
6. Send through the outbox (E03-S06) so a mail failure cannot roll back or duplicate the token.
7. Rate limit per email and per IP; exceeding it still returns 202 — the limit must not become an enumeration oracle.
8. The email states the expiry and says to ignore it if unexpected. It contains no account detail beyond the address it was sent to.

## Acceptance criteria

- [ ] Existing and non-existing email produce identical status, body, and headers
- [ ] Median timing difference between the two under 10 % over 100 trials
- [ ] A token works exactly once; the second attempt fails
- [ ] An expired token fails; the error is identical to an invalid one
- [ ] Requesting a second reset invalidates the first token
- [ ] Successful reset revokes all sessions for that identity
- [ ] Rate-limited requests still return 202
- [ ] Token plaintext appears in no log, no audit row, and no database column
