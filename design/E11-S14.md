## Requirements (inlined)

- **VEN-004** — Users must be able to submit a new-vendor onboarding request.
- **VEN-010** — Vendor tax identifiers and other configured unique identifiers must be checked for duplicates.
- **A11Y-006** — Forms: programmatic labels, field-level errors, an error summary, input preserved after a validation failure.
- **UX-005** — Errors say what happened, what was preserved, and how to recover.

## Screen `/vendors/new` (and `/vendors/:id/edit` for the requester's own draft)

Cards: `Company` (trading and legal name), `Identifiers` (tax id with country, plus configured
identifiers), `Where It Applies` (global, or units from a unit picker), `Contacts` (Billing and
Service and Delivery are always shown, with the `RFQs and POs` checkbox per contact, defaulting as
the server says), `Questionnaire` (typed fields from the published version; **no weights or points
are ever shown**), `Documents` (upload per required type through the existing attachment upload).
Sticky action bar: `Save Draft` and `Submit for Approval`, with the MASTER §7.11 status text
(`Required fields are still empty` / `All required fields complete`).

- **Live duplicate check:** on blur of an identifier (debounced 400 ms; no request per keystroke), call `GET /vendors/duplicate-check`. A match is shown **at the field** as a `Signal` with the existing vendor named only when the server names it, a `Use Existing Vendor` link to that profile, and, for holders of `vendor.approve`, `Override with a Reason`, which opens a reason field sent with submit.
- **Submit is never disabled** to signal an error. A failed submit shows a focused `role=alert` summary of `Category: link` entries (each link focuses its field), keeps every typed value, and maps server 422s field by field (contacts, answers, identifiers) and 409 `duplicate_identifier` to the identifier fields.
- **Submitted state:** names the approver(s) from the approval response and what happens next. 409 `workflow_not_set_up` reads: "Vendors cannot be submitted yet: no approval workflow is published. Your draft is saved. Ask an administrator to set one up."
- Tax id and bank values typed here are **write-only**: never echoed back into the form from a response, and never in the URL or the title.

## Amendment, 22 Oct 2026 (operator; canvas DECISIONS 237)

The author found a requester (`vendor.request` only) cannot save contacts (`vendor.edit`) or tax/bank details
(`vendor.edit` + `vendor.sensitive.reveal`), so cannot submit. Rule (decided):

- **Owner-draft write:** on `POST/PATCH/DELETE /vendors/{id}/contacts…`, the identifier and document write routes and
  `PUT /vendors/{id}/sensitive`, the server allows the write when the caller holds `vendor.edit` (unchanged) **or**
  holds `vendor.request` **and** `vendor.created_by` is the caller **and** `vendor.status = 'draft'`. Implement it once
  in the vendors service (one `can_write_draft(vendor, caller)` used by every write path), not per router, and lock
  the vendor row before the status check so a concurrent submit cannot interleave.
- **Sensitive is write-only for the owner:** `PUT /vendors/{id}/sensitive` no longer needs `vendor.sensitive.reveal`
  for the owner-draft case; the response and every read stay masked; reveal is unchanged (decision 124).
- **Locks on submit:** after `pending_approval` the owner's writes return 409 `not_draft`.
- Someone else's draft, or another tenant's vendor: **404**, never 403 (AGENTS.md 3.2).
- Regenerate the API client.

**Scope change:** `api/vendors.py` (route dependencies only) and the vendors module service are now **in** scope for
exactly this. Acceptance gains, as API tests: the owner (requestor role) saves contacts, an identifier, a document and
tax/bank details on their draft and submits it; the saved tax id comes back masked; the same owner gets 409 after
submit; another requester gets 404 on that draft; a vendor manager can still edit any vendor; a TEN-010 isolation case
for the new path. Plants: drop the `created_by` check, the other-requester test fails; drop the status check, the
after-submit test fails; return the sensitive value unmasked, the masking test fails.

## Amendment 2, 23 Oct 2026 (operator; canvas DECISIONS 239 and 240)

Review round 1 finding 3: a requester without `vendor.view` cannot reopen their draft. Decided:

- **Owner-draft read (239):** `GET /vendors/{id}`, `GET /vendors/{id}/contacts`, `GET /vendors/{id}/documents`
  admit the caller when they hold `vendor.view` (unchanged), **or** hold `vendor.request` **and**
  `vendor.created_by` is the caller, **in any status** (a submitted request reopens read-only). Implement one
  `can_read_request(vendor, caller)` in the vendors service beside `can_write_draft` (same order of checks, no row
  lock, no status check), used by all three routes;
  the route dependency admits `vendor.view` OR `vendor.request` and leaves the decision to the service.
  Sensitive values stay masked. Someone else's vendor and a foreign tenant: **404**.
  A member holding neither permission: 403.
- **`can_override` (240):** `DuplicateResult` gains `can_override: bool` from the service's `vendor.approve`
  check (the one the override path at `changes.py` makes). The form shows Override with a Reason only when it is
  true. **Remove the nil-id POST probe** in `VendorRequestForm.tsx`.
- Regenerate the API client.

Acceptance gains, as tests: the owner (requestor role) reads their draft, its contacts and documents (200, tax id
masked); a second requester gets 404 on all three; the owner still reads all three after submit (200, masked); a TEN-010 case for the reads;
`can_override` is true for a vendor manager and false for a requestor; Playwright: a requester saves a draft,
reloads `/vendors/:id/edit` and sees their values and the required document types; no override control for a
requester. Plants: drop the `created_by` check in `can_read_request`, the second-requester test fails; return
`can_override: true` always, the requester spec fails.

## Amendment 3, 23 Oct 2026 (operator; canvas DECISIONS 241)

Planner pre-flight before round 2: the Where It Applies unit picker calls `GET /api/v1/org/units`, which needs
`org.unit.read`. No baseline role that holds `vendor.request` has it (E22-S06 does not add it), so a requester who
chooses Selected units gets an empty list (the 403 is swallowed) and cannot submit a restricted vendor. Decided:

- **Units for requesters (241):** `GET /org/units` admits `org.unit.read` (unchanged) **or** `vendor.request`. The route
  dependency admits either permission; the org service decides. A caller holding `vendor.request` without
  `org.unit.read` gets only **active** units of their own organization (force `active=true`, same `OrgUnitRead`
  shape, same cursor paging). Neither permission: **403**. `GET /org/units/{id}` and all unit writes are unchanged.
- The form shows a units load failure as a field error with Try again, never as an empty list.
- Regenerate the API client.

**Scope change:** `apps/api/src/flo/api/org.py` (the `list_units` dependency only) and the org service's
`list_units` are **in** scope for exactly this.

Acceptance gains, as tests: a requestor lists units (200, inactive units absent even with `active=false`); an
org.unit.read holder still sees inactive units; a member with neither permission gets 403; a TEN-010 case (another
tenant's units never appear); Playwright: a requester chooses Selected units and sees the unit options. Plant: drop
the `vendor.request` admission, the requestor test fails; drop the forced active filter, the inactive-unit test fails.

**Nothing else in this story is open.** Decisions 237 (owner-draft writes, locked at submit), 239 (owner reads in any
status, masked), 240 (`can_override`) and 241 (units) are final. If a further gap appears, do not block the story on
it: implement everything else, put the gap in `notes.followup` with the route and the role that hits it, and finish.
Block only if the acceptance above cannot be met without a new authorization, money or state rule.
