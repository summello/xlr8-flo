# E11-S20 — A directly created vendor and the onboarding questionnaire

**Epic** E11 · **M3** · **engine/S** · after **E11-S05**, **E11-S06** · tags: — · **status: blocked (operator)**
Origin: M3 epic checkpoint E11 (codex-a finding 2, 8 Nov 2026).

## Requirements (inlined)

- **VEN-004** — Users must be able to submit a new-vendor onboarding request.
- **VEN-005** — Vendor creation, activation, scope changes, suspension, and reactivation must support approval.
- **VEN-006** — Administrators must be able to configure onboarding questionnaires with typed fields, required answers, weights, and scoring.

## Finding

A vendor created through `POST /api/v1/vendors` (holder of `vendor.create`) has no `vendor_onboarding`
row. `submit` (`apps/api/src/flo/modules/vendors/changes.py:259`) deliberately skips required-answer
validation and scoring when that row is absent (a `ponytail:` comment: "require one if policy says
otherwise"). So a vendor can reach approval and activation with no questionnaire evidence, while one
requested through `/vendors/request` must answer the published questionnaire.

## Blocked

**Question for the operator:** must every vendor, including one a `vendor.create` holder creates
directly, answer the published onboarding questionnaire before it can be submitted for approval?

- (a) **Yes, always.** Direct create pins the published version too; submit refuses with
  `answers_incomplete` until the required answers are given; with no published questionnaire, submit
  refuses with `questionnaire_unpublished`.
- (b) **No: direct create is the trusted path** (today's behaviour). The approver's evidence block says
  "Created directly; no questionnaire" so the approver sees the difference. A one-line UI story.
- (c) **A setting** `vendor.require_questionnaire_on_create` (default on), as with
  `vendor.allow_local_disable`.

This is a state-transition rule (what a vendor needs to leave `draft`), so the planner does not choose.
The design and acceptance are written once the operator answers.
