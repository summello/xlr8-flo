# E11-S20 — The approver sees that a vendor was created directly, without a questionnaire

**Epic** E11 · **M3** · **ui/S** · after **E11-S05**, **E11-S06**, **E11-S15** · tags: —
Origin: M3 epic checkpoint E11 (codex-a finding 2, 8 Nov 2026).

## Requirements (inlined)

- **VEN-004** — Users must be able to submit a new-vendor onboarding request.
- **VEN-005** — Vendor creation, activation, scope changes, suspension, and reactivation must support approval.
- **VEN-006** — Administrators must be able to configure onboarding questionnaires with typed fields, required answers, weights, and scoring.

## Finding

A vendor created through `POST /api/v1/vendors` (holder of `vendor.create`) has no `vendor_onboarding`
row. `submit` (`apps/api/src/flo/modules/vendors/changes.py:259`) deliberately skips required-answer
validation and scoring when that row is absent (a `ponytail:` comment: "require one if policy says
otherwise"). So a vendor can reach approval and activation with no questionnaire evidence, while one
requested through `/vendors/request` must answer the published questionnaire.

## Decision (operator, 8 Nov 2026)

(b) **Direct create stays the trusted path** (today's behaviour). The approver's evidence block says
"Created directly; no questionnaire", so the approver sees the difference. Submit, scoring and the state
machine do not change; the `ponytail:` comment at `changes.py` ~259 is replaced by a one-line comment citing
this decision.

## Design

- **Server, `vendors/changes.py` `submit` (~259):** when the vendor has no `vendor_onboarding` row, the change
  payload gets `"questionnaire": false` (today it gets nothing). That is the only server change. The flag is
  written at submit, so it is part of the change from the start and rides in the evidence (`evidence()`
  ~470 copies `change.payload`); a change submitted before this story has no flag and shows nothing new
  (no backfill, no migration). Do not compute it in `evidence()` from today's tables: the evidence is dated at
  the request and is part of the approval snapshot.
- **Web, `components/approvals/evidence/VendorEvidence.tsx`:** for `kind === "create"` and
  `payload.questionnaire === false`, render `<Signal tone="neutral" label="Created directly; no questionnaire" />`
  where the score signal renders for an onboarded vendor (the two are exclusive: no score without a
  questionnaire). Use the existing `Signal` tones only (MASTER §2.3); text carries the meaning, not colour.
- No new endpoint, no client regeneration (the payload is already an untyped JSON object on the wire).

## Acceptance

- [ ] pytest: submitting a directly created vendor stores `payload["questionnaire"] is False`; submitting a vendor that came through `/vendors/request` stores no `questionnaire` key and still carries `score`/`threshold`/`breakdown`; the approval evidence for the direct one carries the flag.
- [ ] pytest: direct-create submit still succeeds without answers (no new refusal), and the existing `answers_incomplete` test for an onboarded vendor still passes.
- [ ] Playwright (`apps/web/tests/e2e/vendor-evidence.spec.ts`; stub): evidence with `payload.questionnaire: false` shows the text "Created directly; no questionnaire" and no score signal; evidence with a score shows the score and not the text.
