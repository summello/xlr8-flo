## Design

A `Tax and Banking` card on `/vendors/:id`, in the grid slot E11-S12 leaves for it.
- **Masked:** values from the detail response (`•••• 4821`) in the mono face with +0.04em tracking (MASTER §7.15), so the width does not change on reveal.
- **Restricted:** when the response says `restricted: true`, the card reads `Restricted` and who to ask (the role label from the server).
- **Reveal Values** appears only when the server lists `vendor.sensitive.reveal` in the caller's allowed actions. It calls `POST /vendors/{id}/sensitive/reveal`, then shows the values and `Revealed by you, 14:02. Logged.` (time in the user's locale).
- **Re-mask** after 60 s (a constant named `REVEAL_SECONDS`, with a `ponytail:` naming open question E11-S08 #3), or when focus or the pointer leaves the card, whichever comes first. Re-masking **drops the values from React state and the DOM**; it does not hide them with CSS.
- **Edit** (holders of `vendor.edit` and reveal): an inline form that never pre-fills the full values without a reveal first.
- The values never go into the page title, `aria-live` text, a `console` call, the URL, `localStorage`, or the query cache. Fetch with the query client's `gcTime: 0` and never key the result into a shared cache.

## Amendment, 22 Oct 2026 (planner; canvas DECISIONS 236, applying 124)

The author found the server contract this card needs was never shipped by E11-S04. Decided:

- **Server (now in scope, vendors module only):** `VendorDetail` gains
  `sensitive_access: {can_reveal: bool, ask: str}`. `can_reveal` comes from the same authorization check
  `POST /vendors/{id}/sensitive/reveal` makes (`vendor.sensitive.reveal`), evaluated in the service, not the
  router. `ask` is the organization's role names holding that permission, joined for display ("Vendor Manager or
  Finance"); an empty list reads "an administrator". No `restricted` flag: a caller without `vendor.view` gets 403
  on the whole profile, so the card never renders for them.
- **Card states:** `can_reveal` true, masked values and `Reveal Values`. `can_reveal` false, masked last four,
  `Restricted` and `Ask <ask> to reveal these values.`, no button (decision 124). This replaces acceptance item 2's
  "a sourcing specialist sees masked values and no button" and "a user without vendor.view sees Restricted".
- **Reveal reason:** `Reveal Values` opens a small form with a required reason (the four closed codes, labelled
  `Verify a payment`, `Vendor asked`, `Audit support`, `Other`) and an optional note (200 characters, no figures;
  the server already rejects digit runs, show its message as a field error). Then reveal; the 60 s re-mask
  (decision 221) is unchanged.
- Regenerate the API client.

Acceptance gains: `sensitive_access.can_reveal` is true for a finance user and a vendor manager and false for a
sourcing specialist (API test per role); `ask` names the roles that hold the permission; the card shows `Restricted`
with the ask text and no button for the sourcing specialist; a reveal without a reason is blocked in the form and
the server still 422s a forced one. Plants: hardcode `can_reveal: true`, the sourcing-specialist test fails; render
the button whenever values are masked, the Restricted UI test fails.
