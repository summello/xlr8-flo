# E13-S10 — Deliverability: SPF/DKIM/DMARC check, bounce and complaint ingestion, suppression list

**Epic** E13 · **M3** · **engine/M** · after **E13-S09** · tags: `security` (Opus review)

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** D-17 (one origin; the webhook is under `/api/*`), invariant 6 (outbound calls go
> through kernel ports: the `module-external-effects` import-linter contract forbids `httpx` in
> modules), project memory (secrets: Secret Manager in production, keychain locally; never in a
> file). `design-system/pages/purchase-orders.md` §4.11. Back end only; the admin screen is E13-S21.
> **Writes:** every `PATCH`/`PUT`/`DELETE` on an editable resource follows `docs/m2-conventions.md` §O (`If-Match` with the integer version, `ETag` on reads, 400 when missing, 409 `stale_version` on mismatch). `Idempotency-Key` protects **POST** commands only (the middleware ignores other methods); where a packet says "(Idempotency-Key)" on a non-POST route, read §O instead.
> **RLS:** every new tenant table gets literal `ALTER TABLE <t> ENABLE ROW LEVEL SECURITY; … FORCE …; CREATE POLICY tenant_isolation ON <t> …` statements in the migration text, one block per table, never generated by a helper or f-string (the static gate in `tests/isolation/test_ci_guards.py` reads the text; the light check runs it).

> **Scheduling (planner, 16 Oct, from Opus on E11-S03):** production runs internal work only from the Cloudflare worker's `runScheduledWork` (`apps/web/worker/api-proxy.ts`): `tickJobs` on every trigger, and daily jobs at minute 30 of a mapped UTC hour (2, 3, 7, 16, 18 and 4 are taken). A job that is only registered in `api/internal.py` **never runs**. Add `email-domain-check` to the hour map at a free hour (for example 5). Extend `apps/web/src/api-proxy.test.ts` to assert it.

## Requirements (inlined)

- **EML-001** — The sending domain must publish SPF, DKIM and DMARC, verified by an automated check before first customer send.
- **EML-002** — Bounces and complaints must be ingested, stored against the vendor contact, and surfaced on the PO transmission record.
- **EML-003** — A hard-bounced or complained address must enter a suppression list and must not be retried silently; the PO must show as undelivered and be actionable (PO-015).
- **EML-006** — Every send must record provider message id, recipient, template version, document snapshot id, and result (PO-004).

## Design

**Domain check (EML-001):** extend the kernel email port with `domain_status() -> DomainStatus(spf,
dkim, dmarc: pass|fail|unknown, detail)`. The Resend adapter calls the provider's domain endpoint;
the SMTP adapter (local) returns `unknown` with "Local mail catcher". A daily job `email-domain-check`
(registered in `api/internal.py`) stores `email_domain_status(checked_at, spf, dkim, dmarc,
detail)`. **Gate:** the outbox dispatcher refuses to send a `po` email while the latest status is
not all `pass` **in production**. There is no environment setting: the gate is
`settings.email_provider == "resend"` (only production sends through Resend; local and CI use
`smtp`). The transmission row becomes `failed` with `result_reason = "Sending domain not verified"`.
Locally and in tests, `unknown` is allowed. **Reason storage:** the migration adds
`po_transmission.result_reason text NULL` (set on `failed`, `bounced`, `complained`, and
`address_suppressed`; cleared otherwise) and `PoTransmissionRead` gains `result_reason: str | None`.

**Webhook (EML-002):** `POST /api/v1/webhooks/email` is **unauthenticated by session but
signature-verified** (Resend signs with Svix: `svix-id`, `svix-timestamp`, `svix-signature`).
The secret is a new setting `resend_webhook_secret: SecretStr | None` (alias
`RESEND_WEBHOOK_SECRET`) in `kernel/config.py`, never logged; when unset the webhook fails closed
(401 on every call). Production binds it like `RESEND_API_KEY`: add
`"RESEND_WEBHOOK_SECRET": "flo-resend-webhook-secret:latest"` to
`apps/api/scripts/check_deploy_resources.py` and a keychain/Secret Manager step to `infra/SETUP.md`
beside the Resend API key (creating the secret is an operator step: `notes.followup`).
**CSRF and Idempotency-Key:** follow the worker precedent in `infra/cron-worker/jobs-tick.ts`. The
Cloudflare proxy (`apps/web/worker/api-proxy.ts`), for `POST /api/v1/webhooks/email` only,
synthesizes the double-submit pair (`Cookie: flo_csrf=<uuid>` and `X-CSRF-Token: <uuid>`) and sets
`Idempotency-Key` to the incoming `svix-id`; it forwards the body and Svix headers unchanged. No
exemption is added to the CSRF middleware or `IDEMPOTENCY_KEY_EXEMPT_PATHS`. Extend
`apps/web/src/api-proxy.test.ts`: the webhook path gets the pair and `Idempotency-Key == svix-id`;
any other path does not get them synthesized. It rejects a bad
signature with 401 and replays older than 5 minutes with 401. It is idempotent per provider event
id (`email_event(provider_event_id UNIQUE, …)`). It maps `delivered`, `bounced` (hard only;
soft → keep `sent`), `complained` and `failed` to `po_transmission.result` by `provider_message_id`.
The org is resolved **from the transmission row**, never from the payload (invariant 4). An unknown
message id → 200 and ignored (no oracle).

**Contact attribution (EML-002):** `po_transmission` stores only recipient name and email, and the
send path drops the contact id. The migration adds `po_transmission.vendor_contact_id uuid NULL`
(FK to the E11-S02 vendor contact, same org), and `modules/purchasing/transmission.py` sets it from
the chosen contact at send. `email_event` stores `transmission_id` and `vendor_contact_id` (copied
from the transmission), so a later contact email edit does not re-attribute the event.

**Suppression (EML-003):** `email_suppression(id uuid PK, org_id, email_normalised, reason, source_event_id,
created_at, UNIQUE(org_id, email_normalised))`, which a hard bounce or a complaint adds. The vendor contact (E11-S02) gains a computed
`suppressed: bool` on read. E13-S09's `enqueue` already refuses suppressed addresses. Removal is an
admin action (`DELETE /admin/email-suppressions/{id}`, `org.setting.manage`, reason, audited).

## Blocked

**Q-T1 (tenancy, operator/Opus; pre-flight 1 finding 5, 1 Nov 2026).** The webhook carries no
session, so tenant context is never set, and `po_transmission` has forced RLS with only
`tenant_isolation`. The packet says "the org is resolved from the transmission row", but reading
that row needs a cross-tenant lookup by `provider_message_id`, which today's RLS forbids. Which
mechanism is allowed?
(a) a worker-scoped policy on `po_transmission` (`app.worker = 'webhook'`, SELECT only, matched by
`provider_message_id`), then `SET LOCAL app.org_id` to the row's org for the update;
(b) a narrow non-tenant routing table `email_message_route(provider_message_id PK, org_id)` written
at send time, read under the worker flag like the outbox, then `SET LOCAL app.org_id`;
(c) Resend tags set at send (`org_id`), trusted only because the payload is Svix-signed. This
contradicts invariant 4's "never from the payload" wording.
**Decided (operator, 1 Nov 2026): (b).** A narrow non-tenant routing table
`email_message_route(provider_message_id PK, org_id)`, written at send time and read under the worker
flag like the outbox, then `SET LOCAL app.org_id` to the row's org for the update. Not (a), not (c):
`org_id` never comes from the webhook payload (invariant 4). The design author folds this into the
packet (migration with literal RLS statements, the write at send time in the same transaction as the
`po_transmission` row, the worker-flag read, the isolation test, the plant) and removes this section;
then pre-flight 2.

## Acceptance

- [ ] Webhook: a valid signature updates the transmission; a bad signature → 401; a replay → 401; the same event twice → one row; an unknown message id → 200 with no change; the org comes from the transmission (a forged org in the payload is ignored).
- [ ] Hard bounce → `bounced` + suppression; complaint → `complained` + suppression; soft bounce → stays `sent`.
- [ ] A suppressed contact on resend → `address_suppressed` without an outbox email.
- [ ] Production gate: with a failing domain status, a PO send fails with the reason; in test mode it sends.
- [ ] The signing secret never appears in logs (log-capture assertion); with the secret unset every call → 401.
- [ ] Proxy test: the webhook path gets the synthesized CSRF pair and `Idempotency-Key == svix-id`; other paths do not.
- [ ] Failed, bounced, complained and suppressed transmissions return `result_reason`; the event row carries `vendor_contact_id`.
- [ ] `DELETE /admin/email-suppressions/{id}` removes by the suppression `id`.
- [ ] TEN-010 on the admin routes; `flo check` green.

## Plants

1. Accept the org id from the payload: the forged-org test fails.
2. Skip the signature check: the 401 test fails.
