# E05-S11 — Login throttling: per-identity and per-client failure limits, trusted client IP behind Cloudflare

**Epic** E05 · **M1** · **security/M** · after **E05-S09** · tags: `auth`, `security`

> **Conventions:** read `docs/m1-conventions.md`. It applies unless this packet says otherwise.

## Why this story exists

The M0 release review found that `LocalIdentityProvider.authenticate` performs an argon2 verify per attempt with no failed-attempt limit (only the MFA path has a window and lock), and that the API never learns the real client address: every request arrives from a Cloudflare edge address, so any per-IP control keyed on `request_device().ip_prefix` is either useless or spoofable.

## Requirements

- **AUTH-007** — Authentication errors must not reveal whether an account exists.
- **AUTH-004** — Password minimum lengths (the throttle must not weaken or bypass the policy).
- **SEC-001** — Designed and verified against OWASP ASVS 5.0 Level 2 (V2: anti-automation against credential stuffing and brute force).

## Design decisions (confirm on review)

- **D-M1-28 Trusted client address.** The API trusts the client address only from the `CF-Connecting-IP` header, and only on requests that already passed the origin-secret check (so only Cloudflare can set it). A request that carries `CF-Connecting-IP` without the valid origin secret is ignored for addressing (the header is dropped, the socket address is used). The address is recorded as a prefix (`/24` IPv4, `/64` IPv6) as the session store already does. Do not rely on `X-Forwarded-For` or on `uvicorn` proxy-header trust.
- **D-M1-29 Same response, same timing class.** A throttled attempt returns the same status and problem body as a wrong password (401, uniform authentication failure) so the throttle reveals nothing about account existence (AUTH-007). It sets `Retry-After` only when the **client-prefix** limit triggers, never for the identity limit, because the identity limit would otherwise confirm an account exists. Throttled attempts skip the argon2 verify (that is the point) but wait a randomized 150 to 300 ms so latency does not separate throttled from verified failures by much.
- **D-M1-30 Storage.** A table `login_attempt(id bigserial, kind text check (kind in ('identity','client')), key_hash bytea not null, occurred_at timestamptz not null default now())` with index `(kind, key_hash, occurred_at)`. Keys are SHA-256 of the lowercased email or of the address prefix, never plaintext. Rows older than 24 h are deleted by the existing job runner. This table carries no `org_id` (the tenant is unknown at login) and is a documented global table; add it to the isolation gate's global-table allow-list with a reason.

## Contract

Settings (all with safe defaults, validated ranges): `login_identity_max_failures=10` per `login_window_seconds=900`; `login_client_max_failures=30` per window. Counting is of **failed** attempts only; a successful login does not reset the client counter, but resets the identity counter. Limits are checked **before** the argon2 verify. A lock is the window itself (no permanent lockout): the identity counter ages out. Every throttle decision writes an audit event `auth.login_throttled` with the hashed key prefix (first 8 hex chars), the kind and the count, never the email or address.

Interaction with MFA: the existing MFA failure window and lock stay as they are.

## Acceptance criteria

- [ ] 10 wrong passwords for one email, then the 11th attempt with the **correct** password still fails with the uniform 401 and no argon2 verify is performed (assert via a spy); after the window passes (clock injected) the correct password succeeds
- [ ] 31 failures from one address prefix across different emails throttle the 32nd attempt and set `Retry-After`; the identity-limit case never sets `Retry-After`
- [ ] The responses for unknown email, wrong password and throttled identity are byte-identical apart from `correlation_id`
- [ ] `CF-Connecting-IP` is honoured only when the origin secret is valid; a spoofed header without the secret is ignored (test both)
- [ ] IPv6 addresses collapse to their /64; the session store records the same prefix
- [ ] Concurrency: 20 simultaneous failed attempts for one identity record exactly 20 rows and the limit triggers at the configured count (no lost updates)
- [ ] Plaintext email or address never appears in `login_attempt`, the audit row, logs or the problem body
- [ ] Old rows are purged by the job runner (test with injected clock)
- [ ] Migration up, down, data-preservation; plant tests: raise the limit to infinity and the throttle test fails; trust the header unconditionally and the spoof test fails

## Files

`migrations/<next>_login_attempt.py`, `kernel/identity/local.py` (throttle hook), `kernel/identity/throttle.py` (new), `kernel/session/store.py` (`request_device` address source only), `api/origin_auth.py` or wherever the origin secret is verified (expose a verified-origin flag only), `kernel/config.py` (the four settings), the job registration for the purge, tests under `apps/api/tests/identity/` and `apps/api/tests/session/`, the isolation allow-list.

## Out of scope

CAPTCHA · permanent lockout and unlock UI · per-organization policy · password reset throttling changes · any UI.

## Pre-flight amendments (Opus, 9 Oct 2026, traced against the code at 6dc07df) — authoritative, override anything above

Every item below is a place the packet as written could not be built. **Block (`notes.blocked`) only on a money, authorization, session or state-transition rule, or a value this packet does not state; defer anything else with a one-line `notes.followup`.** Write tests for a Linux CI runner (no `/private/tmp` or `/Users/` paths). Start this story after E05-S05 has merged (both edit `apps/web/worker/api-proxy.ts` and take the next migration number).

1. **The hook is in the login route, not in `local.py`.** `LocalIdentityProvider.authenticate(email, password)` has no client address. Create `kernel/identity/throttle.py` (`LoginThrottle`, a connection-based service in the style of `kernel/identity/reset.py`) and call it from `api/auth.py::login` through a `get_login_throttle` dependency: check before `provider.authenticate`; record a failure after; record a success after a good login. `kernel/identity/local.py` is not edited. The throttle exposes, as public surface for E05-S13: `check_client(prefix) -> bool` and `record_client_failure(prefix)`.
2. **Model the table on `password_reset_rate_limit` (migration 0010), do not invent a second shape.** `login_attempt(id bigserial PK, kind text NOT NULL CHECK (kind IN ('identity','client')), key_hash char(64) NOT NULL CHECK (key_hash ~ '^[0-9a-f]{64}$'), outcome text NOT NULL CHECK (outcome IN ('failed','throttled','succeeded')), occurred_at timestamptz NOT NULL)`, indexes `(kind, key_hash, occurred_at DESC)` and `(occurred_at)`. Keys are the SHA-256 **hex** of the lowercased (`casefold`) email or of the address prefix, never plaintext. (The packet's `bytea` is replaced by the repo's existing `char(64)` hex convention.) Counting rules: only `failed` rows count; the identity counter counts failures since that key's latest `succeeded` row; the client counter ignores successes. No `org_id`, so no RLS and no allow-list entry (the global-table guard only flags tables with `org_id`). Migration: the next revision after the head at start, with the up/down/data tests and the revision appended to `tests/kernel/test_migrate.py`.
3. **Trusted client address: the Worker sets it; the packet's `CF-Connecting-IP` plan is replaced.** We cannot verify what Cloudflare forwards on a Worker subrequest to `run.app`. Instead `cloudRunRequest` in `apps/web/worker/api-proxy.ts` deletes any inbound `X-FLO-Client-IP`, then sets it from the inbound `CF-Connecting-IP` (which Cloudflare sets and a client cannot spoof inside the Worker), alongside the existing origin-secret header. The API trusts `X-FLO-Client-IP` **only when the same request carries a valid `X-FLO-Origin-Secret`**. This cannot be a flag set by the `require_origin_secret` dependency: dependencies run after the session middleware, which already calls `request_device`. So add `kernel/session/client_address.py::trusted_client_host(request)`: compare the secret header with `Settings().origin_shared_secret` using `hmac.compare_digest` (cached `Settings`; the kernel must not import `flo.api`, the layering contract forbids it), then accept the header value only if `ipaddress.ip_address` parses it; otherwise return `None`. `request_device` (`kernel/session/store.py`) uses `trusted_client_host(request) or request.client.host`. Prefix rule stays `/24` IPv4, `/64` IPv6 (`_ip_prefix`). Side effect to note in the commit: session `ip_prefix` now records the visitor instead of the Cloudflare edge. Tests: a spoofed header without the secret is ignored; with the secret it is honoured; with the secret but an unparsable value it is ignored; the Worker strips a client-supplied `X-FLO-Client-IP` and sets its own (extend `apps/web/src/api-proxy.test.ts`).
4. **Purge cannot be a job.** The job queue is tenant-scoped (`job.org_id NOT NULL`), and nothing schedules global work yet. Purge opportunistically: inside the failure path, `DELETE FROM login_attempt WHERE id IN (SELECT id FROM login_attempt WHERE occurred_at < %s - interval '24 hours' LIMIT 100)`, with an injected clock, and a `# ponytail:` comment ("bounded delete per failure; move to the nightly Worker trigger if the table grows"). Test with an injected clock.
5. **Audit (AUTH-011): `audit_log` is `org_id NOT NULL` and `session_security_event.identity_id` is `NOT NULL`, so neither can hold a throttle decision for an unknown email.** The evidence is the `login_attempt` row with `outcome='throttled'` plus one structured WARNING log line per decision (`auth.login_throttled kind=<kind> key_prefix=<first 8 hex> count=<n>`), never the email or address. Retention is therefore 24 hours; a durable lockout audit trail beyond that is a recorded `notes.followup` for the operator, not built here.
6. **Behaviour, exactly.** Settings in `kernel/config.py` with safe defaults and validated ranges: `login_identity_max_failures=10`, `login_client_max_failures=30`, `login_window_seconds=900`, `login_throttle_jitter_min_ms=150`, `login_throttle_jitter_max_ms=300`. A request is throttled if **either** counter is at its limit. A throttled attempt: no argon2 verify, an `asyncio.sleep` of a random jitter from an injected rng, a `throttled` row, then `ProblemError(ErrorCode.UNAUTHORIZED)` identical to a wrong password; `Retry-After` is added **only** when the client limit triggered (the identity limit must never set it). Count-then-insert is not locked: a concurrent burst may overshoot the limit slightly but never loses a row (`# ponytail`).
7. **Tests go through the real production `app`** (the lesson of the cron tick): a cold browser flow with the CSRF pair, the origin secret, no session. Required: 10 wrong passwords then the correct one still fails with no argon2 call (spy); the byte-identical-apart-from-correlation-id responses for unknown email, wrong password and throttled identity; 31 failures from one prefix throttle the next and set `Retry-After`, while the identity case never does; 20 simultaneous failures record exactly 20 rows; plaintext never appears in `login_attempt`, logs or the problem body; window expiry via the injected clock; success resets the identity counter but not the client counter; the opportunistic purge. Plants: raise the limit to infinity and the throttle test fails; trust the header without the secret and the spoof test fails; make a throttled response differ from a wrong-password response and the uniformity test fails.
8. **Files (replaces the list above):** `kernel/identity/throttle.py` (new), `api/auth.py`, `kernel/session/client_address.py` (new), `kernel/session/store.py` (`request_device` only), `kernel/config.py`, `apps/web/worker/api-proxy.ts` and `apps/web/src/api-proxy.test.ts`, the migration, `tests/kernel/test_migrate.py`, tests under `tests/identity/` and `tests/session/`. Out of scope, unchanged: any UI (the sign-in screen already renders one uniform alert), the MFA failure window, CAPTCHA, a durable lockout audit.

## Pre-flight amendments 2 (Opus, 9 Oct 2026, after codex's first block) — authoritative

Amendment 6 named "validated ranges" without stating them. They are, in `kernel/config.py` (pydantic `Field` bounds, inclusive):
- `login_identity_max_failures`: default 10, `ge=3, le=100`.
- `login_client_max_failures`: default 30, `ge=5, le=1000`.
- `login_window_seconds`: default 900, `ge=60, le=86400`.
- `login_throttle_jitter_min_ms`: default 150, `ge=0, le=2000`.
- `login_throttle_jitter_max_ms`: default 300, `ge=0, le=5000`.
- A model validator rejects `login_throttle_jitter_min_ms > login_throttle_jitter_max_ms` (equal is allowed: fixed delay). No other cross-field rule: the client limit need not exceed the identity limit.
- Out-of-range values fail settings validation at startup (an environment override cannot silently disable the throttle). Add a test for a value below each lower bound, above each upper bound, and for min > max; the plant is raising a bound and watching its test fail.

## Pre-flight amendments 3 (Opus, 9 Oct 2026, after codex's second block) — authoritative

The packet was wrong about the session store: `kernel/session/store.py::_ip_prefix` truncates IPv6 to **/48** (and IPv4 to /24) on purpose (E02-S02 criterion 8, PRIV-001) and that does not change in this story. Ruling:
- **Do not edit `_ip_prefix` or any session prefix rule.** Existing sessions and their `/48` values are untouched; no migration of session data.
- The throttle has its **own** collapse, in `kernel/session/client_address.py` (the new file already planned): IPv4 to `/24` is NOT used for throttling; use the **full IPv4 address** and the IPv6 **/64** as the client key input (one household or one host is the unit being limited; a /24 would lump unrelated users). Hash it like the identity key (SHA-256, salted per the existing key-hash approach in this packet's amendment 2).
- `kernel/session/store.py` therefore needs **no edit at all**; where amendment 8 lists it (`request_device`), the only permitted change is to make `request_device` read the trusted address from the same `client_address` resolver so the session's recorded (still /24 and /48) prefix is derived from the trusted address rather than the Worker's socket address. If that is already what `request_device` does after your resolver lands, leave the file alone.
- Replaces the acceptance criterion "IPv6 addresses collapse to their /64; the session store records the same prefix" with: "the throttle key collapses IPv6 to the /64 (two addresses in one /64 share a client counter; two in different /64s do not), and a test pins that the session still records the /48 prefix for the same request."
- Two things stay untouched and need a test only because the resolver is new: the plant "trust the header unconditionally" still fails the spoof test; and a request with a valid origin secret but no `X-FLO-Client-IP` falls back to the socket address.

## Pre-flight amendments 4 (Opus, 9 Oct 2026, after codex's third block) — authoritative

- **Correction: keys are NOT salted.** Amendment 3's word "salted" was wrong. Follow the repo convention exactly (`kernel/identity/reset.py::_rate_key`): unsalted SHA-256 hex, domain-separated by a literal prefix. Identity key input: `f"identity:{email.casefold()}"` (strip surrounding whitespace first). Client key input: `f"client:{client_value}"`. The hash exists so no plaintext is stored; it is not a secret-keyed MAC and the packet does not require one.
- **`client_value`** is the string produced by one helper in `kernel/session/client_address.py`, `throttle_client_value(request) -> str`: the full IPv4 address, or the IPv6 address collapsed to its `/64` network string (`ipaddress.ip_network(f"{addr}/64", strict=False)`), or the literal `"unknown"` if no address can be resolved. Amendment 1's public surface becomes `check_client(client_value: str) -> bool` and `record_client_failure(client_value: str)` (S13 calls them with the helper's output).
- **Standing rule for the rest of this story:** an unstated low-level detail (hash encoding, a constant, a name, where a helper lives, a log field order) is never a block. Pick the choice that matches the nearest existing code, and record it in one `notes.followup` line. Block only on a money, authorization, session or state-transition rule, and only if a decision genuinely changes what an attacker or a user can do.
