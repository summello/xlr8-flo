# E05-S11 — Login throttling: per-identity and per-client failure limits, trusted client IP behind Cloudflare

**Epic** E05 · **M1** · **security/M** · after **E05-S09** · tags: `auth`, `security`

> **Conventions:** read `docs/m1-conventions.md`. It applies unless this packet says otherwise.

## Why this story exists

The M0 release review found that `LocalIdentityProvider.authenticate` performs an argon2 verify per attempt with no failed-attempt limit (only the MFA path has a window and lock), and that the API never learns the real client address: every request arrives from a Cloudflare edge address, so any per-IP control keyed on `request_device().ip_prefix` is either useless or spoofable.

## Requirements

- **AUTH-007** — Authentication errors must not reveal whether an account exists.
- **AUTH-004** — Password minimum lengths (the throttle must not weaken or bypass the policy).
- **SEC-001** — Designed and verified against OWASP ASVS 5.0 Level 2 (V2: anti-automation against credential stuffing and brute force).

## Design decisions (confirm on review)

- **D-M1-28 Trusted client address.** The API trusts the client address only from the `CF-Connecting-IP` header, and only on requests that already passed the origin-secret check (so only Cloudflare can set it). A request that carries `CF-Connecting-IP` without the valid origin secret is ignored for addressing (the header is dropped, the socket address is used). The address is recorded as a prefix (`/24` IPv4, `/64` IPv6) as the session store already does. Do not rely on `X-Forwarded-For` or on `uvicorn` proxy-header trust.
- **D-M1-29 Same response, same timing class.** A throttled attempt returns the same status and problem body as a wrong password (401, uniform authentication failure) so the throttle reveals nothing about account existence (AUTH-007). It sets `Retry-After` only when the **client-prefix** limit triggers, never for the identity limit, because the identity limit would otherwise confirm an account exists. Throttled attempts skip the argon2 verify (that is the point) but wait a randomized 150 to 300 ms so latency does not separate throttled from verified failures by much.
- **D-M1-30 Storage.** A table `login_attempt(id bigserial, kind text check (kind in ('identity','client')), key_hash bytea not null, occurred_at timestamptz not null default now())` with index `(kind, key_hash, occurred_at)`. Keys are SHA-256 of the lowercased email or of the address prefix, never plaintext. Rows older than 24 h are deleted by the existing job runner. This table carries no `org_id` (the tenant is unknown at login) and is a documented global table; add it to the isolation gate's global-table allow-list with a reason.

## Contract

Settings (all with safe defaults, validated ranges): `login_identity_max_failures=10` per `login_window_seconds=900`; `login_client_max_failures=30` per window. Counting is of **failed** attempts only; a successful login does not reset the client counter, but resets the identity counter. Limits are checked **before** the argon2 verify. A lock is the window itself (no permanent lockout): the identity counter ages out. Every throttle decision writes an audit event `auth.login_throttled` with the hashed key prefix (first 8 hex chars), the kind and the count, never the email or address.

Interaction with MFA: the existing MFA failure window and lock stay as they are.

## Acceptance criteria

- [ ] 10 wrong passwords for one email, then the 11th attempt with the **correct** password still fails with the uniform 401 and no argon2 verify is performed (assert via a spy); after the window passes (clock injected) the correct password succeeds
- [ ] 31 failures from one address prefix across different emails throttle the 32nd attempt and set `Retry-After`; the identity-limit case never sets `Retry-After`
- [ ] The responses for unknown email, wrong password and throttled identity are byte-identical apart from `correlation_id`
- [ ] `CF-Connecting-IP` is honoured only when the origin secret is valid; a spoofed header without the secret is ignored (test both)
- [ ] IPv6 addresses collapse to their /64; the session store records the same prefix
- [ ] Concurrency: 20 simultaneous failed attempts for one identity record exactly 20 rows and the limit triggers at the configured count (no lost updates)
- [ ] Plaintext email or address never appears in `login_attempt`, the audit row, logs or the problem body
- [ ] Old rows are purged by the job runner (test with injected clock)
- [ ] Migration up, down, data-preservation; plant tests: raise the limit to infinity and the throttle test fails; trust the header unconditionally and the spoof test fails
