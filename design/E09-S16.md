# E09-S16 — Sub-project funding: an approved requisition's sub-project draws from its main project

**Epic** E09 · **M2** · **ledger/L** · after **E09-S13** · tags: `money`, `concurrency`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (H: `on_outcome` runs inside the
> decision's transaction), `docs/author-traps.md`. Decisions: E09-S13 packet, 4, 7, 11 (D-M2-19, D-M2-22, D-M2-26).

## Why
Today an approved requisition's reservation stays on the main project and the generated sub-project
holds nothing (`requisitions/approval.py` `_approved`, project-linked branch). The operator's model: the
sub-project holds the money, so M3's purchase orders draw against their immediate project only.

## Requirements
- **REQ-002** — approval creates a requisition-generated sub-project funded from its parent.
- **ACC-001** — no reservation exceeds available budget; two approvals against one main project cannot overdraw it.
- **WF-003** — the transition and every ledger entry commit atomically.
- **FIN-011** — a release happens exactly once.
- **D-M2-19** — main → sub transfer, reservation on the sub-project, one transaction. **D-M2-22** — cancel after approval: funds back to the main project, entries on both, sub-project `abandoned`.

## Design — final approval of a project-linked requisition (and a Project Request assigned to an existing project)
In `_approved`, inside the decision transaction, after the sub-project is generated (`_generate`):
1. Lock `project_balance` for main and sub in project-id order (`LedgerRepository.balance(lock=True)`, as `transfers.transfer` does).
2. **Release** the live reservation on the main project (`release_reservation`, key `req:{id}:release:{round}:approved`, reason "approved, funds moved to sub-project").
3. **Transfer** the amount main → sub with `post_legs` (`budget/transfers.py:31`): legs `[(main, -amount, ":out"), (sub, +amount, ":in")]`, entry type `transfer`, key `req:{id}:fund:{round}`, `source_type="requisition"`, `source_id`=requisition, codes from the requisition. Regardless of funding mode (roll-down or roll-up): this is a transfer, not an allocation.
4. **Reserve** the amount on the sub-project (`reserve`, key `req:{id}:reserve:{round}:sub`), and set `requisition.reservation_entry_id` to it.
5. Net effect on the main project: allocated −X, reserved −X, available unchanged. Sub-project: allocated +X, reserved +X, available 0.
6. Assigned-project Project Requests (E09-S06 branch) follow the same three steps against the assigned project.

## Design — after approval
- **Stop** (`lifecycle.stop_approved`): release the sub-project reservation (remaining), transfer the
  unreserved remainder sub → main (`post_legs`, key `req:{id}:unfund:{round}`), then `abandon_generated`
  (which already refuses if the sub-project still holds anything). One transaction, locks in id order.
- **Amendment total change** (E09-S08, `requisitions/approval.py` amendment branch): an increase transfers
  main → sub then reserves the difference on the sub-project; a decrease releases the difference on the
  sub-project then transfers it back. Funds check on the main project under the lock.
- **`reduce_to`** (`requisitions/funding.py:40`, M3 caller): acts on the sub-project reservation; the released
  amount stays on the sub-project (M3 decides when to return it).
- **Drafts and pre-approval** are unchanged: reserve at submit on the main project (D-M2-15).

## Acceptance
- [ ] Approval: main allocated −X and reserved −X; sub allocated +X and reserved +X; one `transfer` group with two legs; drift empty.
- [ ] Concurrency (real Postgres): two approvals against one main project that can fund only one → exactly one succeeds, the other rolls back fully.
- [ ] Stop after approval: sub reservation released once, funds back on the main project, sub `abandoned`; repeat stop is a no-op.
- [ ] Amendment +Y and −Y move money as above; insufficient main funds refuse the increase with nothing written.
- [ ] Replay of the final decision (same Idempotency-Key) creates nothing twice.
- [ ] `tests/requisitions/test_exit_criterion.py` (E09-S14) updated: reservation on the sub-project, transfer legs on both.
- [ ] Plants: skip the release (drift or reservation test fails); transfer before locking both (concurrency test fails).
