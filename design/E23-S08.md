# E23-S08 — Structured, commit-bound test-evidence records that `flo gate` verifies

**Epic** E23 · **MT** · **chore/M** · tags: `security` (a change to the merge gate, so a fresh Opus session reviews it) · backlog item T7 · no dependency

> MT stories ship by a pull request to `main`, as E21-S01 did (PR #18).
> **No new dependency** (AGENTS.md §0.6). Opus review is required because this story edits `cmd_gate`, the only code that enforces the reviewer floor and the gated-story rule. A defect here weakens every later story.

## Why, and a correction to the backlog

`cmd_gate` counts a review when `r.get("ran_tests") is True` (`agents/scripts/flo`, ~line 838). The boolean is the reviewer's word. Nothing says what ran, against which commit, or with what result.

The backlog motivates this with three Codex re-reviews on 22 Oct that approved with `ran_tests: false`. **That failure is a different one.** Those reviewers told the truth: they hit the command cap before running anything (`project-memory.md`, 22 Oct: budget raised 25 to 40 and hard cap 35 to 55, tests required within the first 10 commands). The gate already rejects `ran_tests: false`. This story does not prevent that failure by itself.

What it does fix:

1. A `ran_tests: true` that is false, mistaken, or about a different commit is accepted today.
2. A reviewer cannot cite a green run that already exists. The author's submit step already ran `flo check --light` on the submitted commit and cached the green tree (`checked()`, ~line 2046). A reviewer spends commands re-running what is on record. With evidence records a reviewer can cite it at command 1, which attacks the actual 22 Oct cause.

## Pre-flight findings (Opus, 22 Oct 2026, traced against `799797d`)

- `checked(wt, profile)` already stores `task.json["check"] = {"tree", "profile"}` on a green, clean tree. It records a tree and a profile, no commit, no result list, no failure, no time. Keep that key (the cache reads it); add the new record beside it.
- `run_check(cwd, profile)` returns a bare True/False. Which steps ran is not captured.
- A reviewer's verdict does not carry the commit it reviewed. The reviewed SHA exists only as `.scratch/<S>.<R>.sha` markers read by `flo_facts.verdict_state(review, reviewed_sha, submitted_sha)`.
- The gate runs after `finish.sh` merges the milestone branch into the story (`AGENTS.md` §2.5), so `HEAD` at gate time differs from the commit the reviewer saw. **Binding evidence to `HEAD` at the gate would reject every story.** Bind it to `task.json["submitted_sha"]`, the commit that was submitted for review.
- In-flight stories have `task.json` files without any evidence. Enforcing on them would fail all of them mid-flight, and "no evidence list means skip" would be a bypass. Use an explicit flag set at start (below).
- `reviews/*.json` is gitignored and written by the reviewer agent by hand. A reviewer *could* write a forged evidence block. The defence is that the gate checks it against a record `flo` wrote itself in `task.json`. The threat modelled is a wrong or stale claim, not a reviewer editing runner state; say so in the code comment.

## Design

### 1. `flo` writes evidence, only `flo`

Add `record_evidence(wt, profile, ok, steps, seconds)`. Called from `checked()` after `run_check` returns (both pass and fail), it appends to `task.json["evidence"]` (a list):

```json
{"profile": "light", "commit": "<git rev-parse HEAD>", "tree": "<HEAD^{tree}>",
 "clean": true, "result": "pass", "seconds": 212,
 "steps": [{"name": "ruff", "ok": true}, ...], "at": "2026-10-22T12:00:00+0530"}
```

- `run_check` gains an optional `report=None` list; when given it appends `{"name", "ok"}` per step run (including the story tests it chose). Its return value and printing do not change.
- A cached hit in `checked()` appends nothing new; the earlier record stands.
- `clean` is `git status --porcelain` empty. **Only a clean record can prove anything about a commit.**

### 2. Verdict contract

A review that sets `"ran_tests": true` must also set `"evidence": {"commit": "<sha>", "profile": "light"}`. `flo review` prints the commit to cite and whether a green clean record for it already exists (the review prompt text, ~lines 610 to 760, and both JSON examples in it are updated). A reviewer may cite an existing record or run `flo check --light` themselves; either way the gate sees the same thing.

### 3. Gate verification (`cmd_gate`)

Enabled for a story when `task.json["evidence_required"]` is true. `cmd_start` sets it for every story started after this merges. Without the flag the gate behaves exactly as today.

For each review with `ran_tests` true, in addition to the existing checks:

1. `evidence.commit == task.json["submitted_sha"]`.
2. `task.json["evidence"]` has a record with that `commit`, the same `profile`, `result == "pass"` and `clean == true`.
3. Otherwise add a failure naming the reviewer and the commit (`codex: ran_tests=true but no passing evidence for commit abc1234`) and do not count that review. The failure must be explicit: silently dropping it would read as "0/1 reviews", hiding the cause.

The gated-story rule is untouched: `opus_final` still demands `reviews/<id>.opus.json` with `approve`. A valid evidence record never substitutes for it.

### 4. Docs and scorecard note

One paragraph (where `flo gate` is documented: `grep -rn "flo gate" docs/ agents/`). Add a `notes.followup`: `ran_tests` in the scorecard now means "a green clean light check exists for the reviewed commit", so `test_compliance` will trend to 100% by construction; if a reviewer-ran measure is wanted, add it separately.

## Design decisions (confirm on review)

1. **Citing is allowed.** Evidence is keyed to the commit, so who ran the check does not matter. The alternative (require a record created after the review launched) is stricter and re-creates the cost this story is meant to cut.
2. **Profile.** Only `light` is required, because that is what the story gate runs. A `full` pass also satisfies a `light` claim (full covers light).
3. **Tag `security`.** The tag list is for product risk, and a gate bug is not strictly that. It is used here because it is the mechanism that forces a fresh Opus review on the one file that enforces every other review rule. Recommended; confirm.

## Acceptance criteria

- [ ] `flo check --light` on a clean tree appends one evidence record with commit, tree, `clean: true`, `result: pass`, a non-empty `steps` list, `seconds`, `at`; a red check appends `result: fail`; a dirty tree appends `clean: false`.
- [ ] `cmd_start` sets `evidence_required: true`; a packet without the flag gates exactly as before (an unchanged fixture passes).
- [ ] With the flag: a verdict `ran_tests: true` and no `evidence` block makes the gate fail with a message naming the reviewer.
- [ ] With the flag: `evidence.commit` different from `submitted_sha` fails.
- [ ] With the flag: matching commit but no record, a `fail` record, or a `clean: false` record fails.
- [ ] With the flag: matching commit and a passing clean record passes the reviewer check.
- [ ] A gated story with a valid evidence record and **no** Opus verdict still fails with the Opus message.
- [ ] `flo review` output shows the commit to cite and the evidence status for it.
- [ ] Usage text and docs paragraph updated; follow-up recorded.

## Plants (AGENTS.md §2.2: each guard shown to fail)

1. Delete the evidence record from the fixture while keeping `ran_tests: true`: gate must fail. (This is the backlog's required plant.)
2. Change the verdict's `evidence.commit` by one character: gate must fail.
3. Set the record to `clean: false`: gate must fail.
4. Set the record to `result: fail`: gate must fail.
5. Remove `evidence_required` from the fixture: gate must pass (proves the flag, and so the rollout path, is real).
6. Comment out the Opus-file check: the gated-story test must fail, so the new code is shown not to mask it.
