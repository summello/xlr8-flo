## 1. Award reads skip the evaluator gate (blocker)

`modules/sourcing/awards.py`: `AwardService.read` (~522) and `AwardService.awards` (~907) return `AwardLineRead.unit_price`, `amount_vendor`, `amount_rfq` and `bid_id` to any `rfq.view` holder. `bids.py:352,374` and `comparison.py:661,679` call `assert_may_see_bids(self.repo, rfq_id, self.actor_id)` (`evaluation.py:244`) first; the award reads do not. A recused evaluator gets 409 on `/comparison` and the prices on `GET /sourcing/rfqs/{id}/award` and `/awards`.

Fix: call `assert_may_see_bids` inside the tenant transaction of the two **public** read methods, after `self._rfq(rfq_id)` (so a foreign RFQ is still 404 first). Do not put it in `_read`: write paths return through `_read`/`read` after their own checks, and the approval adapter reads awards for approvers who are not evaluators (the gate is a no-op for a non-evaluator, but keep it out of internal calls). Check every other caller of `read()` inside `awards.py` (`put_lines`, `patch`, `submit`, `withdraw`, `cancel`, `supersede` end with `self.read(...)`): for a recused evaluator those already fail earlier through `_standing` → comparison, or are not reachable; if any write path would now turn a committed write into a 409 on its final read, split a private `_read_for(rfq_id)` that the writes use and gate only the two GET entry points. Say which you did in the PR notes.

## 2. `not_lowest` is trusted from save time at submit (major)

`awards.py` `_store` (~698) stores `not_lowest = vendor not in tied` from the standing at `put_lines`. `submit` (~776) recomputes `standing` but reads `r.not_lowest` from the row (~802, ~809), and the award evidence (~1184) uses the stored flag too. A late bid accepted after the lines were saved (bid submit is refused only for `awarded` and an `approval_pending` award, `bids.py:108`) changes the standing; the flag does not follow.

Reproduced: A and B both quote 80, B is awarded with a `tie_override_reason`, a lead accepts a late bid from C at 70, submit → `approval_pending`, `not_lowest` false, no justification, setting on.

Fix, in `submit`, before the per-row checks: for each row compute `not_lowest = r.vendor_id not in standing.get(r.rfq_line_id, (set(), None))[0]`; where it differs from the stored value, `UPDATE award_line SET not_lowest = …` and use the fresh value in the two checks and everything after (re-read `rows`, or carry the value; the evidence at ~1184 must see the fresh flag). Nothing else about the checks changes. A 422 rolls the update back with the transaction, which is correct.

## 3. `ordered_value` counts superseded and cancelled POs (major)

`modules/purchasing/service.py` `awarded()` (~390-397) sums `po_line.line_total` for every PO with `status <> 'deleted'`. A change order (`changes.py:787 _write_revision`) copies the lines, `award_id` included, onto the new revision and leaves the old row `superseded` with its lines; a cancelled PO keeps its lines too. So `ordered_value` doubles per applied change order and keeps a cancelled PO's value while `ordered_qty` (the counter) is correct.

Fix: `p.status NOT IN ('deleted', 'superseded', 'cancelled')` in that one query. Display figure only; no ledger or counter is touched.

## 4. Non-ASCII webhook signature is an unhandled exception (minor)

`kernel/adapters/resend.py` `verify_svix` (~260): `hmac.compare_digest(expected, entry[3:])` on `str` raises `TypeError` for non-ASCII input. Starlette decodes headers as latin-1, so an unauthenticated `POST /api/v1/webhooks/email` with `svix-signature: v1,é` and a current timestamp is a 500.

Fix: compare bytes — `hmac.compare_digest(expected.encode(), entry[3:].encode())`. Result: `False`, so the route answers 401 as for any bad signature.

## 5. PO history cuts the newest events (minor)

`purchasing/service.py` `history()` (~611-631): `ORDER BY a.occurred_at, a.id LIMIT 201` keeps the **oldest** 200. Past the cap the cancel or the latest change is what is dropped.

Fix: select the newest `HISTORY_CAP + 1` (`ORDER BY a.occurred_at DESC, a.id DESC`), keep `HISTORY_CAP` of them, and return them in the order the endpoint returns today (oldest first, so reverse). `truncated` unchanged.

With a justification saved first (which re-stores the lines) → `approval_pending` and the read shows `not_lowest` true.

- [ ] **Ordered value:** issue a PO for an award line, apply one change order → `awarded-lines.ordered_value` equals the live revision's line total, not the sum of both; cancel the PO → `ordered_value` is 0 for that line. Hand-computed amounts in the test.

- [ ] **History cap:** with `HISTORY_CAP` monkeypatched to 3 and five audit rows on a PO, the three newest come back oldest-first and `truncated` is true.
- [ ] TEN-010: no new endpoint, so no new isolation case; the existing award and PO isolation cases stay green.
- [ ] `flo check --light` green.

## Plants

1. Remove the `assert_may_see_bids` call from `AwardService.awards` only: the `/awards` leg of the gate test fails.
2. In `submit`, use `r.not_lowest` from the row again: the stale-flag test fails (submit succeeds).
3. Put `'superseded'` back into the ordered-value sum: the change-order assertion fails.
4. Restore the `str` comparison in `verify_svix`: the non-ASCII test raises `TypeError`.
5. Restore ascending order with the limit in `history()`: the cap test returns the oldest three.
