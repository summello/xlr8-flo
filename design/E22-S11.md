# E22-S11 — Faster checks: template test databases, sharded backend and E2E CI

**Epic** E22 · **M3** · **chore/M** · tags: none

> Operator decision, 22 Oct 2026 ("go ahead on the CI speed-up for GitHub as well as local reviews").
> Evidence (planner, 21-22 Oct): the hosted `backend` job takes ~28 min and `frontend` ~13 min; the
> 40 slowest tests sum to ~5 min, so the backend cost is per-test fixed cost on one runner. Locally,
> creating a database and applying all 62 migrations takes 0.38 s; `CREATE DATABASE … TEMPLATE` of a
> migrated database takes 0.055 s. 59 test files build a database per test through `bootstrap_db` /
> `empty_database` + `apply_migrations`. This is the "template-database fix" the CI comment at the
> backend `pytest` step already names (pipeline plan step 6, 13 Oct).
> **Conventions:** `docs/author-traps.md`. **No new dependency** (AGENTS.md §0.6): stdlib, pytest,
> Playwright's built-in `--shard`, and GitHub Actions only.

## Design

### 1. Template databases (local and CI)

- In `apps/api/tests/` add one session-scoped fixture (in the shared `conftest.py` or beside
  `empty_database` in `tests/kernel/test_migrate.py`, wherever the other modules already import from)
  that, once per pytest session, creates a template database and applies every migration to it.
  - **Name:** `flo_tpl_<12 hex of sha256(the migrations directory's file names and contents)>_<dbname of TEST_DATABASE_URL>`.
    The migrations hash makes a changed migration build a new template; the worktree's own test
    database name keeps parallel lanes (one Postgres server, one database per worktree) from
    sharing or racing on a template.
  - Reuse it when it already exists **and** is marked complete (a `COMMENT ON DATABASE … IS 'complete'`
    written last, so a template interrupted mid-build is dropped and rebuilt). Drop templates with
    the same worktree suffix and a different hash.
  - The template has no open connection when it is cloned (Postgres refuses otherwise).
- A helper `migrated_database()` (fixture) that yields a fresh database cloned from the template;
  `bootstrap_db` and every fixture that today does `empty_database` + `apply_migrations(<all>)`
  uses it instead. Find them: `grep -rn "apply_migrations(" apps/api/tests`.
- **Unchanged:** every test that exercises migrations themselves (applies a prefix, up, down, data
  preservation, `test_migrate.py`'s chain and roundtrip tests) keeps `empty_database` and its own
  `apply_migrations` calls.
- `flo check --light` and the reviewers' runs get this for free.

### 2. Backend CI in 4 shards

- `backend` becomes a matrix job `backend-shard` with `shard: [1, 2, 3, 4]`, each with its own
  Postgres service, running `pytest -q` on its quarter of the test **files**: the sorted list of
  `apps/api/tests/**/test_*.py`, file *i* to shard `i % 4 + 1`, except that
  `tests/requisitions/test_exactly_once_property.py` (~103 s alone) is pinned to shard 1 and the
  others skip it. Put the selection in one small script, `apps/api/scripts/test_shard.py N TOTAL`,
  printing the files.
- Each shard runs with `--cov=flo --cov-report=` and uploads its `.coverage` file as an artifact
  (`coverage-<shard>`; set `COVERAGE_FILE` per shard).
- The static steps (ruff, mypy, import-linter, money floats, gitleaks install, SBOM, OpenAPI and
  migration guards, route authorization, TEN-010 isolation suite) run **once**, in shard 1 or in the
  final job, not four times.
- A final job **named exactly `backend`** (`needs: backend-shard`, `if: always()`) downloads the
  four coverage files, runs `coverage combine` and `coverage report --fail-under=80` (the existing
  `fail_under`), and fails if any shard failed. The name matters: branch protection's required
  check is `backend`, and a matrix job alone reports `backend-shard (1)` etc.

### 3. Frontend E2E in 3 shards

- Lint, typecheck, the generated-client check, the colour guard, vitest and the SBOM stay in one job.
- E2E runs as a matrix `frontend-e2e` with `shard: [1, 2, 3]`: `test:e2e -- --shard=${{ matrix.shard }}/3`.
- A final job **named exactly `frontend`** needs both and fails if any failed (required check).

### 4. Local Playwright

- Do not change `playwright.config.ts` (workers, retries, ports). Local E2E is out of scope beyond
  what the template databases give the API under test.

## Acceptance

- [ ] **Shards cover every test file exactly once:** a test (`tests/gates/test_shards.py`) asserts
      the union of `test_shard.py N 4` for N=1..4 equals the sorted file list and the shards are disjoint.
      Plant: drop one file from the selection → the test fails.
- [ ] **A failing test in any shard turns `backend` red:** demonstrated on this story's branch CI with a
      planted `assert False` test file (in the PR body: the red run's link), then removed.
- [ ] **A failing E2E in any shard turns `frontend` red:** same, with a planted failing spec.
- [ ] Coverage still enforces 80 %: the combined report runs in `backend` with `--fail-under=80`.
- [ ] Template: a test asserts a cloned database has every migration applied (the migration table's
      head equals the newest revision) and that changing the migrations hash yields a different
      template name. Plant: clone from an empty database → the head assertion fails.
- [ ] Local: `apps/api` full `pytest -q` wall time before and after, on the same machine, in the PR
      body (expect a large drop). CI: the `backend` and `frontend` wall times of the story's own run.
- [ ] Branch protection's required checks (`detect`, `governance`, `security`, `backend`, `frontend`)
      all still report on the PR to `main`.
- [ ] `flo check` green.

## Plants

1. Drop a file from the shard selection: `test_shards.py` fails.
2. Clone from an unmigrated template: the template head test fails.
3. A planted failing test in shard 3 and a planted failing spec in E2E shard 2: `backend` and
   `frontend` are red on GitHub (then remove both).
