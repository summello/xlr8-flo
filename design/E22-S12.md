# E22-S12 — Balanced E2E shards on a production build; backend static job; combined checks need detect

**Epic** E22 · **M3** · **chore/M** · tags: none

> Operator decision, 22 Oct 2026, from Opus's E22-S11 review (`reviews/E22-S11.opus.json`, three minor
> findings). Evidence: E22-S11's own CI run had E2E shard 1 at 12 min and shards 2 and 3 at ~30 s,
> because Playwright shards by file when `fullyParallel` is off; frontend wall time barely moved
> (13 → 12 min). The same overloaded shard then flaked the milestone: `requisitions.spec.ts:402`
> (keyboard focus, `outline` "none") failed both tries on 1ace86c, a roadmap-only commit, and passed
> on rerun. `playwright.config.ts` already names the cause and the cure in a `ponytail:` comment: CI
> serves the Vite **dev** server, which compiles modules on first request, so focus assertions miss
> their window under load; "serve a production build (vite preview) in CI and drop the retry".
> Backend shard 1 is the long pole (13.5 min) because it also runs every static step.
> **No new dependency** (AGENTS.md §0.6).

## Requirement (inlined)

- **SEC-012** — Dependency scanning, secret scanning, static analysis, dynamic testing, and an SBOM must be part of release controls.

## Design

### 1. E2E on a production build in CI (`apps/web/playwright.config.ts`)

- On CI (`process.env.CI`), `webServer.command` builds once and serves the build:
  `npm run build && npm run preview -- --host 127.0.0.1 --port ${port} --strictPort`
  (use the project's existing `build`/`preview` scripts; add a `preview` script only if missing,
  `vite preview`). Locally keep the dev server and `reuseExistingServer` exactly as today.
- Raise `webServer.timeout` only as far as the build needs on CI (measure; state the number).
- **Keep `retries: 1` on CI in this story.** Dropping it is a follow-up after three consecutive green
  milestone runs with zero flaky tests reported (update the `ponytail:` comment to say so).
- Anything the dev server provided that the built app relies on (an env var, a proxy for `/api`) must
  work under `preview` too; the E2E suite stubs the API with `page.route`, so check, do not assume.

### 2. Balanced shards (`fullyParallel: true`)

- Set `fullyParallel: true` so `--shard` splits by test, not by file.
- A spec whose tests depend on order or shared state inside the file gets
  `test.describe.configure({ mode: "serial" })` at its top, with a one-line reason. Find them by
  running the suite fully parallel locally (several times); do not mark files serial pre-emptively.
- The `perf` project (frame budget, runs after `main`) stays as is.
- Target: the three E2E shards finish within 3 minutes of each other on CI; report the real numbers.

### 3. Backend static checks in their own job (`.github/workflows/ci.yml`)

- Move ruff, mypy, import-linter, money-float check, gitleaks install (if only the gate self-tests need
  it, keep it where those tests run), the TEN-010 isolation suite, tenancy guards, route
  authorization check and the Python SBOM out of `backend-shard (1)` into a job `backend-static`
  (same Python setup, its own Postgres service if a step needs one).
- `test_exactly_once_property.py` stays pinned to shard 1 (the shards are now equal without the
  static steps); if shard 1 is still >3 min longer than the others, move the pin to the lightest shard.
- The combined `backend` job needs `backend-static` as well and fails if it failed.

### 4. Combined jobs require detect

- `backend` and `frontend` also fail when `needs.detect.result != 'success'` (today a failed `detect`
  lets both pass without running anything). Keep the existing skip when `detect` succeeded but said
  the area is untouched.
