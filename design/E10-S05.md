# E10-S05 — Execution engine: instances, tasks, any-one/all/quorum groups, membership rule

**Epic** E10 · **M2** · **engine/L** · after **E10-S04** · tags: `concurrency`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (H, K especially) and `docs/author-traps.md`. Decisions: D-M2-2, D-M2-9, D-M2-11; canvas `DECISIONS.md` 82.

## Requirements

- **APR-009** — Approval groups must support **any one**, **all**, and configured quorum behavior.
- **APR-018** — Group membership must be snapshotted when an approval task is created, or a documented dynamic-membership rule must apply consistently. **D-M2-2 chose live membership; the documented rule is D-M2-9 / convention K, and this story implements it.**
- **WF-002** — A status transition must validate actor, current state, required fields, approvals, and financial side effects.

**Frozen here for every adapter** (E09-S05/S06 and E10-S13 code against these; add them to `approvals/schemas.py`):

```python
class Outcome(StrEnum): APPROVED = "approved"; REJECTED = "rejected"; RETURNED = "returned"; WITHDRAWN = "withdrawn"

@dataclass(frozen=True)
class OutcomeContext:
    actor_id: UUID                       # the user whose decision ended the instance (the requester, for WITHDRAWN)
    decision_id: UUID | None             # the approval_decision row (E10-S06); None for auto-approval at start
    assign_project_id: UUID | None       # REQ-004: the final approver's project choice; only accepted when the
                                         # adapter sets accepts_project_assignment (requisitions only), else 422
    permitted: Callable[[str, AuthorizationTarget], bool]  # evaluated for actor_id with the production resolver
                                         # bound to this transaction's scope (the E08-S03 RowContext.can pattern)
    reject_mode: Literal["return_to_draft", "permanent"] | None  # set only with REJECTED (D-M2-1): the
                                         # approver's choice; RETURNED is the separate "return for changes" action

class DocumentAdapter(Protocol):        # full protocol after this story
    document_type: str
    approve_permission: str              # E10-S04
    accepts_project_assignment: bool
    def fields(self) -> Mapping[str, FieldType]: ...                                    # E10-S02
    def snapshot(self, conn, scope, document_id) -> DocumentSnapshot: ...
    read_permission: str                 # convention P; e.g. "requisition.view" (replaces a can_read() callable)
    def summaries(self, conn, scope, document_ids: Sequence[UUID]) -> Mapping[UUID, DocumentSummary]: ...
        # one query for many documents (E10-S10's inbox list); DocumentSummary =
        # {number: str, title: str, amount: Money | None, requester_id: UUID, href: str}
    def on_outcome(self, conn, scope, document_id, outcome: Outcome, context: OutcomeContext) -> None: ...
```

An auto-approval at `start` (rule 2.4) passes `actor_id = requester`, `decision_id = None`, `assign_project_id = None`, and `permitted` evaluated for the requester.

**Frozen response shapes** (`approvals/schemas.py`; E09-S05, E09-S11 and E10-S09/S10/S12 code against these, all people as emails per D-M2-16):

```python
class RouteStepState(StrEnum): UPCOMING="upcoming"; OPEN="open"; COMPLETED="completed"; CARRIED="carried"

class ExcludedApprover(BaseModel): email: str; reason: str     # E10-S04 reason codes: separation_of_duty, not_eligible_in_scope, ...

class RouteStep(BaseModel):
    node_id: str
    label: str                       # the node's name, as the author typed it
    mode: Literal["any", "all", "quorum"]; quorum: int | None
    rule: str                        # words: "role finance_approver", "listed by name", ...
    approver_emails: list[str]       # CURRENT members, sorted (live membership, D-M2-2)
    excluded: list[ExcludedApprover]
    state: RouteStepState            # always UPCOMING/OPEN in a preview; COMPLETED/CARRIED/OPEN on an instance
    due_at: datetime | None

class RouteProblem(BaseModel):
    code: Literal["no_workflow", "no_eligible_approver", "route_blocked"]
    step_label: str | None           # None for no_workflow
    message: str                     # the WF-006 sentence, ready to show

class RoutePreview(BaseModel):
    workflow_version_id: UUID | None
    workflow_version: int | None
    steps: list[RouteStep]           # in route order, only steps reached so far (a condition's untaken branch is absent)
    problems: list[RouteProblem]     # empty = routable; a problem never raises from preview_route

class TaskRead(BaseModel):
    id: UUID; node_id: str; label: str
    mode: Literal["any", "all", "quorum"]; quorum: int | None
    status: Literal["open", "completed", "cancelled"]; outcome: str | None
    approver_emails: list[str]; due_at: datetime | None; completed_at: datetime | None

class InstanceRead(BaseModel):
    id: UUID; document_type: str; document_id: UUID; workflow_version: int; document_version: int
    status: Literal["running", "approved", "rejected", "returned", "withdrawn", "superseded"]
    requester_email: str; current_node_id: str | None
    route: list[RouteStep]; tasks: list[TaskRead]; started_at: datetime; finished_at: datetime | None
```

`preview_route` **returns problems instead of raising** (E09-S05 turns them into submission problems); `start` raises the same three conditions as `CONFLICT` (rule 2). The acceptance criteria assert each field above.

`GET /api/v1/approvals/instances/{id}`, guarded by `require_resolved` (convention P): load the instance, then its adapter's `read_permission` at the document snapshot's `target` → 200 `InstanceRead` = `{id, document_type, document_id, workflow_version_id, document_version, status, current_node_id, route: [RouteStep], tasks: [TaskRead]}`. Decisions are E10-S06; this story has no decision route.

## Behaviour

1. **Tables** (one migration):
   - `approval_instance(id uuid PK, org_id, document_type text NOT NULL, document_id uuid NOT NULL, workflow_version_id uuid NOT NULL REFERENCES workflow_version, document_version int NOT NULL, material_digest text NOT NULL, requester_id uuid NOT NULL, status text NOT NULL CHECK (status IN ('running','approved','rejected','returned','withdrawn','superseded')), current_node_id text, route jsonb NOT NULL DEFAULT '[]', started_at, finished_at)`; `UNIQUE (org_id, document_type, document_id) WHERE status = 'running'` (one live instance per document).
   - `approval_task(id uuid PK, org_id, instance_id uuid NOT NULL REFERENCES approval_instance, node_id text NOT NULL, name text NOT NULL, approver_rule jsonb NOT NULL, mode jsonb NOT NULL, allow_repeat boolean NOT NULL, status text NOT NULL CHECK (status IN ('open','completed','cancelled')), outcome text, created_at, due_at timestamptz, completed_at)`; `UNIQUE (instance_id, node_id)` (a node is visited at most once: the graph is acyclic, E10-S03).
   - RLS on both. `approval_instance.workflow_version_id` is the version pin (APR-011, ACC-007): it is set once at `start` and never updated (a trigger refuses a change to `workflow_version_id`, `document_version`, `requester_id` or `document_type/id`).
2. **`start`** (called by a document's submit transition, inside that transaction):
   1. `snapshot = adapter.snapshot(...)` (convention H); `version = resolve_version(document_type, snapshot bu)` (E10-S01). With no published version, raise `ProblemError(CONFLICT, checks.problem = "no_workflow")` and a WF-006 detail ("No approval workflow is published for requisitions in this business unit. Ask a workflow administrator.").
   2. Walk the graph from `start` (route rule): from a `condition` node take the **first** outgoing edge, in stored order, whose `when` evaluates true (E10-S02), else the `default` edge. Each evaluation and its trace is appended to `route`. A `ConditionError` (for example `currency_mismatch`) stops the start with `CONFLICT`, `checks.problem = "route_blocked"`, naming the field.
   3. At the first `approval` node, create its task with `due_at = now + due_days` when set, and compute `eligible_approvers` (E10-S04). If **no current member** exists, the start fails with `CONFLICT`, `checks.problem = "no_eligible_approver"`, naming the step, so a document never waits on nobody.
   4. Reaching `end` without any approval node means the instance is immediately `approved`, and the adapter's `on_outcome(approved)` runs in the same transaction.
   5. A second `start` while one is `running` is a 409 `CONFLICT`, `checks.problem = "approval_in_progress"`, enforced by the partial unique index, not only in code.
3. **Completion rule (convention K, D-M2-9, live membership).** Implemented as one function, `step_complete(task, decisions, current_members) -> bool | "rejected"`, used by E10-S06:
   - `any`: one `approve` by a user who is a current member.
   - `all`: every *current* member has an `approve` on this task; removed members drop out, members added since must also approve.
   - `quorum(n)`: at least `n` approvals by current members; an approval by someone no longer a member does not count.
   - A `reject` or `return` by any current member ends the step (and the instance) with that outcome, whatever the mode.
   - **One decision per person per document** (canvas 82): a user who decided on an earlier step of this instance is not a current member of a later step unless that step has `allow_repeat: true`. Encode this in membership, so it applies to every mode.
4. **Advancing** (called by E10-S06 after a decision completes a step): mark the task `completed` and continue the route walk from that node (rule 2.2) to the next approval node (create its task) or to `end` (instance `approved`, `finished_at`, then `adapter.on_outcome(approved, context)` in the **same transaction**, convention H).
5. **Concurrency** (WF-002): every advance or decision locks the `approval_instance` row `FOR UPDATE` first, then re-reads the task. Two decisions racing on an `any` step complete it once: the second sees the task `completed` and gets 409 `CONFLICT`, `checks.problem = "task_closed"`.
5a. **Resume after a non-material return** (operator-drawn `approval-inbox.md` §4, canvas 57: a non-material resubmit goes back to the **same step**, a material one restarts from step 1). `start(..., resume_from: UUID | None = None)`. When given:
   - `resume_from` must name this document's **latest** instance (by `started_at`, then `id`), with status `returned`, else 409 `CONFLICT`, `checks.problem = "cannot_resume"`.
   - Its `material_digest` must equal the current snapshot's, else 409 `cannot_resume` with detail "This change is material; the request restarts from the first step." The approvals module enforces this itself, not only the caller.
   - The new instance pins the **same** `workflow_version_id` as the returned one, even if that version has since been superseded: the resumed route is a continuation, ACC-007.
   - It copies the returned instance's route entries for completed steps, marked `"carried": true` with the source instance id. They are not new decisions; their `approval_decision` rows stay on the old instance.
   - It opens a fresh task at the node whose task returned the document. Membership there is live, as always.
   - Without `resume_from`, `start` resolves the current published version and begins at `start` (step 1).

6. **`preview_route`** runs rules 2.1 to 2.3 without writing and returns the route plus, for each approval step reached, its current eligible members and exclusions. E09-S05 uses it for submission validation (REQ-011 "approval routing"); E10-S09 uses it for explanations.
7. **Route authorization (convention P), added to `kernel/authz.py` by this story:** factor `require`'s outcome logic into one `_decide(request, permission, target)`; add `require_resolved(resolve)` and `require_member()`, each setting the gate's marker. Tests in `tests/authz/test_enforcement.py`: both guards satisfy `route_authorization_failures`; `require_resolved` gives exactly `require`'s 404/403/allowed outcomes over the convention-A table; a route with neither guard still fails the gate (planted). This story's instance route uses `require_resolved` with the adapter's `read_permission`.
8. **Stale canvas copy:** `approval-inbox.md` §2.4 and `approval-workflow-builder.md` §3 describe snapshot membership. Record in `notes.followup` that the boards must be redrawn for live membership (D-M2-2). Do not implement a snapshot.

## Acceptance criteria

- [ ] With no published workflow, `start` fails `no_workflow` and writes nothing.
- [ ] A condition routes a 300,000 request to the "Finance" step and a 100,000 one to `end` (auto-approved, `on_outcome(approved)` called exactly once, same transaction).
- [ ] `any`: the first approval completes the step; a concurrent second approval gets `task_closed`; exactly one advance happens (a real two-connection test).
- [ ] `all` over {A, B}: A approves, B is removed from the role, the step completes without B; then the same with C added before completion: the step waits for C.
- [ ] `quorum(2)` over {A, B, C}: A approves, A leaves the role, B approves, so one counts; C approves and the step completes.
- [ ] A user who approved step 1 is not a member of step 2 unless step 2 has `allow_repeat`.
- [ ] A step whose rule resolves to nobody fails the start (or the advance) with `no_eligible_approver`, naming the step.
- [ ] Publishing v2 of the workflow while an instance runs on v1: the instance keeps v1's route to the end (ACC-007).
- [ ] The partial unique index refuses a second running instance even when two `start` calls race.
- [ ] `preview_route` returns `RoutePreview` exactly as frozen above: a published two-step workflow gives two `RouteStep`s with sorted `approver_emails`; no published workflow gives `problems == [no_workflow]` and no steps; a step with nobody eligible gives `no_eligible_approver` naming its `step_label`.
- [ ] Updating `workflow_version_id` on an instance fails in the database.
- [ ] `resume_from` a returned instance with an unchanged material digest: the new instance has the same version (even after v2 is published), carries step 1 as `carried`, and opens step 2's task; with a changed digest, 409 `cannot_resume`; resuming from a non-latest or non-returned instance, 409 `cannot_resume`.

## Plants

0. Make `require_resolved` skip `_decide` and return allowed: the convention-A outcome table test fails; drop its marker: the route-gate test fails.

1. Count approvals from removed members in `quorum`: the quorum test fails.
2. Evaluate membership at task creation and store it (snapshot): the `all`/add-member test fails.
3. Remove `FOR UPDATE` on the instance: the concurrent `any` test fails (two advances).
4. Drop the partial unique index: the concurrent `start` test fails.
5. Ignore `allow_repeat`: the repeat-approver test fails.
