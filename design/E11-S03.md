# E11-S03 — Vendor documents: type, issue and expiry, verification, reviewer, expiry notifications

**Epic** E11 · **M3** · **crud/M** · after **E11-S01**, **E09-S10** · tags: `security`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** canvas DECISIONS 122 and 123 (6h-2, 6h-3), D-M2-8 (attachments never shared
> externally), `design-system/pages/vendors.md` §2 "Documents expire on a calendar" and §3.6
> "Document sheet". Back end only.

## Requirements (inlined)

- **VEN-003** — Vendor profiles must store required tax, incorporation, insurance, certification, banking-verification, and other configured documents as protected attachments.
- **VEN-011** — Required documents must support issue date, expiry date, verification status, reviewer, and expiry notifications.
- **OBS-004** — Business monitoring must expose stuck approvals, unreconciled balances, expired vendor documents, and failed transmissions.
- **COL-004 / COL-005** — attachments keep filename, storage key, type, size, checksum, uploader, time, scan status and linked record; uploads are allow-listed, validated, size-limited, access-controlled and scanned. *(Already delivered by E09-S10; reuse it, do not re-implement.)*

## Design

**The file is an E09-S10 attachment.** Register the `vendor` document type with collaboration's
`register_document_access` (read = `vendor.view`, write = `vendor.edit`) and upload through the
existing attachment routes, so the allow-list, scan, versions and storage are not re-implemented.
This story adds the vendor-specific metadata around it.

**Document types are master data.** Add a kind `vendor_document_type` to
`modules/org/master_kinds.py` `RULES` with the attribute `required` (bool, mandatory) and an
optional `category` attribute that holds a `vendor_category` master code. The per-category rule is
an open question (pages/vendors.md §7.1, parked in E11-S08): store it, but do not apply it yet.
`required` applies to every vendor in M3.

Table `vendor_document` (RLS): `id`, `org_id`, `vendor_id`, `type_code text NOT NULL` (a
`vendor_document_type` code), `attachment_id uuid NOT NULL` (FK attachment, `document_type =
'vendor'`), `issue_date date NULL`, `expiry_date date NULL` (≥ issue_date when both are set),
`verification text NOT NULL` CHECK in `unverified`, `verified` and `rejected` (default
`unverified`), `reviewed_by uuid NULL`, `reviewed_at`, `rejection_reason text NULL` (required when
rejected; the uploader sees it), `created_at`. A **replace** uploads a new attachment *version* and
resets verification to `unverified`; earlier versions stay readable through E09-S10's version list.
Never delete a row; replacing is the only change to the file.

**Document state for a vendor**, as one service function
`service.document_state(vendor_id, on: date) -> list[DocState]` that E11-S11's eligibility rule
calls. There is one row per required type, plus every supplied optional document, each row being:
- `missing`: a required type with no document
- `rejected`
- `expired`: `expiry_date < on`
- `expiring`: `expiry_date` within 30 days of `on` (inclusive). Carry `days_left`.
- `unverified`
- `ok`

Precedence is the order above. **This function never changes the vendor's status** (decision 123).

**Expiry notifications (VEN-011, OBS-004):** a job `vendor-document-expiry`, registered in
`api/internal.py` beside `budget-reconcile`, runs once per day per org. For each document that
**became** `expiring` (30 days) or `expired` since the last run, it enqueues one notification
through the **outbox** to the vendor-manager role holders for the vendor's units (a global vendor
→ org-scope holders). Batch them into one digest email per recipient per day (the Resend 100/day
ceiling, project memory). Idempotent per (document, threshold): store `notified_expiring_at` and
`notified_expired_at` on the row. Expose a count of expired required documents for the business
monitor the way `budget-reconcile` exposes drift.

## API

| Method and path | Permission | Behaviour |
|---|---|---|
| `GET /vendors/{id}/documents` | `vendor.view` | `document_state` rows plus the metadata and the attachment's current version and scan state. |
| `POST /vendors/{id}/documents` (Idempotency-Key) | `vendor.edit` | Body `{type_code, attachment_id, issue_date?, expiry_date?}`. The attachment must belong to this vendor (`document_type='vendor'`, same id), or 422. A type that already has a document → 409 `use_replace`. |
| `POST /vendors/{id}/documents/{did}/replace` (Idempotency-Key) | `vendor.edit` | Body `{attachment_version_id, issue_date?, expiry_date?}` → resets verification. |
| `POST /vendors/{id}/documents/{did}/verify` and `/reject` (Idempotency-Key) | `vendor.approve` | Reject needs `reason` (1..500). Records the reviewer and the time. A reviewer cannot verify a file they uploaded: 409 `separation_of_duty`, using the org setting `approval.separation_of_duty`. |

Audited: `vendor.document.add`, `.replace`, `.verify` and `.reject`. **No document content in any
log.** File names are logged only through E09-S10's existing path.

## Acceptance

- [ ] Migration up, down and data preservation.
- [ ] `document_state` covers all six states and their precedence: a rejected document that is also expired reads `rejected`; a missing required type is a row; a missing optional type is not.
- [ ] Expiring boundary: 30 days → `expiring`; 31 → `ok`; expiry today → `expiring` with `days_left = 0`; yesterday → `expired`.
- [ ] Job: a document crossing 30 days notifies once; a second run the same day sends nothing; crossing into expired notifies once more. The notification goes through the outbox (no direct send), in one digest per recipient.
- [ ] Separation of duty: an uploader verifying their own document → 409 when the setting is on.
- [ ] A vendor's status is unchanged after its required document expires (assert it).
- [ ] TEN-010 on every route; a foreign attachment id → 422/404, never linked. Authorization per role.
- [ ] `flo check` green.

## Plants

1. Make `expired` lower precedence than `unverified`: the precedence test fails.
2. Drop the idempotency stamp: the second-run test sends twice and fails.
3. Send the email directly instead of through the outbox: the outbox assertion fails.
