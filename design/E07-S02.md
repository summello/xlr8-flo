# E07-S02 — project_balance rollup maintained in-transaction with the ledger write

**Epic** E07 · **M1** · **ledger/L** · after **E07-S01** · tags: `money`, `concurrency`

> **Conventions:** read `docs/m1-conventions.md` (authorization outcomes, scope targets, wire formats). It applies unless this packet says otherwise.

## Requirements

- **FIN-005** — Project balances must be derived from and reconcilable to ledger entries.
- **FIN-006** — Budget validation and the corresponding ledger write must occur atomically to prevent concurrent overspend.
- **BUD-011** — A user must be able to reconcile a displayed balance to its component entries.
- **D-11** — Balances | Rollup table maintained **in the same transaction** as the ledger write, plus a nightly recompute that **reports** drift | Materialized views refreshed on change (nemotron) | `REFRESH MATERIALIZED VIEW` is not transactional — a dashboard could show a balance that no ledger state ever produced, breaking FIN-005 and BUD-013. | —

## Contract

Migration (reversible): the next revision after the current head at story start (revision id `20260826_<next 4-digit number>`, `down_revision` = the head `python -m flo.kernel.migrate --check` validates today); stories merge one at a time, so there is no gap or fork: `project_balance(project_id uuid pk, org_id, bu_id, currency char(3) not null, allocated numeric(18,4) not null default 0, reserved ... 0, committed ... 0, actual ... 0, available numeric(18,4) generated always as (allocated - reserved - committed - actual) stored, version bigint not null default 0, updated_at)`; RLS forced; `CHECK (reserved >= 0 AND committed >= 0 AND actual >= 0)`. **No `CHECK (available >= 0)`**: negative availability is a policy (D-M1-3), enforced in the service, because an authorized negative-budget org must be able to go below zero.

The single write path — `modules/budget/ledger.py`, exported through `modules/budget/service.py` as `post_entry(...)`:

```python
post_entry(conn, scope, *, project_id, entry_type, amount: Decimal, currency, source_type, source_id,
           effective_date, actor_id, department_code, ledger_account_code, reason=None,
           bucket=None, transfer_group_id=None, reverses_entry_id=None,
           idempotency_key, allow_negative: bool|None=None) -> LedgerEntry
```

## Behaviour (one transaction, in this order — AGENTS.md 3.1, FIN-006)

1. Resolve `bucket` from `BUCKET_FOR_TYPE` (callers pass it only for `release`).
2. `SELECT … FROM project_balance WHERE project_id = %s FOR UPDATE` **before any validation** (lock first). A missing balance row is created inside the same transaction with `INSERT … ON CONFLICT DO NOTHING` then re-selected FOR UPDATE.
3. Currency: must equal the balance row's `currency`, else `CurrencyMismatch` (FIN-003). All amounts are `Decimal`; reject `float`; quantize through `kernel/money.py` to the currency exponent, never `round()`.
4. `fiscal.service.assert_postable(org, effective_date)` (E05-S04) → `PeriodClosed`.
5. Idempotency: `INSERT … ON CONFLICT (org_id, idempotency_key) DO NOTHING RETURNING`; on conflict return the **original** entry unchanged and make no balance change (FIN-012). A reused key with different content is a 422 `idempotency_conflict` (compare entry_type, amount, project, source).
6. Availability rule for entries that *consume* funds (reservation, commitment, actual, and negative adjustment/transfer-out): `available - amount < 0` is rejected as `InsufficientBudget(available, requested)` **unless** `allow_negative` resolves true (org setting `allow_negative_budget`, via `org.service.effective_setting`). **D-M1-3: default false.**
7. Insert the ledger row, then `UPDATE project_balance SET <bucket> = <bucket> + amount, version = version + 1`. Both in the same transaction as the caller's business change.
8. Audit row for every post (`ledger.post`), with entry id, type, bucket, amount, source.

Error mapping to RFC 9457 (add problem types to `kernel/errors` only if absent): `InsufficientBudget` 409, `PeriodClosed` 409, `CurrencyMismatch` 422, `idempotency_conflict` 422.

Read helper `get_balance(conn, scope, project_id) -> BalanceRead` (no lock; used by E07-S06).

No router in this story — post_entry is a module-internal primitive consumed by E07-S03 through S08 and M2.

- [ ] Concurrent identical `idempotency_key` posts from two sessions create exactly one ledger row and one balance change
- [ ] After a random mixed sequence of 200 valid posts (seeded RNG in the test), `project_balance` equals `SUM(amount) GROUP BY bucket` for that project (FIN-005)
- [ ] The balance row is locked before the availability read (assert via a test that holds the lock in session A and shows session B blocks, using `pg_locks`/statement timeout)
- [ ] A mixed-currency post is rejected; a `float` amount is rejected; an amount with more decimals than the currency exponent is rejected or quantized per `kernel/money.py` (test pins which)
- [ ] With `allow_negative_budget=true` a reservation may drive `available` below zero; with it false it may not

- [ ] A failure after the ledger insert but before the balance update (monkeypatch) rolls both back
- [ ] `float` lint passes on `modules/budget/`; no `round(`/`//`/`%` on money in the module (grep test)

## Amendments (preflight audit — authoritative, override anything above)

- **Availability rule (replaces step 6's formula):** compute `projected = available_after_this_entry`: for bucket `allocated` it is `available + amount`; for `reserved`, `committed` or `actual` it is `available - amount`. An entry that **lowers** availability (`projected < available`) is rejected with `InsufficientBudget` when `projected < 0` and negative budget is not allowed. This covers consuming entries, negative adjustments, transfer-out legs and **reversals** (a reversal's amount is the negation of the original, so reversing a release or a positive allocation is checked the same way).
- **Reversal bucket** is never passed by callers: `post_entry` loads the reversed entry under the lock, takes its bucket, currency, project and negated amount from it, and validates the linkage.
- **Idempotency order and payload:** right after taking the balance lock (and before period, currency or availability validation), look up `(org_id, idempotency_key)`. If found, compare the **complete immutable payload** (entry_type, bucket, amount, currency, project, source_type, source_id, effective_date, transfer_group_id, reverses id (releases id joins in E07-S04), reason, department and account codes) and return the original, or raise `IDEMPOTENCY_KEY_REUSED` on a mismatch. A replay therefore still succeeds after the period has since closed.
- Errors follow conventions D (existing `ErrorCode` + `checks["problem"]`); ignore "add problem types to `kernel/errors`".
- **Project service edits authorized here:** on project creation insert the zero `project_balance` row in the same transaction; this story's migration backfills a balance row for every existing project. (`bu_id`, `currency`, `department_code` and `ledger_account_code` are already immutable from E06-S01, so no posting lock on them is needed.)
- `post_entry` takes two internal-only keyword parameters used by later stories: `releases_entry_id: int | None = None` and `skip_period_check: bool = False` (only the release primitive may pass True). Add the parameters now. The `releases_entry_id` column does **not** exist until E07-S04, so in this story a non-null `releases_entry_id` raises `NotImplementedError('release linkage arrives in E07-S04')` before any I/O, and the idempotency payload comparison covers `reverses_entry_id` only (E07-S04 extends the comparison with `releases_entry_id` when it adds the column). `skip_period_check` is accepted and ignored when False.
