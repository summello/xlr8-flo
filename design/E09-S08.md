## Requirements

- **REQ-012** — Changes after submission must use a controlled return, amendment, or resubmission process and preserve prior values.
- **APR-015** — A document changed in a material way after approval must be resubmitted according to policy.
- **DATA-002** — Concurrent edits must use optimistic concurrency or equivalent version checks; stale writes must not silently overwrite newer data.
- **D-M2-13** — Material fields: amount (estimate), project, ledger account, catalogue item, line count. A change to any of them requires resubmission. Text, dates and attachments are not material. Not configurable.

## Design decisions (this packet)

- **Every submission and every applied amendment is an immutable revision.** `requisition_revision` holds the full header and lines as submitted. "Version 1, Version 2" on the screens is `revision_no`, and version 1 is never overwritten (REQ-012).
- **Before approval: return, edit, resubmit.** A requisition returned for changes (E09-S05: `RETURNED` → `draft`, reservation kept) is edited with the normal draft routes. Resubmit is E09-S05's submit, extended here:
  - **Nothing changed** since the latest revision (every header field and every line identical) → 409 `CONFLICT`, `checks.problem = "nothing_changed"`, detail "Not resubmitted. Nothing has changed."
  - **Not material** (the current material digest equals the returned instance's): `approvals.service.start(..., resume_from=<returned instance id>)`, which continues at the step that returned it (canvas 57, "the approver sees the diff"). On 409 `cannot_resume`, start fresh. Approvals enforces its own guards (E10-S05).
  - **Material:** `start(...)` without `resume_from`, so routing restarts from step 1. The reservation follows E09-S05 step 2.3: release the round's remaining and reserve the new total under the same lock, with a funds check of `need = new estimate − remaining`.
  - A requisition rejected to draft holds no reservation and resubmits like a first submission. Its revisions still record history.
- **After approval: an amendment, with the approved version in force until the amendment is approved** (E10-S07 policy item 4). Status stays `sourcing_in_progress` throughout.
  - **One open amendment at a time** (`requisition.pending_amendment_id`). An amendment may not change `project_id`: 422 "To move it to another project, withdraw it and raise a new requisition."
  - **Not material** (the proposed digest equals `approval_state(...).approved_material_digest`): applied immediately, with no approval instance.
  - **Material:** a new approval instance with `document_type = "requisition"` (the previous instance is `approved`, not running). While it runs, the adapter's `snapshot()` presents the amendment's values and version (E09-S05 adapter branch), and `assert_current_approval` fails `stale_version`, so nothing downstream can be created mid-amendment (WF-001). That is intended. On approval, the amendment instance becomes the latest and carries the amended digest.
  - **The reservation moves only when the amendment is approved:** **any estimate change, up or down, releases the round's remaining (reason `resubmit`) and reserves the new total (round + 1), under the lock** (E09-S07 wins: this story never calls `reduce_to`; every estimate change is material, D-M2-13). A funds shortfall at approval → 409 `INSUFFICIENT_BUDGET`, and the decision fails, so the approver sees why. At amendment submit, an increase is pre-checked (E09-S04 with `need = increase`, `lock=True`) so the requester learns early.
  - **Stopping a requisition with an amendment running** (E09-S07's post-approval withdraw, cancel and expiry): E09-S07 owns the rule and this story mirrors it: it does **not** read `pending_amendment_id` there (this story creates it and E09-S07 merges first). It asks `approvals.service.active_instance(conn, scope, "requisition", id)`. A running instance on an approved requisition is exactly a pending amendment: `approvals.service.withdraw` it first (its `on_outcome(WITHDRAWN)` takes the amendment branch, below), then proceed with the stop. The non-material test keeps comparing with `approval_state(...).approved_material_digest`, which E10-S07 now reads from the **in-force** instance (a later rejected, returned or withdrawn amendment is ignored), so the approved digest is still available after a failed amendment.
- **Who:** the requester or a holder of `requisition.edit` creates and edits amendments, and `requisition.submit` submits them, the same permissions as the draft flow. Withdrawing a running amendment is the requester's (`requisition.withdraw`).

## Contract

| Route | Permission (record) | Success | Errors |
|---|---|---|---|
| `GET /api/v1/requisitions/{id}/revisions` | `requisition.view` | 200 `[RevisionSummary]` newest first: `{revision_no, kind ("submission"\|"amendment"), status, created_by, created_at, note}` | 404 |
| `GET /api/v1/requisitions/{id}/changes?against=<revision_no>` | `requisition.view` | 200 `ChangeSet` (below); the default compares the working copy (the draft, or the open amendment) with the latest submission or applied revision | 404 |
| `POST /api/v1/requisitions/{id}/amendments` (Idempotency-Key, `If-Match` requisition version) | `requisition.edit` | 201 `AmendmentRead` (a copy of the current values), `ETag` = amendment version | 409 `invalid_transition` (not `sourcing_in_progress`); 409 `amendment_open` |
| `PUT /api/v1/requisitions/{id}/amendments/{revision_no}` (`If-Match`) | `requisition.edit` | 200 `AmendmentRead` | 409 `stale_version`; 409 `not_editable` (not `draft`); 422 (E09-S01/S02 validators; `project_id` change refused) |
| `POST /api/v1/requisitions/{id}/amendments/{revision_no}/submit` (Idempotency-Key, `If-Match`; body `{note?: str}`, 1..1000 characters, plain text, stored as the amendment revision's `note`) | `requisition.submit` | 200 `RequisitionRead` (applied, or pending approval) | 409 `nothing_changed`; 422 `submission_invalid` (E09-S04 shape) |
| `POST /api/v1/requisitions/{id}/amendments/{revision_no}/withdraw` (Idempotency-Key) | requester + `requisition.withdraw` | 200 | 409 `invalid_transition` |
| `DELETE /api/v1/requisitions/{id}/amendments/{revision_no}` | `requisition.edit` | 204, a draft amendment only | 409 `not_editable` |
| `GET /api/v1/requisitions/{id}/amendments/current` | `requisition.view` | 200 `AmendmentRead` of the open amendment (status `draft` or `pending`) | 404 when none |

- **The adapter's `summaries()` (E09-S05) now fills `note`** from the latest `submission` or pending `amendment` revision's `note` (authorized edit to `requisitions/approval.py`); the approver sees it as "Note from the requester" (E10-S10). `GET …/revisions` already returns it.
- **`RequisitionRead` gains `amendment: {revision_no, status, can_continue: bool} | null`** (filled on `GET /requisitions/{id}`, PATCH and the transitions response, null in lists; `can_continue` is true for a `draft` amendment the caller may edit). Authorized edit to `modules/requisitions/schemas.py`, the same pattern as E09-S05's `reservation` and `approval` blocks. E09-S12 uses it, because `transitions/available` has no amendment entry.
- **`AmendmentRead`**: `{revision_no, status, version, header: {...the E09-S01 editable fields}, lines: [{line_id?, line_type, description, quantity, uom_code, unit_price, category_code, catalogue_item_id}], estimate}`. A `PUT` replaces the whole proposal. A line with `line_id` updates that line, one without adds a line, and an omitted existing line is a removal. Amounts and the estimate are derived (E09-S02's rules).
- **`ChangeSet`**: `{from_revision, to: "draft"|"amendment", nothing_changed, material, routing: "restarts"|"same_step"|"not_applicable", rows: [{field, label, was, now, change: "changed"|"added"|"removed", delta?: {amount, percent, direction: "up"|"down"}}], funding: {reserved_now, reserved_after, outcome: "unchanged"|"released_once"|"reserved_more", project_available_after, currency} | null}`. Labels are words ("Estimate", "Line 3 quantity"). `delta` exists only on money rows; `percent` is to one decimal place, half-up, through `kernel/money.py` rules. `routing` reflects the rule above (`same_step` only for a returned requisition with a non-material change). `material` is computed with the E10-S07 digest function, never a second implementation.

## Behaviour

1. **Migration** (reversible): `requisition_revision(id uuid PK, org_id, requisition_id, revision_no int NOT NULL, kind text CHECK IN ('submission','amendment'), status text CHECK IN ('draft','pending','applied','rejected','returned','withdrawn'), snapshot jsonb NOT NULL, material_digest char(64) NOT NULL, version int NOT NULL DEFAULT 1, created_by uuid NOT NULL, created_at, decided_at, note text)`, `UNIQUE (requisition_id, revision_no)`. A trigger refuses UPDATE unless the old row is `draft`, or the only change is `status` from `pending` to a decided value. It refuses DELETE unless the row is a `draft` amendment. `ALTER TABLE requisition ADD COLUMN pending_amendment_id uuid REFERENCES requisition_revision(id)`. RLS.
2. **Submission revisions (and the note):** this story **owns the revision writer** and replaces E09-S05's `record_submission_revision` hook with it, so the submit body's `note` (E09-S05, 1..1000 characters) is stored in `requisition_revision.note` of the new `submission` revision. E09-S05's submit (authorized edit) inserts a `submission` revision with status `applied` in the submit transaction, after validation and before `start`. Resubmit implements the rules above in the same transaction.
3. **Amendment submit**, one transaction: lock `project_balance` → requisition → the amendment row. Check versions and that the amendment is `draft`. Compute the digest. Apply it, or set `pending`, set `pending_amendment_id`, and call `start`.
4. **Adapter branches** (authorized edit to `requisitions/approval.py`): when `pending_amendment_id` is set, `snapshot()` returns the amendment's values, `version = requisition.version`, and the amendment digest. `on_outcome` on a requisition in `sourcing_in_progress` with a pending amendment: `APPROVED` applies it (writes header and lines from the snapshot, adjusts the reservation, revision `applied`, clears the pointer, requisition `version + 1`). `REJECTED` (either mode) and `RETURNED` mark the revision `rejected` or `returned` and clear the pointer, with no money. `WITHDRAWN` marks it `withdrawn` and clears the pointer. Every branch writes a status event (`from = to = sourcing_in_progress`, `reason = "amendment <outcome>"`) and an audit row.
5. **Applying** (both the immediate and the approved path) writes the header columns and lines in place, then inserts the applied state as a new `amendment` revision with status `applied`. The history therefore holds every value the requisition ever had.

## Acceptance criteria

- [ ] Return → edit justification only → resubmit: the new instance resumes at the returning step (`route` marks earlier steps carried), the reservation is unchanged, and revision 2 exists. Changes shows `material: false, routing: "same_step"`.
- [ ] Return → change a line quantity → resubmit: a fresh instance from step 1, the old round released once, the new total reserved (round + 1), `material: true, routing: "restarts"`. Each material field (estimate, ledger account, catalogue item, line count) is tested separately. A project change before approval is a normal draft edit and restarts.
- [ ] Return → no change → resubmit → 409 `nothing_changed`, nothing written.
- [ ] Revision 1's snapshot is byte-identical after any number of later edits, and an UPDATE of an applied revision fails in the database.
- [ ] Amendment, not material (justification): applied immediately, no instance, `assert_current_approval` still passes.
- [ ] Amendment, material, an increase of 40 with 50 available: pending, a new instance running, `assert_current_approval` raises `stale_version`, the reservation unchanged. Approved: the reservation is now the new total (round + 1), the requisition holds the new values, and `assert_current_approval` passes. The same with only 30 available at approval → the decision fails 409 `INSUFFICIENT_BUDGET` and nothing changes.
- [ ] Amendment, material, a decrease from 100 to 70: on approval the round's 100 is released once (key `req:<id>:release:<round>:resubmit`) and 70 is reserved once (round + 1), so 30 is freed net, each exactly once.
- [ ] Amendment rejected or returned: values and reservation unchanged, the revision marked, a new amendment allowed.
- [ ] Cancel while an amendment is running: the amendment instance is withdrawn, then the requisition is cancelled and released once.
- [ ] Two concurrent amendment PUTs with the same `If-Match`: one wins, the other 409 `stale_version`. Two amendments opened concurrently: one 201, one 409 `amendment_open`.
- [ ] ChangeSet money rows carry `delta` (`Down 3,500.00`, `2.0%`), every row has a word label, and `funding` matches what the submit then does.
- [ ] Foreign tenant → 404 on every route. View-only grant → 403 on writes.
- [ ] Migration up/down/up preserves revisions.

## Plants

1. Pass `resume_from` on a material change: approvals' `cannot_resume` fires and the code must start fresh. Remove that fallback and the material-resubmit test fails.
2. Adjust the reservation at amendment submit instead of at approval: the "unchanged while pending" test fails.
3. Let the revision trigger allow updates to `applied` rows: the immutability test fails.
4. Compute `material` with a local field list that omits catalogue items: the catalogue-item material test fails.

## Pre-flight amendments (11 Oct 2026, Opus; binding, they override anything above)

Each item below was found by reading the code this story touches. A block on any of them is a packet defect, not an author failure.

1. **Lock order** follows E09-S05 amendment 1: amendment submit takes balance → requisition → the amendment row (no instance exists yet); the approval of an amendment arrives as `instance → balance → requisition`; stopping a requisition with an amendment running withdraws the amendment's instance first (E09-S07 amendment 2).
2. **A pre-approval project change is a funding move.** E09-S05 amendment 4 releases on the old project and reserves on the new. `ChangeSet.funding.outcome` therefore gains a fourth value, `moved` ("Released on `<old project>`, reserved on `<new project>`"), with `reserved_now`/`reserved_after` and `project_available_after` computed on the new project. E09-S12 renders the server's word.
3. **`material_digest` must be importable.** E10-S07 defines it in `approvals/material.py` but its re-export list names only `approval_state`, `requires_resubmission`, `supersede` and `assert_current_approval`. This story needs `approvals.service.material_digest(snapshot)` (never a local hash, plant 4). Read the merged E10-S07; if it is not exported, write `notes.blocked` naming it. Do not import `approvals.material`.
4. **Revision money in `snapshot jsonb`** is stored as decimal strings with four places, and compared as `Decimal`, never as JSON numbers.
