## Requirements (inlined)

- **PO-010** — Issued POs must be immutable; changes must create a numbered, approved change order/version.
- **PO-011** — A change order must preserve the prior version, identify changed fields/lines, recalculate budget
  effects, and be reapproved when policy requires.
- **ACC-005** — Changing an issued PO creates a new version/change order and preserves the vendor-sent snapshot.

Router `apps/api/src/flo/api/purchasing.py:262-344`, service `apps/api/src/flo/modules/purchasing/changes.py`.

| Call | Guard | Notes |
|---|---|---|
| `POST /api/v1/purchase-orders/{id}/changes` body `{reason?}` → 201 `PoChangeRead` | `purchase_order.amend` (`AmendContext`, `purchasing.py:79`) | 409 `po_not_issued`; 409 `change_in_progress` when the PO already has a `draft` or `approval_pending` change (`changes.py:434-446`) |
| `GET …/{id}/changes` → `list[PoChangeRead]`, `GET …/{id}/changes/{number}` → `PoChangeRead` + `ETag` | `purchase_order.view` | `number` runs across the whole revision chain; any revision's id finds it (`changes.py:130-132`, `_root` `:630`) |
| `PATCH …/{id}/changes/{number}` body `PoChangePatch` → `PoChangeRead` | amend, `If-Match` | each PATCH bumps `version` (`changes.py:417`); 409 `invalid_transition` when not draft, 409 `stale_version` (`changes.py:488-491`) |
| `POST …/{number}/apply` → `PoChangeRead` | amend, `If-Match` | non-material only; 409 `approval_required` when material (`changes.py:606-607`); 422 `no_changes` on an empty diff (`changes.py:638-639`); 200 sets `status: "approved"` and `result_po_id` (the new revision) |
| `POST …/{number}/submit` → `PoChangeRead` | amend, `If-Match` | material only; 422 `no_changes`, 409 `not_material`, 409 `workflow_not_set_up` (`changes.py:520-531`, `approvals/service.py:235`); 200 → `approval_pending` |

`PoChangeRead` (`purchasing/schemas.py:333-349`; web type `PoChange` already exported from
`components/purchasing/api.ts:12`): `id, po_id` (the revision it changes), `number, version, status`
(`draft | approval_pending | approved | rejected | withdrawn`), `material: bool`, `reason, created_by,
created_at, draft, result_po_id, total` (order total if applied, PO currency), `budget_total_project`, and:
- `diff`: list of `{line_no: int | null, field, label, was: str | null, now: str | null}`, already words and
  formatted strings (`_entry`, `changes.py:95-98`; entries built at `:200-210`, `:328-383`). `field` is one of `quantity, unit_price, tax,
  freight, document_freight, line, terms, needed_by`.
- `budget_effect`: list of `{project_id, department_code, ledger_account_code, currency, delta}`, `delta` a signed
  decimal string, only non-zero groups (`changes.py:386-410`).
- **Materiality is the server's** `material` (`MATERIAL`, `changes.py:62`: quantity, unit price, tax, freight,
  document freight, line count are material; terms and needed-by are not, decision 166). The page never decides it.

`PoChangePatch` (`schemas.py:316-331`): `reason` (≤500), `terms` (≤4000, nullable), `needed_by` (date,
nullable), `document_freight` (document freight mode only, else 422 `freight_mode_mismatch`), `lines:
list[PoChangeLineEdit]`. **`lines` replaces the draft's whole line list** (`changes.py:502-507`), so every
PATCH sends the complete set of edited lines. `PoChangeLineEdit`: `line_no`, `quantity` (decimal string > 0, ≤4
decimals), `unit_price` (down only: 422 `price_increase`, `changes.py:214-219`), `tax`, `freight` (line mode
only, else 422 `freight_mode_mismatch`). A `project_id`, `department_code` or `ledger_account_code` is refused
422 `use_transfer` (`changes.py:477-484`); **the screen offers no control for them**, so it never sends one.
`remove` and `add` exist in the API but are **out of scope** here (page spec §4.7 lists quantities, freight and
needed-by; record "remove and add lines in a change order" in `notes.followup`).

## Screen `/purchase-orders/:id/changes/:n`

**Loading.** `GET …/{id}/changes/{n}` (the change), then `GET /api/v1/purchase-orders/{change.po_id}` (the
revision it changes: lines, currency, freight mode, terms, needed-by, `actions`) and `GET
…/{change.po_id}/budget-summary` (project code and name only). Use `useLoad` (`components/requisitions/useLoad.ts:6`).
Skeleton as `detail.tsx:26`. 404 on the change or the PO → "This change order does not exist or you cannot see
it." with a link back to `/purchase-orders/{id}`. Import the same stylesheets as `detail.tsx:9-13`.

**Header.** `h2.po-number` with `PO number · Change order {n}`; beneath it the status in words
(`label(change.status)`, `requisitions/api.ts:25`), `Changes v{po.revision + 1}` and a link `View v{po.revision + 1}`
to `/purchase-orders/{change.po_id}` (the prior version stays readable, PO-011).

**Editable when** `change.status === "draft"` **and** `po.actions.includes("change_order")`. Otherwise the same page
is read-only (no inputs, no buttons), with one sentence:
- draft without the action: "You can view this change order. Changing it needs purchase order amend access."
- `approval_pending`: "Sent for approval. The issued PO is unchanged until the change is approved."
- `approved`: "Applied as v{n}." with a link to `/purchase-orders/{result_po_id}`.
- `rejected` / `withdrawn`: "This change order was {rejected|withdrawn}. The issued PO is unchanged."

**Layout.** Reuse `po-page`, `po-body`, `po-col` and `req-card` (`styles/purchase-orders.css`); no new CSS is
expected. If any is needed it uses tokens only. Left column: `Changes` (the form). Right column: `What Changes`
(the diff), `Budget Effect`, and the approval line with the action button.

**Form (`Changes` card).** Built from `po.lines` (the revision's frozen values) and the draft:
- `Reason` textarea (≤500, `reason`), help "Shown with the change order in the version list." (XFN-008).
- `Needed by` native date input, clearable; `Terms` textarea (≤4000), each prefilled from `po`.
- In document freight mode (`po.freight_mode === "document"`) a `Document freight` `MoneyInput`
  (`components/form/MoneyInput.tsx`), prefilled with `po.document_freight`.
- A table, one row per line: description and unit; beneath it the project (`project_code project_name` from the
  budget summary, else the text `Project`), department and ledger account codes as read-only text, and once,
  under the table: "Project, department and ledger account cannot change in a change order. Use a budget transfer
  instead." (the words of `use_transfer`). Columns: Quantity (`Input`, decimal string), Unit price (`MoneyInput`,
  help "A price can only go down."), Tax (`MoneyInput`), Freight (`MoneyInput` in line mode; read-only `Money` in
  document mode), and the current Line total read-only (`Money`, `components/ui/Money.tsx`). Inputs are prefilled
  from the draft where it has a value (`change.draft.lines[String(line_no)]`, `terms`, `needed_by`,
  `document_freight`), else from `po`. The table never computes a new price or total: new figures come only from
  `What Changes` and the totals below.

**What Changes card.** From `change.diff`, in order, one list item each, in words:
`{line_no ? "Line " + line_no + " · " : ""}{label}: <del><span class="visually-hidden">was </span>{was}</del> now {now}`;
`was === null` reads "was not set", `now === null` reads "cleared"; values verbatim (server strings, never
reformatted or recomputed). Empty → "No changes yet." Then `Order total if applied: <Money value={change.total}
currency={po.currency} />`.

**Budget Effect card.** One row per `budget_effect` entry: the project (`project_code project_name` from the budget
summary, else `Project`), `department_code`, `ledger_account_code`, then `<Money value={delta} currency={currency}
zero="value" />`. `Money` already shows a negative signed, parenthesised (`lib/money.ts:15`), with an icon
(`MinusCircle`) and the outflow colour (`styles/projects.css:16`), so colour never carries it alone. Beneath a
negative delta: "Lower: this amount is released from the PO's commitment and held again for the requisition, so
another PO can order it without new approval." (DECISIONS 209). Empty list → "No budget effect." A budget-summary
403 or failure only loses the names; the effect still renders.

**Approval line** (`approvalLine(change)`, a pure function in `components/purchasing/changes/approval.ts`), from
the server's `material` and the diff's `field`s only:
- empty diff → "No changes yet."
- `material` → "Needs approval: " + the reasons present, joined by " and ": "the amount changes" (any of
  quantity, unit_price, tax, freight, document_freight), "the line count changes" (`line`); no reason matched →
  "Needs approval."
- not `material` → `No approval needed: only {parts}`, where the parts present are "the needed-by date"
  (`needed_by`) and "the terms" (`terms`): one part → "No approval needed: only the needed-by date changes" /
  "No approval needed: only the terms change"; both → "No approval needed: only the needed-by date and the terms
  change"; neither matched → "No approval needed."

**Action button** (editable only; never disabled): `Submit for Approval` when `change.material`, else `Apply`.

## Writes and sequencing

Every write sends `writeHeaders()` (`apps/web/src/features/auth/api.ts:32`: the CSRF header the middleware
requires on every unsafe method, `kernel/session/csrf.py:81`, plus an `Idempotency-Key`, which only POSTs use).
Versioned writes add `"If-Match": String(change.version)` (the pattern of `components/projects/Transitions.tsx:21`).

**Body.** `changeBody(po, edited)` in `components/purchasing/changes/body.ts`, a pure function returning the
**complete** desired draft: `reason`; `terms` and `needed_by` always (the edited values, `null` when empty: sending the
PO's own value yields no diff, `changes.py:368-383`, which is how an edit is undone); `document_freight` only in
document mode; `lines` **always**, as `[]` when nothing differs: every line whose edited quantity, unit price, tax
or freight differs from `po`'s, with `line_no` and only the differing keys. Reverting a line drops it from the list,
and because a field left out of a PATCH is unchanged (`changes.py:500`, `schemas.py:318`), omitting `lines` would
leave the reverted edit in the draft; `[]` clears it.

**As you type (debounced, server-computed).** 400 ms after the last edit (the precedent of a server check while
typing, `components/vendors/request/VendorRequestForm.tsx:199`; it is a request delay, not a motion value, so no
token applies), send `PATCH …/{id}/changes/{n}` with `changeBody`. **One PATCH in flight at a time:** edits made
while one is in flight wait; when it returns, if the body changed, send once more with the response's `version`.
Never two concurrent PATCHes, so the server's version counter never refuses the page's own writes. Each 200
replaces `change` (diff, effect, material, total, version). While a PATCH is pending or in flight, the diff card
shows "Updating…" in a `role="status"` region; figures stay the last ones the server returned.

**PATCH failures** (typed values are always kept):
- 422: map `errors[].field` to the input — `lines/<n>/<field>` (`_invalid`, `purchasing/service.py:99`), or the
  pydantic form `lines[<i>].<field>` (`kernel/errors/handler.py:55-65`; `i` indexes the body's `lines`, map it back
  to `line_no`), `terms`, `needed_by`, `reason`, `document_freight`, `lines` — show the message under it and list
  all in `ErrorSummary` (`components/form/ErrorSummary.tsx`). The diff card adds "Showing the last figures the
  server accepted."
- 409 `over_open_quantity`: `checks["open.<rfq_line_id>"]` is the quantity still open; under that line's quantity
  (`po.lines[].rfq_line_id`): "Only {open} is still open to order on the award."
- 409 `stale_version`: "Someone changed this change order after you opened it. Your edits are still here; reload to
  see theirs (reloading discards yours)." with `Reload`.
- 409 `invalid_transition`: reload the change (it was submitted or applied elsewhere) and show the read-only state.
- Anything else: `failure(error, "Saving the change order")`.
Register the unsent-edits guard with `registerGuard` (`lib/navigation-guard.ts:12`) while edits are pending, in
flight or failed.

**Apply / Submit for Approval.** First flush: cancel the timer, wait for any PATCH in flight, and if the body
differs from the last one sent, PATCH now. If that fails, stop and show its error — nothing else is sent. If the
flushed response's `material` differs from the button that was pressed, stop and say "This change now needs
approval. Review it and press Submit for Approval." (or "…no longer needs approval. Review it and press Apply.").
Then `POST …/{n}/apply` or `…/{n}/submit` with `{ ...writeHeaders(), "If-Match": String(change.version) }`, one key
per press, busy flag against double press.
- apply 200 → `navigate(`/purchase-orders/${data.result_po_id}`)` (the new version; the old one stays viewable).
- submit 200 → replace `change`; the page becomes read-only with the `approval_pending` sentence.
- 422 `no_changes` → "This change order changes nothing yet."
- 409 `workflow_not_set_up` → "No purchase order change workflow is published. Ask an administrator to set one up.
  Your change order is kept as a draft."
- 409 `approval_required` / `not_material` → reload the change and show the matching sentence above.
- 409 `stale_version` → as for PATCH. 409 `over_open_quantity` → as for PATCH. 403 → the server's `detail`.
  Anything else → `failure(error, "Applying the change order")` / `"Submitting the change order"`.

No withdraw and no discard control here (withdraw exists for `approval_pending`, the creator only; a draft has no
discard command in the API). Record both in `notes.followup`.

## Plants (prove each check fails, then `git checkout -- <file>`)

1. `approvalLine` decides from the fields instead of `material` (e.g. treat `tax` as non-material) → the vitest and
   the material e2e fail.
2. Compute the total or the effect in the client → the odd-figures e2e fails.
3. Drop the in-flight serialisation (send on every debounce) → the two-PATCH e2e fails.
4. Apply without flushing → the PATCH-then-POST e2e fails.
5. Show `Start Change Order` without checking `actions` → the detail e2e fails.
