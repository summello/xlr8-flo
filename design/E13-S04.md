## Requirements (inlined)

- **PO-003** — POs must follow a configurable approval workflow before issue.
- **APR-003** — Workflows must support … POs.

## Design

`purchasing/approval.py` implements `DocumentAdapter` for `document_type = "po"`, with
`approve_permission = "purchase_order.approve"`, `read_permission = "purchase_order.view"`, and the
PO's unit as the target. Register it at import. **Fields for conditions** (pre-flight): `total`
(`"money"`, a `Money` in the **PO currency**, from `PoRead.total`) and `budget_total_project`
(`"money"`, a `Money` in the **project currency**, from `PoRead.budget_total_project`), the same
`Money(Decimal, currency)` shape `requisitions/approval.py` uses for `amount` (a `"decimal"` field
needs a real `Decimal`, never a string: `approvals/conditions.py`); `vendor_id` and `unit_id` as
`"code"`. A condition in another currency raises `currency_mismatch`, as for requisitions.

- `POST /purchase-orders/{id}/submit` (Idempotency-Key, `purchase_order.create`):
  1. `require_workflow_for(conn, scope, "po", id, "purchase orders")`, or 409 (decision 208). **Never auto-approve.**
  2. `assert_current_upstream(conn, scope, requisition_id, <live version>)` for each requisition on
     the PO's lines, passing the requisition's **live** version, exactly as `sourcing/awards.py`
     does (every status write bumps the version, so no version recorded at PO create survives
     the PO's own `ordered` write; no new column). It still refuses a requisition that left
     sourcing-or-later, has an amendment pending, lost its current approval, or has expired codes.
     `# ponytail:` comment naming the ceiling: an amendment approved between PO create and submit
     is not detected; upgrade by persisting the post-create version on `purchase_order`.
  3. The vendor's eligibility again (E11-S11, `VendorService.eligibility`): not eligible → 409
     `vendor_not_eligible` (same problem shape as `_eligibility` in `purchasing/service.py`),
     unless the PO already carries an override. **"Carries an override"** means
     `vendor_snapshot.eligibility.eligible` is `false`: create only stores an ineligible snapshot
     on the override path, so no new column. A vendor eligible at create and ineligible now → 409.
  4. `lifecycle.transition(submit)`, then start the approval.
- `on_outcome`: approve → `approved`; reject → `draft` (claude-plan §14 #9); **nothing is posted** (approval never commits).
- `POST …/withdraw` by the submitter → `draft`.
- **Evidence (`snapshot`)** for the panel: the source award with its justification lines, the budget effect when issued (`budget_total_project` per project from E13-S02), vendor eligibility **now**, and what will be sent (the recipient and the vendor-visible items from E13-S11, when present).
- Separation of duty follows the approvals engine's existing org setting; nothing new.

## Acceptance

- [ ] No published `po` workflow → 409, nothing written.
- [ ] Approve → `approved`, and the ledger is unchanged (assert no entry).
- [ ] Reject → `draft`; withdraw → `draft`.
- [ ] A vendor that became ineligible between draft and submit → 409.
- [ ] Workflow conditions on `total` route as configured (one condition test).
- [ ] TEN-010 and authorization per role; `flo check` green.

## Plants

1. Commit on approval: the "ledger unchanged" assertion fails.
2. Auto-approve without a workflow: the 409 test fails.
