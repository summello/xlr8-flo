## Requirements

- **REQ-012** — Changes after submission must use a controlled return, amendment, or resubmission process and preserve prior values.
- **APR-015** — A document changed in a material way after approval must be resubmitted according to policy.
- **DATA-002** — Concurrent edits must use optimistic concurrency or equivalent version checks; stale writes must not silently overwrite newer data.
- **UX-003** — Unsaved changes must be detected before accidental navigation.
- **UX-004**, **UX-005**, **A11Y-006** — loading, empty, partial and error states; errors that say what happened, what was kept and how to recover; forms with labels, field errors, an error summary and preserved input.

## Contract

**No new backend.** The screens use only E09-S08's routes (`/revisions`, `/changes`, `/amendments…`), E09-S05's submit transition and E09-S11's edit routes, all through the generated client. If a screen needs a field E09-S08 does not return, stop and write `notes.blocked` naming it: do not compute it in the browser.

| Route | Screen | Data |
|---|---|---|
| `/requisitions/<uuid>/resubmit` | Review changes before resubmitting a returned (or rejected-to-draft) requisition | `GET …/changes` (working draft against the latest submission), `GET …/revisions`, E09-S05 submit |
| `/requisitions/<uuid>/amend` | Start or continue an amendment of an approved requisition (`sourcing_in_progress`) | `POST`/`PUT`/`DELETE …/amendments…`, `GET …/changes?against=` |
| `/requisitions/<uuid>/amend/review` | Review the amendment's changes and submit it | `GET …/changes`, `POST …/amendments/{n}/submit` |

Register them in `apps/web/src/routes/__root.tsx` beside E09-S11's requisition routes (routing only).

## Behaviour

1. **Entry points.** E09-S11's `Edit and Resubmit` opens the existing edit route; its primary action on a returned draft becomes `Review and Resubmit`, which goes to `/resubmit`. On an approved requisition, the detail page's `Amend` action (shown when `transitions/available` allows it) opens `/amend`. Edit E09-S11's files only for these two buttons.
2. **What Changed** (spec §4): one `.diff` table `Field | Version N | Version N+1 | Change` from `ChangeSet.rows`. The old value is struck through and the new value bold. The change is a `StatusPill`-style pill with an icon and a word (`Changed`, `Added`, `Removed`), never colour alone. Money rows show the server's `delta` ("Down 3,500.00 USD (2%)"), rendered from the server strings through the `Money` component, never computed. Below 520px card width each row stacks and keeps its column names.
3. **What Happens When You Resubmit:** from `ChangeSet.material` and `ChangeSet.routing`. `restarts` reads "Material change: approval restarts from the first step; earlier decisions no longer apply; the reservation is adjusted". `same_step` reads "Not a material change: it returns to the step that sent it back, and the approver sees this diff". The screen shows the server's answer; it never decides materiality itself (D-M2-13 is server-side).
4. **Funding Check** (when `ChangeSet.funding` is not null): reserved now, reserved after, and the outcome word (`Unchanged`, `Released Once`, `Reserved More`) with an icon, plus the project's available amount after. All are server figures. An increase is checked under the lock at submit (D-M2-15). A shortfall comes back as the submit's problem: show it in the alert, with the shortfall amount and the draft kept.
5. **Note to the Approver** (optional, kept if the send fails) and **Versions**, a lineage list from `/revisions` (number, kind, status, who, when, note), newest first.
6. **Resubmit for Approval / Submit Amendment** is never disabled (MASTER §7.13). Outcomes go to a summary with `role=alert` and focus:
   - `nothing_changed`: "Not resubmitted. Nothing has changed."
   - `stale_version`: "This requisition changed since you opened it. Reload to see the current version." Typed text is kept.
   - `submission_invalid`: the E09-S04 problems list, each linking to its field on the edit screen.
   - A funds shortfall: the amount short, with the draft kept.
   - Success: "Resubmitted as Version N" with who is now asked (from the response). The summary takes focus, then the page offers `Back to Requisition`.
7. **Amendment editor** (`/amend`): reuses E09-S11's header and line form components on the amendment's values. `Save` sends a `PUT` with `If-Match`. `Review Changes` goes to `/amend/review`. `Discard Amendment` (a draft amendment only) opens an `alertdialog` with focus on `Keep Amendment`. A project change is refused by the server (422 on `project_id`), so render the project as read-only text with the reason. Status after submit: an applied non-material amendment says "Applied. The requisition is now Version N"; a material one says "Sent for approval. The approved version stays in force until it is approved".
8. **UX-003:** unsaved changes on `/amend` and on the edit route guard navigation (the same guard E09-S11 uses, not a second implementation).
9. Every state: loading (skeleton at final height), error (`Could not load the changes`, reference id, `Try again`, typed values kept), partial (the funding check fails alone and says so, while the diff and submit still work), and empty (`Nothing has changed yet` with a link back to the editor).
10. Tokens only; nothing copied from the canvas (AGENTS.md). Stale-board items go to `notes.followup`.

## Acceptance criteria

- [ ] A returned requisition with a justification-only edit shows `Not a material change` and `same_step`; after resubmit, the success summary names the same approver step.
- [ ] A changed line quantity shows a money delta from the server, `Material change`, `restarts`, and the funding outcome; after resubmit, `Reserved More` or `Released Once` matches the server.
- [ ] `nothing_changed`, `stale_version`, `submission_invalid` and a funds shortfall each render their alert, focus it, and keep typed text.
- [ ] The amendment flow: start, edit a line, save (`If-Match`), review, submit. Non-material is applied immediately; material shows "Sent for approval".
- [ ] Navigating away with unsaved amendment edits asks first (UX-003).
- [ ] No money is computed in the browser: a vitest plant that formats a delta from two numbers fails the "server string only" test.
- [ ] Keyboard-only path through return → edit → review → resubmit; axe passes on all three routes in light and dark; the MASTER §8 checklist is ticked in the PR body.

2. Disable `Resubmit for Approval` while a request is in flight instead of using `aria-busy`: the never-disabled test fails.
3. Drop the navigation guard on `/amend`: the UX-003 test fails.

## Pre-flight amendments (11 Oct 2026, Opus; binding, they override anything above)

Each item below was found by reading the code this story touches. A block on any of them is a packet defect, not an author failure.

1. **Funding outcome words** are the server's: `Unchanged`, `Released Once`, `Reserved More`, and now `Moved` (E09-S08 amendment 2). Render whatever `ChangeSet.funding.outcome` says through one label map and add `Moved` to it; a value outside the map renders the raw word and fails the vitest that covers the map.
2. **Reservation figures** come from `ChangeSet.funding` only, never from `RequisitionRead.reservation` (that is the live state; the change set is the proposed state).
3. **XFN-008 and UX-007** apply as in E09-S11 amendment 6: helper text on the note and amendment fields through `components/form`, locale formatting for dates, canonical values untouched.
