# E11-S19 — Live duplicate check carries identifiers in the body, never the URL

**Epic** E11 · **M3** · **security/S** · after **E11-S06**, **E11-S14** · tags: `security`
Origin: M3 epic checkpoint E11 (codex-a finding 1, 8 Nov 2026).

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.

## Requirements (inlined)

- **VEN-014** — Sensitive vendor data, including tax and banking information, must receive field-level access control and masking where appropriate.
- **AUD-006** — Secrets, passwords, raw tokens, session identifiers, sensitive banking data, and unnecessary personal information must not be written to logs.
- **VEN-005**, **VEN-010** — unchanged behaviour of the duplicate check itself (E11-S06).

## Defect

`GET /api/v1/vendors/duplicate-check?tax_id=…&identifiers[type]=…` (`apps/api/src/flo/api/vendors.py:156`,
called from `apps/web/src/components/vendors/request/model.ts:79` `duplicateQuery` and the request form ~195)
puts the raw tax id and identifiers in the request URL. URLs are written to the Cloudflare, Cloud Run and
browser-history logs, outside the audited reveal path. E11-S14's own contract says tax data is "never in the URL".
E11-S06's packet specified the GET; this story supersedes that one line.

## Design

- Replace the route with `POST /api/v1/vendors/duplicate-check`, body
  `DuplicateCheck {tax_id?: str(1..64), tax_id_country?: str(2), identifiers?: dict[str(1..64), str(1..64)]}`
  (`extra="forbid"`, at most 20 identifiers). Response `DuplicateResult` unchanged; same permission as
  today (`RequestContext` = `vendor.request`, `api/vendors.py` ~94; `vendor.view` alone stays 403); same service call `VendorService.duplicate_check(tax_id, tax_id_country, identifiers)`.
  The GET route is deleted, not kept beside it.
- It changes no state. It goes through the idempotency middleware like every POST: the web client sends an
  `Idempotency-Key` per check exactly as its other POSTs do (find how in `apps/web/src/api/`); do not add an
  exemption to `IDEMPOTENCY_KEY_EXEMPT_PATHS`.
- No cache header: a POST response is not cached by browsers or the edge, and the idempotency replay keeps
  only `location`/`etag` (`kernel/idempotency/middleware.py` ~32), so a `no-store` header would not survive a
  replay anyway. Pre-flight 1, 8 Nov 2026.
- **Replay is accepted as is (planner ruling, pre-flight 2):** a completed key replays its stored response without
  entering the handler (`middleware.py` ~297), so a caller whose `vendor.view` is revoked between a check and a
  retry of that same check gets the answer they already received. That is the rule for every POST in the app; the
  key is random per check and never reused across checks (a new check, even with the same body, gets a new key),
  so a replay is only the client's own network retry of one request. Do not add an authorization step to replay
  and do not exempt the path.
- Web: `duplicateQuery` becomes `duplicateBody` returning the body object; the form calls the POST.
  Regenerate the API client (`schema.ts`); never hand-write the type.

## Acceptance

- [ ] pytest: the POST returns the same matches as the old GET did for tax id, tax id + country, and an identifier; a foreign tenant's vendor never matches; a caller without `vendor.view` sees the field, not the vendor (existing E11-S06 tests moved to the POST).
- [ ] pytest: `GET /api/v1/vendors/duplicate-check?tax_id=X` no longer returns 200: with the GET deleted it falls to `GET /api/v1/vendors/{id}` (`api/vendors.py` ~185), which refuses `duplicate-check` as a malformed id with **422** (pre-flight 2: not 404/405; do not add a route to change that). Assert 422 and that no route in `app.routes` declares a `tax_id` query parameter.
- [ ] Playwright (`vendor-request.spec.ts`): the duplicate check request is a POST and no request URL the page makes contains the typed tax id.
- [ ] `flo check --light` green.

## Plants

1. Put `tax_id` back on the URL in the web client: the Playwright URL assertion fails.
2. Re-add the GET route: the 422 test fails (the GET answers 200).
