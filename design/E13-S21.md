## Requirements (inlined)

- **EML-001** — The sending domain must publish SPF, DKIM and DMARC, verified by an automated check before first customer send. (Narrowed by the operator to SPF and DKIM automated; DMARC is a documented manual step, `infra/SETUP.md:208`.)
- **EML-003** — A hard-bounced or complained address must enter a suppression list and must not be retried silently; the PO must show as undelivered and be actionable (PO-015). This story makes the list visible and actionable for administrators.

### 2. Reads and the check request — `modules/purchasing/transmission.py`

Schemas in `modules/purchasing/schemas.py`:
- `SendingDomainRead(spf: Literal["pass","fail","unknown"] | None, dkim: same | None, detail: str, checked_at: datetime | None, check_pending: bool, po_email_allowed: bool)`. `spf`/`dkim` are null and `detail` is `""` before the first stored check.
- `SuppressionRead(id: UUID, email: str, reason: Literal["bounced","complained"], created_at: datetime)` and `SuppressionPage(rows: list[SuppressionRead], next_cursor: str | None)`.

Service functions (all inside `tenant_transaction(conn, scope)`; tenant SQL through `PurchaseOrderService(conn, scope).repo.execute`, as `remove_suppression` does):
- `sending_domain(conn, scope, settings) -> SendingDomainRead`: `check = latest_domain_check(conn)`; `check_pending = EXISTS (SELECT 1 FROM job WHERE org_id = %(org_id)s AND kind = %(kind)s AND state IN ('queued','running'))`; `po_email_allowed = po_domain_gate(settings, check.status if check else None)(TEMPLATE) is None` (`TEMPLATE = "po-issued-v1"`, `transmission.py:31`). The browser never derives pass/fail or "allowed" itself.
- `request_domain_check(conn, scope, settings) -> SendingDomainRead`: if `check is not None and check.recent` → `ProblemError(ErrorCode.TOO_MANY_REQUESTS, detail="The sending domain was checked less than a minute ago.", checks={"problem": "domain_check_recent"})` (429, existing code, `kernel/errors/codes.py:31`, `:162`); otherwise, when no `queued`/`running` job of that kind exists for the org, `JobQueue(conn, scope).enqueue(DOMAIN_CHECK_JOB, {}, max_attempts=1)`; return `sending_domain(...)` (now `check_pending = true`). A second click while pending enqueues nothing and answers the same.
- `list_suppressions(conn, scope, q: str | None, cursor: str | None, page_size: int = PAGE) -> SuppressionPage`: `WHERE org_id = %(org_id)s`, newest first by `(created_at, id)`, the `list_orders` cursor and `LIMIT page+1` mechanics; `q` stripped and lower-cased, empty means none, otherwise `email_normalised LIKE <escaped q> || '%'` (a **prefix** match; `%`, `_`, `\` escaped as `service.py:471-475`; backslash is Postgres' default `LIKE` escape). `email` in the read is `email_normalised`.

Thin: parse, authorize, call one service function, serialize. Every route `require("org.setting.manage", organization_target)` (as the DELETE at `:438-440`), so a user without it gets 403, never data.
- `GET /api/v1/admin/email-suppressions` on the existing `suppressions_router`: `q: Annotated[str | None, Query(max_length=254)] = None`, `cursor: Annotated[str | None, Query(max_length=200)] = None` → `SuppressionPage`.
- New `sending_domain_router = APIRouter(prefix="/api/v1/admin/sending-domain", tags=["administration"])`, mounted in `api/health.py` beside `suppressions_router` (`:126`):
  - `GET ""` → `SendingDomainRead`, `settings: Annotated[Settings, Depends(get_auth_settings)]` (as `create_purchase_order`, `api/purchasing.py:124`).
  - `POST "/check"`, `status_code=202` → `SendingDomainRead`. A state-changing POST: the client sends `writeHeaders()` (CSRF and `Idempotency-Key`); no exemption is added to the CSRF or idempotency middleware, no MFA or organization-selection allow-list change (an ordinary signed-in, MFA-verified, organization-selected route).

### 4. The job — `api/internal.py`

`_domain_check_job(settings) -> Callable[[Job], None]` beside `_run_email_domain_check`, registered in the `_run_jobs_tick` handler map (`:359-376`) as `DOMAIN_CHECK_JOB: _domain_check_job(settings)`. The handler:
1. opens its own `psycopg.connect(database_url)` and, in one transaction, reads `latest_domain_check`; if it is `recent`, returns without calling the provider (two organizations clicking in the same minute make one provider call);
2. otherwise calls `_run_email_domain_check(settings)` (provider first, then one row on its own connection);
3. a `ProblemError` from it → `raise PermanentJobError("email domain check unavailable") from None` (no row; the job goes `dead` with that fixed text; the last stored status stays in force, as for the daily run).

The job row carries the requesting organization's `org_id` (tenant-scoped like every job; the runner's audit rows land in that org); the row it writes is global, exactly like the daily run. Scheduling: nothing new in `api-proxy.ts`; the existing per-minute `tickJobs` runs it. No external call is made from the request handler (invariant 6).

- "Last checked" with the locale date and time of `checked_at` (`Intl.DateTimeFormat`, the user's locale; "Never" when null), and the `Check Now` button (secondary). Click → `POST …/check` with `writeHeaders()`:
  - 202 → a polite `role="status"` line "Check queued. The result appears here within two minutes." and the page re-reads `GET` every 5 s while `check_pending` is true, at most 24 times.   - The button is never disabled to signal an error (DECISIONS 45); it shows `aria-busy` while the POST is in flight.

**Card 2 — Suppressed Addresses.**
