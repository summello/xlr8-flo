## Requirements (inlined)

- **PO-008** — Approval or issue must convert the applicable requisition reservation into a commitment atomically. *(Issue, per claude-plan §14 #5.)*
- **PO-012** — Duplicate clicks, retries, worker retries, and integration retries must not issue or transmit a PO more than once unintentionally.
- **FIN-005 / invariant 3** — lock before you validate; ledger insert and balance update in one transaction.

## Issue (`POST /purchase-orders/{id}/issue`, Idempotency-Key, `purchase_order.issue` on the unit)

**One transaction, lock order:** every involved `project_balance` (the sub-projects of the lines) in
id order, then the requisitions in id order, then the PO `FOR UPDATE`.
1. The PO must be `approved` and its version current. If it is already `issued` at this version, return the **same** result (200 with the issued PO); never commit again (PO-012).
2. `assert_current_upstream` for each requisition (expired codes block, D-M2-25).
3. **Freeze the budget amounts first.** Until issue, `budget_amount`/`budget_amount_project` follow the unit's live tax/freight settings (`purchasing/service.py` `live` branch, "E13-S05 freezes it at issue"). Under the locks, recompute each line with the same `self._budget(figures, flags, rate, currency)` the read path uses and `UPDATE po_line SET budget_amount, budget_amount_project` to those values; the stored columns are authoritative from here on (the read path's non-live branch reads them). Then, for each line, group by (requisition, sub-project, department, ledger account): `amount = Σ budget_amount_project` of the frozen values (E13-S02, at the PO's stored rate, decision 167). Test: change the unit's tax/freight setting after the last draft write, issue → the commitment equals the amount under the new setting, and the issued PO reads back the same frozen figure after a further settings change.
4. **Commit** each group via `budget.service.commit(conn, scope, project_id=sub_project, amount, currency=project currency, source_type="purchase_order", source_id=po.id, department_code, ledger_account_code, idempotency_key=f"po:{id}:v{version}:commit:{group_key}", from_reservation_entry_id=requisition.reservation_entry_id, …)`. That converts that much of the requisition's reservation into a commitment.
   - **Opus decision (recorded):** if a group's amount exceeds the reservation remaining (possible only by rounding or a tax/freight edit on the draft), the excess must fit the sub-project's **availability** under the same lock, or the issue fails 409 `over_reservation`. Raise `ProblemError(ErrorCode.CONFLICT, detail="This purchase order needs more than the requisition reserved and the project has available.", checks={...})`, the existing 409 code (no new `ErrorCode`; `over_reservation` is only the `problem` label, as `purchasing/service.py` ~215 does for its own conflicts). `checks` values must all be strings: `{"problem": "over_reservation", "group_key": f"{requisition_id}|{sub_project_id}|{department_code}|{ledger_account_code}" (the first failing group in lock order, an empty string where a code is null), "requested": str(group amount), "reservation_remaining": str(…), "excess": str(requested − reservation_remaining), "available": str(sub-project availability under the lock)}`, all Decimal strings in the project currency. Nothing is ever committed beyond reservation plus availability.
5. `requisitions.service.issue_lines(conn, scope, [(line_id, qty)], actor)`: a new `requisition_line.issued_qty numeric(18,4) NOT NULL DEFAULT 0` column with `CHECK (issued_qty >= 0)` and `CHECK (issued_qty <= ordered_qty)` (the `20261009_0040` quantity-counter shape), `+= qty`.
6. `lifecycle.transition(issue)` → `issued`; store `issued_at`, `issued_by`, and the fixed `rate`.
7. **Requisition `completed` (decision 206):** when every non-cancelled line of a requisition has `issued_qty = quantity − cancelled_qty`, `requisitions.service.mark_completed`, audited.
8. Enqueue the transmission (E13-S09's `transmission.enqueue(po_id, version)`; until E13-S09 merges, a no-op hook) **in this transaction**, so a failed send never strands a commitment and a rolled-back issue never sends.

Notify the requester internally (an in-app notification, not an email copy; decision 168). The notification engine is E17-S02 (M4, unmerged) and no notification table exists, so call a no-op hook `notify_requester_issued(conn, scope, po_id)` in `issue.py` **in this transaction**, like item 8; E17-S02 wires it. No new table in this story; record the hook in `notes.followup`.

## Decided

**28 Oct 2026, operator (final)**, pre-flight 1:

1. **No zero-value line exists, so no zero-value group does (supersedes the 28 Oct skip rule).** The operator ruled that a line with no quantity or no price is never listed, stored or shown on a PO. E12-S23 stops it at the source (bids refuse a quoted line whose price is 0 or whose line amount rounds to 0; every quantity is already `CHECK > 0`), so a group's `Σ budget_amount_project` is always `> 0`. Issue still guards the invariant: a group amount `≤ 0` (`postings.py:143` would reject it anyway) raises `ProblemError(ErrorCode.CONFLICT, checks={"problem": "zero_value_line"})` before anything is written, rather than a 500 from the ledger. Test: force one `po_line` to `0` by direct SQL, issue fails 409, nothing written. There is nothing to omit from the vendor copy (E13-S08 carries no zero-line rule).
2. **No release at completion (operator, 28 Oct 2026, rule: release only if the award does not return the surplus).** E12-S08 already releases the unused reservation at award approval (`unused = scope of the awarded lines − award amount`) and transfers it back to the main project (decision 205), so the requisition's reservation is already cut to the award amount before issue. What can remain after issue is only rounding or a tax/freight setting difference between the award amount and `Σ budget_amount_project`. `mark_completed` (item 7) therefore releases nothing. The residual stays reserved on the sub-project, and an excess is handled by the `over_reservation` rule in item 4. Record in `notes.followup`: a closing sweep of that residual belongs to E13-S07 (PO close) or a later step; the nightly drift report is unchanged.
3. **A null accounting code refuses the issue (operator, 29 Oct 2026, pre-flight 4: option a).** `po_line.department_code` and `ledger_account_code` are nullable (`20261027_0078`), but `ledger_entry` requires both `NOT NULL` (`20260826_0019`). Before any lock-ordered write, if a group's line has either code null, issue fails 409 `ErrorCode.CONFLICT` with `checks = {"problem": "missing_accounting_code", "line_no": str(...)}` (the first such line), nothing written, the PO stays `approved`. Never fall back to the requisition's header codes and never pass `str(None)`. Test: one line with a null `ledger_account_code` by direct SQL, issue fails 409 with that problem and no ledger row. **Also check, read-only:** the requisition reserve path (`requisitions/approval.py` ~272) wraps its header codes in `str(...)`, which would store the text `"None"` for a null. Do not change that file in this story: assert in a test that a submitted requisition's header codes are never null (find the submit validation), or, if they can be, record it under `notes.blocked` for the operator.

## Acceptance

- [ ] Hand-computed example: a PO of 2 lines on one sub-project (different ledger accounts) → two commitment entries converting the reservation; the reservation remaining drops by the same total; **drift empty** (`budget/reconcile`).
- [ ] **Concurrency (real Postgres):** two simultaneous issues of one PO → exactly one commits; the other returns the same issued result; the ledger has one set of entries.
- [ ] Retry with the same Idempotency-Key and with a new key → no second commitment (PO-012).
- [ ] Over reservation by one cent with no availability → 409, nothing written; with availability → commits.
- [ ] Approval alone posts nothing (regression from E13-S04).
- [ ] Requisition `completed` after its last line is issued; not before.
- [ ] Stale requisition / expired codes → 409, nothing written.
- [ ] TEN-010 and authorization per role; `flo check` green.
