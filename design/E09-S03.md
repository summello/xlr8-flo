# E09-S03 — Catalogue: BU/OU-scoped suggestions from prior requested, sourced and purchased items

**Epic** E09 · **M2** · **engine/M** · after **E09-S02** · tags: `migration`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (G–O) and `docs/author-traps.md`. Consumer: `design-system/pages/requisition-create.md` §5 "Catalogue Suggestions" and §3 (the selects). Read both before writing the read models.

## Requirements

- **REQ-007** — Line entry must suggest previously requested, sourced, or purchased items/services within the authorized scope.
- **REQ-008** — The catalogue must retain BU/OU scope and vendor sourcing/supply/service history.
- **XFN-009** — Foreign-key fields such as department, ledger account, vendor, project, and item must use scoped dropdown/type-ahead selection rather than free text.

## Design decisions (this packet)

- **The catalogue is built from events, never edited by hand.** One row per distinct (BU/OU, line type, normalised description, unit). Each event (requested, sourced, purchased, supplied, serviced) is an append-only row. M2 writes only `requested`, at submission (E09-S05 calls `record_requested`). M3 stories call `record_event` for the others, with a vendor.
- **Scope = the item's BU/OU and its ancestors.** A requisition in unit U sees items recorded in U or any ancestor of U, never a sibling's or a descendant's (no sideways or upward leak). This matches how grants inherit downward (`docs/m1-conventions.md` B).
- **Normalised description** = `lower(regexp_replace(trim(description), '\s+', ' ', 'g'))`.
- **The XFN-009 lookups live here, in one requisition-scoped endpoint.** The baseline Requestor role holds `requisition.*` and `project.view` but not `master.read` or `project.read`, so it cannot use `/api/v1/master/{kind}` or `/api/v1/projects` to fill the create form's selects. Granting it those would widen reads beyond the form's need, so this story serves exactly the options the form shows. Raise the M1 gap (`project.read` and `master.read` are not in any baseline role) in `notes.followup`.

## Contract

| Route | Permission (target) | Success |
|---|---|---|
| `GET /api/v1/catalogue?bu_id=&q=&line_type=&limit=` | `requisition.create` (the BU/OU `bu_id`) | 200 `{rows: [CatalogueItemRead]}` |
| `GET /api/v1/requisitions/lookups/{kind}?q=&bu_id=&limit=` | `requisition.create` (organization; `bu_id`-dependent kinds also check `requisition.create` on that BU/OU with `permits`, 404 when it fails) | 200 `{rows: [LookupOption]}` |
| `POST /api/v1/requisitions/{id}/lines` (extended) | as E09-S02 | body may carry `catalogue_item_id` instead of the typed fields |

- **Catalogue search:** `q` of 2..100 characters, matched case-insensitively as a substring of the normalised description; `limit` 1..20 (default 4, the page shows four). Order by `last_event_at DESC, id`. `# ponytail:` ILIKE scan within one org's catalogue; add a `pg_trgm` index when an organization passes about 50k items.
- **`CatalogueItemRead`**: `id, line_type, description, uom_code, category_code, last_unit_price, currency, last_event ("requested"|"sourced"|"purchased"|"supplied"|"serviced"), last_event_at, last_vendor_id, last_vendor_name (null in M2), bu_id`.
- **Adding from the catalogue:** `LineCreate` gains `catalogue_item_id` (exclusive with `description`/`line_type`/`uom_code`/`category_code`; `quantity` defaults to `"1"`, `unit_price` defaults to `last_unit_price`, either may be given). The item must be visible from the requisition's BU/OU (else 422 on `catalogue_item_id`, which never confirms that a foreign id exists), and its currency must equal the requisition's (else 422 `currency_mismatch`). The line stores `catalogue_item_id`.
- **Lookups**, `kind` ∈:
  - `project`: projects with `status = 'active'` that the caller may raise a requisition in (`permits(requisition.create, project target)` per row). Each row carries `{value: id, label: "<number> <name>", disabled: bool, note}`; a requisition-generated project is listed **disabled** with `note = "created from REQ-00277"` (the page lists it but disables it, canvas decision 48). Depth-5 projects are listed with `disabled: true, note: "at the five-level limit"` (D-M2-12).
  - `bu`: active org units where the caller holds `requisition.create`.
  - `department`, `ledger_account`, `uom`, `item_category`, `service_category`: active master records effective today (`org.service` listing), `{value: code, label: "<code> <name>"}`.
  - `delivery_address`: `ship_to` addresses effective today on `bu_id` and its ancestors (requires `bu_id`).
  - `q` filters by prefix on code/number or substring on name; `limit` 1..50 (default 20). Unknown `kind` → 422.
  - `# ponytail:` `project` and `bu` evaluate `permits` per candidate over the first 200 matches. Move to a resolver-side scope filter when a tenant has more than 200 active projects matching a typical query.

## Behaviour

1. **Migration** (reversible; next revision at story start):
   - `catalogue_item(id uuid PK, org_id, bu_id uuid NOT NULL, line_type text NOT NULL CHECK (line_type IN ('item','service')), description text NOT NULL, normalized text NOT NULL, uom_code text NOT NULL, category_code text, last_unit_price NUMERIC(18,4) NOT NULL, currency char(3) NOT NULL, last_event text NOT NULL, last_event_at timestamptz NOT NULL, last_vendor_id uuid, times_requested int NOT NULL DEFAULT 0, created_at)`; `UNIQUE (org_id, bu_id, line_type, normalized, uom_code)`; index `(org_id, bu_id, last_event_at DESC)`.
   - `catalogue_event(id bigserial PK, org_id, catalogue_item_id uuid NOT NULL, event text NOT NULL CHECK (event IN ('requested','sourced','purchased','supplied','serviced')), source_type text NOT NULL, source_id uuid NOT NULL, vendor_id uuid, quantity NUMERIC(18,4) NOT NULL, unit_price NUMERIC(18,4) NOT NULL, currency char(3) NOT NULL, at timestamptz NOT NULL DEFAULT now())`; **append-only** with the existing `raise_append_only()` triggers (row and TRUNCATE), following `migrations/20261008_0025_project_lifecycle.py`; `UNIQUE (org_id, source_type, source_id, catalogue_item_id, event)` so a repeated call records nothing new.
   - `ALTER TABLE requisition_line ADD COLUMN catalogue_item_id uuid` with an FK to `catalogue_item(id)`.
   - RLS on both new tables.
2. **`requisitions.service.record_event(conn, scope, *, bu_id, line_type, description, uom_code, category_code, event, source_type, source_id, quantity, unit_price, currency, vendor_id=None) -> UUID`**: upsert the item on its unique key (update `last_*`, increment `times_requested` for `requested`), insert the event (`ON CONFLICT DO NOTHING`), return the item id. **`record_requested(conn, scope, requisition_id)`** records one `requested` event per line, with `source_type = 'requisition_line'` and `source_id = line.id`. E09-S05 calls it inside the submit transaction. Both are exported for M3. A line created from the catalogue records against that item. Any other line resolves its item by the unique key.
3. The catalogue is never written by an HTTP route directly.

## Acceptance criteria

- [ ] Recording the same line twice creates one event and increments nothing the second time.
- [ ] An item recorded in BU A is suggested to a requisition in A and in A's child unit A1, never in sibling BU B and never in A's parent from A1's record.
- [ ] Search is case- and whitespace-insensitive (`"  Proximity   SENSOR"` finds "Proximity sensor"); a 1-character `q` → 422.
- [ ] Adding from the catalogue creates a line with quantity 1, the last price, the item's type, unit and category, and `catalogue_item_id` set. An item from a sibling BU → 422 that does not reveal it exists.
- [ ] `catalogue_event` cannot be updated, deleted or truncated (as the application role).
- [ ] Lookups: `project` lists a requisition-generated project as disabled with its note, omits projects the caller cannot raise against, and omits non-active projects. `ledger_account` omits inactive codes. `delivery_address` returns only `ship_to` addresses of the unit and its ancestors. An unknown `kind` → 422.
- [ ] Foreign tenant: a catalogue query with another tenant's `bu_id` → 404; a lookup never returns another tenant's rows.
- [ ] Migration up/down/up preserves items and events.

## Plants

1. Match catalogue scope on `bu_id IN (descendants)` instead of ancestors: the sideways/upward-leak test fails.
2. Remove the event unique key: the record-twice test fails.
3. Drop the append-only trigger: its test fails.
4. Skip the per-row `permits` in the `project` lookup: the omitted-project test fails.
