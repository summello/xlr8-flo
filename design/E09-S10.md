# E09-S10 — Notes and attachments on all business documents, upload validation, quarantine

**Epic** E09 · **M2** · **security/L** · after **E03-S06** · tags: `security`, `migration`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (G: new module `modules/collaboration/`; H: the registry pattern) and `docs/author-traps.md`. Decisions: **D-M2-8**; `docs/claude-plan.md` **D-14** (malware-scanning compensating controls). Screens consuming this API: the Attachments card in `design-system/pages/requisition-create.md` §5 and the project detail Attachments tab (canvas decision 31). States and copy come from there: scan states `Clean`, `Scanning`, `Quarantined`, each icon plus text, and a blocked file says why it cannot be opened.

## Requirements

- **COL-001** — All business documents must support timestamped notes and attachments.
- **COL-002** — Notes must identify author and visibility, including internal-only versus externally shareable.
- **COL-003** — Edited notes should preserve edit history; notes used as approval rationale must be immutable.
- **COL-004** — Attachments must retain original filename, generated storage key, media type, size, checksum, uploader, upload time, scan status, and linked record.
- **COL-005** — Uploads must use allow-listed extensions/types, content and signature validation, safe filenames, size limits, access control, and malware scanning.
- **COL-006** — Files must be stored outside the public web root and downloaded through an authorized, time-limited path or application response.
- **COL-007** — Quarantined, rejected, or unscanned files must not be available to ordinary users or external recipients.
- **COL-008** — Attachment versions, deletion/retention actions, downloads of sensitive files, and external sharing must be audited.
- **D-14** — Malware scanning is allow-list plus magic-byte verification plus size cap plus quarantine-until-cleared plus SHA-256 reputation lookup (hash only, never the file). No in-process ClamAV. Full AV is a hard gate at graduation (E19-S04).
- **D-M2-8** — Attachments that pass the allow-list, magic-byte and size checks are marked `basic_checks_passed` and are downloadable by authorized users. They are never shared externally until full scanning exists (E19-S04).

## Design decisions (this packet)

- **Allow-list (extension and verified signature must agree):** `.pdf` (`%PDF-`), `.png` (`\x89PNG\r\n\x1a\n`), `.jpg`/`.jpeg` (`\xFF\xD8\xFF`), `.xlsx` and `.docx` (ZIP `PK\x03\x04` whose `[Content_Types].xml` declares the matching main part, and which contains **no** `vbaProject.bin`, so macro files are refused even when renamed), `.csv` and `.txt` (valid UTF-8, no NUL byte). Anything else → 422 `unsupported_file`. The media type stored is the one the signature proves, never the client's `Content-Type`.
- **Size:** 1 byte to 10 MiB (the import precedent). Over → 413 (`PAYLOAD_TOO_LARGE`, already in the taxonomy). Empty → 422.
- **Scan states:** `pending`, `basic_checks_passed`, `clean`, `quarantined`, `rejected`. M2's `BasicChecksScanner` runs synchronously in the upload request. A file that passes is stored as `basic_checks_passed`. A file that fails is **not stored**: the request gets a 422 and an audit row records the refusal (name, size, checksum, reason). `quarantined` and `clean` are set by E19-S04's reputation lookup. They exist now so the read rules are written once.
- **Readable states (COL-007):** a download needs `basic_checks_passed` or `clean`. `pending`, `quarantined` and `rejected` are never served, to anyone, through this API (409 `file_unavailable`, with the reason in words). External sharing does not exist in M2 (D-M2-8), so there is no share route.
- **Downloads are an application response** (COL-006), not a presigned URL. Each request is authorized and streamed with `Content-Disposition: attachment; filename*=UTF-8''<safe name>`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, and `Cache-Control: private, no-store`. That keeps the single origin (D-17) and puts the authorization check on every byte. Every download is audited (COL-008: all attachments are treated as sensitive).
- **Safe display name:** strip path components and control characters, collapse whitespace, keep at most 120 characters while preserving the extension. The original filename is stored verbatim for the record (COL-004) and never used as a storage key (`kernel.ports.storage.opaque_storage_key()`).
- **Who may do what is registered per document type** (the convention H pattern, because `collaboration` must not import document modules): `collaboration.service.register_document_access(DocumentAccess(document_type, read_permission, write_permission, target(conn, scope, document_id) -> AuthorizationTarget))`. Registered in `api/document_types.py::register_document_types()`: `requisition` (read `requisition.view`, write `requisition.edit`), `project` (read `project.read`, write `project.update`). Reading notes and attachments needs the read permission. Adding a note needs only the read permission (an approver must be able to comment). Uploading, versioning and deleting attachments need the write permission. An unregistered `document_type` → 404.
- **Notes are editable by their author only**, keep every prior body in an append-only `note_revision` (COL-003), and can be locked: `collaboration.service.lock_note(note_id)` makes a note immutable. E10 approval rationale lives in its own append-only `approval_decision`, so it is immutable by construction. `lock_note` is there for a note that is cited as rationale.
- **Deletion is soft:** `deleted_at` and `deleted_by`, and the object stays in storage. `# ponytail:` there is no purge; add a retention job when a retention policy is decided (record it in `notes.followup`).

## Contract

New module `modules/collaboration/`, router `api/collaboration.py`. Each route is guarded by `require("record.read", document_target)` for 401/404 concealment and the route gate (`record.read` is in every baseline role). The service then checks the registered permission with `kernel.authz.permits` (403 when it fails, the E06-S03 round-3 pattern).

| Route | Needs | Success |
|---|---|---|
| `GET /api/v1/documents/{document_type}/{document_id}/notes` | read | 200 `[NoteRead]` newest first |
| `POST …/notes` (Idempotency-Key) body `{body (1..10000), visibility: "internal"\|"shareable"}` | read | 201 `NoteRead` |
| `PATCH /api/v1/notes/{id}` (`If-Match`) body `{body?, visibility?}` | author, not locked | 200; 409 `note_locked`; 403 when not the author |
| `GET /api/v1/notes/{id}/revisions` | read | 200 prior bodies, oldest first |
| `GET /api/v1/documents/{document_type}/{document_id}/attachments` | read | 200 `[AttachmentRead]` (latest version per attachment, `versions` count) |
| `POST …/attachments` (Idempotency-Key), multipart field `file` | write | 201 `AttachmentRead`; 413; 415 (non-multipart); 422 `unsupported_file` |
| `POST /api/v1/attachments/{id}/versions` (Idempotency-Key), multipart | write | 201, version + 1 |
| `GET /api/v1/attachments/{id}/content?version=` | read, readable scan state | 200 stream; 409 `file_unavailable` |
| `DELETE /api/v1/attachments/{id}` | write | 204; already deleted → 204, writes nothing |

`AttachmentRead`: `id, document_type, document_id, version, original_filename, display_name, media_type, size_bytes, sha256, scan_status, uploaded_by, uploaded_by_email, uploaded_at, deleted_at`. `NoteRead`: `id, author_id, author_email, body, visibility, locked, created_at, edited_at, version`.

## Behaviour

1. **Kernel additions** (authorized):
   - `kernel/ports/scan.py`: `ScanVerdict = Literal["basic_checks_passed","rejected"]`, `ScanResult(verdict, media_type, reason)`, `class Scanner(Protocol): def scan(self, data: bytes, *, filename: str) -> ScanResult`. A `BasicChecksScanner` implements the allow-list above. E19-S04 adds a reputation step behind the same port.
   - `kernel/multipart.py`: move the bounded streaming reader out of `modules/imports/multipart.py` as `read_multipart(request, *, file_field="file", text_fields: Mapping[str, int], max_file_bytes) -> MultipartUpload`, and make `modules/imports/multipart.py` a thin caller with **unchanged behaviour**. The existing import tests must pass untouched.
2. **Migration** (reversible): `note(id uuid PK, org_id, document_type text, document_id uuid, author_id uuid NOT NULL REFERENCES identity(id), body text NOT NULL, visibility text CHECK IN ('internal','shareable'), locked boolean NOT NULL DEFAULT false, version int NOT NULL DEFAULT 1, created_at, edited_at)`; `note_revision(id bigserial, org_id, note_id, body, visibility, edited_by, edited_at)`, append-only; `attachment(id uuid PK, org_id, document_type, document_id, created_by, created_at, deleted_at, deleted_by)`; `attachment_version(id uuid PK, org_id, attachment_id, version int, original_filename text, display_name text, storage_key text NOT NULL UNIQUE, media_type text, size_bytes bigint CHECK (size_bytes BETWEEN 1 AND 10485760), sha256 char(64), scan_status text NOT NULL CHECK IN ('pending','basic_checks_passed','clean','quarantined','rejected'), uploaded_by, uploaded_at)`, `UNIQUE (attachment_id, version)`. A trigger allows an `attachment_version` UPDATE only of `scan_status` and refuses DELETE. Indexes on `(org_id, document_type, document_id)`. RLS on all four.
3. **Upload:** read the multipart (cap), scan, then on pass generate an opaque key, `Storage.put` **before** the database insert (an orphan object on rollback is harmless and recorded as a `# ponytail:` with a sweep as its upgrade path; a row without an object is not harmless), insert the rows, audit `attachment.upload`. On a refusal, audit `attachment.refused` and store nothing.
4. **Download:** load the version, check the scan state, `Storage.get`, stream, audit `attachment.download` with the version and size.
5. **Note edit:** lock the note `FOR UPDATE`, check `If-Match`, the author and `locked`, insert the prior body into `note_revision`, update it, audit.
6. Every route has a `COVERED` foreign-tenant test.

## Acceptance criteria

- [ ] Each allowed type uploads with the right `media_type`. A PE executable renamed `.pdf`, a `.docm` renamed `.docx` (contains `vbaProject.bin`), a `.svg`, an HTML file renamed `.txt` that contains a NUL byte, and a zero-byte file → 422 `unsupported_file`, nothing stored, one refusal audit row each.
- [ ] 10 MiB + 1 byte → 413. Exactly 10 MiB of valid PDF passes.
- [ ] The stored key is an opaque UUID unrelated to the filename. `../../etc/passwd.pdf` displays as `passwd.pdf`, and the original is kept verbatim.
- [ ] A `quarantined` or `pending` version (set directly in the fixture) → 409 `file_unavailable` on download, for every role including an organization administrator.
- [ ] Download headers: `attachment` disposition, `nosniff`, `sandbox` CSP, `no-store`. The body bytes' SHA-256 equals the stored checksum. One audit row per download.
- [ ] A new version keeps the previous one downloadable and listed. A delete is soft, the row and object remain, and the delete is audited.
- [ ] Notes: the author edits twice and `revisions` returns both prior bodies. A non-author → 403. A locked note → 409 `note_locked`. An approver with only `requisition.view` can add a note but cannot upload an attachment (403).
- [ ] An unregistered `document_type` → 404. A foreign-tenant document, attachment or note → 404 on every route. No grant on the document → 404.
- [ ] `attachment_version` rows cannot be deleted, and only `scan_status` can change (as the application role).
- [ ] The existing import upload tests pass unchanged after the multipart extraction.
- [ ] Migration up/down/up preserves notes, revisions and attachments.

1. Trust the client `Content-Type` instead of the signature: the renamed-executable test fails.
2. Skip the `vbaProject.bin` check: the `.docm` test fails.
3. Serve `quarantined` versions: the quarantine test fails.
4. Use the original filename as the storage key: the opaque-key test fails.
5. Drop the download audit: its test fails.

## Pre-flight amendments (11 Oct 2026, Opus; binding, they override anything above)

Each item below was found by reading the code this story touches. A block on any of them is a packet defect, not an author failure.

1. **The multipart reader is import-specific today.** `modules/imports/multipart.py::read_upload` hard-codes the part names `{"file", "template", "external_key"}`, requires `template`, caps `template` at 1024 bytes, and reports problems through `imports.parsers.invalid` (which `kernel` may not import). Extract `kernel/multipart.py::read_multipart(request, *, file_field="file", text_fields: Mapping[str, int], required: frozenset[str], max_file_bytes)` by moving the parser loop verbatim and parameterizing exactly those three things. Errors raise `ProblemError(ErrorCode.VALIDATION_FAILED, errors=(ProblemFieldError(field, message),))` with the **same field names and message strings** the import tests assert today (`"Send exactly one template and one file part."`, `"Incomplete multipart upload."`, and so on). `modules/imports/multipart.py` becomes `read_upload = thin caller` that supplies `text_fields={"template": 1024, "external_key": 1024}`, `required={"template"}`, and builds the unchanged `Upload`. The existing import upload tests are the guard; run them first and last. The attachments route calls it with `text_fields={}`.
2. **Storage.** Use `kernel.storage.create_storage(settings)` through a dependency in `api/collaboration.py` mirroring `api/imports.py::get_import_storage`. Do not import from another router. The port is `Storage.put(key, data, *, content_type)` and `Storage.get(key)`; `kernel.ports.storage.opaque_storage_key()` makes the key.
3. **`record.read` is in every baseline role** and is in `PERMISSION_CODES`; the route gate uses it. `project.read` and `project.update` (the `project` registration) are seeded permissions outside the catalogue and are checked through `permits` only.
4. **Streaming.** `Storage.get` returns `bytes`; a 10 MiB object is fine in memory. The `# ponytail:` records the ceiling and the upgrade (a streaming `get`) when the cap rises.
