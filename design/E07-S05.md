# E07-S05 — Commitment, actual and reversal primitives with source-document lineage

**Epic** E07 · **M1** · **ledger/L** · after **E07-S04** · tags: `money`

## Requirements

- **FIN-004** — Posted financial entries must be append-only; corrections use reversal and replacement entries.
- **FIN-011** — Failed, rejected, cancelled, expired, or reduced transactions must release unused reservations and commitments exactly once.
- **AUD-007** — Financial events must retain immutable lineage from project balance to source document and approval.

## Contract

Service-only primitives in `modules/budget/postings.py`, exported through `service.py`:

- `commit(conn, scope, *, project_id, amount, currency, source_type, source_id, effective_date, actor_id, department_code, ledger_account_code, idempotency_key, from_reservation_entry_id=None)` — `entry_type=commitment`, `bucket=committed`. When `from_reservation_entry_id` is given, it **converts** a reservation: in one transaction it posts the `release` of up to `amount` from that reservation (E07-S04's `release_reservation`) and the commitment, so funds never double-count and never dip through `available`.
- `release_commitment(conn, scope, *, commitment_entry_id, amount|None, ...)` — `entry_type=release`, `bucket=committed`, same exactly-once rule as E07-S04 (use `releases_entry_id`).
- `record_actual(conn, scope, *, project_id, amount, currency, source_type, source_id, effective_date, actor_id, department_code, ledger_account_code, idempotency_key, from_commitment_entry_id=None)` — `entry_type=actual`, `bucket=actual`; with `from_commitment_entry_id` it releases that much commitment in the same transaction (invoice consuming a PO commitment).
- `reverse_entry(conn, scope, *, entry_id, actor_id, effective_date, reason, idempotency_key) -> LedgerEntry` — posts the `reversal` row (bucket = the original's bucket, `amount = -original.amount`, `reverses_entry_id` set). A replacement is a separate, explicit second post by the caller (FIN-004: correction = reversal + replacement).

Lineage view (AUD-007): migration `20260826_0022` (down `…_0021`) creates `ledger_lineage(entry_id, org_id, project_id, source_type, source_id, chain_root_id, depth)` as a recursive view following `reverses_entry_id` and `releases_entry_id` so any entry resolves to the source document and the entries it reverses/releases. (Approval lineage joins in M2; leave a nullable `approval_instance_id uuid` **column on the view only**, always NULL in M1.)

## Behaviour

1. Every function goes through `post_entry` (E07-S02): lock, validate, insert, update balance, audit, one transaction.
2. `commit` with a conversion: `amount` must be `>= 0`; the released amount is `min(amount, reservation.remaining)`; if the commitment exceeds the remaining reservation the excess is validated against availability like a fresh commitment.
3. `reverse_entry` rules: cannot reverse a reversal; cannot reverse an entry already reversed (unique partial index from E07-S01); reversing a `reservation`/`commitment` whose remaining is smaller than its amount (partly released) is a 409 — the caller releases instead; reversing an `allocation` that would drive `available` below zero is rejected unless `allow_negative_budget`.
4. Reversal uses the original's currency and department/account codes. It ignores period closure only when the reversed entry's own period is open; otherwise it posts to the current open period (the reversal's `effective_date` must be in an open period, else `PeriodClosed`).
5. `record_actual` requires `department_code` and `ledger_account_code` (PROJ-014); they are validated through `org.service.assert_usable('department'|'ledger_account', code, effective_date)` (E05-S03).

## Acceptance criteria

- [ ] Reserve 100, commit 100 `from_reservation`: balance shows `reserved=0, committed=100`, `available` unchanged by the conversion
- [ ] Commit 120 from a reservation of 100 with 20 available: succeeds; with 10 available: `InsufficientBudget`, nothing written
- [ ] Actual 60 `from_commitment` of 100 leaves `committed=40, actual=60`; a second actual of 50 from the same commitment raises (only 40 remains)
- [ ] `reverse_entry` on an actual returns the bucket to its prior value; a second reverse of the same entry fails in the database and readably in the service; reversing a reversal fails
- [ ] Concurrent reversal of one entry: exactly one succeeds
- [ ] `record_actual` without department or ledger account code → 422-type error; with an inactive code → `MasterCodeUnusable`
- [ ] After a seeded random sequence mixing all primitives, `project_balance` equals `SUM(amount) GROUP BY bucket` and no bucket other than `allocated` is negative
- [ ] `ledger_lineage` returns the chain commitment → release and actual → reversal for a planted chain, and root entries have depth 0
- [ ] Every primitive's replayed `idempotency_key` returns the first result with no balance change
- [ ] Migration up/down/data-preservation
