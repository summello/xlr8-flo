# E08-S02 — Dry-run preview, row/column error report, atomic or explicitly partial commit

**Epic** E08 · **M1** · **engine/L** · after **E08-S01** · tags: 

> **Conventions:** read `docs/m1-conventions.md` (authorization outcomes, scope targets, wire formats). It applies unless this packet says otherwise.

## Requirements

- **IMP-005** — Users must receive row/column-level errors and a downloadable error report.
- **IMP-006** — A dry-run preview must show creates, updates, skips, warnings, and errors before commit.
- **IMP-007** — The committed batch must be atomic where practical, or explicitly report partial outcomes with recovery instructions.

## Contract

Builds on E08-S01's batch, template and mapping.

- `POST /api/v1/imports/{id}/validate` (Idempotency-Key) → 202 `{status:'validating'}`, or 200 when small (<= 500 rows) completing inline → `ImportBatchRead` with `status` `validated|failed_validation` and `counts{create,update,skip,warning,error}`
- `GET /api/v1/imports/{id}/preview?kind=create|update|skip|warning|error&cursor=&page_size<=50` → 200 keyset-paged rows `{row_no, action, record_preview, issues:[{column,code,message}]}` (IMP-006 dry-run preview)
- `GET /api/v1/imports/{id}/errors.csv` → 200 `text/csv` (IMP-005): `row_no, column, code, message, original_value` for every error and warning; values that begin with `=`, `+`, `-`, `@` are prefixed with `'` (CSV injection defence)
- `POST /api/v1/imports/{id}/commit` body `{mode: 'atomic'|'partial'}` (Idempotency-Key) → 202/200 `ImportBatchRead` | 409 `NotValidated` | 409 `HasErrors` (atomic mode with any error) | 409 `StaleValidation` (data changed since validation)

## Behaviour (IMP-004 to IMP-007)

1. Validation runs every check in one pass and reports **all** errors, not the first: type parse, required, enum, duplicate keys within the file, reference resolution (codes through `org.service.assert_usable`; project/BU lookups scoped to the org), permission to create/update each target (`import.run` plus the target's own permission, e.g. `project.create` at the row's BU/OU), and business rules registered by the template (`Template.validate_row(row, ctx)`). Nothing is written to target tables.
2. Classification: `create` (no existing record for the key), `update` (exists, and fields differ), `skip` (exists, identical), `warning` (valid but notable, e.g. a deactivated code about to be used on a historical date), `error` (cannot be committed).
3. Per-row `issues` carry `column`, a stable `code` and a plain-language `message` naming the offending value.
4. **Commit modes (IMP-007):** `atomic` commits every row in **one transaction** or none (refuses when any error exists); `partial` commits each valid row in its own savepoint, skips error rows, and the final report states exactly which rows were committed and which were skipped with recovery instructions ("fix rows 7 and 9 in the file and re-upload; committed rows will be skipped as unchanged"). Re-importing after a partial commit is safe because committed rows classify as `skip` (idempotent).
5. `StaleValidation`: a content hash of the target records the validation read (per-key version/updated_at) is rechecked inside the commit transaction under row locks; any drift refuses the commit and asks for re-validation. The commit also re-runs the row validation inside the transaction (never trusts the earlier verdict).
6. Everything produced here is org-scoped; the preview and error file respect `import.read`.

## Acceptance criteria

- [ ] A 100-row file with 7 distinct error kinds reports all of them in one validate call, in the preview and in `errors.csv` with correct row numbers
- [ ] `errors.csv` neutralises a cell value `=HYPERLINK("http://x")` by prefixing a quote
- [ ] Dry-run changes nothing: row counts of every target table are identical before and after validate
- [ ] Atomic commit with one error is refused; atomic commit of a clean file inserts every row in one transaction; an exception injected on row 50 leaves zero rows
- [ ] Partial commit inserts the valid rows, skips the invalid ones, reports both lists with recovery text; re-uploading the corrected file commits only the previously skipped rows
- [ ] `StaleValidation`: changing a target record between validate and commit makes commit return 409
- [ ] A user without the target permission gets row-level permission errors for those rows, not a 403 for the whole batch, and cannot commit them
- [ ] Preview endpoints page with `page_size=50` over a 5,000-row batch without repeats or gaps
- [ ] Foreign-tenant batch id → 404 on validate/preview/errors/commit (isolation gate entries)
- [ ] Migration up/down/data-preservation

## Amendments (preflight audit — authoritative, override anything above)

- **Execution:** validation and commit run **inline** in this story, capped at 5,000 rows (larger files get 422 `file_too_large_for_inline` until E08-S03 adds the background path). Remove the 202 wording for S02; E08-S03 makes large batches asynchronous.
- `import_row` and `import_result` carry `org_id NOT NULL` with a composite FK `(org_id, batch_id)` to `import_batch(org_id, id)` (add `UNIQUE (org_id, id)` on `import_batch` in S01's migration) and the standard tenant policy.
- **Staleness without row locks:** commit takes `pg_advisory_xact_lock(hash(org_id, template))` for its transaction, then re-runs full row validation (types, references, permissions, business rules) inside the transaction and compares the resulting create/update/skip plan with the validated plan; any difference is `StaleValidation`. Do not rely on row locks for rows that do not exist yet.
- **Warning example:** drop "deactivated code on a historical date" (`assert_usable` rejects inactive codes). A valid warning is, for instance, "update changes the project owner".
