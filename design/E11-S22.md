## Requirements (inlined)

- **VEN-015** — Performance scores must retain source transaction, scorer, period, rationale, and any dispute/adjustment history.
- AGENTS.md §3.2: authorization stays server-side; this story only stops the UI offering what the server will refuse (DECISIONS 238: a control renders only when the server lists it).

## Defect

`apps/web/src/components/vendors/performance/ScorecardSheet.tsx` (~52) renders `Add Score`, `Dispute` and
`Resolve` to every `vendor.view` caller. The server requires `purchase_order.view` + `vendor.view` for
`POST /vendors/{id}/scores`, `vendor.edit` for `…/disputes`, `vendor.approve` for `…/disputes/{did}/resolve`
(`apps/api/src/flo/api/vendors.py` ~395-425). A read-only user is led into 403s.

## Design

- `PerformanceRead` gains `actions: list[Literal["add_score", "dispute"]]`, computed in the
  service from the caller's permissions with the same codes the routes enforce (one table beside
  `ACTION_PERMISSIONS` in `vendors/service.py`, the pattern the vendor header already uses).
- **Resolve is per dispute** (pre-flight 1, 8 Nov 2026): the server also refuses the dispute's raiser
  (409 `separation_of_duty`, `vendors/performance.py` ~386) and an already-resolved dispute. So
  `DisputeRead` gains `can_resolve: bool` = caller holds `vendor.approve` **and** did not raise it **and** it
  is unresolved, computed in the service with the same checks the route makes.
- `ScorecardSheet` renders `Add Score` and `Dispute` only when listed in `actions`, and `Resolve` on a dispute
  only when its `can_resolve` is true. Regenerate the API client (`openapi.json` and `schema.ts`).

## Acceptance

- [ ] pytest: per role, `actions` lists exactly the actions whose route that role passes (vendor.view only → `[]`; purchasing user → `["add_score"]`; vendor editor → includes `dispute`), and each listed action's route succeeds for that role while each unlisted one is 403.
- [ ] pytest: `can_resolve` is false for the dispute's raiser even with `vendor.approve`, false once resolved, false without `vendor.approve`, and true otherwise; when true the resolve route succeeds.
- [ ] Playwright (`vendor-performance.spec.ts`): a stub with `actions: []` shows none of the three controls; the existing full-permission path still passes.
- [ ] axe both themes unchanged; `flo check --light` green.

## Plants

2. Drop the raiser check from `can_resolve`: the separation-of-duty pytest fails.
