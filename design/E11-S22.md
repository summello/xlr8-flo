## Requirements (inlined)

- **VEN-015** — Performance scores must retain source transaction, scorer, period, rationale, and any dispute/adjustment history.
- AGENTS.md §3.2: authorization stays server-side; this story only stops the UI offering what the server will refuse (DECISIONS 238: a control renders only when the server lists it).

## Defect

`apps/web/src/components/vendors/performance/ScorecardSheet.tsx` (~52) renders `Add Score`, `Dispute` and
`Resolve` to every `vendor.view` caller. The server requires `purchase_order.view` + `vendor.view` for
`POST /vendors/{id}/scores`, `vendor.edit` for `…/disputes`, `vendor.approve` for `…/disputes/{did}/resolve`
(`apps/api/src/flo/api/vendors.py` ~395-425). A read-only user is led into 403s.

## Design

- `PerformanceRead` gains `actions: list[Literal["add_score", "dispute", "resolve"]]`, computed in the
  service from the caller's permissions with the same codes the routes enforce (one table beside
  `ACTION_PERMISSIONS` in `vendors/service.py`, the pattern the vendor header already uses).
- `ScorecardSheet` takes `actions` and renders each control only when listed. Regenerate the API client.

## Acceptance

- [ ] pytest: per role, `actions` lists exactly the actions whose route that role passes (vendor.view only → `[]`; purchasing user → `["add_score"]`; vendor manager → includes `dispute`, `resolve` as its permissions allow), and each listed action's route succeeds for that role while each unlisted one is 403.
- [ ] Playwright (`vendor-performance.spec.ts`): a stub with `actions: []` shows none of the three controls; the existing full-permission path still passes.
- [ ] axe both themes unchanged; `flo check --light` green.

## Plants

1. Ignore `actions` in the sheet: the empty-actions Playwright test fails.
2. Map `resolve` to `vendor.edit`: the per-role pytest fails.
