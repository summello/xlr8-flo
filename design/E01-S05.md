# E01-S05 — Deploy API to Cloud Run and SPA to Cloudflare Pages from CI

**Epic** E01 · **M0** · **chore/L** · after **E01-S04** · tags: `security`

## Requirements

- **SEC-003** — All external traffic must use authenticated TLS; insecure transport must redirect or fail closed as appropriate.
- **SEC-005** — Secrets must not be stored in source code, browser bundles, logs, or ordinary configuration files.
- **COMP-004** — Deployments must externalize configuration and avoid environment-specific code branches.
- **SEC-012** — Dependency scanning, secret scanning, static analysis, dynamic testing, and an SBOM must be part of release controls.

## Deliverable

`main` deploys itself. This is the story that turns the repository into a running product at a real domain — and the story that makes the *deployed artefact*, not just the source tree, a scanned and resource-bounded thing.

## Behaviour

### Deploy

1. **Authentication to GCP uses Workload Identity Federation.** No service-account JSON key is created, downloaded, or stored — a long-lived key in a GitHub secret is exactly what SEC-005 forbids. CI holds only `GCP_WIF_PROVIDER`, `GCP_DEPLOY_SA`, `GCP_PROJECT`.
2. **The image is built in CI, scanned, pushed, and deployed by digest.** The current `gcloud run deploy --source apps/api` is replaced: `--source` builds server-side in Cloud Build, which leaves no local artefact to scan before it is promoted, and pins nothing. Instead:
   - `docker build -f apps/api/Containerfile` → local tag
   - Trivy image scan (below) — **gates the push**
   - `docker push` to Artifact Registry
   - `gcloud run deploy flo-api --image <registry>/flo-api@sha256:<digest>`

   Deploying by digest, never by tag, is the same SEC-013 rule the base image already follows: a tag can be repointed, a digest cannot.
3. Deploy order is **migrate, then serve** — never the reverse:
   - `gcloud run jobs execute flo-migrate --wait` runs Alembic and must exit 0
   - `gcloud run deploy flo-api …`
   - a failed migration aborts the deploy and leaves the previous revision serving
4. Secrets reach the container through Secret Manager references (`--set-secrets DATABASE_URL=flo-database-url:latest`), never as literal `--set-env-vars`.
5. The SPA builds and deploys to Cloudflare Pages via `wrangler`. **The bundle must contain no secret** — only `VITE_API_BASE_URL` is injected, and CI greps the built assets for `sk-`, `-----BEGIN`, and the project id before publishing.
6. TLS and HSTS terminate at Cloudflare; the Cloud Run service rejects plain HTTP. Cloudflare is configured Full (strict).
7. Rollback is one command against the previous Cloud Run revision, documented in `infra/SETUP.md`.
8. Artifact Registry pruning to the last 3 images stays as-is (free tier is 0.5 GB).

### Public origin — one host, path-split (D-17)

`docs/claude-plan.md` D-17 fixes the public origin as **`xlr8flo.summello.com`**, single origin for both halves. Cloudflare splits by path: `/api/*` proxies to Cloud Run, everything else serves from Pages. The browser never makes a cross-origin request.

9. Cloudflare routes `xlr8flo.summello.com/api/*` to the Cloud Run service and everything else to the Pages project. A Worker route is the mechanism; the Cloud Run service URL is the origin.
10. **`VITE_API_BASE_URL` becomes the relative string `/api`.** No absolute API URL is compiled into the bundle. This also removes the Cloud Run hostname from the shipped assets, which is one less internal name published (SEC-011).
11. **No CORS middleware is added, and none is configured.** Same origin needs none. If a future story finds it needs CORS, that is a signal D-17 has been violated, not a reason to add a header.
12. Cloud Run ingress is restricted so the service is reachable through Cloudflare rather than directly from the internet. Document the exact setting in `infra/SETUP.md`; if the free tier cannot restrict it as tightly as intended, record what was achievable in `notes.followup` rather than silently leaving it open.

Session cookies themselves are E02-S02 and stay out of this story. This story's job is to make the `__Host-` prefix *available* to it by delivering a single origin.

### Container-image scanning (SEC-012)

CI today runs Trivy with `scan-type: fs` only. That scans the *source tree's* dependency manifests. It has never scanned the thing that actually runs: the built image, with its Debian base layer and its resolved OS package set. A CVE in `libssl` inside the runtime layer is invisible to the current gate.

13. Add a second Trivy invocation in the `deploy` job, on the **built image**, before the push:
   - `scan-type: image`, `severity: CRITICAL,HIGH`, `exit-code: 1`, `ignore-unfixed: true` — identical thresholds to the existing filesystem scan, so one policy governs both.
   - `format: sarif`, uploaded with `category: trivy-container-image`. **A distinct category from the existing `trivy-dependency-scan`** — SARIF uploads sharing a category overwrite each other, and the second scan would silently erase the first's findings from the Security tab.
   - Pin the action by digest, as the existing one is.
14. **The scan fails closed.** A failed image scan aborts before `docker push`, so an unscanned or vulnerable image never reaches Artifact Registry and never reaches a revision. Do not add `continue-on-error`.
15. The SBOM E01-S04 produces stays source-tree-scoped. Add an image SBOM (`trivy image --format cyclonedx`) as a build artefact alongside it, so the deployed artefact has a manifest and not only its source does.

### Argon2 resource bound

E02-S01 shipped argon2id at `memory_cost = 64 MiB`, `parallelism = 4`, unbounded in concurrency. The deploy command sets `--concurrency 80` and specifies **no `--memory` and no `--cpu`**, so Cloud Run applies its 512 MiB default. Eight simultaneous logins request 512 MiB of hashing memory on a 512 MiB instance. The instance is OOM-killed, in-flight requests on it die, and the killed instance is replaced — which is a denial of service reachable by an unauthenticated caller at the login endpoint, with no credentials and no volume worth calling an attack.

This is a **resource** bound. It is not login rate limiting, which is E19-S03 and stays there.

16. Add `identity_argon2_max_concurrency` to `kernel/config.py` (default `4`, `ge=1`, `le=32`). A module-level `asyncio.Semaphore` in `kernel/identity/local.py` guards **every** argon2 operation — `hash`, `verify`, and the dummy verify — so at most N run at once. Run the hash itself in a thread (`asyncio.to_thread`); argon2-cffi is blocking and releases the GIL, so holding the event loop for 250–500 ms per login is its own availability bug.
17. **Acquire the permit before branching on whether the account exists.** If the semaphore is taken only on the real-verify path, a saturated server answers unknown emails fast and known emails slow — the semaphore becomes precisely the enumeration oracle AUTH-007 and E02-S01's timing test exist to close. The permit is acquired first, and the dummy verify consumes one exactly as a real verify does.
18. Waiting for a permit is bounded (`asyncio.wait_for`, 2 s). On timeout the endpoint returns **503** with `Retry-After`, not a queued request and not a 401. The 503 is independent of the submitted email, so it leaks nothing.
19. **The memory invariant is asserted, not documented.** Required instance memory is
    `(memory_cost_kib / 1024) × max_concurrency + 256 MiB baseline`
    — at the defaults, `64 × 4 + 256 = 512 MiB`, so `--memory 1Gi` carries real headroom. Enforce it in two places:
    - **At startup**: read the cgroup v2 limit from `/sys/fs/cgroup/memory.max`; if it is readable and below the requirement, refuse to start with a clear message. If unreadable or `max` (local dev), skip — do not guess.
    - **In CI**: a check parses the `--memory`, `--cpu` and `--concurrency` flags out of the deploy workflow and asserts they satisfy the invariant against the config defaults. This is the half that cannot be skipped, and it is what stops a future story raising `memory_cost` without raising the instance.
20. Deploy with `--memory 1Gi --cpu 2`. `parallelism = 4` on a single vCPU serialises the lanes and inflates wall-clock per hash, so E02-S01's 250–500 ms target must be **re-measured on the deployed revision**, not assumed from laptop timings.

## Acceptance criteria

- [ ] A push to `main` deploys both API and SPA with no human step
- [ ] No service-account JSON exists in any secret, file, or log
- [ ] A deliberately failing migration aborts the deploy and the prior revision keeps serving
- [ ] `curl http://<domain>` redirects to HTTPS; HSTS header present
- [ ] Built SPA assets contain no `sk-`, no `-----BEGIN`, no GCP project id — asserted in CI
- [ ] `/readyz` returns 200 against Neon from the deployed revision
- [ ] Rollback to the previous revision succeeds and is documented
- [ ] The SPA and the API answer on the **same origin**: `xlr8flo.summello.com/` serves the app, `xlr8flo.summello.com/api/healthz` reaches Cloud Run
- [ ] Built assets contain no absolute API URL and no Cloud Run hostname
- [ ] No CORS middleware or `Access-Control-Allow-Origin` header exists anywhere in the API
- [ ] The deployed revision references an image **by `sha256:` digest**, not a tag
- [ ] **Image scan bites**: a build whose Containerfile pins a base with a known CRITICAL fails the `deploy` job before `docker push`, and no image reaches Artifact Registry — evidence linked in the PR body, change reverted
- [ ] Image-scan SARIF appears in the Security tab under its own category, and the existing dependency-scan findings are **still present** after it uploads
- [ ] An image SBOM is attached to the run alongside the source SBOM
- [ ] At most `identity_argon2_max_concurrency` argon2 operations run concurrently — proven by a test that fires 32 concurrent logins and asserts peak in-flight hashes never exceeds the configured bound
- [ ] The permit is acquired on the unknown-email path too: E02-S01's timing test still passes with the semaphore saturated (median unknown-email vs wrong-password within 10 %)
- [ ] A 33rd concurrent login that waits past 2 s receives **503 with `Retry-After`**, never 401, never 200
- [ ] Startup refuses to boot when the cgroup memory limit is below the computed requirement; boots normally when the limit is unreadable
- [ ] **The CI invariant check bites**: raising `identity_argon2_memory_cost_kib` in config without raising `--memory` fails CI; reverting passes
- [ ] Measured p50 login latency on the deployed revision is within the 250–500 ms band E02-S01 specifies

## Out of scope

Neon/R2/Secret Manager provisioning (E01-S06) · custom domain purchase (operator task, tracked on the board) · login rate limiting and account lockout (E19-S03) · raising the argon2 cost parameters themselves — this story bounds concurrency at the existing values, it does not retune them.

> **Operator prerequisite** — this story cannot be verified end to end until a GCP project with WIF, a Cloudflare account with an API token, and a registered domain exist. They are on the delivery board under "Waiting on you". The argon2 bound, the CI invariant check and the image scan are all verifiable without them and must not wait.
