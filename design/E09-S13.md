## Requirements

_Pending: the operator writes these._ The open points they must settle:

1. **Standalone funding (D-M2-5 versus canvas Decision 99).** Today a standalone requisition's
   final approval creates a top-level project and posts a Direct allocation for the estimate, so
   approval **creates budget**. Decision 99 says an allocation draws on the organization's available
   budget and there is no separate unallocated pool. Operator, 13 Oct 2026: D-M2-5 stands as an
   explicit exception until this story. Note from the map below: every Direct allocation (manual,
   imported or standalone approval) creates budget the same way, so a pool would apply to all of
   them, not only to standalone requests.
2. **Who may assign a standalone request to an existing project.** E09-S06 implements: the final
   approver must hold `requisition.approve` on the assigned project's scope, or 403. Unconfirmed.
3. **Master-code re-check at approval.** E09-S06 copies `department_code` and `ledger_account_code`
   from the requisition, validated at submit, onto the generated or standalone project and onto
   every ledger entry it posts, without re-checking them. A code retired between submit and approval
   reaches the project, and from there the purchase orders (M3). Open choice for the operator: at
   approval, a retired code **rejects** the approval, **returns the requisition for changes**, or
   **lets the approver substitute an active code**. Each is a different state transition.
4. **Does any Direct allocation create budget?** Not only standalone approvals: every Direct
   allocation (Flow 1) posts budget with no organization-level pool behind it. That covers the manual
   allocation endpoint, the `budget_allocations` import template, any top-level project in either
   funding mode, and every project in `roll_up`. If Decision 99 holds, define the pool these draw
   from, who funds it, and whether existing allocations need an opening entry against it.
5. **Should allocations go through approval?** Today they never do. Only adjustments and transfers
   route through approval, and only when the BU has a published `budget_change` workflow
   (Flows 2–3). An allocation posts immediately for anyone holding `budget.allocate`. Decide whether
   allocations, including those made by imports and by a standalone approval, need their own
   approval route.
6. **What happens to a standalone-created project when its requisition stops** (withdraw after
   approval, cancel, expiry)? E09-S07 leaves the project and its allocation in place; the reservation
   is released, so the created budget sits on an orphaned project for someone to move or reverse.
   Decide whether stopping the requisition should reverse the allocation, close the project, or
   leave both (and who is told).
7. **A ledger-account-only amendment** (E09-S08): changing only `ledger_account_code` with the same
   estimate restarts approval but leaves the reservation's ledger entry on the old account. Decide
   whether such an amendment re-reserves under the new code (release and reserve) or keeps the
   original posting.

## Current budget workflow — every flow, as built (13 Oct 2026)

Context for the requirements, mapped from the code on `milestone/M2-governed-demand` plus E09-S06
(in review). File references are under `apps/api/src/flo/modules/`.

### The model

- **One balance row per project** (`project_balance`): four buckets, `allocated`, `reserved`,
  `committed` and `actual`, plus a generated `available = allocated − reserved − committed − actual`.
  Updated in the same transaction as each ledger row (D-11); a nightly job reports drift and never
  corrects it.
- **Append-only ledger** (`ledger_entry`). Every row carries project, bucket, signed amount,
  currency, source document, effective date, actor, **department code and ledger account code**, and
  an idempotency key. Entry types and their buckets (`budget/ledger_rules.py`):

  | Entry type | Bucket | Sign | Meaning |
  |---|---|---|---|
  | allocation | allocated | + | Budget given to a project |
  | adjustment | allocated | ± | Budget added or removed directly |
  | transfer | allocated | ± (paired) | Budget moved between projects |
  | reservation | reserved | + | Requisition holds funds |
  | commitment | committed | + | PO holds funds (M3; converts a reservation) |
  | actual | actual | + | Spend recorded (M3+; converts a commitment) |
  | release | reserved or committed | − | Frees a hold, exactly once per remainder |
  | reversal | any | mirror | Correction of a posted entry |

- **Every posting** (`budget/ledger.py` `post_entry`): lock the project's balance row `FOR UPDATE`,
  replay on a known idempotency key, check currency, quantize through `kernel/money.py`, check the
  fiscal period is open (releases exempt, D-M1-12), check sign, check the project's status allows it
  (below), then refuse if it would take `available` below zero, unless the BU's
  `allow_negative_budget` setting is on. Insert, update the balance, and write an audit row, all in
  one transaction.
- **Project status gates postings** (`projects/service.py` `assert_posting_allowed`): allocations
  in `draft` or `active` (an outgoing negative amount is always allowed); reservations and
  commitments only in `active`; actuals in `active` or `deferred`; releases and reversals always.

### Flow 1 — Allocate budget

`POST /api/v1/projects/{id}/budget/allocations`, permission `budget.allocate`. Also the
`budget_allocations` import template (`imports/templates/budget_allocations.py`), same rules.
The organization's **funding mode** (setting `funding_mode`, resolved from the BU up to the
organization, default `roll_down`, locked once any ledger entry exists) decides the shape
(`budget/funding_policy.py`):

- **Direct** (a top-level project in either mode, or any project in `roll_up`): one `allocation`
  entry on the project. **This creates budget from nothing**: no organization-level pool is checked.
- **From the parent** (a child project in `roll_down`): two legs, `−amount` on the parent and
  `+amount` on the child, in one transaction, never letting the parent go negative. Needs
  `budget.allocate` on the parent too. Evidence is required if the BU sets
  `budget.evidence_required`.

Allocations are **not** routed through approval workflows.

### Flow 2 — Adjust budget

`POST /api/v1/projects/{id}/budget/adjustments`, permission `budget.adjust`. A signed `adjustment`
on the project's allocated bucket, reason ≥ 10 characters. Adds or removes budget directly.
**If the BU has a published `budget_change` workflow**, the adjustment is dry-run (every check,
then rolled back) and stored as a pending `budget_change_request`; it posts only when that workflow
approves it (`budget/change_requests.py`, `budget/approval.py`). Rejected or withdrawn requests post
nothing.

### Flow 3 — Transfer budget

`POST /api/v1/budget/transfers`, permission `budget.transfer` on **both** projects. Same tree only.
Siblings, or `roll_up` mode: two legs, out of the giver and into the recipient. Otherwise, in
`roll_down`: the amount walks the hierarchy through the lowest common ancestor, one out/in pair per
hop. Every node on the path is locked in id order. Receiving nodes must be `draft` or `active`;
currencies must match; evidence rule as in allocation. Routed through the `budget_change` workflow
exactly like an adjustment when one is published.

### Flow 4 — Project-linked requisition: submit reserves (D-M2-15)

`POST /api/v1/requisitions/{id}/transitions` to `approval_pending`, permission `requisition.submit`
(`requisitions/lifecycle.py`). Lock the project's balance row, validate (REQ-011 funds check under
the lock), post a `reservation` for the estimate (round 1, key `req:{id}:reserve:1`, with the
requisition's department and ledger account codes), then start the approval instance, all in one
transaction. Two concurrent submissions against funds for one: exactly one succeeds.

### Flow 5 — Requisition approval outcomes (`requisitions/approval.py`, E09-S06 in review)

Run inside the approval decision's transaction.

- **Approved, project-linked:** keep the submit reservation on the parent project. Generate an
  `active` sub-project (parent's BU and currency, requisition's codes, owner = requester, marked
  `generated_by_requisition_id`). **The sub-project holds no allocation and no reservation.**
- **Approved, standalone, new project (D-M2-5):** the final approver needs `budget.allocate` on the
  requisition's BU. Create a top-level `active` project, post a **Direct allocation** for the
  estimate (Flow 1, so budget is created), then reserve it (round 1).
- **Approved, standalone, assigned to an existing project:** the approver needs
  `requisition.approve` on that project. The project must be active, not itself generated, at depth
  under 5, and in the same currency, with enough available funds. Reserve round 1, then generate a
  sub-project under it.
- **Withdrawn** (from pending or draft) and **cancelled:** release the live reservation remainder.
- **Rejected:** release. **Rejected with return to draft:** release, and the requisition goes back
  to `draft`.
- **Returned for changes:** keep the reservation; the requisition goes back to `draft`.

### Flow 6 — Resubmit

Submitting again after a return: if the project changed or the estimate differs from the remaining
reservation, release the round's remainder and reserve the new total as round N+1 under the same
lock (`requisitions/lifecycle.py`, `requisitions/funding.py`).

### Flow 7 — Release (`budget/reservations.py`)

Releases the remainder of one reservation (or a stated part), never more than remains, refused on a
reversed reservation, idempotent per key (`req:{id}:release:{round}:{reason}`), exempt from fiscal
period closure. **Still to come in M2:** E09-S07 adds expire and reduce, and proves exactly-once
release on every path.

### Flow 8 — Commit, actual, reversal (service only, no caller yet)

`budget/postings.py`: `commit` converts a reservation into a commitment; `record_actual` converts a
commitment into actual spend; `release_commitment` frees a commitment; `reverse_entry` posts an
append-only correction. M3's purchase orders are the first callers. **Open M3 question from
E09-S06:** does a PO commit against the parent project, which holds the reservation, or against the
requisition-generated sub-project, which holds nothing?

### Flow 9 — Read and reconcile

`GET /projects/{id}/balance`, `/balance/aggregate` (subtree totals per currency, one snapshot),
`/ledger` (paged entries), `/balance/reconcile`, `/api/v1/budget/summary`, and the nightly
reconciliation (`budget/reconcile.py`, `/budget/reconciliation/status` and `/drift`): reports drift
between balance rows and the ledger, never repairs it.
