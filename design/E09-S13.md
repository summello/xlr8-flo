## How budget works — a guide for users

*Written for the people who use XLR8 FLO. Where M2 is still changing something, it says so.*

### Where budget comes from
Your organisation's money lives in **projects**. Each year's approved capital projects, and any special
projects, are set up with a budget. There is no separate central pot: every amount you can spend belongs
to a project.

A project is created in one of two ways:
- **Create Project** (the button on the Projects screen, or an Excel import), by people whose role allows
  it. You name one or more **sponsors**: the people who fund or approved it. A project can stand alone with
  its own new budget, or sit under an existing **main project** and take its budget from it. Either way it
  goes through a project approval before it becomes active. *(Arriving early in M3.)*
- **A Project Request** that has been fully approved (see below).

### Asking for money
- **Requisition** — the everyday way to ask to spend. You pick the main project that pays for it. You
  cannot raise one against a sub-project that another requisition created. When you submit, the amount is
  **reserved** on that project straight away, so two people cannot spend the same money.
- **Project Request** — for managers and leadership who want to start something new that no project
  covers yet. Only people whose role allows it see this option. You name the sponsors. It has its own
  approval route, set up separately from requisitions. *(E09-S15.)*

### What approval does
- **An approved requisition** becomes a **sub-project** under the main project you picked. The reserved
  amount moves with it: the main project hands that budget to the sub-project, which holds it from then
  on. Purchase orders later spend from the sub-project only, so it can run on its own without touching the
  main project each time. *(Moving the money into the sub-project arrives with E09-S16; until then it stays
  reserved on the main project.)*
- **An approved Project Request** becomes a new **main project** with its own budget. Nothing is created
  until the last approver says yes.
- If a department or ledger-account code has **expired** while the document was waiting, the approver
  whose turn it is must replace it before approving. They can still reject without replacing it.
  *(E09-S18.)*

### What happens if a request stops
- **Before approval** (withdrawn, rejected, cancelled, expired): the reservation is released, exactly once.
  "Return for changes" keeps it while the requester edits.
- **After approval, before anything is bought** (withdrawn or cancelled during sourcing or purchasing):
  - a sub-project is marked **Abandoned** and its budget goes back to the main project, with an entry on
    both *(E09-S16)*;
  - a project made from a Project Request is marked **Abandoned**; it stops counting in the budget
    totals and shows in a separate **Abandoned** group instead *(E09-S15)*.

### Spending it *(M3)*
A purchase order spends from the project its requisition created. Issuing it turns the reservation into a
**commitment**; receiving and paying turns that into **actual** spend.

### What you can and cannot change
- A draft can be edited freely, and deleted *(soft delete, early M3; deleted drafts are kept, and a Bin to
  view them is on the future roadmap)*.
- After approval, the amount and lines can be amended through an approved amendment. The department,
  ledger account and project **cannot** be changed by amendment. To move budget, raise a **transfer** or
  **adjustment request**; those have their own approval.
- An expired code on an approved document is replaced by a **Project Manager**. Until then, sourcing and
  purchasing documents for it are blocked, and the code is flagged wherever the project appears.

### When an approval route is missing
Some actions need an approval route that an administrator publishes first: Project Requests, creating a
project with budget, and budget transfers, adjustments and allocations. Until one is published, the action
is refused with a message telling you to set it up. *(E09-S17.)*

### Seeing it
Each project shows **allocated**, **reserved**, **committed**, **actual** and **available** amounts.
Summaries roll a project and everything under it up per currency. Abandoned projects made from Project
Requests are shown apart from the totals.

## Operator decisions, 14 Oct 2026 (D-M2-16 to D-M2-28)

1. **No organisation pool.** Budget lives in projects. The organisation-pool workflow is on **M7 — Future Roadmap**. D-M2-5 (standalone approval creates budget) is superseded by 3 and 7.
2. Regular requisitions select an existing **main** project; requisition-generated sub-projects cannot be selected (REQ-003, already enforced).
3. Standalone requisitions become **Project Requests**: own document type and workflow, own UI name, created only with `project_request.create`. Everyone else must pick a budget source. (E09-S15)
4. On approval a regular requisition's **sub-project draws from its main project**: main → sub transfer, reservation on the sub-project, one transaction. (E09-S16)
5. Direct project creation (button, Excel) is role-gated, needs one or more sponsors, may be standalone or a child, goes through the project approval workflow, and posts an entry on the project and on its main project. (E22-S01, early M3)
6. **Block until set up:** with no published workflow, Project Requests, project creation with budget, and budget transfers, adjustments and allocations refuse. (E09-S17)
7. A Project Request's project is created only on full approval. Cancelled later: standalone project → `abandoned`, excluded from totals into an Abandoned category; sub-project → `abandoned`, funds back to the main project. (E09-S15, E09-S16)
8. Code, account and project changes by amendment are **blocked**; budget moves go through transfer and adjustment requests. Release-and-re-reserve on a code change is on **M7**. (E09-S18)
9. Project Request creation is role-gated (3).
10. **Expired codes:** the current approver must substitute to approve, or may reject without substituting. After approval, M3 sourcing and purchasing documents are blocked until a Project Manager substitutes. Flagged on project screens and wherever such a project is selected. (E09-S18)
11. A purchase order draws only against its **immediate project** (the sub-project). For the M3 E13 packets.
12. Every document can be **soft-deleted while draft** (`deleted` status, hidden, audited, number never reused). A Bin/Trash view is on **M7**. (E22-S02)
13. One audit helper instead of twelve, behaviour-preserving. (E22-S03)

## Story — roles and permission catalogue (this story's code scope)

### Why first
The API checks permission codes that no role is ever granted. Migrations 0013, 0015, 0016, 0017, 0019,
0025, 0027 and 0028 insert codes into `permission` (`project.read`, `project.update`, `project.submit`,
`project.complete`, `project.close.override`, `budget.allocate`, `budget.adjust`, `ledger.read`,
`fiscal.*`, `org.unit.*`, `org.setting.manage`, `master.read`, `master.manage`, `import.run`,
`import.read`, `fx.read`) but grant none of them. `seed_baseline_roles`
(`modules/identity/service.py:464`) grants only `BASELINE_ROLE_PERMISSIONS`, built from
`PERMISSION_CODES` (`modules/identity/models.py:121`), which lacks them. A new tenant's Organization
Administrator therefore cannot allocate budget, read the ledger, update a project or run an import. Every
role-gated decision above (3, 5, 9, 10) depends on this being right.

### Requirements
- **USR-007 / SEC** — authorization is role-based, default-deny, server-side, and every permission the API checks is grantable through a baseline role.
- **TEN-010** — isolation holds for every changed endpoint (none expected; the change is grants).

### Behaviour

   listed above plus the two new ones: `project_request.create`, `master_code.substitute`. Keep
   `project.view`/`project.edit` only if something checks them; otherwise retire them from the catalogue
   and from baseline roles in favour of `project.read`/`project.update` (grep first; record the result).

3. **Baseline grants** (`BASELINE_ROLE_PERMISSIONS`):
   - Organization Administrator: all codes (unchanged rule, now complete).

### The model

- **One balance row per project** (`project_balance`): four buckets, `allocated`, `reserved`,
  `committed` and `actual`, plus a generated `available = allocated − reserved − committed − actual`.
  Updated in the same transaction as each ledger row (D-11); a nightly job reports drift and never
  corrects it.
- **Append-only ledger** (`ledger_entry`). Every row carries project, bucket, signed amount,
  currency, source document, effective date, actor, **department code and ledger account code**, and
  an idempotency key. Entry types and their buckets (`budget/ledger_rules.py`):

  | Entry type | Bucket | Sign | Meaning |
  |---|---|---|---|
  | allocation | allocated | + | Budget given to a project |
  | adjustment | allocated | ± | Budget added or removed directly |
  | transfer | allocated | ± (paired) | Budget moved between projects |
  | reservation | reserved | + | Requisition holds funds |
  | commitment | committed | + | PO holds funds (M3; converts a reservation) |
  | actual | actual | + | Spend recorded (M3+; converts a commitment) |
  | release | reserved or committed | − | Frees a hold, exactly once per remainder |
  | reversal | any | mirror | Correction of a posted entry |

- **Every posting** (`budget/ledger.py` `post_entry`): lock the project's balance row `FOR UPDATE`,
  replay on a known idempotency key, check currency, quantize through `kernel/money.py`, check the
  fiscal period is open (releases exempt, D-M1-12), check sign, check the project's status allows it
  (below), then refuse if it would take `available` below zero, unless the BU's
  `allow_negative_budget` setting is on. Insert, update the balance, and write an audit row, all in
  one transaction.
- **Project status gates postings** (`projects/service.py` `assert_posting_allowed`): allocations
  in `draft` or `active` (an outgoing negative amount is always allowed); reservations and
  commitments only in `active`; actuals in `active` or `deferred`; releases and reversals always.

### Flow 1 — Allocate budget

`POST /api/v1/projects/{id}/budget/allocations`, permission `budget.allocate`. Also the
`budget_allocations` import template (`imports/templates/budget_allocations.py`), same rules.
The organization's **funding mode** (setting `funding_mode`, resolved from the BU up to the
organization, default `roll_down`, locked once any ledger entry exists) decides the shape
(`budget/funding_policy.py`):

- **Direct** (a top-level project in either mode, or any project in `roll_up`): one `allocation`
  entry on the project. **This creates budget from nothing**: no organization-level pool is checked.
- **From the parent** (a child project in `roll_down`): two legs, `−amount` on the parent and
  `+amount` on the child, in one transaction, never letting the parent go negative. Needs
  `budget.allocate` on the parent too. Evidence is required if the BU sets
  `budget.evidence_required`.

Allocations are **not** routed through approval workflows.

### Flow 2 — Adjust budget

`POST /api/v1/projects/{id}/budget/adjustments`, permission `budget.adjust`. A signed `adjustment`
on the project's allocated bucket, reason ≥ 10 characters. Adds or removes budget directly.
**If the BU has a published `budget_change` workflow**, the adjustment is dry-run (every check,
then rolled back) and stored as a pending `budget_change_request`; it posts only when that workflow
approves it (`budget/change_requests.py`, `budget/approval.py`). Rejected or withdrawn requests post
nothing.

### Flow 3 — Transfer budget

`POST /api/v1/budget/transfers`, permission `budget.transfer` on **both** projects. Same tree only.
Siblings, or `roll_up` mode: two legs, out of the giver and into the recipient. Otherwise, in
`roll_down`: the amount walks the hierarchy through the lowest common ancestor, one out/in pair per
hop. Every node on the path is locked in id order. Receiving nodes must be `draft` or `active`;
currencies must match; evidence rule as in allocation. Routed through the `budget_change` workflow
exactly like an adjustment when one is published.

### Flow 4 — Project-linked requisition: submit reserves (D-M2-15)

`POST /api/v1/requisitions/{id}/transitions` to `approval_pending`, permission `requisition.submit`
(`requisitions/lifecycle.py`). Lock the project's balance row, validate (REQ-011 funds check under
the lock), post a `reservation` for the estimate (round 1, key `req:{id}:reserve:1`, with the
requisition's department and ledger account codes), then start the approval instance, all in one
transaction. Two concurrent submissions against funds for one: exactly one succeeds.

### Flow 5 — Requisition approval outcomes (`requisitions/approval.py`, E09-S06 in review)

Run inside the approval decision's transaction.

- **Approved, project-linked:** keep the submit reservation on the parent project. Generate an
  `active` sub-project (parent's BU and currency, requisition's codes, owner = requester, marked
  `generated_by_requisition_id`). **The sub-project holds no allocation and no reservation.**
- **Approved, standalone, new project (D-M2-5):** the final approver needs `budget.allocate` on the
  requisition's BU. Create a top-level `active` project, post a **Direct allocation** for the
  estimate (Flow 1, so budget is created), then reserve it (round 1).
- **Approved, standalone, assigned to an existing project:** the approver needs
  `requisition.approve` on that project. The project must be active, not itself generated, at depth
  under 5, and in the same currency, with enough available funds. Reserve round 1, then generate a
  sub-project under it.
- **Withdrawn** (from pending or draft) and **cancelled:** release the live reservation remainder.
- **Rejected:** release. **Rejected with return to draft:** release, and the requisition goes back
  to `draft`.
- **Returned for changes:** keep the reservation; the requisition goes back to `draft`.

### Flow 6 — Resubmit

Submitting again after a return: if the project changed or the estimate differs from the remaining
reservation, release the round's remainder and reserve the new total as round N+1 under the same
lock (`requisitions/lifecycle.py`, `requisitions/funding.py`).

### Flow 7 — Release (`budget/reservations.py`)

Releases the remainder of one reservation (or a stated part), never more than remains, refused on a
reversed reservation, idempotent per key (`req:{id}:release:{round}:{reason}`), exempt from fiscal
period closure. **Still to come in M2:** E09-S07 adds expire and reduce, and proves exactly-once
release on every path.

### Flow 8 — Commit, actual, reversal (service only, no caller yet)

`budget/postings.py`: `commit` converts a reservation into a commitment; `record_actual` converts a
commitment into actual spend; `release_commitment` frees a commitment; `reverse_entry` posts an
append-only correction. M3's purchase orders are the first callers. **Open M3 question from
E09-S06:** does a PO commit against the parent project, which holds the reservation, or against the
requisition-generated sub-project, which holds nothing?

### Flow 9 — Read and reconcile

`GET /projects/{id}/balance`, `/balance/aggregate` (subtree totals per currency, one snapshot),
`/ledger` (paged entries), `/balance/reconcile`, `/api/v1/budget/summary`, and the nightly
reconciliation (`budget/reconcile.py`, `/budget/reconciliation/status` and `/drift`): reports drift
between balance rows and the ledger, never repairs it.
