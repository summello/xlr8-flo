# E13-S31 — Start Evaluation from a closed RFQ, by keyboard

**Epic** E13 · **M3** · **ui/S** · after **E12-S03**, **E12-S10**, **E12-S11**, **E12-S15** · tags: `ui`
Origin: E13-S29 pre-flight 7 (9 Nov 2026). ACC-008 is an M3 exit criterion.

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **UI authority:** `design-system/MASTER.md`, `apps/web/src/styles/tokens.css`, `design-system/pages/sourcing.md`
> §2 (never disabled to signal an error), §4 item 4 (RFQ detail) and §6 (keyboard).

## Requirements (inlined)

- **ACC-008** — A complete project-to-PO workflow is operable without a mouse.
- **SRC-004** — RFQs must support Draft, Published, Closed, Under Evaluation, Awarded, and Cancelled states.

## Defect

E12-S03 shipped `POST /api/v1/sourcing/rfqs/{id}/start-evaluation` (`apps/api/src/flo/api/sourcing.py` ~355,
`RfqLifecycle.start_evaluation`, `modules/sourcing/lifecycle.py` ~415: `closed` → `under_evaluation`, permission
`rfq.edit` on the RFQ's unit). Nothing in the web app calls it. `components/sourcing/RfqHeaderActions.tsx` ~12-20
offers only `Open Comparison` for a closed RFQ, the comparison page only GETs, and award creation requires
`under_evaluation` (`sourcing/awards.py` ~565-572). So no user can get from a closed RFQ to an award in the
product, with a keyboard or otherwise.

## Design

No API, schema, migration, permission or token change. `POST .../start-evaluation` is already in
`apps/web/src/api/generated/schema.ts`; do not regenerate the client and do not hand-write a type.

**New `apps/web/src/components/sourcing/StartEvaluation.tsx`,** props `{ rfq: Rfq; navigate: (href: string) => void }`,
one real `<button type="button">` labelled `Start Evaluation` with a Phosphor `ClipboardText` icon
(`aria-hidden="true"`, `weight="regular"`). No dialog: the transition moves no money, tells no vendor, and
`Open Comparison` is offered in both states.

**In `RfqHeaderActions.tsx`,** add to the actions array, immediately before the `compare` entry:
`rfq.status === "closed" && rfq.can_edit ? <StartEvaluation key="start-evaluation" rfq={rfq} navigate={navigate} /> : null`.
`rfq.can_edit` is the server's own answer (`api/sourcing.py` ~185, `permits(request, "rfq.edit", target)`), the same
permission the route requires. It decides only whether the control is drawn; the route still refuses without it, and
the pytest below proves that.

**The request,** the same shape as RFQ publish after ef53aa85 (`components/sourcing/editor/Editor.tsx` ~43-44, ~79-81):

```tsx
const key = useRef<string | null>(null), inFlight = useRef(false);
const start = async () => {
  if (inFlight.current) return;
  inFlight.current = true; setBusy(true); setMessage(null);
  key.current ??= crypto.randomUUID();
  try {
    const { data, error } = await apiClient.POST("/api/v1/sourcing/rfqs/{id}/start-evaluation", { params: { path: { id: rfq.id } }, headers: mutationHeaders(key.current) });
    key.current = null; // a response arrived, so the outcome is known
    if (data) { navigate(`/sourcing/rfqs/${rfq.id}/evaluation`); return; }
    setMessage(failure(error as Problem | undefined, "Starting evaluation"));
  } catch { setMessage(failure(undefined, "Starting evaluation")); } // no response: the key is kept, so a retry replays
  finally { inFlight.current = false; setBusy(false); }
};
```

`mutationHeaders` and `failure` come from `components/requisitions/api`. `mutationHeaders(key)` carries the CSRF
token and `Idempotency-Key`. The route has no `If-Match`, so pass no version.

**States.**
- Idle: `Start Evaluation`.
- Pending: the label reads `Starting…` and `aria-busy="true"` is set. **The button is not `disabled`**: a disabled
  button drops keyboard focus and `pages/sourcing.md` §2 forbids it. The `inFlight` ref makes a second press a no-op.
- Failure: `<p role="alert" className="field-error">{message}</p>` directly after the button, inside the
  `StartEvaluation` fragment. Focus stays on the button; the page stays where it is. A 403, a 409 (`invalid_transition`,
  whose server text says to reload) and a network failure all render this way. The RFQ is not reloaded and nothing is
  retried automatically.
- Success: `navigate` to `/sourcing/rfqs/{id}/evaluation` (E12-S15's screen, route already wired). The shell's
  `useFocusOnRouteChange` moves focus to the main region and announces the page, so this story adds no focus code.

**Non-evaluators.** The screen is the same for everyone: an evaluator sees the declaration first, and anyone else
sees the shipped `You are not an evaluator on this RFQ` with `Back to the RFQ`. That hop is how a buyer who is not an
evaluator reaches `Open Comparison`; the RFQ is now `under_evaluation`, and `Open Comparison` is still offered. Do not
add a branch, a second destination, or a new link on this screen.

**Styling.** No new CSS. `.req-page button` and `.req-actions` (`styles/requisitions.css` ~5, ~9, ~154) already style
and wrap the control with tokens, and `.field-error` exists. This story states no numeric UI value.

## Acceptance

- [ ] A `closed` RFQ with `can_edit: true` shows `Start Evaluation` in the `RFQ actions` group, before `Open Comparison`.
- [ ] It is absent when `can_edit` is false on a closed RFQ, and absent in `draft`, `published`, `under_evaluation`,
      `awarded` and `cancelled` even with `can_edit` true.
- [ ] Playwright, keyboard only: focus the control by Tab from the preceding header element, assert it is focused with
      a visible focus indicator (non-`none` computed `outline-style` or `box-shadow`), press Enter; exactly one POST
      reaches `/start-evaluation` with an `idempotency-key` and `x-csrf-token` equal to the `flo_csrf` cookie
      (`tests/e2e/po-editor.spec.ts` ~8, ~24); the URL ends `/evaluation`; focus is on the main region.
- [ ] Space activates it too (one POST).
- [ ] Non-evaluator: lands on `/evaluation`, sees `You are not an evaluator on this RFQ`; `Back to the RFQ` by keyboard
      returns to a detail page offering `Open Comparison` and no longer offering `Start Evaluation`.
- [ ] Pending: with the POST held open, `Starting…` shows, the button is still focused and not `disabled`, and a second
      Enter sends no second POST.
- [ ] 409: the server's `detail` shows in `role="alert"`, the URL is unchanged, focus stays on the button.
- [ ] Lost response: the first POST is aborted (`route.abort()`), the alert shows, and the retry carries the **same**
      `idempotency-key`. After any response arrives, a later press carries a new key.
- [ ] axe passes on the closed-RFQ detail page, in light and dark, with the control visible, and again with the failure
      alert showing.
- [ ] pytest in `apps/api/tests/sourcing/test_rfq_lifecycle.py`, in the style of
      `test_only_editors_publish_and_viewers_read_versions` (~460): on a closed RFQ, `["rfq.view"]` gets 403 from
      `POST /rfqs/{id}/start-evaluation` and the RFQ stays `closed`; with `rfq.edit` it gets 200 and `under_evaluation`.
- [ ] MASTER §8 checklist holds; no hardcoded colour, spacing, radius or duration; icon from Phosphor, regular weight.
- [ ] `flo check --light` green.

## Plants

1. Remove `&& rfq.can_edit` from the gate: the "absent without `can_edit`" test fails.
2. Change the gate to `rfq.status !== "draft"`: the "absent in other states" test fails.
3. Set `key.current = null` before the `await` (or inside `catch`): the lost-response test fails on a different key.
4. Remove the `inFlight` guard: the pending test sees two POSTs.
5. Add `disabled={busy}`: the pending test fails on focus and on `disabled`.
6. Remove `require("rfq.edit", ...)` from the route's context (swap `EditContext` for `ViewContext`): the pytest's 403
   case fails.
