# E11-S09 — Status vocabulary aligned to MASTER §2.3: vendor, RFQ, award and purchase-order maps

**Epic** E11 · **M3** · **ui/S** · after **E11-S01** · tags: `ui`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`. **UI authority, in order:** `design-system/MASTER.md` §2.3 (as amended 13 Oct 2026) and `apps/web/src/styles/tokens.css`, then `design-system/pages/vendors.md` §9, `pages/sourcing.md` §3 and §10, `pages/purchase-orders.md` §3. Nothing here is drawn; it is a vocabulary and a test.

> **Why this sits second in M3 and in E11.** It is design-system debt, not vendor work. It is placed second so that it lands **before any M3 screen renders a vendor, RFQ, award or PO pill** and before the first M3 packet is authored against the old keys. It depends on **E11-S01** only so that the vendor status values the server actually sends are known before the map is written (see "Key strings").

## Requirements

- **TAG-001**, **TAG-002**, **TAG-003** — status is a closed vocabulary per document type, mapped in code, never author-coloured, never rendered without its icon (the E04-S05 contract, unchanged).
- **A11Y-004** — Color must not be the only way to communicate status, risk, validation, or financial direction.
- **VEN-012** — A vendor that is inactive, suspended, expired, or not approved must not be invited or selected unless policy explicitly permits an authorized override. *An expired required document makes a vendor not eligible and does not change its status (canvas decision 123); eligibility is a signal, never a status.*
- **PO-007** — The lifecycle should support Draft, Approval Pending, Approved, Issued, Partially Delivered, Delivered, Accepted, Closed, Cancelled, and Superseded. *(Wording amended 13 Oct 2026 on the operator's decision, canvas 169; the old text said Partially Fulfilled and Fulfilled.)*

## Contract

No API, no migration. Four changes to the web status package, all under `apps/web/src/components/status/`:

1. **`map.ts`** — `STATUS` becomes exactly this (tones are MASTER §2.3, verbatim):

   | docType | statuses (tone) |
   |---|---|
   | `purchase_order` | `draft` neutral · `approval_pending` info · `approved` info · `issued` success · `partially_delivered` info · `delivered` success · `accepted` success · `closed` neutral · `cancelled` danger · `superseded` warning |
   | `vendor` | `draft` neutral · `pending_approval` info · `active` success · `suspended` warning · `inactive` neutral · `rejected` danger |
   | `rfq` | `draft` neutral · `published` info · `closed` **info** (was neutral) · `under_evaluation` info · `awarded` success · `cancelled` danger |
   | `award` (**new** `DocType`, added to `DOC_TYPES`) | `draft` neutral · `approval_pending` info · `approved` success · `superseded` warning · `cancelled` danger |

   `project`, `requisition`, `budget` and `user` are **unchanged**.
2. **`labels.ts`** — remove `partially_fulfilled`, `fulfilled`, `pending` (**keep `expired`**: `requisition.expired` uses it; planner ruling after round 1); add `pending_approval`, `partially_delivered`, `delivered`, `accepted`; add `award: "Award"` to `DOC_TYPE_LABELS`. Keep the file's existing sentence-case convention (`Partially delivered`), see "Open point".
3. **`__tests__/StatusPill.test.tsx`** — `expectedStatus` and `expectedLabels` are the table above; the count assertion follows.
4. **`routes/_dev/status-gallery.tsx`** — no change expected (it iterates `DOC_TYPES`); confirm it renders the `award` group.

### Key strings: the server is the authority for spelling, MASTER for tone and words

The keys above are MASTER §2.3's. **Before writing `vendor`**, read E11-S01's merged vendor status enum from the generated client (`apps/web/src/api/generated/schema.ts`). If a key differs (the likely one: the server says `approval_pending` where canvas decision 121 says `pending_approval`), **the map follows the server** and the label stays `Pending approval`; record the divergence in `notes.followup` so the design session can correct MASTER. Never add a server value the map lacks: an unmapped status throws in development by design.

### `expired` goes, and eligibility is not a status

The old `vendor.expired` key is **deleted from the vendor map, not kept** (the `expired` *label* stays for `requisition.expired`). Nothing renders a `vendor` pill yet, so nothing else changes. Do not add an eligibility status. The `signal` component (MASTER §7.14) is a separate story's job.
