# E10-S13 — Wire workflows to projects and budget changes (vendors, RFQs, awards and POs register in M3)

**Epic** E10 · **M2** · **engine/M** · after **E10-S07** · tags: `migration`, `money`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (H, I, L) and `docs/author-traps.md`. Decisions: D-M2-11.

## Requirements

- **APR-003** — Workflows must support Projects, Capital Requisitions, Vendors, RFQs, Awards, POs, budget adjustments/transfers, and configured document types. **In M2: projects and budget changes here, requisitions in E09-S05. Vendors, RFQs, awards and POs register their adapters in their own M3 stories** (E11-S06, E12-S03, E12-S08, E13-S04); the `document_type` CHECK already allows them (E10-S01).
- **PROJ-002** — A project must support configurable approval before activation; it must activate automatically when no approval applies.
- **BUD-007** — Manual adjustments/transfers require a reason, effective date, supporting evidence when configured, and approval when applicable.
- **VEN-005** — Vendor creation, activation, scope changes, suspension, and reactivation must support approval. **Deferred to E11-S06**, which registers the vendor adapter; nothing here.
- **WF-003** — The document transition and its financial entries must commit atomically.

## Contract

0. **Migration:** the table only, `<next>_budget_change_requests.py`; `budget.approve` already exists.
1. **Composition.** `apps/api/src/flo/api/document_types.py::register_document_types()` (convention H), called from `api/health.py` at import and from `_run_jobs_tick`. **Whichever of E09-S05 and this story merges first creates the file; the second adds its adapters to it.**
2. **Project adapter** (`modules/projects/approval.py`): `document_type = "project"`, `approve_permission = "project.approve"` (existing; held by `project-administrator`), `read_permission = "project.read"`, `accepts_project_assignment = False`, `fields()` **empty in M2** (a project workflow routes by approval steps only, with no conditions; Phase 2 adds attributes), `snapshot` (version = `project.version`, requester = the submitter from the latest `project_status_event` into `approval_pending`, target = `AuthorizationTarget(PROJECT, project.id, …)` as the project routes use, `material` = `{bu_id, parent_id, currency, department_code, ledger_account_code}`), `summaries` (number, name, no amount), `on_outcome`.
3. **Budget-change adapter** (`modules/budget/approval.py`): `document_type = "budget_change"`, `approve_permission = "budget.approve"` (**already in the shipped catalogue**, granted to the baseline `budget-finance-user` role; no new permission), `read_permission = "ledger.read"`, `fields() = {"amount": money}` (the change's absolute amount), `summaries`, `on_outcome`.
4. **Routes changed** (`api/budget.py`): `POST /api/v1/projects/{id}/budget/adjustments` and `POST /api/v1/budget/transfers` keep their permissions, bodies and idempotency. When `resolve_version("budget_change", bu)` returns a published version for the (giving) project's BU/OU, they answer **202** `BudgetChangeRequestRead` instead of posting; otherwise they post exactly as today (201). The 202 is a new response, declared in OpenAPI on both routes.
5. `GET /api/v1/budget/change-requests/{id}` (`ledger.read` on the project) → 200 `BudgetChangeRequestRead`.

## Behaviour

1. **Project submit (PROJ-002).** The existing `draft → approval_pending` transition (`project.submit`, E06-S03) gains, in the same transaction: `resolve_version("project", project.bu_id)`; with a version, `approvals.service.start(...)` (the project stays `approval_pending`); **with none, the project moves straight on to `active`**, audited as `project.activated` with reason `no_approval_applies`, and its two status events written (`draft → approval_pending → active`, so history shows that no approval applied).
2. **Project outcomes:** `APPROVED` moves `approval_pending → active`; `REJECTED` (either mode) and `RETURNED` move to `draft` (the existing transition; the reason is the decision comment); `WITHDRAWN` moves to `draft`. Each goes through `Lifecycle`'s write, so status events and audit stay one path. **While an instance is running for the project, the manual `approval_pending → active` and `approval_pending → draft` transitions are refused** with 409 `CONFLICT`, `checks.problem = "approval_workflow_active"` ("This project is waiting for its approval workflow."). With no running instance, the manual path is unchanged, so projects submitted before this story still complete.
3. **Budget change requests (BUD-007):** table `budget_change_request(id uuid PK, org_id, kind text CHECK (kind IN ('adjustment','transfer')), project_id uuid NOT NULL (adjustment project, or the giving project), payload jsonb NOT NULL (the validated `AdjustmentCreate`/`TransferCreate`), amount numeric(18,4) NOT NULL, currency char(3) NOT NULL, requested_by uuid NOT NULL, idempotency_key text NOT NULL, status text CHECK (status IN ('pending','approved','rejected','withdrawn')), created_at, decided_at, result jsonb)`; RLS; `UNIQUE (org_id, idempotency_key)`. The route validates the body fully (reason, effective date, evidence when configured, the same checks as an immediate posting) **before** creating the request, so an invalid change never waits for approval.
4. **Posting on approval (WF-003):** `on_outcome(APPROVED)` calls `adjust` or `transfer` **inside the decision's transaction** with `actor_id = requested_by` and `idempotency_key = f"bcr:{request.id}"`, stores the result, and sets the request `approved`. If posting fails (for example `InsufficientBudget`, because the giving project was spent in the meantime), the whole decision rolls back and the approver sees that problem; the request stays `pending` (E10-S06 rule 3). `REJECTED`, `RETURNED` and `WITHDRAWN` set the request `rejected` or `withdrawn` with **no ledger effect**. A returned budget change does not reopen for editing: it ends `rejected` with the comment, and the requester submits a new one.
5. **Separation of duty:** E10-S04 excludes the requester from deciding their own change.

## Acceptance criteria

- [ ] Submitting a project with no published project workflow activates it, with both status events and the audit reason `no_approval_applies`.
- [ ] With a published workflow, submit starts an instance; approval activates the project; rejection, return and withdrawal return it to `draft`.
- [ ] While the instance runs, the manual `approval_pending → active` is 409 `approval_workflow_active`; without an instance it still works.
- [ ] An adjustment with no budget-change workflow posts at once (201, unchanged); with one it answers 202, posts nothing, and posts exactly once on approval (`bcr:<id>` key) with `actor_id` = requester.
- [ ] Approving a transfer whose giving project no longer has funds rolls the decision back with `InsufficientBudget` and leaves the request `pending`.
- [ ] A rejected or withdrawn request writes no ledger entry; `project_balance` reconciles after every case (use `reconcile.py`).
- [ ] The requester cannot approve their own budget change; `budget.approve` is required to be eligible.
- [ ] An invalid change body is refused at request time (422), not at approval.
- [ ] Routes: 202 declared in OpenAPI; `COVERED` foreign-tenant tests for the new GET route; the 202 path tested for isolation.

## Required tests

`apps/api/tests/approvals/test_project_wiring.py`, `apps/api/tests/budget/test_change_requests.py` (real app, real Postgres, real engine with a published fixture workflow), the migration test appended, and the existing project lifecycle and budget suites still green untouched (allowed edits only where convention C says so, each listed in the commit body).

## Plants

1. Post the budget change before the decision commits (outside `on_outcome`): the rollback-on-insufficient-funds test fails.
2. Let a project with a running instance be approved manually: the `approval_workflow_active` test fails.
3. Use a random idempotency key for the approved posting: a replayed decision posts twice, and its test fails.
4. Skip validation at request time: the 422 test fails.
