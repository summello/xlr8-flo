## Requirements (inlined)

- **PO-004** — Phase 1 must send approved POs by email and record recipient, time, delivery result, and the exact document version.
- **PO-012** — Duplicate clicks, retries, worker retries, and integration retries must not issue or transmit a PO more than once unintentionally.
- **PO-015** — Failed email/API/cXML transmissions must be visible, retryable, and auditable without duplicating the PO.
- **ARCH-006** — External effects such as email/API delivery must use a transactional outbox or equivalent durable handoff.
- **ACC-002** — Retrying an approved transfer or PO issue cannot duplicate ledger entries or vendor transmission.
- **EML-006** (shared with E13-S10) — Every send must record provider message id, recipient, template version, document snapshot id, and result.

## Design

### What exists (verified on `milestone/M3-sellable`)

- Hook **`enqueue_transmission(conn, scope, po_id, version)`**, a no-op at `purchasing/issue.py:34`,
  called in the issue transaction at `issue.py:153` (`version + 1`, the row's version after the
  `issue` transition) and in change-order apply at `changes.py:696` for the new revision (`2`: inserted
  at 1 in `_write_revision`, issued at `changes.py:826`). An issue retry returns at `issue.py:59-60`
  before it. **Keep the name, signature and both call sites**; the body becomes
  `transmission.enqueue(conn, scope, po_id, version)`.
- Each revision is its own `purchase_order` row (same `unit_id` + `number`, unique with `revision`;
  `supersedes_id` points back). An `issued` or `superseded` row is frozen by `purchase_order_immutable`
  (`migrations/20261029_0084_po_change.py:57-92`): only status/version transitions and the one
  `issued_at`/`issued_by` stamp. Rows in other statuses (`approved`) are writable.
- `purchase_order.recipients` is a JSON list of `{name, email}` (`HEADER`, `service.py:71-75`).
  `vendor_contact.email` is `NOT NULL` (`migrations/20261014_0057_vendor_contacts.py:19`).
- Outbox: `OutboxStore.add_email(*, to, template, context, idempotency_key)`
  (`kernel/outbox/store.py:147`), `email_handler` (`kernel/outbox/dispatcher.py:69`),
  `EmailSender.send(to, template, context, idempotency_key)` (`kernel/ports/email.py:20`). No
  attachments; no callback into modules. `outbox` states `pending|sent|failed|dead` (`failed` = retry
  scheduled), `UNIQUE (org_id, idempotency_key)`, and `sent` ⇔ `provider_message_id` and `sent_at` set
  (`migrations/20260825_0007_jobs_outbox.py:86-92`); `sent` blanks the payload (`store.py:221-229`).
- Precedent: RFQ sends join `outbox` by `outbox_id` and derive the state from `outbox.state`
  (`sourcing/service.py:386-392`).

### Issue refuses a PO with no recipients (Resolved 2) — `purchasing/issue.py`

In `issue()`, under the PO lock, **after** the status and version checks (`issue.py:59-64`, so a retry
still returns at :60) and **before** the first write (`UPDATE po_line`, :91) and every posting:

```python
recipients = h["recipients"] or [
    r.model_dump() for r in VendorService(conn, scope, actor_id).document_recipients(h["vendor_id"])
]
if not recipients:
    raise conflict("no_recipients", "The vendor has no contact that receives documents. Add one, then issue.")
if not h["recipients"]:
    service.repo.execute("UPDATE purchase_order SET recipients = %(r)s WHERE org_id = %(org_id)s AND id = %(id)s", {"id": po_id, "r": Jsonb(recipients)})
```

The PO's create-time list is used when it has one (today's behaviour); only an empty list is
refreshed from the vendor's current document contacts, so adding a contact with
`receives_documents` (or an email to one) unblocks the issue without recreating the PO. The row is
`approved` here, so the trigger allows the write, and the transition that follows moves the version.
Locks: `document_recipients` is a plain read (`vendors/service.py:810-820`; vendor `_row` takes no lock,
:146), the `UPDATE` hits the PO row already held; no new lock edge. Contact writes lock the vendor row
then the contact (`vendors/changes.py:121-139`), never a PO. Nothing is posted before the raise.

### Table `po_transmission` (one migration, reversible)

`org_id uuid NOT NULL REFERENCES organization(id)`, `id uuid PRIMARY KEY`, `po_id uuid NOT NULL`
(FK `(org_id, po_id)` → `purchase_order(org_id, id)`: the revision sent, and the **document snapshot
id**, since `po_version` is keyed by it), `version int NOT NULL` (the hook's argument: the row's
version at issue), `attempt int NOT NULL CHECK (attempt >= 1)`, `recipient_name text NOT NULL`,
`recipient_email text NOT NULL`, `template_version text NOT NULL`, `outbox_id uuid`, `result text CHECK
(result IN ('address_suppressed','delivered','bounced','complained','failed'))`, `result_at
timestamptz`, `created_by uuid NOT NULL REFERENCES identity(id)`, `created_at timestamptz NOT NULL
DEFAULT now()`.

- `CHECK ((outbox_id IS NULL) = (result IS NOT DISTINCT FROM 'address_suppressed'))`
- `CREATE UNIQUE INDEX po_transmission_once ON po_transmission (org_id, po_id, attempt, lower(recipient_email))`: the database-level PO-012 guard.
- `result` stays NULL while the outbox owns the state. Only `enqueue`/resend (`address_suppressed`)
  and E13-S10's webhook (`delivered`, `bounced`, `complained`, `failed`, with `result_at`) write it.
- Down drops the table. Append the revision to `tests/kernel/test_migrate.py` (head's date prefix, next number, after E13-S08's).

**Read state** (one SQL expression, a module constant in `transmission.py`, used by every reader):
`COALESCE(t.result, CASE o.state WHEN 'sent' THEN 'sent' WHEN 'dead' THEN 'failed' ELSE 'queued' END)`
over `po_transmission t LEFT JOIN outbox o ON o.org_id = t.org_id AND o.id = t.outbox_id`.
`provider_message_id` = `o.provider_message_id`; `result_at` = `COALESCE(t.result_at, o.sent_at)`. A
dead outbox row is `failed`, never `bounced` (a bounce is a provider event, E13-S10; the RFQ
precedent's `dead → bounced` is not copied).

### `transmission.enqueue(conn, scope, po_id, version)` — `modules/purchasing/transmission.py` (new)

Runs in the caller's transaction. Takes **no lock** (both callers hold the PO row); writes only
`po_transmission` and `outbox`.

1. Recipients: `revision = 0` → the row's `recipients`. A later revision → the recipients of the
   highest `attempt` on the superseded row (`supersedes_id`), so a recipient chosen at resend carries
   forward; none → the row's `recipients` (copied from the old row, `changes.py:801-806`).
   Empty → `conflict("no_recipients", …)` (Resolved 4).
2. Document: `pdf = pdf_for(conn, scope, po_id)`; `summary = email_summary(VendorCopy.model_validate(<po_version.snapshot for po_id>))`.
   One `EmailAttachment("application/pdf")`, filename `{number}.pdf`, or `{number}-rev{revision}.pdf`
   when `revision > 0` (E13-S08's `Content-Disposition` form).
3. `created_by` = the row's `issued_by` (one scoped `SELECT`; both callers stamp it first,
   `issue.py:146-150`, `changes.py:827-831`). Resend passes its actor instead.
4. Dedupe the recipients by `lower(email)`, keeping the first occurrence in list order (two vendor
   contacts may share an email; `vendor_contact` has no unique email, `migrations/20261014_0057_vendor_contacts.py`),
   so `po_transmission_once` never raises. Every path (issue, change-order apply, resend) goes through
   this step. For each remaining recipient, `row_id = uuid4()` first:
   - `_suppressed(conn, scope, email) -> bool` (stub returning `False`; E13-S10 fills it) → insert the
     row with `result = 'address_suppressed'`, `outbox_id` NULL, no email;
   - otherwise `rec = OutboxStore(conn, scope).add_email(to=email, template=TEMPLATE, context=…,
     idempotency_key=f"po_transmission:{row_id}", attachments=[pdf])`, then insert the row with
     `id = row_id`, `outbox_id = rec.id`. Both CHECKs hold at every statement.

The key is the row id: unique per (PO, attempt, recipient) through `po_transmission_once`, stable
across dispatcher retries (Resend dedupes on it). `TEMPLATE = "po-issued-v1"`; `template_version` =
`TEMPLATE`. Context (Resend: keys `[A-Za-z0-9_]` ≤ 50 chars, string values ≤ 2,000 chars):
`po_number`, `revision`, `vendor_name`, `summary` (cut to 1,999 characters plus `…` if longer). Local
fixture `apps/api/templates/email/po_issued.html`, mirroring `rfq_version.html`.

### Kernel: attachments

- `ports/email.py`: `@dataclass(frozen=True) class EmailAttachment: filename: str; content_type: str; content: bytes`;
  `EmailSender.send(..., attachments: Sequence[EmailAttachment] = ())`.
- `OutboxStore.add_email(..., attachments: Sequence[EmailAttachment] = ())` adds
  `"attachments": [{"filename", "content_type", "content_b64"}]` to the payload **only when non-empty**.
- `email_handler`: when `attachments` is present, decode it (not a list of three-string objects, or bad
  base64 → `PermanentOutboxError`) and pass `attachments=`; when absent, call `send` exactly as today,
  so existing senders and test fakes are untouched.
- `adapters/resend.py`: body gains `"attachments": [{"filename", "content": <base64>, "content_type"}]`
  only when non-empty (Resend `POST /emails` accepts it with `template`). `adapters/smtp.py`:
  `message.add_attachment(content, maintype=…, subtype=…, filename=…)` from `content_type`.
- `# ponytail:` in `transmission.py`: the PDF travels base64 in each recipient's outbox payload until
  sent (`sent` blanks it); move to a storage key resolved at dispatch if PDFs pass ~1 MB.

### Resend — `POST /api/v1/purchase-orders/{id}/transmissions/resend`

`IssueContext` (`api/purchasing.py:59`; `po_target` gives 404 for a foreign, deleted or unknown id
before the permission). Body `TransmissionResend {contact_ids: list[UUID] | None = None}`
(`min_length=1`, `max_length=20`, `extra="forbid"`; `[]` → 422). 200 → the transmission log (as `GET` below). One
`tenant_transaction` in a service function in `transmission.py`, one lock:

1. `h = PurchaseOrderService(conn, scope, actor)._row(id, lock=True)` (`service.py:130`).
2. `h["status"] != "issued"` → 409 `not_resendable` (Resolved 1).
3. A row of this `po_id` whose read state is `queued` → 409 `transmission_queued` ("A send of this version is still queued.").
4. No `po_transmission` row for this `po_id` (issued before this story; none in production, M3 is not
   on `main`) → 409 `nothing_to_resend`. Else `attempt` = `max(attempt) + 1`, `version` = `h["version"]`
   (an issued row's version cannot move while it stays `issued`, so it equals the rows' `version`).
5. Recipients: `contact_ids` given → each must be in `VendorService(...).list_contacts(h["vendor_id"])`
   (`vendors/service.py:688`), else 422 `unknown_contact` (`_invalid("contact_ids", …)`,
   `purchasing/service.py`); recipients = those contacts' `{name, email}`. Not given → the recipients of
   the highest attempt.
6. `enqueue`'s step 4 with this `attempt`, `created_by = actor`, the same `pdf_for` bytes.
7. `audit_event(..., action="purchase_order.transmission.resend", target_type="purchase_order",
   target_id=id, after={"attempt": …, "recipients": [emails]})` (`kernel/audit/writer.py:212`).

No ledger entry, no `purchase_order` write, no status change. **Change Recipient is this body**, not a
separate write (the issued row's `recipients` is frozen); E13-S16's picker posts `contact_ids`.

### Lock order

- **Issue** (E13-S05, plus E13-S07's award first): [award] → balances (id order) → requisition → PO.
  This story adds an unlocked contact read and a write to the held PO row, then (unchanged position)
  `enqueue`, which inserts new rows only.
- **Change apply** (`ChangeService._lock`, `changes.py:610-625`): award → balances → requisition → PO →
  change row; `enqueue` adds inserts only.
- **Resend**: the PO row only, then inserts. It waits on nothing after the PO, so it closes no cycle
  with issue, apply, E13-S07's cancel/reduce or E13-S23's withdraw/submit. A resend of a row a change
  apply is superseding blocks on the PO lock, then re-reads it `superseded` → 409 `not_resendable`.
  Two resends serialize on the PO; the second sees the first's `queued` rows → 409.

### Reads

- `GET /api/v1/purchase-orders/{id}/transmissions` (`ViewContext`): every row whose `purchase_order`
  has the same `org_id`, `unit_id` and `number` as `{id}`, newest first (`created_at DESC, attempt
  DESC, id`), as `PoTransmissionRead {id, po_id, revision, version, attempt, recipient_name,
  recipient_email, template_version, provider_message_id, result, created_at, result_at}`, `result`
  from the read-state expression.
- **Business monitor (OBS-004):** `transmission.attention_counts(conn, scope, days=7) -> dict[str, int]`:
  counts of `failed`, `bounced` and `address_suppressed` read states with `created_at` in the window.
  No route here; E19-S07 surfaces it.

## Acceptance

- [ ] Issue enqueues one outbox email and one `po_transmission` row per recipient, in the issue transaction; making `notify_requester_issued` raise rolls the issue back with no outbox row and no transmission row.
- [ ] **No recipients:** an approved PO whose `recipients` is `[]` and whose vendor has no `receives_documents` contact → `POST …/issue` 409 `no_recipients`; no `ledger_entry` row, PO still `approved` at the same version, no outbox or transmission row. Then `create_contact` with `receives_documents=true` and issue again → 200, `purchase_order.recipients` holds that contact, one transmission row to its email.
- [ ] A PO with a non-empty `recipients` list issues to that list even after the vendor's document contacts change.
- [ ] The issue retry (`If-Match` = version - 1 on an issued PO) adds no row and no outbox email; calling `enqueue` twice for one PO in one transaction raises `UniqueViolation`.
- [ ] Change-order apply enqueues for the new revision with `version = 2`, to the recipients of the superseded revision's highest attempt (one changed by a resend with `contact_ids` carries forward); `enqueue` on a row whose resolved recipients are empty raises 409 `no_recipients`.
- [ ] The outbox payload before dispatch has exactly one attachment, `content_type = "application/pdf"`, whose decoded bytes equal `pdf_for(po_id)` and whose sha256 is the row's `po_version.pdf_sha256`; no `text/html` attachment.
- [ ] Dispatcher retry: a fake sender raises `TransientEmailError` on call 1 and succeeds on call 2 (`run_after = now()` between runs, as `tests/kernel/test_outbox.py:211-214`); both calls carry the same idempotency key and one attachment, there is one outbox row, and the transmission reads `sent` with the fake's message id.
- [ ] An existing outbox email without `attachments` dispatches through a sender whose `send` has no `attachments` parameter (the existing test fakes pass unchanged).
- [ ] Read states: before dispatch `queued`; after `sent`; after the outbox row goes `dead`, `failed`; a row with `result = 'bounced'` written directly reads `bounced` while the outbox row stays `sent`.
- [ ] Suppressed: with `_suppressed` patched to `True`, issue writes an `address_suppressed` row with no `outbox_id` and no outbox email.
- [ ] Resend after a dead send: attempt 2, same `version`, one new outbox email per recipient; no new `ledger_entry` row; `purchase_order` row byte-identical (`to_jsonb`) before and after; one audit row `purchase_order.transmission.resend`.
- [ ] Resend with `contact_ids` sends to those contacts; a contact of another vendor → 422 `unknown_contact`; while a row is queued → 409 `transmission_queued`; on a `superseded`, `cancelled` or `closed` PO → 409 `not_resendable`; on an issued PO with no transmission rows → 409 `nothing_to_resend`.
- [ ] Two `receives_documents` contacts sharing one email (different case) → issue writes one `po_transmission` row and one outbox email for it; resend with `contact_ids` naming both does the same. Resend with `contact_ids: []` → 422.
- [ ] Real-Postgres concurrency (two connections): two simultaneous resends of a PO whose last send is dead → exactly one 200, the other 409 `transmission_queued`, one set of attempt-2 rows, no `DeadlockDetected`.
- [ ] No send from a request handler: with a recording fake sender installed, `POST …/issue` and `POST …/transmissions/resend` return with zero sender calls and the outbox rows present.
- [ ] `GET …/transmissions` on a revised PO lists both revisions' rows newest first, with `revision`, `version`, `template_version` and `result`.
- [ ] `attention_counts` counts one each of a `failed`, a `bounced` and an `address_suppressed` row inside 7 days, and not one created 8 days ago.
- [ ] Quota: 80 sent email outbox rows (`state='sent'`, `provider_message_id` and `sent_at` set) inside 24 h → `email_sends` in `alerts` with that action and cost; 79 → not; one sent 25 h ago does not count. Every collector mapping and expected metric set in `tests/test_internal.py` includes `email_sends`.
- [ ] Authorization: `GET` without `purchase_order.view` → 403; resend without `purchase_order.issue` → 403. TEN-010: both routes → 404 for another tenant's PO, both in `COVERED` (`tests/isolation/test_route_coverage.py:62`). Migration in `tests/kernel/test_migrate.py`. `flo check --light` green.

## Plants

1. Call the sender directly in `enqueue`: the rolled-back-issue and no-send-from-handler tests record a call and fail.
2. Drop `po_transmission_once`: the double-enqueue test gets no `UniqueViolation` and fails.
3. Remove `FOR UPDATE` from resend's PO read: the concurrency test sees two 200s and fails.
4. Map outbox `dead` to `sent` in the read state: the `failed` read-state test fails.
5. Drop the `document_recipients` refresh in `issue()`: the add-contact-then-issue test gets 409 and fails.
6. Pass `attachments=()` unconditionally in `email_handler`: the no-`attachments`-parameter sender test fails with `TypeError`.
7. Remove the dedupe in `enqueue` step 4: the shared-email test raises `UniqueViolation` on `po_transmission_once` and fails.

## Resolved (operator, 30 Oct 2026)

1. Resend is allowed only on an `issued` PO; every other status → 409 `not_resendable`.
2. A vendor with no document-contact email at issue: the issue is **refused**, 409 `no_recipients`,
   until a contact email is set. This changes merged E13-S05's `issue()` (above); there is no
   `not_sent` transmission row. An empty create-time list is refreshed from the vendor's current
   document contacts at issue, which is what makes "until a contact email is set" reachable without
   recreating the PO.
3. The vendor cancellation email is a new story, **E13-S24** (deps E13-S07, E13-S09). Nothing here
   wires `notify_vendor_cancelled`; this story only provides `enqueue`'s building blocks (outbox
   attachments, the transmission table) that E13-S24 may reuse.
4. A change-order revision with no recipients (was OPEN 1): option (a). `enqueue` raises 409
   `no_recipients`, so the apply is refused and rolls back; on a final approval decision E13-S06's
   `settle` runs the apply inside `decide`, so that decision fails too. Reachable only for a PO
   issued before this story merged; none exists in production.
