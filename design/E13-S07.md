# E13-S07 — Cancel or reduce a PO: release the unused commitment exactly once, keep history

**Epic** E13 · **M3** · **ledger/M** · after **E13-S06** · tags: `money` (Opus review)

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** canvas DECISIONS **209** (the released commitment is re-reserved on the sub-project
> for the reopened quantity; if the requisition line is cancelled too, it is released and returned to
> the main project, as 205), D-M2-26. `design-system/pages/purchase-orders.md` §2 "Cancel or reduce
> releases only the unused commitment, once", §4.8.
> **Writes:** every `PATCH`/`PUT`/`DELETE` on an editable resource follows `docs/m2-conventions.md` §O (`If-Match` with the integer version, `ETag` on reads, 400 when missing, 409 `stale_version` on mismatch). `Idempotency-Key` protects **POST** commands only (the middleware ignores other methods); where a packet says "(Idempotency-Key)" on a non-POST route, read §O instead.
> **RLS:** every new tenant table gets literal `ALTER TABLE <t> ENABLE ROW LEVEL SECURITY; … FORCE …; CREATE POLICY tenant_isolation ON <t> …` statements in the migration text, one block per table, never generated by a helper or f-string (the static gate in `tests/isolation/test_ci_guards.py` reads the text; the light check runs it).

## Requirements (inlined)

- **PO-013** — Cancelling or reducing a PO must release the unused commitment exactly once and must not erase its history.
- **ACC-006** — Cancelling a requisition or PO releases only its unused funds, once.
- **FIN-011** — a release happens exactly once.

## Design

`POST /purchase-orders/{id}/cancel` and `POST /purchase-orders/{id}/reduce` (Idempotency-Key,
**and `If-Match` with the PO's integer version**, as `POST /{id}/issue` takes it: 400 when missing,
409 `stale_version` on mismatch, passed as the expected version to `lifecycle.transition`;
`purchase_order.amend`, reason required, **and** `cancel_requisition_lines: bool` default false).
`/reduce` also takes `lines: list[PoChangeLineEdit]` (E13-S06's schema, `line_no` plus a lower
`quantity` or `remove`; any other field, or a quantity that does not fall, is 422).

**Returning quantity** always moves all three counters by the negative delta, in E13-S06's order
(`changes.py` around `order_award_lines`): `order_award_lines` (so `award_line.ordered_qty`, which
PO availability reads, falls), `order_lines` and, after issue, `issue_lines`.

- **Before issue** (`draft`, `approval_pending`, `approved`): cancel → `cancelled`. Nothing was committed. Quantity returns (`order_award_lines` and `order_lines`, negative; nothing was issued). An open approval is withdrawn.
- **After issue — cancel:** for each commitment group, **each commitment entry** in it with `remaining > 0` (a change order can add several per group; read them as E13-S06's decrease path does, `commitment_remaining` joined to `ledger_entry`), `release_commitment(entry_id, amount=None)` (the remainder, i.e. **unused**: `remaining()` already nets any actuals; M3 has none, M4 adds receipts). Key `po:{id}:cancel:{group}:{entry_id}`. Then:
  - default (decision 209): `requisitions.service.rereserve` the released amount on the sub-project, and return the quantity (all three counters, above), so the requisition line is open to order again;
  - `cancel_requisition_lines = true`: release and **return to the main project** (`release_unawarded`-style transfer sub → main, key `po:{id}:cancel:return:{req}`), and `requisitions.service.cancel_lines` raises `cancelled_qty`.
  - PO → `cancelled` through `lifecycle.transition`. The vendor is told (E13-S09: a cancellation email through the outbox) unless `notify_vendor=false`.
- **After issue — reduce:** a quantities-only change order through E13-S06, so reduction is one code path. The route is a shortcut: it creates the change (`ChangeService` create + update with `lines`) and then **submits** it, since a reduction is material and E13-S06's `apply` refuses material changes. The response is the change in `approval_pending`; the release happens when E13-S06 applies it on approval, never in this route. A retry with the same key returns the same change.
- A requisition that was `completed` and regains open quantity returns to `open_for_purchase` via `requisitions.service.reopen_for_purchase`, audited.
- **History:** the PO, its versions, PDFs and transmissions stay readable. A cancelled PO shows the released figure.

## Acceptance

- [ ] Cancel after issue: one release per group equal to the remainder, one re-reservation of the same amount, drift empty; retried → nothing more (FIN-011).
- [ ] With `cancel_requisition_lines`: release, transfer back to main, and `cancelled_qty` up; the requisition can complete without those lines.
- [ ] Cancel before issue: no ledger entry; quantity back.
- [ ] Reduce uses the change-order path: one `po_change` row in `approval_pending`, no ledger entry until it is approved; on approval the commitment falls and `award_line.ordered_qty` falls by the reduced quantity.
- [ ] Cancel after a change order added a second commitment entry to a group: both entries released, `commitment_remaining` zero, no idempotency-key collision.
- [ ] Cancel or reduce without `If-Match` → 400; with a stale version → 409 `stale_version`.
- [ ] **Concurrency:** cancel and issue racing on an approved PO → one wins and the ledger is consistent.
- [ ] TEN-010 and authorization; `flo check` green.

## Plants

1. Release `amount = original` instead of the remainder: the "unused only" test with a prior partial release fails.
2. Skip the re-reservation: the decision-209 test fails.
