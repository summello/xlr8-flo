# E13-S07 — Cancel or reduce a PO: release the unused commitment exactly once, keep history

**Epic** E13 · **M3** · **ledger/M** · after **E13-S06** · tags: `money` (Opus review)

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** canvas DECISIONS **209** (the released commitment is re-reserved on the sub-project
> for the reopened quantity; if the requisition line is cancelled too, it is released and returned to
> the main project, as 205), D-M2-26. `design-system/pages/purchase-orders.md` §2 "Cancel or reduce
> releases only the unused commitment, once", §4.8.
> **Writes:** every `PATCH`/`PUT`/`DELETE` on an editable resource follows `docs/m2-conventions.md` §O (`If-Match` with the integer version, `ETag` on reads, 400 when missing, 409 `stale_version` on mismatch). `Idempotency-Key` protects **POST** commands only (the middleware ignores other methods); where a packet says "(Idempotency-Key)" on a non-POST route, read §O instead.
> **RLS:** every new tenant table gets literal `ALTER TABLE <t> ENABLE ROW LEVEL SECURITY; … FORCE …; CREATE POLICY tenant_isolation ON <t> …` statements in the migration text, one block per table, never generated by a helper or f-string (the static gate in `tests/isolation/test_ci_guards.py` reads the text; the light check runs it). This story adds no table and no migration.

## Requirements (inlined)

- **PO-013** — Cancelling or reducing a PO must release the unused commitment exactly once and must not erase its history.
- **ACC-006** — Cancelling a requisition or PO releases only its unused funds, once.
- **FIN-011** — a release happens exactly once.

## Design

### Routes

| Route | Permission | Body | Response |
|---|---|---|---|
| `POST /purchase-orders/{id}/cancel` | `purchase_order.amend` (`AmendContext`, api/purchasing.py:62) | `reason: str` (1..500, required), `cancel_requisition_lines: bool = False`, `notify_vendor: bool = True` | 200 `PoCancelRead` = `PoRead` + `notice: str \| None`, with `ETag` |
| `POST /purchase-orders/{id}/reduce` | `purchase_order.amend` | `reason: str` (required), `lines: list[PoChangeLineEdit]` | 201 `PoChangeRead`, with `ETag`, as `POST /{id}/changes` |

Both take `Idempotency-Key` (POST) **and** `If-Match` with the PO's integer version, parsed by
`lifecycle.parse_if_match` (400 when missing, 409 `stale_version` on mismatch), as `/issue` does.
`/reduce` refuses with 422 any `lines` entry that sets a field other than `line_no`, `quantity` and
`remove`, or whose `quantity` is not lower than the line's current quantity (problem `reduce_only`,
checked in the route before `propose`, which would accept a rise).
`PurchaseOrderTransitionCreate.action` stays `Literal["close"]` (schemas.py:91): a cancel through
`/transitions` would skip every release.

A PO draws on **one award and one requisition** (`create` refuses `mixed_requisitions`,
purchasing/service.py:409-414; a change order refuses a line of another requisition,
changes.py:248-253), both on the PO header. So cancel makes at most one `rereserve` and one
`release_unawarded` per PO.

### Lock order (cancel, every path)

All in one `tenant_transaction`, in this order, nothing locked outside it:

1. `service._row(po_id)` unlocked: 404 first; read `award_id`, `requisition_id`.
2. `lock_award(award_id)` (sourcing/service.py:1264). It raises 409 `invalid_transition` when the
   award is not `approved`; cancel lets it through, so nothing is posted.
3. `lock_balance` on one id-sorted set: every `po_line.project_id`, the requisition's `project_id`
   (the main project, which `release_unawarded` pays into), and the live reservation's project when
   there is one (`reservation_remaining(entry).project_id`, read unlocked as `lock_funding` does,
   funding.py:24-33; it equals the line project, because `commit` refuses to convert a reservation
   on another project, postings.py:165-166, so the set is normally two ids).
4. `reservation_entry(requisition_id, lock=True)`: the requisition row.
5. **Only when the PO is `approval_pending`** (read unlocked after step 4): compare `If-Match` with
   that read's version (409 `stale_version`) and require the caller to be the PO's creator (`PurchaseOrderService._creator_only`, service.py:810-814: 403 "Only the buyer who drafted this order can do that."; operator, 30 Oct 2026: only the creator may end a pending PO approval, as the existing withdraw), then call `approvals.service.withdraw(document_type='po',
   document_id=po_id, actor_id=..., reason=body.reason)`. It locks `approval_instance`, then the
   adapter (`PurchaseOrderService.settle`, service.py:878-891) locks the PO and moves it to `draft`
   (version + 1). Approval instance before PO is the order `decide` takes (decisions.py:226, then
   the adapter). Not `PurchaseOrderService.withdraw`: it locks the PO before the instance and is
   creator-only. If the instance is no longer running, its 409 `task_closed` (decisions.py:368)
   propagates and the transaction rolls back; cancel never retries against the new state.
6. `service._row(po_id, lock=True)`, then the status and version checks below.

This is `ChangeService._lock`'s order (award, balances, requisition, PO; changes.py:610-625) with
the main project added to step 3 and the approval instance inserted before the PO. `issue` must
take the award first too: today it takes balances, requisition, PO (issue.py:53-57), and its PO
update holds a KEY SHARE lock on the award row through `purchase_order.award_id`, so cancel
(award, then balances) and issue (balances, then award) deadlock on an approved PO (author
measured `DeadlockDetected` 3/3, 30 Oct 2026). Fix in `issue.py`: right after the unlocked
`service._row(po_id)`, call `lock_award(conn, scope, h["award_id"])` exactly as
`ChangeService._lock` does (changes.py:612-615), then the existing balances, requisition, PO.
An approved PO's award is always `approved` (supersede refuses once a PO exists), so the 409
`lock_award` can raise is not a new outcome for issue. After this every writer below takes
award, balances, requisition, PO, in that order or a prefix; no writer of these rows
locks the PO, the instance or the requisition and then an award or a balance. One pre-existing
cycle is out of scope: `PurchaseOrderService.withdraw` (PO, then instance) against `decide` or this
cancel (instance, then PO).

**Supersede** locks balances before the award (awards.py:854-855), the reverse of step 2-3. It gains
an **unlocked** `SUPERSEDE_GUARDS` probe right after `live = self._award(rfq_id)`, before
`award_funding(lock=True)`, and keeps the locked re-check. `_po_exists` counts every PO that is not
`deleted` (service.py:925-937), and a cancel only runs on an existing PO, so a supersede of an award
a cancel holds refuses 409 `po_exists` holding no lock.

### Status and version checks (under the step 6 lock)

`version` = the locked row's version.

- `cancelled` and `expected in (version, version - 1)`: replay, return the PO, post nothing (as
  issue.py:59-60). A retry of an `approval_pending` cancel (version moved by 2) relies on the
  `Idempotency-Key` replay; with a new key and the old `If-Match` it is 409 `stale_version`.
- `approval_pending` path (step 5 ran): the PO must be `draft` at exactly `expected + 1`, otherwise
  409 `stale_version` and everything, withdrawal included, rolls back.
- Otherwise `expected != version` → 409 `stale_version`.
- Then `draft` or `approved` → **before issue**; `issued` → **after issue**; any other status
  (`superseded`, `closed`, `cancelled` outside the replay window) → 409 `invalid_transition`.

Every `transition(...)` call passes this locked `version`, never the header read in step 1.

### Before issue (`draft`, `approval_pending` now `draft`, `approved`)

Nothing was committed or posted (approval posts nothing, service.py:879).

1. `service._move(row, None)`: both counters fall by each line's quantity (service.py:580-627,
   as draft `delete` does at :780). Nothing was issued.
2. `transition(conn, scope, po_id, "cancel", actor, version, body.reason)`.
3. `cancel_requisition_lines` is **ignored** (operator, 30 Oct 2026): `cancelled_qty` and the
   reservation do not move, no 422. `notice` = "Requisition lines were not cancelled: the PO was
   never issued. Cancel them on the requisition." when the flag was true, else `None`.
4. No vendor message: nothing was sent.

### After issue (`issued`)

Let `root = PurchaseOrderService._root(po_id)` (today `ChangeService._root`, changes.py:627-639; moved, see Files): every commitment of the PO's life is
sourced to it. Let `entry` = the step 4 reservation entry (may be None). Steps, in order:

1. **Open change order:** a `po_change` with `root_po_id = root` in `draft` or `approval_pending`
   → 409 `change_in_progress` (the query and code of changes.py:436-443). The author withdraws it
   first. `ChangeService.create` refuses a PO that is not `issued` (changes.py:431-434), so no
   change can start after the cancel.
2. **Release:** for each `ledger_entry` with `source_type='purchase_order'`, `source_id = root`,
   `entry_type='commitment'` whose `commitment_remaining.remaining > 0` (the join at
   changes.py:760-770, without the group filter), in id order:
   `release_commitment(conn, scope, commitment_entry_id=e, amount=None, actor_id=actor,
   reason="Purchase order cancelled", idempotency_key=f"po:{po_id}:cancel:{e}")`.
   `amount=None` releases the remainder, i.e. only the **unused** part (`remaining` already nets
   earlier releases and actuals; M3 has no actuals). `released` = the sum of the released amounts.
3. **Re-reserve (decision 209):** when `entry is not None` and `released > 0`:
   `rereserve(conn, scope, requisition_id, amount=released, key=f"po_cancel_{po_id}", actor_id=actor)`
   (lifecycle.py:406), on the reservation's own project, as `changes._post` does (changes.py:785-793).
4. **Return the quantity**, all three counters by the negative line quantity, in the falling order of
   changes.py:665-683: `order_award_lines`, then `issue_lines`, then `order_lines`. Issued falls
   before ordered because `issued_qty <= ordered_qty` is a CHECK (migrations/20261029_0083_po_issue.py:11).
5. **Only with `cancel_requisition_lines = true`** (operator, 30 Oct 2026, option B):
   1. when `entry is not None` and `released > 0`: `release_unawarded(conn, scope, requisition_id,
      released, None, actor, version=version, source=f"po:{po_id}",
      key=f"po:{po_id}:cancel:return:{requisition_id}", reason=f"Purchase order {number} cancelled,
      unused funds of requisition {req_number} returned")`. It releases `released` from the
      reservation step 3 just grew and moves it sub-project → main. Two postings, one net effect:
      sub-project available unchanged, reservation remaining unchanged, main up by `released`,
      never negative (the reservation holds the amount again when it is reduced);
   2. `cancel_lines(conn, scope, [(requisition_line_id, qty), ...], actor)` raises `cancelled_qty` by
      the returned quantity (after step 4, so `ordered_qty + cancelled_qty <= quantity`,
      `line_order_ceiling`, holds at every step).
6. `reopen_for_purchase` then `mark_completed` (each a no-op unless its condition holds, as
   changes.py:692-695 calls them): the default path reopens a `completed` requisition; the flag path
   can complete one whose remaining lines are all issued or cancelled.
7. `transition(conn, scope, po_id, "cancel", actor, version, body.reason)`.
8. Unless `notify_vendor=false`, call a stub `notify_vendor_cancelled(conn, scope, po_id)` in
   `cancel.py` (E13-S09 wires the outbox email there, as `enqueue_transmission` in issue.py:34).

**No live reservation** (`entry is None`) — a deliberate exception to decisions 209 and 205 (operator,
30 Oct 2026, option 1): issue committed the whole amount from the project's available (the `excess`
path, issue.py:106-112), so step 2's release returns it exactly where it came from. Skip step 3
(`rereserve` needs a live reservation; `changes._post` skips it the same way, changes.py:785) and
step 5.1; the funds stay available on the commitment's project. Step 5.2 still raises
`cancelled_qty`. Scoped to this case only.

**Zero release:** `released == 0` skips steps 3 and 5.1 (no empty funding round).

### `cancel_lines` (new, requisitions/sourcing.py, exported through `requisitions.service`)

Option B, line-level block (operator, 30 Oct 2026): `cancelled_qty` lives on `requisition_line`;
there is no `award_line.cancelled_qty` and no migration. `awarded_qty` and `sourced_qty` do not
move, so the award line keeps the cancelled quantity visible as "cancelled, not re-orderable".

- Locks the requisition (`read_row(..., lock=True)`), then the lines in id order, as `order_lines`.
- The requisition must be `open_for_purchase` or `completed`, otherwise 409
  `requisition_not_cancellable`; the raise rolls the whole cancel back, so nothing is posted.
  (`award_lines`, `mark_awarded`, `mark_sourced`, `mark_unsourced`, `sourcing_basis` and
  `sourceable_lines` act only on `sourcing_in_progress` or `sourced` requisitions, so they never see
  a cancelled line and stay unchanged.)
- `ordered_qty + cancelled_qty + qty > quantity` → 409 `over_cancel`, never the CHECK as a database
  error. Audited per line as `requisition.cancel_lines.update` (before/after `cancelled_qty`).

**Where the block is enforced.** Orderable quantity of a requisition line =
`quantity - cancelled_qty - ordered_qty`.

- `order_lines` (requisitions/sourcing.py:221-225): after the existing `awarded_qty - ordered_qty`
  check (409 `over_open_quantity`), a positive delta above the orderable quantity raises 409
  `quantity_cancelled`. Every caller (`PurchaseOrderService.create`, `_move`, `ChangeService._apply`)
  runs it in the transaction that called `order_award_lines` just before, so the rollback leaves
  the award line untouched. `order_award_lines` itself is unchanged.
- Readers clamp to `min(award open, orderable)`: `awarded_lines` (sourcing/service.py:1288-1332)
  returns `orderable` per line (a new last field on `AwardedLine`, sourcing/schemas.py:581-595,
  read from `requisition_line` through the `rfq_line.requisition_line_id` it already joins), and
  `PurchaseOrderService.awarded` `open_qty` (service.py:267) and the change-order increase
  pre-check (changes.py:290-294) use the minimum.

### Reduce (after issue)

A quantities-only change order through E13-S06, so reduction has one code path. In one
transaction: **`ChangeService._lock(po_id)` first** (changes.py:610-625: award, line-project balances in id order, requisition, then the PO `FOR UPDATE`, the cancel order), then `issued` (else 409 `po_not_issued`) and `If-Match`
equal to its version; then `ChangeService.create(po_id, PoChangeCreate(reason=...))`,
`update(po_id, n, PoChangePatch(lines=..., reason=...), str(ch.version))` and
`submit(po_id, n, str(after.version))`. These lock the PO, then the change row (their own order). A
reduction is always material (`quantity` and `line` are in `MATERIAL`, changes.py:61), and `apply`
refuses material changes, so the response is the change in `approval_pending`, or `approved` when
the published workflow auto-approves at start (approvals/engine.py:~700-740), in which case E13-S06's
apply has already run inside `submit`. The release happens in that apply, never in this route's own
code. Because the route already holds award, balances, requisition and PO, an auto-approved apply's own
`_lock` only re-takes rows this transaction holds, so reduce cannot hold the PO while waiting for
the award (which would deadlock with cancel). Plain `ChangeService.submit` outside this route keeps
E13-S06's PO-first order; that existing hazard is out of scope here. An open change → `create`'s 409
`change_in_progress`.

### History

The PO, its revisions, PDFs and transmissions stay readable. `PoRead` gains, computed on read, no
stored column:

- `released_amount: str | None`: the positive absolute sum (release entries are stored negative) of
  `ledger_entry` rows with `entry_type='release'`, `bucket='committed'`,
  `source_type='purchase_order'`, `source_id = root` (lifetime: change-order decreases and the
  cancel), **excluding** releases posted by an actual (`_consume` posts those with the commitment's
  source and reason `"Consumed by actual"`, budget/postings.py:204; that is spend, not a release).
  Name that string once as `CONSUMED_BY_ACTUAL` in `budget/postings.py`, exported through
  `budget.service`, used by `_consume` and by this read. `None` when nothing was released.
- `released_currency: str | None`: the currency those entries carry (the commitments' currency,
  `rate["to"]`, issue.py:131); no conversion to the PO currency.

## Acceptance

- [ ] Cancel after issue: one release per open commitment entry equal to its remainder, one rereserve of the summed amount, requisition `cancelled_qty` unchanged, drift empty; retried (same key, or new key with the new `If-Match`) → nothing more posted (FIN-011).
- [ ] Cancel after a change order added a second commitment entry to a group: both entries released, `commitment_remaining` zero for the PO, no idempotency-key collision.
- [ ] Cancel after issue with a prior partial release on an entry: only the remainder is released.
- [ ] With `cancel_requisition_lines`: release, rereserve, return to main, `cancelled_qty` up; sub-project available and reservation remaining unchanged, main available up by the released amount, drift empty; the requisition reaches `completed` when its other lines are issued.
- [ ] With `cancel_requisition_lines` on a requisition that is not `open_for_purchase` or `completed` → 409 `requisition_not_cancellable`, no ledger entry, counters unchanged.
- [ ] Requisition with no live reservation: cancel succeeds for both flag values, no rereserve and no `release_unawarded` posting, released funds available on the commitment's project, drift empty.
- [ ] Cancel before issue (`draft`, `approved`): no ledger entry; `award_line.ordered_qty` and `requisition_line.ordered_qty` back. With `cancel_requisition_lines=true`: 200, `notice` present, `cancelled_qty` and the reservation unchanged.
- [ ] Cancel of an `approval_pending` PO: the approval instance ends `withdrawn`, PO `cancelled` at version + 2. Racing the final approval decision: either that outcome, or 409 `task_closed` with nothing posted and no quantity moved.
- [ ] Cancel of an `approval_pending` PO by a `purchase_order.amend` holder who is not its creator → 403, approval still running, nothing posted; other statuses are not creator-only.
- [ ] Cancel with a `po_change` in `draft` or `approval_pending` → 409 `change_in_progress`, nothing posted.
- [ ] After `cancel_requisition_lines`, creating a PO for the cancelled quantity → 409 `quantity_cancelled`, award line unchanged; `/awarded` `open_qty` and the change-order increase pre-check do not offer it.
- [ ] Cancel when the award is not `approved` (seeded) → 409 `invalid_transition`, no posting.
- [ ] Reduce (workflow with an approver): one `po_change` in `approval_pending`, no ledger entry; on approval the commitment falls and `award_line.ordered_qty` falls by the reduced quantity. A rise or a price edit in `lines` → 422 `reduce_only`.
- [ ] `released_amount` counts cancel and change-order decrease releases and excludes a release posted by an actual (seed one through `_consume`).
- [ ] Cancel or reduce without `If-Match` → 400; with a stale version → 409 `stale_version`.
- [ ] **Concurrency (real Postgres):** cancel vs issue on an approved PO → one wins (the other 409 `stale_version` or `invalid_transition`), ledger consistent; cancel vs a change-order apply on the same award → no deadlock; cancel vs a reduce whose workflow auto-approves, on the same PO → no deadlock, one wins; supersede of an award whose row another connection holds `FOR UPDATE` → 409 `po_exists` at once, holding no lock; cancel with `cancel_requisition_lines` vs an award approval on the same requisition → no deadlock, drift empty.
- [ ] TEN-010 isolation case for both routes (foreign PO → 404); a caller without `purchase_order.amend` → 403; `flo check --light` green.

## Plants

1. Release `amount=<original amount>` instead of `None`: the prior-partial-release test fails (409 `release_exceeds_commitment`).
2. Skip the rereserve on the default path: the decision-209 test (reservation remaining up by the released amount) fails.
3. Skip the rereserve on the `cancel_requisition_lines` path: `release_unawarded` takes the amount out of the reservation the open lines still need (or 409 `release_exceeds_reservation` when it held less), and the "sub-project available and reservation remaining unchanged" test fails.
4. Delete the `quantity_cancelled` check in `order_lines`: the PO-for-cancelled-quantity test gets the `line_order_ceiling` database error instead of the 409 and fails.
5. Drop the unlocked supersede probe: the probe test (a second connection holds the award row `FOR UPDATE`, as a cancel does after step 2; supersede runs under `SET LOCAL lock_timeout = '1s'`) gets a lock timeout instead of an immediate 409 `po_exists`, and fails.
