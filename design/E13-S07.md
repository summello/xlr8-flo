# E13-S07 — Cancel or reduce a PO: release the unused commitment exactly once, keep history

**Epic** E13 · **M3** · **ledger/M** · after **E13-S06** · tags: `money` (Opus review)

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** canvas DECISIONS **209** (the released commitment is re-reserved on the sub-project
> for the reopened quantity; if the requisition line is cancelled too, it is released and returned to
> the main project, as 205), D-M2-26. `design-system/pages/purchase-orders.md` §2 "Cancel or reduce
> releases only the unused commitment, once", §4.8.
> **Writes:** every `PATCH`/`PUT`/`DELETE` on an editable resource follows `docs/m2-conventions.md` §O (`If-Match` with the integer version, `ETag` on reads, 400 when missing, 409 `stale_version` on mismatch). `Idempotency-Key` protects **POST** commands only (the middleware ignores other methods); where a packet says "(Idempotency-Key)" on a non-POST route, read §O instead.
> **RLS:** every new tenant table gets literal `ALTER TABLE <t> ENABLE ROW LEVEL SECURITY; … FORCE …; CREATE POLICY tenant_isolation ON <t> …` statements in the migration text, one block per table, never generated by a helper or f-string (the static gate in `tests/isolation/test_ci_guards.py` reads the text; the light check runs it).

## Requirements (inlined)

- **PO-013** — Cancelling or reducing a PO must release the unused commitment exactly once and must not erase its history.
- **ACC-006** — Cancelling a requisition or PO releases only its unused funds, once.
- **FIN-011** — a release happens exactly once.

## Design

`POST /purchase-orders/{id}/cancel` and `POST /purchase-orders/{id}/reduce` (Idempotency-Key,
**and `If-Match` with the PO's integer version**, as `POST /{id}/issue` takes it: 400 when missing,
409 `stale_version` on mismatch, checked **once, at entry**, against the PO row read `FOR UPDATE`.
**Lock order is issue's** (`purchasing/issue.py`): `_row(po_id)` unlocked for the 404, then `lock_award` on each award the PO draws on, sorted, **first** (`order_award_lines` requires it and `ChangeService._lock` takes it first, changes.py:610-625; issue never touches the award; an award that is not `approved` makes `lock_award` raise 409 `invalid_transition`, which cancel lets through, before any posting; a cancel racing `AwardService.supersede`, which locks balances before the award (awards.py:854-857), can still deadlock: pre-existing, the change orders share it, and out of scope here), then `lock_balance` on
every line project in sorted order (with `cancel_requisition_lines` after issue, the **union** of the line projects and each requisition's own `project_id`, the main project that `release_unawarded` moves funds into, sorted together, as the award path does in `award_funding`), then `reservation_entry(..., lock=True)` per requisition in sorted order,
**then** the PO `FOR UPDATE`, then the status and version checks. Never lock the PO before a balance or
requisition: the cancel/issue race would deadlock. Cancel then passes the version it
reads after any earlier step in the same transaction to `lifecycle.transition` (a pending approval's
withdrawal advances the PO version first, so cancel re-reads it, never reuses the header). `/reduce`
makes no PO transition: the entry check is its whole PO-version contract (`ChangeService.create` and `submit` take the PO lock themselves and compare nothing against the PO version), and the change order's own
versions are internal to the route; every `lines` edit must fall, checked in the route before `propose`, which would accept a rise;
`purchase_order.amend`, reason required, **and** `cancel_requisition_lines: bool` default false, **and** `notify_vendor: bool` default true; the email hook is a stub until E13-S09). A cancel retried on an already-cancelled PO replays as `issue` does (`expected in (version, version-1)`), otherwise 409 `invalid_transition`.
`/reduce` also takes `lines: list[PoChangeLineEdit]` (E13-S06's schema, `line_no` plus a lower
`quantity` or `remove`; any other field, or a quantity that does not fall, is 422).

**Returning quantity** always moves all three counters by the negative delta, in E13-S06's order
(`changes.py` around `order_award_lines`): `order_award_lines` (so `award_line.ordered_qty`, which
PO availability reads, falls), `order_lines` and, after issue, `issue_lines`.

- **Before issue** (`draft`, `approval_pending`, `approved`): cancel → `cancelled`. Nothing was committed. Quantity returns through `PurchaseOrderService._move(row, None)`, which draft delete already uses (service.py:776-782: `order_award_lines` and `order_lines`, negative; nothing was issued). An open approval is withdrawn. `cancel_requisition_lines` is **ignored** here (operator, 30 Oct 2026): the PO committed and reserved nothing, so `cancelled_qty` and the requisition's reservation do not move, and there is no 422. The response carries `notice: str | None`, the fixed text "Requisition lines were not cancelled: the PO was never issued. Cancel them on the requisition." (`None` otherwise).
- **After issue — cancel:** for each commitment group, **each commitment entry** in it with `remaining > 0` (a change order can add several per group; read them as E13-S06's decrease path does, `commitment_remaining` joined to `ledger_entry`, **by the PO's revision root** (`source_id = _root`, as `changes._post` does, changes.py:758); the key still uses the current `{id}`), `release_commitment(entry_id, amount=None)` (the remainder, i.e. **unused**: `remaining()` already nets any actuals; M3 has none, M4 adds receipts). Key `po:{id}:cancel:{group}:{entry_id}`. Then:
  - default (decision 209): `requisitions.service.rereserve` the released amount on the sub-project, and return the quantity (all three counters, above), so the requisition line is open to order again;
  - `cancel_requisition_lines = true` (operator, 30 Oct 2026, option b): the release already returned the amount to the sub-project's available, so **rereserve first, then return**: `requisitions.service.rereserve` the released amount on the sub-project (exactly as the default path), then `release_unawarded` moves it to the **main project** (it gains keyword-only `source: str` and `key: str` parameters whose defaults keep
today's `award:{award_id}` source and `award:{award_id}:return:{req}` key byte-identical; cancel passes
source `po:{id}` and key `po:{id}:cancel:return:{req}`), and `requisitions.service.cancel_lines` raises `cancelled_qty`. Two postings, one net effect: sub-project available unchanged, main up, never negative because the reservation exists again when `release_unawarded` subtracts. Releases, rereserve and return run in one transaction under issue's lock order.
  - **Per requisition, not per group:** sum the released amounts over the PO's groups and call `rereserve` once (key `po_cancel_{id}`, as `changes.py` names `po_change_{n}`), then the return and `cancel_lines` once with the summed amounts; per-group calls would create extra funding rounds. `release_unawarded` makes `award_id` optional and cancel passes the PO version as its `version`.
  - **No live reservation** (`reservation_entry` is None; issue allows it): skip the `rereserve` as `changes._post` does, and on the `cancel_requisition_lines` path skip `release_unawarded` too, since the funds are already on the project. `cancel_lines` still raises `cancelled_qty`.
  - **Pending change order:** cancel after issue refuses with 409 `change_in_progress` (the code `ChangeService` already uses, changes.py:438) while a `po_change` is in `draft` or `approval_pending`; the author withdraws it first. `ChangeService.submit` and `_apply` also refuse on a cancelled PO.
  - **`cancel_lines` (operator, 30 Oct 2026, option B):** raises `cancelled_qty` by the returned quantity and leaves `awarded_qty` and `sourced_qty` alone: the award line keeps the cancelled quantity visible as "cancelled, not re-orderable". **Line-level block (operator, 30 Oct 2026):** `cancelled_qty` lives on `requisition_line`, there is no `award_line.cancelled_qty` and no migration, and a vendor's award line may still look open. The requisition line's orderable quantity (`quantity - cancelled_qty - ordered_qty`) is the ceiling, enforced where PO quantity is taken: `requisitions/sourcing.py::order_lines` (today `awarded_qty - ordered_qty`, around line 222) raises 409 `quantity_cancelled` when the request fits the award but exceeds the orderable quantity, **before** `sourcing/service.py::order_award_lines` (around line 1395) is reached, so the award line is never touched; never the `line_order_ceiling` CHECK surfacing as a database error. Readers that show open quantity clamp to `min(award open, orderable)`: `purchasing/service.py` `/awarded` `open_qty` (around line 267), `purchasing/changes.py` increase pre-check (around lines 291-293) and the `sourcing/service.py` award-line read (around lines 1393-1396). `award_lines`, `mark_awarded`, `mark_sourced`, `mark_unsourced`, `sourcing_basis` and `sourceable_lines` are unchanged: they act only on `sourcing_in_progress` or `sourced` requisitions, `cancel_lines` requires `open_for_purchase` or `completed`, so cancelled lines never reach them. Guards: the requisition is `open_for_purchase` or `completed` (otherwise 409 `requisition_not_cancellable`, checked **before** any posting), and `cancelled_qty` may not exceed the returned open quantity. Afterwards call `mark_completed` when no open quantity remains, else `reopen_for_purchase`.
  - **One project per requisition:** `rereserve` reposts on the reservation's own project, so cancel asserts that every released group of a requisition belongs to its reservation's project (otherwise 409 `cross_project_cancel`, before any posting). The default path also takes `lock_funding` on that project.
  - **Zero total:** a requisition whose summed released amount is 0 skips `rereserve` and `release_unawarded` (no empty funding round).
  - PO → `cancelled` through `lifecycle.transition`. The vendor is told (E13-S09: a cancellation email through the outbox) unless `notify_vendor=false`.
- **After issue — reduce:** a quantities-only change order through E13-S06, so reduction is one code path. The route is a shortcut: it creates the change (`ChangeService` create + update with `lines`) and then **submits** it, since a reduction is material and E13-S06's `apply` refuses material changes. The response is the change in `approval_pending`; the release happens when E13-S06 applies it on approval, never in this route. A retry with the same key returns the same change.
- A requisition that was `completed` and regains open quantity returns to `open_for_purchase` via `requisitions.service.reopen_for_purchase`, audited.
- **History:** the PO, its versions, PDFs and transmissions stay readable. A cancelled PO shows the released figure: `PoRead` gains `released_amount: str | None` (decimal
string, the positive absolute sum because release entries are stored negative, `None` when nothing was released) plus `released_currency: str | None`, the currency the
release entries carry (the project currency `issue.py` posts commitments in; no conversion to the PO currency) = the sum of ledger entries with `entry_type='release'`, committed bucket and `source_type='purchase_order'`
whose source is this PO's revision root, i.e. lifetime across versions, change-order decreases
included; computed on read, no stored column.

## Acceptance

- [ ] Cancel after issue: one release per group equal to the remainder, one re-reservation of the same amount, drift empty; retried → nothing more (FIN-011).
- [ ] With `cancel_requisition_lines`: release, rereserve, return to main, and `cancelled_qty` up; sub-project available unchanged and never negative, main up by the released amount, drift empty; the requisition can complete without those lines.
- [ ] Cancel before issue: no ledger entry; quantity back. With `cancel_requisition_lines=true`: ignored, `cancelled_qty` and the reservation unchanged, `notice` present, 200.
- [ ] Requisition with no live reservation: cancel succeeds, no rereserve and no `release_unawarded` posting, no 404, drift empty (both flag values).
- [ ] Cancel with a `po_change` in `draft` or `approval_pending` → 409 `change_in_progress`; submitting or approving a change on a cancelled PO is refused.
- [ ] Cancel with `cancel_requisition_lines` racing an award on the same requisition: no deadlock, ledger consistent.
- [ ] A PO spanning two groups of one requisition makes one rereserve (one funding round).
- [ ] After `cancel_requisition_lines`, creating a PO for the cancelled quantity → 409 `quantity_cancelled` with the award line untouched; `/awarded` `open_qty` and the change-order increase pre-check do not offer it.
- [ ] Cancel on a requisition that is not `open_for_purchase` or `completed` → 409 `requisition_not_cancellable`, no posting; a cross-project requisition → 409 `cross_project_cancel`, no posting.
- [ ] Cancel with an award that is not `approved` → 409 `invalid_transition`, no posting; cancel racing a change-order apply on the same award: no deadlock.
- [ ] Reduce uses the change-order path: one `po_change` row in `approval_pending`, no ledger entry until it is approved; on approval the commitment falls and `award_line.ordered_qty` falls by the reduced quantity.
- [ ] Cancel after a change order added a second commitment entry to a group: both entries released, `commitment_remaining` zero, no idempotency-key collision.
- [ ] Cancel or reduce without `If-Match` → 400; with a stale version → 409 `stale_version`.
- [ ] **Concurrency:** cancel and issue racing on an approved PO → one wins and the ledger is consistent.
- [ ] TEN-010 and authorization; `flo check` green.

## Plants

1. Release `amount = original` instead of the remainder: the "unused only" test with a prior partial release fails.
2. Skip the re-reservation: the decision-209 test fails.
3. Skip the rereserve in the `cancel_requisition_lines` path: sub-project available goes negative and that test fails.
