## Requirements (inlined)

- **PO-001** — POs must be creatable from approved and sourced requisitions or authorized project items. *(M3: from approved awards only, decision 163.)*
- **PO-002** — A PO must include requestor, Bill To, Ship To, vendor, items/services, descriptions, quantities, units, unit prices, currency, taxes, freight, terms, dates, project, department, and ledger accounts.
- **PO-006** — PO numbers must be unique within their configured organization/BU/OU sequence.
- **PO-009** — Partial POs must reduce only the corresponding open requisition quantity and value.
- **SRC-018** — Every expenditure line must complete RFQ sourcing before final award, PO submission, or financial effect.
- **VEN-012 / VEN-013** — eligibility at selection; the vendor snapshot is kept.

## The ordered-quantity guard (PO-009)

`open to order = awarded_qty − ordered_qty` on `requisition_line`, but only for quantity awarded **to
this vendor on an approved award** (tracked per award line: `award_line.ordered_qty NUMERIC(18,4) NOT NULL DEFAULT 0
CHECK (ordered_qty >= 0 AND ordered_qty <= quantity)`, a new column added here). Two counters, one transaction,
both updated by every change (quantity only; there is **no** stored ordered amount, see Ordered value): `sourcing.service` first locks
the **award header** (`award_by_id(award_id, lock=True)`, the same `FOR UPDATE` supersede takes in `sourcing/awards.py`
`supersede`) and re-checks `status = 'approved'` under that lock (else 409 `invalid_transition`), so a create and a supersede of
one award serialize: supersede either runs first (the create then sees `superseded`) or waits and then finds the PO through its
`po_exists` probe. Lock order is award header → award lines → requisition lines, matching supersede's award → requisitions, so the
two cannot deadlock. (`ponytail:` the header lock serializes every PO create on one award; per-line locks if that ever queues.)
Then it locks the award lines (key order) and refuses when
`award_line.quantity − award_line.ordered_qty < delta`; then `requisitions.service.order_lines(conn, scope, changes, actor)`
(on the `source_lines` pattern, `requisitions/sourcing.py` ~95–125) locks the **requisition header** first (`read_row(repo, id, lock=True)`),
then its lines in id order, and only then calls `assert_current_upstream` (whose own read is unlocked, `links.py` ~335, so the
header lock is what stops a concurrent amendment or code substitution from racing the create), refuses
when `awarded_qty − ordered_qty < delta`, and applies `requisition_line.ordered_qty += delta`. Both refusals are 409
`over_open_quantity` with the figures; negative deltas (lower or delete) return quantity to both counters. **A draft PO holds its
quantity** (same reasoning as E12-S01). Deleting the draft or lowering a line returns it.

## Ordered value (PO-009 "value", Decisions 1)

Derived, never stored: no `ordered_amount` column on `requisition_line`, `award_line` or `purchase_order`.
Per `po_line`: `value = quantize(quantity × unit_price, po.currency)` (vendor currency) and
`value_converted = quantize(value × rate, rfq_ccy)` with `rate = Decimal(award.rates[po.currency]["rate"])`,
the award's frozen rate, into the RFQ currency the award's figures use (the same rate and per-row
rounding as `sourcing.awards.amounts`, all through `kernel/money.quantize`). The PO's `total` and
`total_converted` are the sums of its lines' figures. Display only: nothing is posted to the ledger here.
`GET /purchase-orders/{id}` returns both per line and in total; `GET /purchase-orders/awarded-lines`
returns per award line `ordered_qty` (the counter) and `ordered_value` (Σ `value` of the `po_line` rows for
that award line). Tax and freight join the value in E13-S02.

## Creation

`POST /api/v1/purchase-orders` (Idempotency-Key, `purchase_order.create` on the unit), body
`{award_id, vendor_id, lines: [{rfq_line_id, quantity}], override_reason?}`. **One PO per vendor and requisition** (Decisions 3). All lines must belong to `vendor_id`:
a line with no award line for that vendor → 422 `mixed_vendors`. All lines must draw from one requisition (the award line's
`requisition_id`): lines from two or more requisitions → 422 `mixed_requisitions` (an award may span several requisitions,
`sourcing/awards.py` ~347; the user makes one PO per requisition). The header's `requisition_id`, `requester_id`,
`ship_to_address_id` and `needed_by` come from that one requisition. The award must be `approved`. The vendor's eligibility (E11-S11)
for the unit is checked: not eligible → 409 `vendor_not_eligible`, unless `override_reason` and
`rfq.approve` on the unit (MASTER §7.14; audited). Bill To and Ship To come from the masters, never
typed (decision 165). The recipients default to `vendors.service.document_recipients` (stored on
the PO, E13-S09 sends).

Also `GET /purchase-orders/awarded-lines?award_id=&vendor_id=` (open to order per award line,
grouped by vendor, each with its `requisition_id`), `GET /purchase-orders/{id}`, `PATCH /purchase-orders/{id}` (draft: terms,
needed-by, Ship To from the allowed list, and `lines: [{line_no, quantity}]`: each listed existing line takes the new quantity
(`> 0`) through both counters by the delta; omitted lines are unchanged; an unknown `line_no` → 422 `validation-failed`. PATCH
neither adds nor removes lines: order more with another PO, and to drop a line delete the draft and create it again),
`DELETE /purchase-orders/{id}` (draft only, `If-Match`; a **soft delete** on the E22-S02 convention, `requisitions/service.py` ~200:
`status = 'deleted'`, the row and its number kept, never reused; returns every line's quantity to both counters; non-draft → 409
`po_not_draft`; add `purchase-orders` to `IDEMPOTENT_DELETE_PATTERN` in `kernel/idempotency/middleware.py` ~53 so the
command replays like a POST, with a test that a replayed DELETE returns the stored response; `deleted` rows are excluded
from the list and its counts, and their detail is 404), and
`GET /purchase-orders?tab=&cursor=` (a paged list with counts per tab for E13-S12).

**Permissions** (Decisions 2; both codes already exist in `modules/identity/models.py` `PERMISSION_CODES`, nothing to register), each checked
on the unit, server-side, through `Depends(require(code, target))` as `api/sourcing.py` does (`_unit`, `rfq_target` ~78–104): the PO's unit for detail/PATCH/DELETE, the award's RFQ unit for POST and awarded-lines.
**The list is the exception:** `GET /purchase-orders` uses `Depends(require_granted("purchase_order.view"))` (`kernel/authz.py`,
as `api/projects.py` `ListScopes` does) and narrows its rows and tab counts to `granted.org_wide OR unit_id = ANY(granted.bu_ids)`
(the `modules/projects/service.py` ~996 pattern); never `require(..., list_target)`, which resolves an unfiltered list to the
organization and would 403 a unit-scoped viewer:

| Route | Permission |
|---|---|
| `GET /purchase-orders`, `GET /purchase-orders/{id}`, `GET /purchase-orders/awarded-lines` | `purchase_order.view` (the list returns only POs on units where the caller holds it) |
| `POST /purchase-orders` | `purchase_order.create` (+ `rfq.approve` for an eligibility override) |
| `PATCH /purchase-orders/{id}`, `DELETE /purchase-orders/{id}` (draft) | `purchase_order.create` |

Foreign tenant → 404 on every route, never 403. Baseline roles today: `purchasing-user` holds both; `organization-administrator` all;
`auditor` holds `purchase_order.view` only (read-only set); `sourcing-specialist`, `requestor` and `executive-viewer` hold neither.

Register the `purchase_order` link-graph node (with `access`) and, from purchasing's own wiring,
`sourcing.service.register_supersede_guard(probe)` (E12-S09) with a probe returning True when a `purchase_order` row
exists for the award, so supersede is refused 409 `po_exists` once a PO exists.

## Acceptance

- [ ] Migrations up, down and data preservation.
- [ ] Numbering: two units each get their own sequence; numbers are unique per unit and never reused.
- [ ] Guard: under, equal and above open → 409 with figures; partial PO reduces only that line's open quantity; deleting the draft returns it.
- [ ] **Concurrency (real Postgres):** two POs for the last 5 units of one award line at once → exactly one.
- [ ] **Concurrency (real Postgres):** PO create and award supersede on one award at once → exactly one succeeds: either the PO exists and supersede is 409 `po_exists`, or the award is superseded and the create is 409 `invalid_transition` with nothing written.
- [ ] Bill To: an address only on the top-level unit is found from a child unit's PO; none anywhere on the chain → 409 `bill_to_missing`.
- [ ] List: a `purchase_order.view` holder on unit A only gets 200 with unit A's POs and none of unit B's (not 403).
- [ ] Mixed vendors → 422 `mixed_vendors`; lines from two requisitions of one award → 422 `mixed_requisitions`, nothing written; header requester, ship-to and needed-by equal the requisition's; unapproved award → 409; stale requisition / pending amendment / expired codes → 409 from `assert_current_upstream`.
- [ ] Ineligible vendor refused; overridden by `rfq.approve` with a reason, audited.
- [ ] Line project = the sub-project (D-M2-26), and codes copied from the requisition header.
- [ ] **Ordered value (hand-computed):** vendor EUR, award rate 1.1000 into USD; PO lines 3 × 10.0000 and 2 × 7.5000 → `value` 30.00 and 15.00 EUR, `value_converted` 33.00 and 16.50 USD, `total` 45.00 EUR, `total_converted` 49.50 USD; awarded-lines `ordered_value` matches; no `ledger_entry` row written; no stored amount column exists (migration schema assertion).
- [ ] Authorization per role and route: `purchasing-user` all routes; `auditor` GETs 200, POST/PATCH/DELETE 403; `sourcing-specialist` and `requestor` 403 on every route; a holder of `purchase_order.create` on unit A only → 403 on a PO of unit B; list shows only permitted units.
- [ ] TEN-010: every new route in the isolation suite; a foreign-tenant PO id or award id → 404.
- [ ] PATCH lines: raising and lowering one line moves both counters by the delta; an omitted line is unchanged; an unknown `line_no` → 422.
- [ ] DELETE: the draft becomes `deleted`, both counters are restored, its number is not reused, a replayed DELETE (same key) returns the stored response.
- [ ] A requisition amendment submitted concurrently with a PO create: the create either completes first or is refused by `assert_current_upstream`; never a PO against the amended version.
- [ ] `flo check` green.

## Plants

1. Put the line on the main project: the D-M2-26 assertion fails.
2. Check open before locking: the concurrency test sees two.
3. Drop the `mixed_requisitions` check: the two-requisition test creates a PO.
4. Guard `PATCH` with `purchase_order.view`: the auditor PATCH test sees 200.
5. Convert at today's FX rate instead of `award.rates`: the hand-computed value test fails.
6. Drop the award-header lock in create: the create-versus-supersede test sees a PO on a superseded award.
7. Guard the list with `require(..., list_target)`: the unit-A-only list test sees 403.

## Decisions

**27 Oct 2026, operator (final)**, from the Codex pre-flight of 27 Oct (packet 7021928607):

1. **Ordered value (PO-009)** is derived from `po_line`: the sum of PO lines in the PO (vendor) currency, converted at the award's stored rate for display. No new stored `ordered_amount` column. The quantity counters stay as specified.
2. **Permissions:** `GET` list, detail and awarded-lines → `purchase_order.view`; `PATCH` and `DELETE` of a draft → `purchase_order.create`; `POST` stays `purchase_order.create`; all scoped to the unit. Foreign tenant → 404. Authorization test per role plus a TEN-010 case.
3. **Scope:** one PO per vendor **and** requisition; a selection mixing requisitions is refused 422 `mixed_requisitions`. Header requester, ship-to and needed-by come from that single requisition.
