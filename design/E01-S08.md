# E01-S08 — Production migration runner, packaged in the image, run by flo-migrate

**Epic** E01 · **M0** · **migration/M** · after **E01-S05** · tags: `migration`, `security`

## Why this story exists

The 12 revision files in `migrations/` are plain Python modules (`revision`, `down_revision`,
`upgrade(connection)`, `downgrade(connection)`). Only tests load them. The Cloud Run job
`flo-migrate` runs `alembic upgrade head`, but the repo has no `alembic.ini`, no alembic
dependency, and the API image copies only `apps/api/src`, so no migration reaches production and
the first deploy cannot pass its migration step. Found by Opus at the M0 milestone review.

## Requirements

- **REL-002** — Transactional operations must fail atomically and return an actionable error or a safely retryable status.
- **SEC-005** — Secrets must not be stored in source code, browser bundles, logs, or ordinary configuration files.

## Deliverable

A runner, `python -m flo.kernel.migrate`, that brings a database to head using the existing revision
files unchanged. Do **not** add alembic; the existing files are the contract.

## Behaviour

1. **Discovery.** Load every `*.py` in the migrations directory by path, sorted by filename. The
   directory is `MIGRATIONS_DIR` (env) defaulting to `/app/migrations`. Skip files starting `_`.
2. **Chain check before touching the database.** Build the `revision → down_revision` chain. Fail
   (exit 1, message names the revision) on: a duplicate revision, a `down_revision` that matches no
   file, more than one head, or a file whose order by filename disagrees with the chain. Revision
   `20260825_0006` does not exist; the chain, not the filename numbering, is the truth.
3. **Version table.** `schema_migration(revision text PRIMARY KEY, applied_at timestamptz NOT NULL
   DEFAULT now())`, created `IF NOT EXISTS`. It is not tenant data: no `org_id`, no RLS.
4. **Serialisation.** The job uses the **pooled** `DATABASE_URL`, so session-level advisory locks
   are unsafe. Inside each revision's transaction, first run `pg_advisory_xact_lock(<fixed key>)`,
   then re-read `schema_migration` and skip the revision if another runner already applied it.
   The lock releases with the transaction.
5. **Apply.** For each unapplied revision in chain order: one transaction containing
   `upgrade(connection)` and the `schema_migration` insert. Any exception rolls that revision back,
   stops the run, exits 1, and prints the revision id and exception type only — never the SQL, the
   DSN, or the exception text (SEC-005, SEC-011).
6. **Already applied revisions are skipped**, not re-run. Re-running at head is a no-op that exits 0.
7. **Applied-but-unknown guard.** If `schema_migration` holds a revision with no file, exit 1: the
   image is older than the database.
8. **Config.** Read `DATABASE_URL` through `flo.kernel.config.Settings` like the API does, so the
   pooled-host guard applies. No new settings except `MIGRATIONS_DIR`.
9. **Image.** `apps/api/Containerfile` copies `migrations/` into `/app/migrations`. The build
   context is currently `apps/api`; change the CI build step to use the repo root as context with
   `--file apps/api/Containerfile`, and adjust the `COPY` paths. Do not widen the runtime image
   otherwise. The image keeps no shell (`/bin/sh` is removed), so the job must invoke Python directly.
10. **Job definition in CI.** The deploy step creates `flo-migrate` when `gcloud run jobs describe`
    fails and updates it otherwise, both with `--command python --args -m,flo.kernel.migrate
    --max-retries 0 --task-timeout 10m` and `--set-secrets DATABASE_URL=flo-database-url:latest`.
    Update `infra/SETUP.md` §7 to the same command and remove the alembic text.
11. **Manual deploy trigger.** Add `workflow_dispatch:` to `on:`. The `deploy` job runs when
    (`github.ref == 'refs/heads/main'` and event is `push`) **or** (event is `workflow_dispatch` and
    `github.ref` is `refs/heads/main` or starts with `refs/heads/milestone/`). A dispatch on any other
    ref must not deploy.

## Acceptance criteria

- [ ] On an empty real-Postgres database the runner applies all revisions in chain order and records each in `schema_migration`
- [ ] A second run applies nothing and exits 0
- [ ] A revision that raises is rolled back completely (its tables absent, no `schema_migration` row), earlier revisions stay applied, exit code is 1
- [ ] Two runners started concurrently against one empty database: both exit 0 and every revision is applied exactly once
- [ ] Duplicate revision, dangling `down_revision`, two heads, and an applied-but-unknown revision each exit 1 with a message naming the cause and no SQL or DSN
- [ ] The runner's output on failure contains neither the database URL nor any password (planted-secret test)
- [ ] Every shipped revision's `downgrade` still works after the runner applied it (apply to head, then downgrade in reverse chain order, ends with an empty schema except `schema_migration`)
- [ ] The built image contains `/app/migrations/*.py` and `python -m flo.kernel.migrate --check` (chain validation only, no database) exits 0 inside it
- [ ] CI contains a test that plants a `workflow_dispatch` on `refs/heads/feature/x` and proves the deploy condition is false, and that `refs/heads/milestone/M0-rails` is true
- [ ] `grep -ri alembic infra apps .github` returns nothing
