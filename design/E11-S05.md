# E11-S05 — Onboarding request and a configurable, versioned, weighted questionnaire

**Epic** E11 · **M3** · **engine/L** · after **E11-S01** · tags: none

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** canvas DECISIONS 126 (6h-6, a low score informs and never blocks) and 137,
> `design-system/pages/vendors.md` §3.3 and §3.5, open questions §7.6. Back end only; the request
> form UI is E11-S14 and the questionnaire admin UI is E11-S17.
> **Writes:** every `PATCH`/`PUT`/`DELETE` on an editable resource follows `docs/m2-conventions.md` §O (`If-Match` with the integer version, `ETag` on reads, 400 when missing, 409 `stale_version` on mismatch). `Idempotency-Key` protects **POST** commands only (the middleware ignores other methods); where a packet says "(Idempotency-Key)" on a non-POST route, read §O instead.

## Requirements (inlined)

- **VEN-004** — Users must be able to submit a new-vendor onboarding request.
- **VEN-006** — Administrators must be able to configure onboarding questionnaires with typed fields, required answers, weights, and scoring.
- **CUS-007** — Changing a definition must not reinterpret historical values silently.

## Design

### Questionnaire versions (VEN-006, CUS-007)

`vendor_questionnaire` (one per org) → `vendor_questionnaire_version`: `id`, `org_id`, `number int`
(1, 2, …), `status` CHECK in `draft`, `published` and `retired`, `threshold int NOT NULL` (0..100),
`published_at`, `published_by`. At most one `published` version per org (partial unique index).
Publishing retires the previous one.

`vendor_question`: `version_id`, `position int`, `key text` (stable within a version), `prompt`,
`type` CHECK in `text`, `number`, `yes_no`, `single_choice`, `multi_choice`, `date` and `file`,
`required bool`, `weight int` (0..100), `options jsonb` (for the choice types:
`[{value, label, points}]` with points 0..100; for yes_no, `{yes, no}` points; for number, an
optional `[{min, max, points}]` band list; text, date and file score `points` 100 when answered,
0 when not).

**A published or retired version is immutable.** Every write to a question or version checks
`status = 'draft'` under `SELECT … FOR UPDATE` on the version row, or returns 409
`version_immutable`. A database trigger enforces the same thing (belt and braces, like the
append-only tables).

**Publish** refuses unless the weights total **exactly 100** (409 `weights_total`, with the actual
total in `checks`) and there is at least one question. To change anything, the admin copies the
published version to a new draft: `POST /admin/vendor-questionnaires/{vid}/copy`.

### Score

`score = Σ(weight × points / 100)` over the questions, an integer from 0 to 100, computed with
`Decimal` and rounded `quantize(Decimal(1), ROUND_HALF_UP)` (a score is not money, so not
`kernel/money`; no float, no `round()`).
An unanswered optional question scores 0. The breakdown per question is stored with the request,
so a later version never re-scores it (CUS-007).

### Onboarding request (VEN-004)

Any authenticated employee (a new permission `vendor.request`, granted to every baseline role by
migration, pattern 0053) creates a **vendor in `draft`** through E11-S01's create, **plus**
`vendor_onboarding` (one per vendor): `vendor_id`, `version_id` (the published version **at
creation**; a draft started on v3 finishes on v3, open question §7.6), `answers jsonb`
(`{key: value}`), `score int NULL`, `breakdown jsonb NULL`, `requested_by`, `submitted_at NULL`.

- `PUT /vendors/{id}/onboarding/answers` (Idempotency-Key) by the requester while `draft`: validates
  each answer against its question's type (422 per field, keyed `answers.<key>`), required answers
  only at submit.
- `file` answers reference an E09-S10 attachment on the vendor (`document_type='vendor'`).
- **Weights and points are never returned to the requester** (pages/vendors.md §3.3). The requester
  gets questions with prompt, type, required and option labels. Admins (`org.setting.manage`) and
  approvers (via E11-S06's evidence) see the weights.
- Score is computed **at submit**. Submitting itself is E11-S06 (it goes to approval with the
  duplicate check). This story exposes `service.score(vendor_id) -> ScoreResult(score, threshold,
  breakdown)` and `service.answers_complete(vendor_id) -> list[str]` (missing required keys).

A score below the threshold is **a fact on the result**, never a refusal (decision 6h-6).

### Admin API (`org.setting.manage`)

`GET /admin/vendor-questionnaires` (versions), `POST …` (new draft), `GET/PATCH …/{vid}`
(threshold), `POST/PATCH/DELETE …/{vid}/questions[/{key}]`,
`POST …/{vid}/questions/{key}/move` with `{direction: "up" | "down"}` (the keyboard-first reorder,
decision 137; no drag API is needed), `POST …/{vid}/publish`, and `POST …/{vid}/copy`.
All writes take Idempotency-Key and are audited (`vendor.questionnaire.*`).

## Acceptance

- [ ] Migrations up, down and data preservation, including the trigger and the new permission grants.
- [ ] Publish refuses at a total of 99 and 101 and accepts at 100; a published version refuses every write (service 409 **and** trigger: a raw UPDATE in the test raises).
- [ ] Copy produces an identical draft with a new number; editing it leaves the published version unchanged.
- [ ] Score: a worked example with each question type (table in the test) gives the hand-computed integer; half-up at .5; unanswered optional → 0.
- [ ] A request started on v1 keeps v1 after v2 publishes, and scores against v1.
- [ ] The requester's question payload contains no `weight` or `points` key at any depth (assert by walking the JSON).
- [ ] Move up on the first question and move down on the last → 409 `cannot_move`.
- [ ] TEN-010 on every route; a requester cannot read another requester's draft vendor (404 for a vendor not visible to them, which is the E11-S01 read rule plus "own drafts").
- [ ] `flo check` green.

## Plants

1. Remove the trigger: the raw-UPDATE test fails.
2. Use `float` in the score: the money-module float lint fails, or the .5 case does; say which.
3. Return `weight` to the requester: the JSON-walk test fails.
