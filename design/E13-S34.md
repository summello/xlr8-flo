# E13-S34 — Change-order and cancellation emails follow the sending-domain gate

**Epic** E13 · **M3** · **engine/S** · after **E13-S30**, **E13-S24**, **E13-S06** · tags: none
Origin: M3 Opus milestone review round 2 (finding on `purchasing/changes.py` ~688, EML-001) and E13-S30's recorded
follow-up (cancel notice). Operator, 23 Nov 2026: known gaps are fixed in PR #22.

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.

Backend only. No migration, no API shape change, no frontend change.

## Requirements (inlined)

- **EML-001** — The system must verify SPF and DKIM for the sending domain before the first PO email is sent.
- **E13-S30 decision (b)** (operator, 8 Nov): issue refuses a PO email the domain cannot send and offers
  issue-without-email, so nothing goes dead in the outbox.

## The defect

E13-S30 made **issue** check `transmission.po_email_allowed(conn, settings)` (`purchasing/issue.py` ~86) before it
queues anything. Two other paths still queue a `po-` email with no check, so while the sending domain is unverified
the row is queued and then dead-lettered by the dispatcher (`kernel/outbox/dispatcher.py` ~114-115,
`PermanentOutboxError(DOMAIN_NOT_VERIFIED)`), and nobody is told:

1. **Change-order apply** (`purchasing/changes.py` ~688): `enqueue_transmission(self.connection, self.scope, new_id, 2)`
   runs unconditionally inside the approval callback.
2. **Cancel notice** (`purchasing/cancel.py` ~116-124): `enqueue_cancellation` runs whenever the PO was issued,
   `notify_vendor` is true and recipients exist.

## Fix

Both paths read `transmission.po_email_allowed(conn, settings)` in their own transaction (the function issue
already uses, `transmission.py` ~478; pass the same `Settings` the callers have or obtain it as issue does) and, when
it is false, **queue nothing and record why**. Neither path may fail on it: change-order apply is an approval
outcome and a cancellation is the operator's decision; both still commit their document and money effects.

1. **Change-order apply:** skip `enqueue_transmission`; write the audit event
   `purchase_order.revision_without_email` on the new revision (actor = the applying actor, `after` =
   `{"revision": <new id>, "reason": "domain_not_verified"}`), matching E13-S30's `purchase_order.issue_without_email`.
   Once the domain passes, the existing **Resend** on the transmission log sends that revision (E13-S16); nothing new
   is needed for that.
2. **Cancel notice:** skip `enqueue_cancellation` and record it exactly as the no-recipient case already does
   (`transition(..., after={"vendor_notified": False})` ~119-121), adding `"reason": "domain_not_verified"` to that
   `after` map so the two cases are distinguishable in the audit.

When `email_provider` is not `resend` (dev, test), `po_email_allowed` is true and both paths queue as today.
