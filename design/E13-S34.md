# E13-S34 — Change-order and cancellation emails follow the sending-domain gate

**Epic** E13 · **M3** · **engine/S** · after **E13-S30**, **E13-S24**, **E13-S06** · tags: none
Origin: M3 Opus milestone review round 2 (finding on `purchasing/changes.py` ~688, EML-001) and E13-S30's recorded
follow-up (cancel notice). Operator, 23 Nov 2026: known gaps are fixed in PR #22.

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.

Backend only. No migration, no API request/response shape change, no frontend change.

## Requirements (inlined)

- **EML-001** — The system must verify SPF and DKIM for the sending domain before the first PO email is sent.
- **E13-S30 decision (b)** (operator, 8 Nov): issue refuses a PO email the domain cannot send and offers
  issue-without-email, so nothing goes dead in the outbox.

## The defect

E13-S30 made **issue** check `transmission.po_email_allowed(conn, settings)` (`purchasing/issue.py` ~86) before it
queues anything. Two other paths still queue a `po-` email with no check, so while the sending domain is unverified
the row is queued and then dead-lettered by the dispatcher (`kernel/outbox/dispatcher.py` ~114-115,
`PermanentOutboxError(DOMAIN_NOT_VERIFIED)`), and nobody is told:

1. **Change-order apply** (`purchasing/changes.py` ~688): `enqueue_transmission(self.connection, self.scope, new_id, 2)`
   runs unconditionally inside the approval callback.
2. **Cancel notice** (`purchasing/cancel.py` ~116-124): `enqueue_cancellation` runs whenever the PO was issued,
   `notify_vendor` is true and recipients exist.

## Fix

Both paths read `transmission.po_email_allowed(conn, settings)` (`transmission.py` ~481) inside their own
transaction and, when it is false, **queue nothing and record why**. Neither path may fail on it: change-order apply is
an approval outcome and a cancellation is the operator's decision; both still commit their document and money effects.

**Where `Settings` comes from** (pre-flight, 23 Nov; `issue` does not obtain it itself, its route injects it):

- **Cancel:** `api/purchasing.py` cancel route (~285) adds `settings: Annotated[Settings, Depends(get_auth_settings)]`
  exactly as the issue route does (~258) and passes it to `cancel(..., settings=settings)` in `purchasing/cancel.py`, which
  hands it to `_cancel_issued`. The new `cancel` parameter is **optional**, `settings: Settings | None = None`, with
  `settings or Settings()` at the check, so existing direct callers (`test_po_reads.py`, `test_lock_order.py`,
  `test_cancel_notice.py`) keep working unchanged. No other route change.
- **Change-order apply:** `ChangeService.__init__` gains `settings: Settings | None = None`, and the check uses
  `self.settings or Settings()`, the existing module pattern (`purchasing/service.py` ~830, `vendors/service.py`
  ~494). The approval outcome (`purchasing/approval.py` ~160) stays as it is and so falls back to `Settings()`
  (env; note `email_provider` reads the alias `EMAIL_PROVIDER`, `kernel/config.py` ~77); `OutcomeContext` and the approvals module are **not** touched. The `apply` route may pass
  its injected settings if it already has them; it need not.

1. **Change-order apply:** skip `enqueue_transmission` (`changes.py` ~688); write the audit event
   `purchase_order.revision_without_email` with `target_id` = the new revision row id (actor = the applying actor,
   `after` = `{"revision": <new revision number, int, as `changes.py` ~701 already stores it>, "reason":
   "domain_not_verified"}`), matching E13-S30's `purchase_order.issue_without_email`.
   **No resend path exists for that revision**: Resend (E13-S16) refuses a revision with no transmission rows
   (`transmission.py` ~317, `nothing_to_resend`) and the UI shows it only after a failed send. Do not change that
   here; the revision's PDF and Vendor Copy remain available. Record the gap in `notes.followup` (sending a
   revision that was never emailed, once the domain passes) for the design session.
2. **Cancel notice:** skip `enqueue_cancellation` and record it exactly as the no-recipient case already does
   (`transition(..., after={"vendor_notified": False})` ~119-121), adding `"reason": "domain_not_verified"` to that
   `after` map so the two cases are distinguishable in the audit.

When `email_provider` is not `resend` (dev, test), `po_email_allowed` is true and both paths queue as today.
