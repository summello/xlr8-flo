# E11-S21 — "Eligible Here" only for a unit the user actually belongs to

**Epic** E11 · **M3** · **ui/M** · after **E11-S11**, **E11-S12** · tags: `ui`
Origin: M3 epic checkpoint E11 (codex-a finding 3, 8 Nov 2026).

> **UI authority:** `design-system/MASTER.md`, `tokens.css`, `design-system/pages/vendors.md`.

## Requirements (inlined)

- **VEN-012** — A vendor that is inactive, suspended, expired, or not approved must not be invited or selected unless policy explicitly permits an authorized override.
- **VEN-008** — Vendor availability must be global or restricted to selected BU/OUs.

## Finding

E11-S11/S12 specify the list's `Eligible Here` column and availability filter "for the user's default
unit". No such concept exists: there is no default/home unit on a user or a membership. The list
(`apps/web/src/routes/vendors/list.tsx:66`, a `ponytail:` comment) and the profile use the **first**
org unit returned by `GET /org/units?page_size=1`, i.e. UUID order. For a user in Plant 7 the column can
say "Eligible Here" about Plant 4. The profile (`apps/web/src/routes/vendors/detail.tsx:37`) does the same, and
the same unit feeds its eligibility card, the "disabled here" notice and the local-disable dialog.

## Decision (operator, 8 Nov 2026)

(c) **Derive the unit from the user's role assignments when they hold exactly one unit; otherwise hide the
column.** No new data, no migration, no picker.

## Design

- **Rule, one place:** `identity.service.assigned_unit(connection, scope, user_id) -> UUID | None` in
  `modules/identity/service.py`. It reads the user's effective `user_role` rows in the session org (the same
  `effective_from` filter as `granted_scopes` ~705) **of any role**: if any assignment is org-scoped the answer is
  `None` (an org-wide holder spans every unit); otherwise the distinct `scope_id`s of the `bu`-scoped assignments,
  and the answer is that id when there is **exactly one**, else `None`. Project-scoped assignments are ignored
  (a project is not a unit). `org_id` from the session, never from input.
- **Route:** `GET /api/v1/vendors/my-unit` → `MyUnit {unit_id: UUID | null, name: str | null}`, permission
  `vendor.view` (the list's own permission), no body, no state change. The vendors router calls
  `identity.service.assigned_unit` and the org service for the name (modules talk through `service` only).
  **Declare it above `GET /{id}`** in `api/vendors.py` (~185): below it, `my-unit` is parsed as a vendor id and
  answers 422.
- **Web, list (`routes/vendors/list.tsx` ~66):** replace the `GET /org/units?page_size=1` load and its
  `ponytail:` comment with `GET /vendors/my-unit`. With a unit: as today (`available_in`, the `Eligible Here`
  column, the `Availability` select reading "Available in <name>"). With `unit_id: null`: no `available_in`, the
  `Eligible Here` column and the `Availability` select are not rendered, `here` is ignored, and one line under
  the filters says "Eligibility by unit shows when you belong to exactly one unit." (`req-sub` style; no new
  token). A `?here=1` URL with no unit lists all vendors.
- **Web, profile (`routes/vendors/detail.tsx` ~37):** the same load replaces the `page_size: 1` one. With
  `unit_id: null`: no eligibility request, no header eligibility, no "disabled here" notice, and no
  Disable/Enable Here (already true: `unitOk` is false without a unit). Nothing else on the profile changes.
- Regenerate the API client (`openapi.json`, `schema.ts`); never hand-write `MyUnit`.

## Acceptance

- [ ] pytest (`assigned_unit`, real Postgres): one BU-scoped assignment → that unit; two roles on the same BU → that unit; two different BUs → `None`; any org-scoped assignment (alone or beside a BU one) → `None`; project-scoped only → `None`; an assignment with `effective_from` in the future is ignored; another tenant's assignments never count.
- [ ] pytest (route): `GET /vendors/my-unit` returns the unit id and name for a one-unit user and nulls otherwise; 403 without `vendor.view`; TEN-010 isolation case (a user of org B never gets an org A unit). Register the route in `tests/isolation/test_route_coverage.py` as its neighbours are.
- [ ] Playwright (`vendors.spec.ts`; stub): with a unit, the column and "Available in Plant 7" show and the list request carries `available_in`; with `unit_id: null`, no column, no select, the one-line notice shows, and no list request carries `available_in`.
- [ ] Playwright (`vendors.spec.ts` or `vendor-status-dialogs.spec.ts`, profile; stub): with `unit_id: null`, no eligibility request is made and no Disable Here action shows.
- [ ] No request the vendors pages make reads `/org/units?page_size=1` any more; axe both themes on list and profile; keyboard path unchanged; `flo check --light` green.

## Plants

1. Return the first BU of a two-BU user from `assigned_unit`: the two-BU pytest fails.
2. Keep rendering the `Eligible Here` column when `unit_id` is null: the Playwright null-unit case fails.
3. Move `my-unit` below `GET /{id}`: the route test fails with 422.
