# E11-S21 — "Eligible Here" for the user's own unit

**Epic** E11 · **M3** · **engine/M** · after **E11-S11**, **E11-S12** · tags: `ui` · **status: blocked (operator)**
Origin: M3 epic checkpoint E11 (codex-a finding 3, 8 Nov 2026).

## Requirements (inlined)

- **VEN-012** — A vendor that is inactive, suspended, expired, or not approved must not be invited or selected unless policy explicitly permits an authorized override.
- **VEN-008** — Vendor availability must be global or restricted to selected BU/OUs.

## Finding

E11-S11/S12 specify the list's `Eligible Here` column and availability filter "for the user's default
unit". No such concept exists: there is no default/home unit on a user or a membership. The list
(`apps/web/src/routes/vendors/list.tsx:66`, a `ponytail:` comment) and the profile use the **first**
org unit returned by `GET /org/units?page_size=1`, i.e. UUID order. For a user in Plant 7 the column can
say "Eligible Here" about Plant 4. The profile (`apps/web/src/routes/vendors/detail.tsx:37`) does the same, and
the same unit feeds its eligibility card, the "disabled here" notice and the local-disable dialog.

## Blocked

**Question for the operator:** where does a user's unit for vendor eligibility come from?

- (a) **A default unit on the membership**, set by the administrator on the member screen (one nullable
  column, migration); with none set the column and filter are hidden and a one-line notice says why.
- (b) **The user picks it** on the vendor list (a unit picker, remembered per browser); the server still
  computes eligibility for the unit sent.
- (c) **Derive it** from the user's role assignments when they hold exactly one unit; otherwise hide the
  column (no new data).

This decides a new piece of identity data and what the screen claims about eligibility, so the planner
does not choose. The design and acceptance are written once the operator answers.
