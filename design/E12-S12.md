## Requirements (inlined)

- **SRC-001** — Sourcing users must be able to create an RFQ from approved requisition lines.
- **SRC-003** — The system must prevent sourcing more than the approved open quantity or amount unless the requisition is amended.
- **REQ-014 / REQ-015** — split sourcing; requested, sourced, awarded, ordered, remaining and cancelled per line.

## Screen `/sourcing/rfqs/new` (optional `?requisition=<id>`)

A table grouped by requisition, from `GET /sourcing/requisition-lines`. Each line is a checkbox row
(no drag, decision 152) with `Requested`, `Already Sourced`, `Open` and an editable `Quantity to
Source` that starts at `Open`. Above open is refused **at the field** with the figure and the way out
(`40 are open on REQ-00418. Amend the requisition to source more`). This is advisory: the server
enforces it under a lock. A line in another currency than the first chosen is disabled with the
reason (`Different currency`); lines are already one unit (see `unit_id` below). A title field, then `Create RFQ
Draft` as the one Primary, **never disabled**. A 409 `over_open_quantity` from the server maps back
to the line fields with the server's figures (someone else sourced first), keeping the user's
choices. Success lands on the RFQ editor (E12-S13; until it exists, the detail page).

**Double activation creates one draft.** `writeHeaders()` mints a fresh `Idempotency-Key` per call,
so the create call overrides it with a stable key held in a ref, as `features/invitation/api.ts`
does. The same key is reused for every activation until the request body changes (lines,
quantities or title) or a final response (2xx or a 4xx other than `request_in_flight`) arrives; then
the next submit mints a new one. A repeat activation while the POST is in flight sends nothing (the
button stays enabled, per MASTER; the handler returns early).

- **Always send `unit_id`** (pre-flight, 24 Oct 2026). Without it `list_target()` targets the organization, and a sourcing user holding `rfq.create` only on a business unit gets 403 (the resolver honours grants on the target or its ancestors). So the page opens with a `Business Unit` select (the first control, `Field` + `Select`, options from `GET /api/v1/org/units` as `ProjectForm.tsx` loads them, business units only), preset from `?unit=`; no lines load until a unit is chosen, and changing it clears the selection (nothing is saved yet). - **Locale quantities (UX-007), one parser and one formatter in `apps/web/src/lib/decimal.ts`** (add
  it to the file list), with vitest cases in `lib/decimal.test.ts`. The locale is the browser's
  (`Intl.NumberFormat(undefined)`); there is no user-locale setting yet.
  - `formatQuantity(canonical: string, locale?: string): string` — split the canonical string at
    `.`, group the integer with `new Intl.NumberFormat(locale, { maximumFractionDigits: 0 }).format(BigInt(int))`
    and join the fraction with the locale's decimal separator, exactly as `lib/money.ts` lines 12-13
    do (never through a JS `Number`: 14+4 digits exceed float precision). Trailing fraction zeros dropped.
  - `parseQuantity(input: string, locale?: string): string | null` — take the group and decimal
    separators from `new Intl.NumberFormat(locale).formatToParts(12345.6)`; trim; remove every
    whitespace character (including U+00A0 and U+202F) and every group separator; replace the decimal
    separator with `.`; return the result only if it matches `^\d{1,14}(\.\d{1,4})?$` (ASCII digits,
    the server's canonical shape in `modules/sourcing/schemas.py`) and is greater than zero
    (`isPositiveDecimal`), else `null`. Non-ASCII digits are not accepted.
  - A `null` parse is a field error: `Enter a quantity like <formatQuantity("1234.5")>.` The over-open
    check compares canonical values with `scaled()`.
  - vitest: `en-US` `"1,234.5"` → `"1234.5"`; `de-DE` `"1.234,5"` → `"1234.5"`; `fr-FR`
    `"1\u202f234,5"` → `"1234.5"`; `"0"`, `"1.23456"` (en-US), `"abc"`, `"١٢"` → `null`; 15 integer
    digits → `null`; `formatQuantity("1234.5", "de-DE")` → `"1.234,5"`.

- **One RFQ per create (pre-flight, 24 Oct 2026, fourth pass).** `POST /api/v1/sourcing/rfqs` makes
  a new RFQ for every distinct `Idempotency-Key`, and `writeHeaders()` mints a fresh key per call, so
  repeat clicks on the never-disabled `Create RFQ Draft` could make several drafts. Guard it twice in
  `new.tsx`, following `features/invitation/Screen.tsx` lines 84-85 (no API change):
  - **In flight:** a `useRef<boolean>` set before the request and cleared in `finally`; a click while
    it is set returns without a request. The button stays enabled (Plant 1 still holds), with
    `aria-busy="true"` and the label `Creating RFQ Draft` while in flight.
  - **Stable key:** `submission = useRef<{ fingerprint: string; key: string } | null>(null)`. The
    fingerprint is `JSON.stringify` of the exact request body. Reuse `submission.current.key` while
    the fingerprint is unchanged; mint `crypto.randomUUID()` when it changes. Send
    `{ ...writeHeaders(), "Idempotency-Key": submission.current.key }`. A retry after a lost response
    replays the stored 2xx and lands on the same RFQ. The middleware does not keep a key whose
    response was 4xx (`kernel/idempotency/middleware.py`, `status_code >= 400` rolls back), so
    after a 409 `over_open_quantity` the same key may be reused safely; the corrected quantities give
    a new fingerprint anyway. Clear `submission.current` on success.
  - A 409 `request_in_flight` (same key still running, for example in a second tab) keeps the key
    and shows in the error summary: `This RFQ is still being created. Wait a moment, then try again.`
  - e2e (stubbed `POST`): two clicks with no wait while the first `POST` is held open → exactly one
    `POST`. A first `POST` aborted by the stub (network failure), then a second click → the second
    `POST` carries the first one's `Idempotency-Key`. A quantity changed after that failure → the next
    `POST` carries a different key.
  - Plants: **3.** Build headers with `writeHeaders()` alone: the same-key-on-retry assertion fails.
    **4.** Remove the in-flight ref: the one-`POST` double-click assertion fails.
