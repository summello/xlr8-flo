## Requirements (inlined)

- **SRC-001** — Sourcing users must be able to create an RFQ from approved requisition lines.
- **SRC-003** — The system must prevent sourcing more than the approved open quantity or amount unless the requisition is amended.
- **REQ-014 / REQ-015** — split sourcing; requested, sourced, awarded, ordered, remaining and cancelled per line.

## Screen `/sourcing/rfqs/new` (optional `?requisition=<id>`)

A table grouped by requisition, from `GET /sourcing/requisition-lines`. Each line is a checkbox row
(no drag, decision 152) with `Requested`, `Already Sourced`, `Open` and an editable `Quantity to
Source` that starts at `Open`. Above open is refused **at the field** with the figure and the way out
(`40 are open on REQ-00418. Amend the requisition to source more`). This is advisory: the server
enforces it under a lock. A line in another currency than the first chosen is disabled with the
reason (`Different currency`); lines are already one unit (see `unit_id` below). A title field, then `Create RFQ
Draft` as the one Primary, **never disabled**. A 409 `over_open_quantity` from the server maps back
to the line fields with the server's figures (someone else sourced first), keeping the user's
choices. Success lands on the RFQ editor (E12-S13; until it exists, the detail page).

**Entry points (pre-flight, 24 Oct 2026; E12-S11 did not ship them, this story does):**

- `apps/web/src/routes/sourcing/rfqs/list.tsx`: a `New RFQ` link (`req-link-button`, Phosphor `Plus`, regular) in the `req-heading` header, the page's one Primary, `href="/sourcing/rfqs/new"`, client-navigated with `navigate` like the row links. It is shown to every member (the list route is `require_member`); the server's `rfq.create` check on `GET /api/v1/sourcing/requisition-lines` and `POST /api/v1/sourcing/rfqs` is the authority. The new page renders a 403 from the lines call as an access state (`You cannot start RFQs here. Ask an administrator for the RFQ create permission.`), not an error toast, and a 401 through the shell's existing sign-in redirect.
- `apps/web/src/routes/requisitions/detail.tsx`: a `Start RFQ` link in the header's `req-actions`, Phosphor `FileText`, regular, shown when `row.status === "sourcing_in_progress"` and `row.amendment?.status !== "pending"` (a pending amendment makes every line `amendment_pending`, so nothing could be picked). `href="/sourcing/rfqs/new?unit=<row.bu_id>&unitName=<row.bu_name>&requisition=<row.number>"` (values URL-encoded). The parameter is the **requisition number**, not the id: `GET /sourcing/requisition-lines` has no requisition filter, and its `q` matches `lower(r.number)`. The new page sends `unit_id=<unit>&q=<number>` and pre-checks every selectable row whose `requisition_number` equals it exactly; the user can clear the search to add lines from other requisitions.
- `apps/web/tests/e2e/sourcing-rfqs.spec.ts`: remove `"New RFQ"` from `FORBIDDEN` (it now ships on `/sourcing/rfqs`); keep `"Start RFQ"` (it never appears on RFQ pages). Add one case: `/sourcing/rfqs` shows `New RFQ` and it lands on `/sourcing/rfqs/new`. The requisition e2e spec gains: a `sourcing_in_progress` requisition shows `Start RFQ`, a `draft` one does not, and following it lands on `/sourcing/rfqs/new?requisition=REQ-…` with that requisition's lines checked.

- **Always send `unit_id`** (pre-flight, 24 Oct 2026). Without it `list_target()` targets the organization, and a sourcing user holding `rfq.create` only on a business unit gets 403 (the resolver honours grants on the target or its ancestors). So the page opens with a `Business Unit` select (the first control, `Field` + `Select`, options from `GET /api/v1/org/units` as `ProjectForm.tsx` loads them, business units only), preset from `?unit=`; no lines load until a unit is chosen, and changing it clears the selection (nothing is saved yet). Every `GET /api/v1/sourcing/requisition-lines` call carries `unit_id`; one RFQ is one unit, so the `Another business unit` disabled state cannot occur and is dropped. `Different currency` stays. A 403 on the lines call for the chosen unit shows the access state for that unit. No API change.

- **Where the units come from (pre-flight, 24 Oct 2026, second pass).** `GET /api/v1/org/units` needs
  organization-level `org.unit.read` (or `vendor.request`, DECISIONS 241) and returns **403** to a user
  whose only grant is `rfq.create` on one business unit (`api/org.py::unit_permission`,
  `modules/org/service.py::list_units`). Do not widen it (no API change, no authorization change). The
  page handles both outcomes:
  - **Units call 200:** the `Business Unit` select as above, business units only, active only, preset
    from `?unit=`.
  - **Units call 403 and `?unit=` present** (the user came from `Start RFQ`): no select. The unit is
    fixed to `?unit=` and shown as read-only text, `Business Unit` label with the value
    `<?unitName=>` — the `Start RFQ` link also carries `unitName=<row.bu_name>` (URL-encoded, display
    only; the request uses only `unit`; `RequisitionRead.bu_name` is nullable, so omit `unitName` when null and show `The requisition's business unit`). Lines load for it at once.
  - **Units call 403 and no `?unit=`** (the user came from `New RFQ`): no select, no lines call. A
    guidance state, not an error: `Start an RFQ from an approved requisition. Open it and choose Start
    RFQ.` with a link to `/requisitions`.
  - A 403 on the lines call itself still shows the access state above.
- Acceptance additions: e2e stubs `GET /api/v1/org/units` with 403 and (a) opens
  `/sourcing/rfqs/new?unit=<id>&unitName=North&requisition=REQ-…`: no select, `North` shown, the lines
  request carries `unit_id=<id>`, the requisition's lines are checked; (b) opens `/sourcing/rfqs/new`:
  the guidance state with its `/requisitions` link and no lines request. With units 200 the select
  path is unchanged.
