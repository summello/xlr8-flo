## Data (one migration, `migrations/<head date>_<next>_bids.py`)

Every table below has `org_id uuid NOT NULL REFERENCES organization(id)` and its own literal
ENABLE / FORCE / `CREATE POLICY tenant_isolation … USING (org_id = current_setting('app.org_id')::uuid)
WITH CHECK (…same…)` block, exactly as `migrations/20261022_0069_rfq_lifecycle.py`.

**`bid`:** `id uuid PK`, `org_id`, `rfq_id uuid NOT NULL`, `vendor_id uuid NOT NULL`,
`rfq_version int NOT NULL` (the version answered), `currency char(3) NOT NULL` (the vendor's;
validated by `modules/org/fx.py::validate_currency`), `sent_at timestamptz NOT NULL` (entered by the
buyer), `evidence_attachment_id uuid NOT NULL` (the vendor's email or file: an `attachment` row with
`document_type = 'rfq'` and `document_id = rfq_id`, not deleted; the service checks it, 422 on
`evidence_attachment_id` otherwise), `keyed_by uuid NOT NULL REFERENCES identity(id)`,
`keyed_at timestamptz NOT NULL DEFAULT now()`,
`freight NUMERIC(18,4) NOT NULL DEFAULT 0 CHECK (freight >= 0)`,
`lead_time_days int CHECK (lead_time_days >= 0)`, `valid_until date`, `delivery_terms text`
(≤ 500), `warranty text` (≤ 2000), `exceptions text` (≤ 5000),
`status text NOT NULL DEFAULT 'draft' CHECK (status IN ('draft','submitted'))`,
`submitted_at timestamptz` with `CHECK ((status = 'submitted') = (submitted_at IS NOT NULL))`,
`replaces_bid_id uuid REFERENCES bid(id)`, `row_version int NOT NULL DEFAULT 1` (§O: `ETag` and
`If-Match`), `UNIQUE (org_id, id)`.
Foreign keys: `(org_id, rfq_id) REFERENCES rfq(org_id, id)`; `(rfq_id, vendor_id) REFERENCES
rfq_invitee(rfq_id, vendor_id)` (only an invitee can bid; invitees are removable in draft only);
`(rfq_id, rfq_version) REFERENCES rfq_version(rfq_id, version)` (only a published version can be
answered); `(org_id, evidence_attachment_id) REFERENCES attachment(org_id, id)`.

**Replacement is a chain; no row changes after submit.** A corrected bid is a new row with
`replaces_bid_id` set to a submitted bid of the same RFQ and vendor (service-checked, 422). A bid is
**replaced** when a *submitted* bid names it in `replaces_bid_id`; that is derived on read, never
written to the original. Partial unique indexes:

- `bid_one_draft UNIQUE (rfq_id, vendor_id) WHERE status = 'draft'`
- `bid_one_original UNIQUE (rfq_id, vendor_id) WHERE status = 'submitted' AND replaces_bid_id IS NULL`
- `bid_replaced_once UNIQUE (replaces_bid_id) WHERE replaces_bid_id IS NOT NULL`

Each (rfq, vendor) therefore has one linear chain; its **current** bid is the submitted bid no
submitted bid replaces. This supersedes the earlier "one submitted bid per (rfq, vendor)" index, which
a replacement could never satisfy.

**`bid_line`:** `org_id`, `bid_id uuid NOT NULL`, `rfq_line_id uuid NOT NULL REFERENCES rfq_line(id)`,
`quantity NUMERIC(18,4) NOT NULL CHECK (quantity > 0)`, `quoted boolean NOT NULL`
(`Not Quoted` = false), `unit_price NUMERIC(18,4) CHECK (unit_price >= 0)`,
`tax NUMERIC(18,4) NOT NULL DEFAULT 0 CHECK (tax >= 0)` (amount for the line),
`line_total NUMERIC(18,4)`,
`CHECK (quoted = (unit_price IS NOT NULL) AND quoted = (line_total IS NOT NULL))`,
`PRIMARY KEY (bid_id, rfq_line_id)`, `FOREIGN KEY (org_id, bid_id) REFERENCES bid(org_id, id)`.
The service checks `rfq_line_id` belongs to the bid's RFQ (422).

**Quantity comes from the version answered, never from live `rfq_line`.** Amendments change
`rfq_line.quantity` in place (`lifecycle.py::_amend` → `_quantities_only`); the quantity each version
sent is `rfq_version.snapshot -> 'lines' -> <requisition_line_id> -> 'quantity'`
(`versions.py::snapshot`). When a line is written, the server copies that quantity for the bid's
`rfq_version` into `bid_line.quantity` and sets
`line_total = kernel.money.quantize(unit_price * quantity, bid.currency)`. Amendments never add or
remove lines (`lines_fixed`), so every version has every `rfq_line`.

**`bid_requirement`:** `org_id`, `bid_id uuid NOT NULL`,
`requirement_id uuid NOT NULL REFERENCES rfq_requirement(id)`, `met boolean NOT NULL`, `note text`
(≤ 1000), `PRIMARY KEY (bid_id, requirement_id)`,
`FOREIGN KEY (org_id, bid_id) REFERENCES bid(org_id, id)`. Requirements are frozen once the RFQ is
published (`put_requirements` and `waive_requirement` are draft-only), so `requirement_id` is
stable; the service checks it belongs to the RFQ and is not waived.

**Immutable after submit: `bid`, `bid_line` and `bid_requirement`.** Use the guard pattern of
`migrations/20261014_0060_vendor_questionnaire.py` (`vendor_version_guard`, `vendor_question_guard`),
`ERRCODE '55000'`:

- `bid_guard()` `BEFORE UPDATE OR DELETE ON bid`: raise on any DELETE (no route deletes a bid), and
  on UPDATE when `OLD.status = 'submitted'`. A draft may be updated, including `draft → submitted`.
- `bid_child_guard()` `BEFORE INSERT OR UPDATE OR DELETE` on `bid_line` and on `bid_requirement`:
  raise unless every parent bid the row leaves or enters (`OLD.bid_id`, `NEW.bid_id`) is `draft`.
- `raise_append_only()` `BEFORE TRUNCATE` on all three, as `rfq_version`.

**Never converted here.** No column in these tables holds another currency (SRC-010). The comparison
(E12-S06) converts.

## API (`/api/v1/sourcing/rfqs/{id}/bids`, in `apps/api/src/flo/api/sourcing.py`)

Every route uses the existing `rfq_target`, so a foreign RFQ is 404 before any permission is
weighed; a `bid_id` of another RFQ is 404. Each write locks `rfq` `FOR UPDATE` first, then the `bid`
row, in that order only.

| Method and path | Permission | Behaviour |
|---|---|---|
| `POST /` (Idempotency-Key) | `rfq.edit` | Body `BidCreate` (`vendor_id`, `rfq_version`, `currency`, `sent_at`, `evidence_attachment_id`). 201 draft, `ETag` = `row_version`. 409 `not_open` unless the RFQ is `published` or `closed`; 422 if the vendor is not an invitee or the version does not exist; 409 `draft_exists` on `bid_one_draft`. |
| `PATCH /{bid_id}` (`If-Match`) | `rfq.edit`, keyer only | Body `BidPatch`: header fields, `lines` (replaces the draft's lines whole), `requirements` (replaces the answers whole). 403 if the caller is not `keyed_by`; 409 `not_draft` if submitted; §O otherwise. Bumps `row_version`. |
| `POST /{bid_id}/submit` (Idempotency-Key, `If-Match`) | `rfq.edit`, keyer only | Body `BidSubmit` (`extra="forbid"`, no fields yet). Validates every RFQ line has a row, quoted lines have a price, and every non-waived requirement is answered: one 422 `VALIDATION_FAILED` listing every problem in `errors` (`lines/<rfq_line_id>`, `requirements/<id>`). Then `status = 'submitted'`, `submitted_at = now()`. **Seam for E12-S05:** one private method `BidService._before_submit(rfq_row, bid_row, body)`, called after validation and before the status update inside the lock, that does nothing in this story. E12-S05 fills it with the late check and adds `accept_late_reason` to `BidSubmit`. Do not create `sourcing/sealing.py` or call anything from it. |
| `POST /{bid_id}/replace` (Idempotency-Key) | `rfq.edit` | **Blocked**, see below. |
| `GET /` and `GET /{bid_id}` | `rfq.approve`, or the bid's keyer | `BidRead`: the columns above, `lines`, `requirements`, `replaced_by_bid_id` (derived) and `current: bool`; `ETag` on `GET /{bid_id}`. E12-S05 replaces this read rule with sealing; until then no other route returns a bid figure. |

Audited (`target_type = 'rfq'`, `target_id` = the RFQ): `bid.create`, `bid.submit`, `bid.replace`,
`after = {bid_id, vendor_id}` only; never a figure in `before` or `after` (figures stay in the bid
tables, which E12-S05 seals until the deadline).

## Blocked

**Q (state transition, money): when may a submitted bid be replaced, and how does a replacement
meet the deadline?** `docs/requirements.md` and `pages/sourcing.md` say only that the original is
never altered and is shown as replaced. The data model above holds under every option; these rules
do not, and the comparison (E12-S06) and award (E12-S08) read whichever bid is current.

1. **RFQ states that allow `replace`:** (a) `published` only; (b) `published` or `closed`, as
   recording a bid, never once `under_evaluation`; (c) any state before `awarded`.
2. **Lateness of a replacement** (E12-S05 enforces it): (a) the replacement's own `sent_at` is
   checked like any bid, so a correction sent after the deadline needs the `rfq.approve` override;
   (b) a replacement inherits the original's timeliness.
3. **Reason:** does `replace` require a reason (1..500, audited)?

Planner's recommendation, not a decision: 1(b), 2(a), 3 yes. Until answered, the author may build
everything except `POST /{bid_id}/replace` and its test; the story does not merge without it.
