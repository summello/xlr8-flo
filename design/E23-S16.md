# E23-S16 — Re-review economy: CI-only commits keep verdicts, void verdicts retry once, milestone red is fixed once

**Epic** E23 · **MT** · **chore/M** · **priority P0** (operator, 23 Oct 2026) · **after E23-S14**

> MT stories start from and merge into the checked-out milestone (d9ba9c3). **No new dependency** (AGENTS.md §0.6).
> **Review: Codex only.** Operator, 23 Oct 2026: every Opus planner and reviewer sleeps until the E23 flo fixes
> (S14 to S18) are on the milestone PR and its CI is green. Codex must plant every violation listed below.

## Requirement (inlined)

- **SUP-005** — Administrator and operator documentation must be updated in the same PR as the feature it describes.

## Why

Revalidated by the planner on `9a53605` (23 Oct 2026):

1. `flo_facts.verdict_state()` marks every verdict stale whenever the submitted sha moves. It cannot
   distinguish a story change from a milestone merge or regenerated API client. After the E12-S03 milestone
   failure, generated-client and formatting-only repair commits caused full Codex and Opus re-reviews of
   E11-S14, E11-S16 and E22-S02. `review.sh` has a 480-second/30-call re-review mode, but the supervisor
   still asks it to reconsider more than the story-only delta requires.
2. A `changes_requested` verdict with no findings is immediately `malformed`. E22-S02 produced a draft
   verdict after the time cap and then waited overnight for a human, although one automatic retry was safe.
   Unlimited retry would be equally wrong: a reviewer that repeatedly writes nothing must become a need.
3. `decide()` starts a story `fix` whenever its submitted CI is red, even while `line_stopped` says the
   milestone is red for the same CI jobs. The stale generated client therefore caused repeated story-local
   fixes and reviews instead of one repair on the milestone.
4. Current `.ci-red` markers contain the `gh --log-failed` job prefix on each line, but `flo facts` exposes
   only a boolean for milestone red. The supervisor lacks the job-name evidence needed to suppress only
   matching failures.

## Design

### 1. Carry forward reviews for a non-story delta

- For each stale reviewer, compute the story-only commits with
  `git log --no-merges <reviewed_sha>..<head> --not origin/<milestone>` and inspect the patches/files from
  exactly those commits. A merge from the milestone contributes no story delta.
- Carry the verdict forward only when that delta is empty, or every changed path is under
  `apps/web/src/api/generated/**`. Any other path makes the verdict stale.
- Carry-forward advances the review baseline to the current submitted sha without rewriting the reviewer's
  verdict or pretending it ran again. Append a structured entry to `task.json` and write
  `.scratch/<STORY>.<REVIEWER>.carried.json` with `carried_from`, `carried_to`, paths and timestamp.
- `flo facts` reports the carried verdict as fresh. `flo gate`, scorecard review-run counts and review
  duration continue to use the original verdict/run; a carry is not a review.
- When a real story delta exists, launch `review.sh` in its existing re-review mode with the delta since the
  previous reviewed sha and that reviewer's previous verdict only. It keeps the 480-second/30-call limits.

### 2. One retry for a void verdict

- A verdict is void when it requests changes with no itemised findings, or when the reviewer log records
  `stopped at the time cap` without a usable verdict.
- E23-S14 gives each reviewer its own run record. Record an attempt number keyed by reviewer and submitted
  sha. The first void result is treated as `missing` and may launch exactly one automatic retry.
- A second void result for the same reviewer and submitted sha is `malformed` and becomes the existing
  operator need. A new submitted sha resets the counter. Successful or itemised verdicts are unchanged.
- The retry is still sequential under E23-S14 and uses re-review limits only when a prior usable verdict exists.

### 3. Fix a shared milestone failure once

- Extend `flo ci-watch`/`flo facts` to expose normalised failing job names for story and milestone red markers.
  Derive them from the tab-separated job prefix already written by `gh run view --log-failed`; ignore step text.
- While `line_stopped` is non-empty, if a red story and its milestone have any failing job name in common,
  `decide()` does not launch `fix`. It emits one de-duplicated need:
  `milestone red: fix it once on the milestone`.
- A story whose failing jobs do not overlap the milestone is unchanged, as is a story fix after the milestone
  is green. Job-name matching suppresses duplicate work; it does not declare the story CI green.

## Invariants

- A verdict never carries across application, test, migration, workflow or tooling changes outside the
  generated API client directory.
- A carry-forward is auditable and is never counted as a new independent review.
- Every reviewer gets at most one automatic retry per submitted sha for a void result.
- Red milestone CI still stops merges. This story only prevents duplicate fixes for the same failing jobs.
- Reviewer selection, model, effort, call caps and Opus gating do not change.

## Acceptance criteria

- [ ] A milestone-only merge between reviewed sha and head carries an approving verdict to the submitted sha
      and records `carried_from` in `task.json` plus the reviewer sidecar.
- [ ] A delta containing only `apps/web/src/api/generated/**` carries; adding one non-generated path makes it stale.
- [ ] A non-generated story delta launches one re-review whose packet contains only that delta and the same
      reviewer's prior verdict.
- [ ] Carry-forward does not increment `review_runs` or replace the original verdict mtime/content.
- [ ] First void verdict for reviewer+sha becomes missing and schedules one retry; a second becomes malformed
      and produces a need. Changing the submitted sha permits one new retry.
- [ ] With story and milestone markers both naming `frontend-static`, `decide()` emits the one milestone-red
      need and no story fix; with disjoint jobs it preserves the current story-fix decision.
- [ ] Multiple affected stories do not produce repeated notifications for the same milestone/job incident.
- [ ] `docs/ops/fleet-tooling.md` explains carry-forward evidence, void retry count and shared-red triage.

## Plants (prove each guard fails)

- Treat any merge-base equality as carryable without checking paths: the non-generated-delta test fails.
- Remove the carry sidecar/task entry: the audit-evidence test fails.
- Reset the void counter every tick: the second-void test observes a third launch.
- Match the words of a failed step instead of job names: the disjoint-job test is suppressed incorrectly.
