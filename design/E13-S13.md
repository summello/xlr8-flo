## Requirements (inlined)

- **PO-001** — POs must be creatable from approved and sourced requisitions (M3: from approved awards only, decision 163).
- **PO-009** — Partial POs must reduce only the corresponding open requisition quantity and value.
- **SRC-018** — every line completes sourcing before a PO.

All three are enforced by the server, which E13-S01 shipped; this story is the screen over it and must not re-implement a rule in the browser beyond the field checks below.

## What the server already does (read it, do not change it)

- `GET /api/v1/purchase-orders/awarded-lines?award_id=<id>` — `apps/api/src/flo/api/purchasing.py:101-111`, guarded by `require("purchase_order.view", award_target)` (`purchasing.py:70-72`). Foreign or unknown award → 404; in-tenant without the permission → 403 (`kernel.authz.require`). Service `PurchaseOrderService.awarded` (`modules/purchasing/service.py:369-403`): `open_qty = min(award_line.quantity − ordered_qty, requisition line quantity − cancelled − ordered)`. It does **not** check the award's status and returns no vendor name (fixed below).
- `POST /api/v1/purchase-orders` — `purchasing.py:113-126` (`create_purchase_order` at line 114), `require("purchase_order.create", create_target)`. Body `PoCreate` (`modules/purchasing/schemas.py:42-53`): `{award_id, vendor_id, lines: [{rfq_line_id, quantity}] (1..500), override_reason?}`; each `quantity` a decimal string > 0 with at most 4 decimals (`schemas.py:18-23`). Returns `PoRead` (201, `id`, `number`, …).
- **Cardinality: one PO per vendor _and_ requisition** (E13-S01 packet line 89, "Decisions 3"). Lines of one vendor from two requisitions → 422 `checks.problem = "mixed_requisitions"` (`service.py:743-748`); a line not awarded to the vendor → 422 `mixed_vendors` (`service.py:740-741`). The screen therefore creates **one POST per (vendor, requisition) group**, never one per vendor.
- Refusals the screen maps (all `ProblemDetails` with `checks.problem`):
  - 409 `over_open_quantity` from the award line (`modules/sourcing/service.py:1426-1443`): `checks["open.<rfq_line_id>"]`, `checks["requested.<rfq_line_id>"]`, `errors[].field = "lines/<rfq_line_id>"`.
  - 409 `over_open_quantity` from the requisition line (`modules/requisitions/sourcing.py:227-244`): the same keys but with **`<requisition_line_id>`**. Map a key to a row by `rfq_line_id` first, then `requisition_line_id`.
  - 409 `vendor_not_eligible` (`service.py:107-113`, raised by `_eligibility` at `service.py:708-721`): `checks.reasons` is one `"; "`-joined string. An override needs a non-blank `override_reason` **and** `rfq.approve` on the award's unit (`purchasing.py:122`); without both the server refuses again.
  - 409 `invalid_transition` "Only an approved award can be ordered from." (`lock_award`, `sourcing/service.py:1306-1307`).
  - 409 from `assert_current_upstream` (stale requisition, pending amendment, expired codes) and 409 `no_project`, `rate_missing`, `bill_to_missing` (`service.py:699, 758, 763`): show the server's `detail` at the group.
  - 409 whose `type` ends with `/request_in_flight` (idempotency middleware): show "This purchase order is still being created. Wait a moment, then try again." at the group (copy the `IN_FLIGHT` handling of `routes/sourcing/rfqs/new.tsx:21,158`).
  - 403 on POST: "You cannot create purchase orders here. Ask an administrator for the purchase order create permission."

### Quantities

- Each field starts at the line's `open_qty`, shown with `formatQuantity` (locale), on first load only.
- **Blank or zero = not ordering this line now.** A (vendor, requisition) group whose lines are all blank or zero is not created. (No zero-value lines are ever sent: operator rule of 28 Oct 2026; the server also refuses `quantity <= 0`.)
- `parseQuantity` (locale → canonical) returns null for anything else that is not a positive quantity: field error "Enter a quantity like <formatQuantity('1234.5')>."
- `scaled(parsed) > scaled(open_qty)`: field error "<formatQuantity(open)> are open on this line. Order at most that." (refused at the field with the figure).
- Ineligible vendor with a non-blank quantity: without `can_override` → error at the vendor "This vendor is not eligible. Leave its quantities blank, or ask someone who can approve RFQs."; with `can_override` and a blank reason → field error on `Override Reason` "Give the reason for ordering from a vendor that is not eligible."
- Nothing to create at all → summary error "Enter a quantity on at least one line."
- Any field error stops the whole run (nothing is sent), shows `ErrorSummary` focused, and keeps every typed value — the `fail(...)` pattern of `rfqs/new.tsx`.

### Create Draft POs

The one Primary button, `Create Draft POs`, **never disabled** (page spec §2; DECISIONS 45). It is busy (`aria-busy`) while a run is in flight; a second click during a run does nothing (`inFlight` ref as `rfqs/new.tsx:49`).

A run sends one `POST /api/v1/purchase-orders` per non-empty (vendor, requisition) group, **sequentially**, ordered by vendor name then requisition number, body `{award_id, vendor_id, lines: [{rfq_line_id, quantity: <canonical>}], override_reason?}` (`override_reason` only for an ineligible vendor). Headers `mutationHeaders(key)` (CSRF + `Idempotency-Key`). **Each group keeps its own key** in a ref keyed by `vendor_id:requisition_id`, as `{fingerprint: JSON.stringify(body), key}`; the key is reused while the body is unchanged and replaced when it changes (the `rfqs/new.tsx:152` pattern), so a retry after a network failure replays the same PO instead of creating a second one.

Each POST is independent: the server commits each on its own, so a later failure never undoes an earlier success, and the run continues past a failed group. After the run:
- A `status` region lists every PO created in this run: "Created <number> for <vendor_name>, <requisition_number>." each `<number>` linking to `/purchase-orders/<id>`. Focus moves to it when nothing failed.
- Each failed group shows its error at the fields (409 `over_open_quantity` → the server's `open.*` figure at each named line, mapped by `rfq_line_id` then `requisition_line_id`; `vendor_not_eligible` → `checks.reasons` at the vendor; anything else → the server's `detail` at the group) and in `ErrorSummary`, focused.
- The awarded lines are re-fetched once, so `Already Ordered` and `Open` show the server's new figures. A **created** group's fields are cleared to blank (so pressing the button again cannot order its remainder by accident); a **failed** group keeps the typed values and override reason. Its key is kept.
- Pressing `Create Draft POs` again re-sends only the groups that still have quantities.
