# E11-S02 — Typed vendor contacts: Billing, Service and Delivery, additional types

**Epic** E11 · **M3** · **crud/S** · after **E11-S01** · tags: none

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** canvas DECISIONS 128 (6h-8), `design-system/pages/vendors.md` §2 "Contacts". Back end only.

## Requirements (inlined)

- **VEN-002** — Each vendor must support billing and service/delivery contacts; additional typed contacts may be added.
- **PRIV-001** — Collect only personal and sensitive data required for stated business purposes.

## Design

Table `vendor_contact` in the vendors module (RLS like every tenant table):
`id`, `org_id`, `vendor_id`, `type text NOT NULL` (`billing`, `service_delivery`, or an
organization-defined code, see below), `name text NOT NULL` (1..200), `email text NOT NULL`
(validated the same way invitations validate email), `phone text NULL` (≤ 40), `receives_documents
boolean NOT NULL`, `created_at`, `updated_at`. **No other personal fields** (PRIV-001).

- **Billing and Service and Delivery are always present.** The vendor create in E11-S01 does not
  require them, but submitting a vendor for approval (E11-S06) does. Expose
  `service.contacts_complete(vendor_id) -> list[str]`, which names the missing types, and E11-S06
  calls it. Exactly one contact per vendor of each of these two types (partial unique index). A
  contact of either type cannot be deleted: 409 `required_contact`. It can be edited.
- **Who receives RFQs and POs (decision 6h-8):** `receives_documents` defaults to `true` for
  `service_delivery` and `false` for every other type, and the user may change it per contact.
  `service.document_recipients(vendor_id) -> list[Recipient(name, email)]` returns the contacts with
  `receives_documents = true`, `service_delivery` first. E12 invitations and E13 transmission call
  this and nothing else. An empty list is a valid answer; the caller decides what to do with it.
- **Additional types:** a master-data kind `vendor_contact_type` (use the existing
  `org.master_kinds` registry and its admin routes; do not build a new admin surface). Its codes are
  valid `type` values. `billing` and `service_delivery` are reserved and cannot be defined as codes.
- Vendor contacts are **not users** and carry names (D-M2-16 applies to people inside the
  organization only).

## API

| Method and path | Permission | Behaviour |
|---|---|---|
| `GET /vendors/{id}/contacts` | `vendor.view` | Ordered: billing, service_delivery, then others by name. |
| `POST /vendors/{id}/contacts` (Idempotency-Key) | `vendor.edit` | 409 `contact_type_taken` for a second billing or service_delivery contact; 422 per field. |
| `PATCH /vendors/{id}/contacts/{cid}` (Idempotency-Key) | `vendor.edit` | Name, email, phone, `receives_documents`. The type is immutable (422). |
| `DELETE /vendors/{id}/contacts/{cid}` (Idempotency-Key) | `vendor.edit` | 409 `required_contact` for the two required types. |

Audited: `vendor.contact.create`, `vendor.contact.update` and `vendor.contact.delete`, with
before/after. The email appears in the audit row; the phone does not (AUD-006 spirit, minimise).

## Acceptance

- [ ] Migration up, down and data preservation.
- [ ] A second `billing` contact → 409; deleting `service_delivery` → 409; changing a type → 422.
- [ ] `document_recipients` returns service_delivery by default, adds a billing contact once its `receives_documents` is true, and returns `[]` when every flag is off.
- [ ] `contacts_complete` lists the missing required types.
- [ ] An unknown additional type → 422; a defined master code works.
- [ ] TEN-010: a foreign vendor's contacts → 404 on every route. Authorization: sourcing-specialist reads but cannot write.
- [ ] `flo check` green.

## Plants

1. Default `receives_documents` true for billing: the default-recipient test fails.
2. Drop the partial unique index: the second-billing test fails (prove the database refuses, not only the service).
