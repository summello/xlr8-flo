## Requirements (inlined)

- **PO-002** — A PO must include requestor, Bill To, Ship To, vendor, items/services, descriptions, quantities, units, unit prices, currency, taxes, freight, terms, dates, project, department, and ledger accounts. (The record holds all of them since E13-S01; this screen shows them and edits the ones the API lets a draft change.)
- **PO-016 / FIN-008** — tax and freight separately visible on line and document; per-unit treatment: `tax.consumes_budget` and `freight.consumes_budget` per BU/OU, default on; when off, that component is shown on the PO and not committed (DECISIONS 211).
- **PO-017** — POs support notes, terms, supporting attachments and vendor-facing attachments; internal-only content is never included accidentally; internal by default.
- **VEN-012** — vendor eligibility shown at the PO vendor field, with an override for the authorized. The override is taken **at creation** (`PoCreate.override_reason` with `rfq.approve`, `api/purchasing.py:113-126`, `purchasing/service.py:709-721`; the create screen is E13-S13). The vendor cannot change on a draft (`PoPatch` has no `vendor_id`, `purchasing/schemas.py:70-80`), so this editor **shows** eligibility and offers no override control.

## Two API additions (this story)

1. **Budget treatment flags on `PoRead`.** Add `tax_consumes_budget: bool | None = None` and
   `freight_consumes_budget: bool | None = None` to `PoRead` (`purchasing/schemas.py:116`). `get()` already
   computes `flags = self._flags(unit_id)` (`service.py:294`, keys `tax.consumes_budget` and
   `freight.consumes_budget`, `service.py:269-275`); set the two fields from it **only while `live`**
   (`service.py:306`: draft, approval_pending, approved) and leave them `None` otherwise (an issued PO's
   budget amounts were frozen at issue, so today's setting says nothing about it). No new read, no new rule.
2. **Ship To options.** `GET /api/v1/purchase-orders/{id}/ship-to-options` → `list[OrgAddressRead]`
   (`flo.modules.org.schemas`, `org/schemas.py:101`), guarded by `EditContext` (`purchase_order.create` on the
   PO's unit, `api/purchasing.py:78`; a foreign/unknown/deleted id is 404 first through `po_target`). It
   exists because the org address route needs `org.unit.read` (`api/org.py:146-168`), which
   `purchasing-user` lacks. Service: `PurchaseOrderService.ship_to_options(id)` returns the active
   `ship_to` addresses of the PO's unit and its ancestors, nearest unit first — exactly the loop in
   `_ship_to_allowed` (`service.py:701-707`). Refactor `_ship_to_allowed` to test membership in the same
   list, so the options and what `PATCH` accepts can never differ. GET: no CSRF or idempotency. Add it to
   `apps/api/tests/isolation/test_route_coverage.py::COVERED` under `PO_READ_ROUTES`. Regenerate the client:
   `cd apps/web && npm run generate:api` (`apps/web/package.json:10`).

Ship To rule, as merged: the draft starts on the requisition's `delivery_address_id`
(`service.py:816`) and `PATCH` may pick any active `ship_to` of the unit or an ancestor (E13-S01 packet,
`design/E13-S01.md:41-42`). Decision 165 says "the delivery locations the requisition uses"; the editor
follows the merged API and marks the requisition's address `(from the requisition)`. Record the wording
gap in `notes.followup`; do not narrow or widen the server rule.

## Writes

Every write sends the CSRF header: `writeHeaders()` (`apps/web/src/features/auth/api.ts:32`). It also adds an
`Idempotency-Key`, which the middleware keys for POST (and the soft-delete DELETEs) only, so a PATCH or PUT ignores it (`kernel/idempotency/middleware.py:236-240`).

- **Save** (`Save`, never disabled): `PATCH` with `{ ...writeHeaders(), "If-Match": String(version) }`
  (the pattern of `components/projects/Transitions.tsx:21`). The body is a pure function
  `patchBody(saved: Po, edited)` in `components/purchasing/editor/patch.ts` that sends only changed header
  fields and only changed lines with only their changed keys (`line_no` always). On 200 replace the page
  state with the response (server totals and the new `version`). On 422 map `errors[].field` to the field
  (`lines/<n>/quantity`, `ship_to_address_id`, `document_freight`, `lines`) and list them in `ErrorSummary`
  (`components/form/ErrorSummary.tsx`), keeping every typed value. On 409 `stale_version`: "Someone saved
  this order after you opened it. Your edits are still here; reload to see theirs (reloading discards
  yours)." with a `Reload` button. On 409 `po_not_draft`: the gate message. Register the unsaved-edits guard
  with `registerGuard` (`lib/navigation-guard.ts:12`).
- **Submit for Approval** (shown when `actions` includes `submit`, never disabled; otherwise "Only the buyer
  who drafted this order can submit it."). **What is approved is what was saved:** with unsaved edits,
  Submit first runs Save exactly as above; if Save fails, stop and show that error — no submit. Then `POST
  …/submit` with `writeHeaders()`, one key per press. 200 → navigate to `/purchase-orders/{id}`. 409 by
  `checks.problem`: `workflow_not_set_up` → "No purchase order workflow is published. Ask an administrator
  to set one up. Your draft is kept."; `vendor_not_eligible` → "This vendor is no longer eligible:
  <checks.reasons>. Your draft is kept."; anything else → the server's `detail` plus "Your draft is kept."
  403 → the server's `detail`.
- There is **no `Approve` button** on this screen in any state.
