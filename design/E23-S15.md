# E23-S15 — Process-owned locks for finish, submit and launch; one live author and one submit per story

**Epic** E23 · **MT** · **chore/M** · **priority P0** (operator, 23 Oct 2026)

> MT stories start from and merge into the checked-out milestone (d9ba9c3). **No new dependency** (AGENTS.md §0.6).
> **Review: Codex only.** Operator, 23 Oct 2026: every Opus planner and reviewer sleeps until the E23 flo fixes
> (S14 to S18) are on the milestone PR and its CI is green. Codex must plant every violation listed below.

## Requirement (inlined)

- **SUP-005** — Administrator and operator documentation must be updated in the same PR as the feature it describes.

## Why

Revalidated by the planner on `9a53605` (23 Oct 2026; Codex assessment finding 3 and live fleet evidence):

1. `finish.sh:13-15` and `submit.sh:23-24` acquire `.scratch/finish.lock` with `mkdir`, wait forever,
   and release only from an `EXIT` trap. SIGKILL bypasses that trap. An ownerless directory then blocks
   every finish and the write phase of every submit until a human notices and removes it.
2. `author.sh` serialises launch against `flo reassign`, but after taking that directory lock it never
   checks whether `.scratch/<STORY>.author.pid` names a live process. On 23 Oct it resumed the same Sonnet
   session a second time while pid 66322 was still alive: two authors could write one branch.
3. `submit.sh` has no per-story exclusion around merge plus `flo check --light`. On 23 Oct the supervisor
   began E22-S02 submit at 02:13 while a manual submit for E22-S02 was already checking, duplicating the
   expensive check and allowing two processes to mutate one worktree.
4. `test_flo_reassign.py` checks the text of the `author.sh` locking convention, but does not execute the
   launcher against a live pid. A guard that has not been seen to reject a real violation is not reviewed.

## Design

### 1. `flo with-lock`

- Add `flo with-lock <name> [--wait SECONDS] -- <command...>` using only Python stdlib
  `fcntl.flock` on `.scratch/<name>.lock`. Restrict `name` to a safe filename component.
- Open and retain the lock file descriptor for the entire child process. The kernel releases the lock
  when the holder exits or is killed; the lock file itself is durable and is never reclaimed by age.
- While held, the file contains the holder pid for diagnostics only. A contender must never treat that
  text, its age, or a failed `kill -0` as authority to unlock it.
- `--wait` is bounded seconds. If the deadline expires, exit **75** and name the lock plus the recorded
  holder pid when present. A zero wait is non-blocking.
- Execute the requested command without a shell reconstruction: argument boundaries and exit status are
  preserved, and signal termination remains observable by the caller.

### 2. Finish and submit locks

- `finish.sh` re-execs its existing body under `flo with-lock finish --wait 1800 -- ...`; remove the
  `mkdir` loop and directory cleanup trap. The milestone merge, gate, squash and push remain inside it.
- `submit.sh` holds `flo with-lock submit.<STORY> --wait 0` around its whole merge/check/submit sequence.
  A second submit of the same story exits 75 immediately and does not touch the worktree or run checks.
- The final `flo submit` section still shares `flo with-lock finish --wait 1800` with `finish.sh`, because
  both write the parent roadmap. The light check remains outside this global lock and inside the story lock.
- Use an explicit internal flag or private body command so re-exec cannot recurse.

### 3. One live author

- Under `author.sh`'s existing per-story launch/reassign lock, check `.scratch/<STORY>.author.pid` before
  reading the assignment or launching. If it names a live process, exit **75** with
  `author of <STORY> already running (pid N)` and launch nothing.
- A missing, malformed or dead pid does not block a new launch. The new pid still lands only after the
  launch succeeds far enough to identify it.
- Keep the launch/reassign exclusion delivered by E23-S06. This story replaces its crash-prone directory
  lock with `flo with-lock launch.<STORY> --wait 30` so SIGKILL cannot strand it.

## Invariants

- At most one process mutates a story worktree through `submit.sh`, and at most one author process is live.
- Finish operations and the roadmap-writing phase of submit remain globally serial.
- A lock is owned by an open file description, never by timestamps or trusted pid-file contents.
- Existing child command output and exit codes are preserved; timeout is the distinct retryable code 75.
- No daemon, database, third-party package or macOS-only `flock(1)` command is introduced.

## Acceptance criteria

- [ ] A subprocess holding `flo with-lock test --wait 0` excludes a second acquirer; the contender exits
      75 and its message names the lock and holder pid.
- [ ] SIGKILL the holder subprocess without deleting its lock file; the next acquirer succeeds.
- [ ] A bounded waiter that cannot acquire before its deadline exits 75 rather than waiting forever.
- [ ] Two simultaneous `submit.sh <STORY>` calls: one proceeds and the other exits 75 before merge or check.
- [ ] Submit for two different stories may run their light checks concurrently, while their final parent
      roadmap writes remain serialised by `finish`.
- [ ] `finish.sh` and the final phase of `submit.sh` have no `mkdir .scratch/finish.lock` polling loop.
- [ ] With a real `sleep` process in `<STORY>.author.pid`, `author.sh` exits 75, launches nothing and leaves
      the pid file unchanged; after the process exits, the launcher may proceed.
- [ ] The former text-only `author.sh` lock test is replaced by an executable guard test.
- [ ] `docs/ops/fleet-tooling.md` documents lock names, wait limits, exit 75 and why lock files are not deleted.

## Plants (prove each guard fails)

- Replace `flock` with existence of the lock file: the SIGKILL/reacquire test fails.
- Remove the bounded wait: the timeout test fails instead of observing exit 75.
- Move the live-author check outside the launch lock: the simultaneous-launch test permits two launches.
- Drop the per-story submit lock: the two-submit test observes both reaching the check.
