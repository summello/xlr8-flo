# E05-S04 — Fiscal calendar and period open/close with authorization and audit

**Epic** E05 · **M1** · **engine/M** · after **E05-S01** · tags: `money`

> **Conventions:** read `docs/m1-conventions.md` (authorization outcomes, scope targets, wire formats). It applies unless this packet says otherwise.

## Requirements

- **BUD-010** — Fiscal calendars must be configurable by organization.
- **FIN-010** — Closing or reopening a financial period must require authorization and create an audit record.

## Design decisions (confirm on review)

- **D-M1-6 Fiscal calendar model.** A calendar has a start month (1-12) and generates **fiscal years by their ending calendar year** (year starting 2026-04 ends 2027-03 and is `FY2027`) and 12 monthly periods per year. Periods are generated lazily by `ensure_year(org, fiscal_year)` and are never deleted. Weeks and 4-4-5 calendars are out of scope.
- **D-M1-7 Period states:** `open` ↔ `closed`. Posting to a `closed` period is rejected. Reopening is allowed with a distinct permission and a mandatory reason.

## Contract

Migration (reversible): the next revision after the current head at story start (revision id `20260826_<next 4-digit number>`, `down_revision` = the head `python -m flo.kernel.migrate --check` validates today); stories merge one at a time, so there is no gap or fork: `fiscal_calendar(org_id pk, start_month smallint check 1..12, changed_at)`; `fiscal_period(id uuid pk, org_id, fiscal_year int, period_no smallint check 1..12, starts_on date, ends_on date, status text check in ('open','closed') default 'open', closed_by, closed_at, UNIQUE (org_id, fiscal_year, period_no), EXCLUDE overlap on (org_id, daterange))`; RLS. A period row is **append-only except for status columns** — a trigger rejects changes to `starts_on`/`ends_on`/`fiscal_year`/`period_no`; every status change inserts into `fiscal_period_event(id, org_id, period_id, action in ('close','reopen'), actor_id, reason, at)` which is append-only by trigger.

- `PUT /api/v1/fiscal/calendar` `{start_month}` → 200; **409 if any period of the org has ever been closed** (no retroactive reinterpretation)
- `GET /api/v1/fiscal/periods?fiscal_year=` → 200 (calls `ensure_year`)
- `POST /api/v1/fiscal/periods/{id}:close` (Idempotency-Key) permission `fiscal.close` → 200 | 409 already closed
- `POST /api/v1/fiscal/periods/{id}:reopen` `{reason}` permission `fiscal.reopen`, step-up re-auth via the existing `requires_recent_auth` (reason required, min 10 chars) → 200 | 409 already open

Service API for the ledger (E07): `fiscal.service.assert_postable(org, effective_date)` raising `PeriodClosed(period)`; and `fiscal.service.period_for(org, date)`, `range_for(org, kind in {'mtd','qtd','ytd','fiscal_year'}, as_of)` used by E07-S06.

## Behaviour

1. Close and reopen are one transaction with the event row and an audit row (FIN-010).
2. Closing requires the previous period to be closed (no gaps); reopening a period requires every later period to be open.
3. `ensure_year` is idempotent and race-safe (`INSERT ... ON CONFLICT DO NOTHING`).

## Acceptance criteria

- [ ] Close then reopen writes two `fiscal_period_event` rows and two audit rows; updating or deleting an event row fails in the database
- [ ] Changing `starts_on` of an existing period is rejected by trigger
- [ ] Changing the calendar after a close returns 409
- [ ] Closing period 3 while period 2 is open returns 409; reopening period 2 while period 3 is closed returns 409
- [ ] Reopen without a recent step-up returns the existing step-up problem type; without `fiscal.reopen` returns 403
- [ ] `assert_postable` raises for a date in a closed period and passes for open; a date with no generated period triggers `ensure_year` and passes
- [ ] Two concurrent `ensure_year` calls leave exactly 12 periods
- [ ] Foreign-tenant period id → 404 (isolation gate entries); migration up/down/data-preservation

## Amendments (preflight audit — authoritative, override anything above)

- Export `assert_postable`, `period_for` and `range_for` from **`org.service`** (the fiscal code may live in `modules/org/fiscal.py`, but consumers import only `org.service`). Wherever this packet or another says `fiscal.service.*`, read `org.service.*`.
- Insert permissions `fiscal.manage` (calendar PUT, year generation), `fiscal.read` (GET periods), `fiscal.close`, `fiscal.reopen` into the global `permission` table in this story's migration.
- **Calendar lock rule (replaces "409 if any period has ever been closed"):** `PUT /fiscal/calendar` is allowed only while **no `fiscal_period` row exists** for the org (409 label `calendar_locked` otherwise). `GET /fiscal/periods` does **not** generate periods. Periods are generated by `POST /api/v1/fiscal/years/{fiscal_year}:generate` (permission `fiscal.manage`, idempotent) and lazily by `assert_postable` / `period_for` when a posting needs a date, so reading never locks the calendar.
- **Posting vs close race:** `assert_postable` selects the period row `FOR SHARE` and holds it until the caller's transaction ends; close and reopen select it `FOR UPDATE`. Lock order for posters is `project_balance` then period, and close/reopen touch only the period row, so there is no cycle. A test closes a period while a posting transaction is open on it and shows the close waits.
