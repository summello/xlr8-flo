## Backend reads (this story; read-only, `purchase_order.view` unless stated)

All in `apps/api/src/flo/modules/purchasing/` (service, schemas) with routes in `api/purchasing.py` calling one
service method each, no logic in the router. Every route is added to `tests/isolation/test_route_coverage.py`
`COVERED`, and a foreign tenant's id is 404 on each.

**B1. List tabs and counts** (`GET /api/v1/purchase-orders?tab=`). `PoTab` (`schemas.py:11`, today `all|draft`)
becomes `all | draft | awaiting | ready | issued | attention`: `draft` = status `draft`; `awaiting` =
`approval_pending`; `ready` = `approved`; `issued` = `issued`; `attention` = an `issued` PO where **any row** of its latest
`po_transmission` attempt (`max(attempt)` on that PO row's `po_id`; one row per recipient per attempt,
`0086:26-27`) has a **derived** result (`READ_STATE` with its outbox join,
`purchasing/transmission.py:32-35`; the `result` column alone is null for queued/sent and misses a dead outbox
row) of `failed`, `bounced`, `complained` or `address_suppressed`; `all` as today. `counts` (`service.py:405` and `:450`) returns all six keys in the same query pass.
`draft` keeps its meaning, so E13-S13's existing callers are unaffected.

**B2. List columns.** `PoListRow` (`schemas.py:156-166`) gains `revision: int`, `projects: list[PoProjectRef]`
(`id`, `code`, `name`; the distinct projects of its lines, ordered by code, at most 3) with `project_count: int`,
and `sent: PoSentRead | None` (`result`, `result_at` of the latest transmission attempt on that PO row's `po_id`,
derived through `READ_STATE` and its outbox join as in B1, so `queued` and `sent` show too; `None` when none exists).
An attempt with several recipients reports its **worst** row, in this order: `failed`, `bounced`, `complained`,
`address_suppressed`, `queued`, `sent`, `delivered`; `result_at` is that row's time. So a PO is under `attention`
exactly when its `sent.result` is one of the first four, and the tab and the column never disagree. One batched query per page, no per-row query.

**B3. Versions** (`GET /api/v1/purchase-orders/{id}/versions` → `list[PoVersionRead]`). The chain of `{id}`
(the PO and every ancestor and descendant by `supersedes_id`, the recursive CTE shape of
`purchasing/vendor_copy.py:108-114`, which walks back only; B3 also walks forward, a second CTE on
`supersedes_id = <id>` for descendants) ordered by `revision`: `revision`, `po_id`, `status`, `total`, `currency`,
`issued_at` (`purchase_order.issued_at`, `issue.py:170`; `None` when not issued), `is_current` (the row with
the highest revision). Change orders for the current revision come from the existing
`GET /{id}/changes`; the control lists versions, then change orders.

**B4. History** (`GET /api/v1/purchase-orders/{id}/history` → `list[PoHistoryRead]`). Reads `audit_log` for the
chain's PO ids (target type `purchase_order`) on the pattern of `approvals/versions.py:53` (`occurred_at`,
actor email via `identity`, `action`, a short `detail` from the audit payload); oldest first, capped at 200
rows with `truncated: bool`. Cancel and reduce entries (PO-013) are included as written by E13-S07.

**B5. Budget Summary** (`GET /api/v1/purchase-orders/{id}/budget-summary` → `PoBudgetSummaryRead`). One entry per
project of the PO's lines, **computed on the server in `Decimal`**: `project_id`, `currency`, `committed` (the
project's commitments from **other** POs, i.e. the committed total minus this PO's share when
`this_po_state = committed`, so this PO is never counted twice, `purchase-orders.md:78`), `this_po` (the PO's budget amount in the project currency, `budget_amount_project`
summed) with `this_po_state` in `reserved | committed | released` (by PO status: `approved` and earlier →
`reserved`, `issued`/`closed` → `committed`, `cancelled` → `released`; `superseded` → 409, see ## Decided below), `available_after_issue`
(equals the project's `available` in every state: `available` is `allocated - reserved - committed - actual`
(`migrations/20260826_0020_project_balance.py:21-22`), so the approval's reservation is already out of it;
subtracting `this_po` again double-counts), and `actual`. Meanings are
DECISIONS 210. The caller needs `ledger.read` on each project (granted to `purchasing-user` above); a missing
grant is 403 with the usual problem body, and the UI shows the card as unavailable, never a partial figure.
Read through `budget.service.get_balance` (`budget/service.py:27`; not `lock_balance`, which takes `FOR UPDATE`),
never SQL on `ledger_entry` from `purchasing`.

**B6. Live vendor status and permitted actions.** `PoRead` gains `vendor_status: str | None` (the vendor's
**current** status, read through the vendors service, `None` when the caller lacks `vendor.view`) next to the
unchanged `vendor_snapshot`, and `actions: list[str]` (the lifecycle and command names the **caller** may run
on this PO now: from `submit, withdraw, edit, delete, issue, cancel, reduce, change_order, close`), computed on the
server from status and the caller's permissions (`purchase_order.create|amend|issue|close`). The browser reads
`actions`; it never infers a permission. Hiding a control is not authorization: every command route keeps its own
check.

**B7. Role grants** (operator, above): `purchasing-user` gains `vendor.view` and `ledger.read` in
`identity/models.py` and one reversible grant migration (0088 or the next free number, 0087 is taken; another lane may take it:
renumber at merge) on the pattern of `20261022_0066_baseline_role_reads.py`. Notes and Files need no
registration: `purchase_order` is a registered collaboration document type since E13-S11.

## Decided (operator, 1 Nov 2026): B5 on a superseded revision

**Option (c): hide the card and link to the current revision.** `GET /purchase-orders/{id}/budget-summary` on a
`superseded` PO returns 409 through the existing helper, `conflict("superseded", ...)` (`kernel/errors/codes.py:213-215`,
as `purchasing/cancel.py:92` uses it): `code: conflict`, `checks.problem == "superseded"` and
`checks.current_id` = the current revision's id. No new `ErrorCode` and no top-level extension field (the
handler serialises only `checks`, `kernel/errors/handler.py:161-189`). The commitment belongs to the current revision, so no figure is shown. The detail
page renders the Budget Summary card as a one-line notice, "This revision was replaced. Budget figures are on
the current revision.", with a link to it. B3 still lets a user open any earlier revision; every other card
(Lines, Notes and Files, Transmissions, Linked Records, History) works on it. Acceptance: a `superseded` PO's
B5 call is 409 with `checks.problem == "superseded"` and `checks.current_id`, and the page shows the notice and link (Playwright). Plant: have
B5 return figures for a superseded row, and the 409 test fails.

## Acceptance

- [ ] B1: each of the six tabs returns the right rows and `counts` has six keys; an `issued` PO with a `bounced` latest attempt appears under `attention` and not under a clean `issued`; `draft`/`all` behave as before.
- [ ] B2: list rows carry `revision`, `projects` (max 3, `project_count`) and `sent`; the page runs a constant number of queries regardless of page size (a query-count test).
- [ ] B3/B4/B5/B6: each route returns the documented shape; a foreign tenant's PO is 404 on every new route (TEN-010, `COVERED`); a role without `purchase_order.view` is 403.
- [ ] B5 figures are `Decimal`-computed strings; `available_after_issue` equals the project's `available` for an `approved` and an `issued` PO (no double count); for an `issued` PO `committed` excludes this PO's share; the PO link provider's href is `/purchase-orders/{id}`; an attempt whose outbox row is dead lists under `attention` with `sent.result = failed`; a caller without `ledger.read` gets 403 and the card renders "unavailable", never a partial number.
- [ ] B6: `actions` for a `draft` PO held by `purchasing-user` includes `submit`, `edit`, `delete`; for an `issued` PO it excludes `edit` and `delete` and includes `change_order`; a `requestor` gets `[]` or only what the role holds; calling a command not in `actions` is still refused by its route.
- [ ] B7: `purchasing-user` holds `vendor.view` and `ledger.read`; `requestor` still lacks both; the grant migration is reversible and leaves a pre-existing grant alone on downgrade.
- [ ] Playwright (seeded or stubbed): list tabs; open an issued PO; the Budget Summary shows server figures; the version control lists v1 and v2 and closes on Escape with focus returned; a bounced PO shows under `Needs Attention` with `Bounced` as a signal.
- [ ] A vendor suspended after issue: the detail shows the suspended status and "The issued PO is unaffected."
- [ ] 40 lines at 375px stack; the body stacks below 1100px.
- [ ] axe on both routes in both themes; keyboard path through tabs, the version control, the cards and every header action.
- [ ] MASTER §8 checklist; tokens only; `notes.followup` records the 70/30 and 1100px note.
- [ ] `flo check --light` green; the regenerated API client is committed (`openapi.json`, `schema.ts`).

## Plants (prove each guard fails)

1. Return only the `all` and `draft` counts: the six-key count test fails.
2. Query transmissions per row in the list: the query-count test fails.
3. Compute `available_after_issue` in the browser: a test that compares the rendered figure to the server field with a deliberately different server value fails.
4. Drop the `ledger.read` check from B5: the 403 test fails.
5. Make `actions` ignore the caller's permissions: the `requestor` test fails.
6. Drop an id from `COVERED`: `test_route_coverage` fails.
7. Hardcode the `1100px` or a colour as a token-less value outside the precedent: the token/lint gate fails.
