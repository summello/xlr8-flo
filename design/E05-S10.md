It is the layout, copy, states and motion for `/sign-in`, `/sign-in/mfa` and `/sign-in/mfa/enroll`.** Where it is more specific than this packet, it wins; it also carries the registered exceptions E-2 to E-4 (ambient backdrop loops exempt from the 300 ms transition cap, 44px controls, no app shell).

## Why this story exists

The M0 release review found no sign-in surface in the deployed SPA: `apps/web/src/routes` has only the dev galleries and the access explorer, and the CSRF cookie is only armed after a first same-origin request, so a browser that has never made one cannot log in. This story builds the entry point to the product.

## Requirements

- **AUTH-007** — Authentication errors must not reveal whether an account exists.
- **AUTH-010** — Users must be able to view and revoke their active sessions where the identity solution supports it.
- **AUTH-001** — User profiles link users to BU/OUs, roles, locale and timezone (the shell shows who is signed in).
- **A11Y-006** (AGENTS.md 3.4) — Forms: programmatic labels, field-level errors, an error summary, input preserved after a validation failure. Keyboard-reachable with visible focus; colour never carries meaning alone.

## Design decisions (confirm on review)

- **D-M1-26 The API arms the CSRF cookie on the first response.** Backend change authorized here: `kernel/session/csrf.py` sets the `flo_csrf` cookie on **any** response (including 401 and 403 problem responses) when the request carries none, so the login form can read it before its first `POST`. A test proves a cold browser's first `POST /api/v1/auth/login` succeeds after a plain `GET /api/v1/auth/csrf`. Add `GET /api/v1/auth/csrf` returning 204 with the cookie set if no existing public `GET` route is suitable. Document the route as intentionally public and uniform-404-guarded like every other route.
- **D-M1-27 Uniform failure.** Wrong password, unknown email and locked account all render the same message ("The email or password is incorrect, or the account is locked. Try again or reset your password.") and the same focus behaviour. The UI never branches on which of them it was.

## Contract

Routes (TanStack Router, matching the existing route conventions): `/sign-in`, `/sign-in/mfa` (challenge), `/sign-in/mfa/enroll` (QR/secret plus recovery codes, using the existing MFA enrollment endpoints), and a Sign out action in the app shell menu calling the logout route. An unauthenticated visit to any other route redirects to `/sign-in` with a `return` path restricted to same-origin relative paths (reject anything with a scheme or `//`). After sign-in the user lands on the stored `return` or the home route. Session expiry (401 from any API call) returns to `/sign-in` preserving the return path and shows "Your session ended. Sign in again."

States: idle, submitting (button disabled, `aria-busy`), field errors, form error summary focused on failure, locked, network error (say what happened, what was preserved, how to retry), MFA code invalid, enrollment shown, success. Input (email) is preserved after failure; the password field is cleared.

**A throttled attempt (E05-S11) renders the same alert as a wrong password. There is no distinct "too many attempts" state.** D-M1-27 and E05-S11 D-M1-29 require the UI never to branch on which credential failure happened, and the server answers all four — wrong password, unknown email, locked account, throttled — with the same 401 problem body. No countdown, no remaining-attempts number. Assert it: a throttled attempt renders the same alert, and the DOM matches no `too many`, `attempts` or `wait`.

**Enrollment includes the recovery codes step** (`sign-in.md` §5): after a valid TOTP confirms enrolment, the same route shows `Save Your Recovery Codes` — eight codes in a `role=list` box labelled `Recovery codes`, Copy and Download, and a checkbox `I saved these codes somewhere safe.` that keeps `Continue to XLR8 FLO` **disabled until it is checked**. Codes are shown once, never logged, never placed in a URL, and reloading the page must not show them again. No autofill blocking; `autocomplete` attributes set correctly (`username`, `current-password`, `one-time-code`).

Active sessions: a "Sessions" panel in the account menu listing active sessions (device, last seen) with Revoke, using the existing session routes (AUTH-010). If those routes do not exist yet, record `notes.followup` instead of inventing endpoints.

## Acceptance criteria

- [ ] Playwright happy path against the API test server: cold browser, open `/`, redirected to `/sign-in`, sign in with a seeded user, land on the return path; sign out returns to `/sign-in`
- [ ] Wrong password, unknown email: identical message, identical DOM apart from the typed email; the DOM never contains the word "exists" or "found"
- [ ] MFA challenge and first-time enrollment complete with a valid TOTP; an invalid code shows a field error and preserves state
- [ ] Enrollment reaches the recovery-codes step: `Continue` is disabled until the acknowledgement box is checked, the codes appear in no log line or URL, and a reload does not show them again
- [ ] A throttled attempt (E05-S11, if merged; otherwise a stubbed 401 identical to the wrong-password body) renders the same alert, and the DOM matches no `too many`, `attempts` or `wait`
- [ ] `@axe-core/playwright` reports zero violations on `/sign-in`, `/sign-in/mfa` and `/sign-in/mfa/enroll` in both themes
- [ ] Keyboard-only: Tab order is email, password, submit; Enter submits; the error summary receives focus on failure; no keyboard trap
- [ ] `return` open-redirect attempts (`https://evil`, `//evil`, `javascript:`) land on home
- [ ] MASTER.md section 8 checklist ticked in the commit body; tokens only, no hardcoded colour, spacing, radius or duration; Phosphor icons; dark and light contrast measured
- [ ] Backend: cold-browser CSRF test (above); the CSRF cookie never carries a session value
- [ ] Plant: remove the CSRF arming and the cold-browser test fails; make the failure message differ for unknown email and the uniform-message test fails

## Round 2 amendments (Opus, 9 Oct 2026) — these supersede the Contract above wherever they differ

Codex correctly blocked round 1 on two contradictions; tracing them found a third gap. All three are resolved here. Nothing below adds scope the story did not already need.

1. **Router.** The Contract's "TanStack Router" was wrong. The app uses a custom History-API router in `apps/web/src/routes/__root.tsx` (`routeFor`, `popstate`, `navigate`) with the path list in `route-paths.ts`. Use it; add no dependency. The three sign-in paths are **not** members of `ROUTES`/`ROUTE_PATHS` (those render inside `AppShell`): declare a separate `AUTH_PATHS` list, and have `RootRoute` branch to the sign-in screens **before** it renders `AppShell` (override E-4: no shell on these routes).
2. **Canvas assets are now in the tree.** `design-system/canvas/project/` (the `SignIn*.dc.html` boards, `xlr8flo.css`) and `design-system/canvas/tests/` came in with the canvas merge. They are the *reference*, never imported by the app: port the SVG geometry and the classes you need into `apps/web/src` using tokens only. `auth.spec.mjs` is a canvas test against canvas HTML; **port its backdrop animation audit into an app Playwright spec** (`apps/web/tests/e2e/sign-in-backdrop.spec.ts`) that reads the computed animations from the real `/sign-in` route, and keep its planted-violation proof.
3. **New endpoint (authorized): `GET /api/v1/auth/session`.** `POST /login` answers a bare 204, so the browser cannot tell whether to go to the MFA challenge, to enrolment, or home, and the router guard has no way to ask "am I signed in?". Add, in `api/auth.py` beside its siblings (same `@public_route` + `current_session` pattern as `GET /sessions`): response `{identity_id: UUID, org_id: UUID | null, mfa: "verified" | "verify" | "enroll"}` and nothing else. `mfa` is `"verified"` when `session.mfa_verified_at` is set; otherwise it is `MfaService.access_requirement(identity_id).value` (`verify` or `enroll`). `org_id` is the session's, never an input. No session answers the existing uniform 401. Add its entry to `tests/isolation/test_route_coverage.py::COVERED` with a real named test, tests for each of the three `mfa` values and for the 401, and regenerate the OpenAPI client.
4. **Flow.** After `POST /login` 204 the UI calls `GET /auth/session`: `verify` goes to `/sign-in/mfa`, `enroll` to `/sign-in/mfa/enroll`, `verified` to the stored `return` or Home. The guard on every other route uses the same probe: 401 sends to `/sign-in?return=<same-origin path>`. After MFA verify or enrolment completes, call it again before navigating. `return` handling and open-redirect rejection are unchanged.
5. **End-to-end tests stub the API.** CI's `test:e2e` starts only the Vite dev server; there is no API and no proxy. The Playwright specs therefore intercept `/api/v1/auth/*` with `page.route`, returning bodies typed from the generated client, and prove the *browser behaviour*: redirects, focus, uniform alert, keyboard path, axe, backdrop audit. Do not start an API from Playwright. The backend half is proven by the Python tests (cold-browser CSRF, the new session route). A live sign-in against a real database is an operator check after deploy; record it in `notes.followup`, not as a claim in the diff.
6. **Dev proxy.** `apps/web/vite.config.ts` may gain a dev-only `server.proxy` for `/api` to `http://127.0.0.1:8000` (single origin, D-17: this is a dev convenience, never CORS). Nothing else in that file changes.
7. **Files, additions.** `apps/web/src/routes/__root.tsx` (the auth branch and guard only), `apps/web/src/routes/route-paths.ts` (only if a type needs it), `apps/web/vite.config.ts` (proxy), `apps/web/tests/e2e/sign-in*.spec.ts` and `apps/web/tests/a11y/` (axe cases), `apps/api/src/flo/api/auth.py` (the one route), `apps/api/tests/session/` and `tests/isolation/test_route_coverage.py`.
8. **Acceptance, additions.** `GET /auth/session` returns each of `verified`, `verify`, `enroll` for the right fixture identities and 401 without a cookie; a request carrying a foreign `org_id` in header, query or body changes nothing; plant: make the route return `verified` for an unverified session and its test fails; make the guard skip the probe and the redirect test fails.

## Round 3 amendment (Opus, 9 Oct 2026) — retracts round 2 items 3 and 8 and edits items 4 and 7

Codex blocked again, correctly: `MfaAccessMiddleware` rejects `GET /api/v1/auth/session` for exactly the sessions that need it (unverified or unenrolled), before the router runs, and widening that gate is an authorization change this story must not make. **The endpoint was unnecessary. Do not add `GET /api/v1/auth/session`, do not touch `mfa_middleware.py`, and add no backend route.** The gate already answers with everything the browser needs, and the existing suite relies on it (`tests/isolation/test_real_sessions.py`, `tests/identity/test_mfa.py`).

**Session probe.** The UI probes `GET /api/v1/auth/sessions` (already exists; it is also what the Sessions panel lists). It is in neither MFA allow-list, so the result tells the state:

| Response | Meaning | Where the UI goes |
|---|---|---|
| 200 | signed in, MFA satisfied | the stored `return` or Home |
| 401 | no session | `/sign-in` (with `return` when arriving from elsewhere) |
| 403 with `WWW-Authenticate: mfa` (problem type `…/mfa-verification-required`) | password accepted, code needed | `/sign-in/mfa` |
| 403 with `WWW-Authenticate: mfa-enroll` (problem type `…/mfa-enrollment-required`) | privileged role, factor not enrolled | `/sign-in/mfa/enroll` |

Branch on the `WWW-Authenticate` header and the problem `type`, never on message text. Any other status renders the generic failure state (never infer "signed in" from an unexpected response). The probe runs after `POST /login` 204, after MFA verify, after enrolment confirms, on app start, and on every guarded navigation.

**Item 4 edit:** read "calls `GET /auth/session`" as "calls the probe above". **Item 7 edit:** remove `apps/api/src/flo/api/auth.py`, `apps/api/tests/session/` and the COVERED entry for the session route from the file list; the only backend change left in this story is D-M1-26 (CSRF cookie armed on the first response, plus `GET /api/v1/auth/csrf` only if no public GET suits), exactly as the Contract states. **Item 8 replaces** with: the Playwright specs stub the four probe outcomes above and assert each destination; a probe answering 200 for a stubbed 403 `mfa` response fails the test (plant it); the guard skipping the probe fails the redirect test.
