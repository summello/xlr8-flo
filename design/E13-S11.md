## Requirements (inlined)

- **PO-017** — POs must support notes, terms, supporting attachments, and vendor-facing attachments. Internal-only content must never be included accidentally.
- **EML-005** — Vendor-facing email must never include internal-only notes or attachments (PO-017); this must be covered by an automated test.
- **COL-002** — Notes must identify author and visibility, including internal-only versus externally shareable.

## What exists (verified on `milestone/M3-sellable`)

- Notes and attachments are E09-S10's generic routes, `/api/v1/documents/{document_type}/{document_id}/notes|attachments`, `PATCH /api/v1/notes/{id}` (`api/collaboration.py:72-217`), each behind `require("record.read", <document target>)` (`api/collaboration.py:57-61`), then gated per type by `DocumentAccess` (`modules/collaboration/service.py:33-57`). No `purchase_order` type is registered (`api/document_types.py:59-66`). All nine routes are already in `tests/isolation/test_route_coverage.py::COVERED` (lines 346-379).
- `DocumentAccess` fields, in order: `document_type, read_permission, write_permission, target, write_guard, write_authorize, read_guard`. `vendors/documents.py:74` builds it **positionally** through `write_authorize`, so a new field goes **last** with a default.
- Note visibility is `'internal' | 'shareable'` (DB CHECK `migrations/20261009_0041_collaboration.py:15`; `Visibility`, `collaboration/schemas.py:9`). `NoteCreate.visibility` is required; `NotePatch.visibility` is optional. `NoteRead` carries `author_id`, `author_email`, `author_name`, `visibility` (COL-002).
- `add_note` (`service.py:162-175`) and `edit_note` (`service.py:177-231`) check only the **read** permission (`authorize(...)` at 165 and 180); `edit_note` then locks the note (`_note(id, lock=True)`, 192), refuses a non-author 403 (193), a locked note 409 (195), a stale version 409 (201), a null field 422 (207), then writes `note_revision` and `note` (211-229). `authorize(..., write=True)` (upload 284 and the route's own call `api/collaboration.py:166`, version 187, delete 394) calls `write_authorize` **instead of** `write_permission` when it is set (`service.py:97-102`).
- `edit_note` is the only code that row-locks `note` (`lock_note`, `service.py:406`, has no caller in `modules/`). `requisitions/links.py:265` reads requisition notes through `notes_unchecked`.
- Attachments have no visibility or vendor flag (migration 0041:27-40).
- A change order writes a **new `purchase_order` row** (`revision + 1`, `supersedes_id` = old id, `ChangeService._write_revision`, `purchasing/changes.py:795-832`); a note belongs to one revision's id. `ChangeService._root` (`changes.py:627-639`) is the recursive `supersedes_id` walk.
- `PurchaseOrderService.unit_of` (`purchasing/service.py:142`) and `.get` (164) are plain reads in their own `tenant_transaction` (a savepoint inside a caller's); both 404 an unknown, deleted or foreign id. `api/purchasing.py:34` `_unit` is the PO's target: `AuthorizationTarget(ScopeType.BU, unit_id, "org_unit", unit_id)`.
- Seeded `purchasing-user` holds `purchase_order.view`, `.create` and `.amend` together (`identity/models.py:316-330`); `requestor` holds `record.read` but no `purchase_order.*`.
- The collaboration document type is **`purchase_order`** (as the ledger's `source_type` and the permission prefix); the approvals type `'po'` is a different registry.

## Design

### 1. Register `purchase_order` — `api/document_types.py`

Beside `requisition_access` and `project_access` (composition root; collaboration never imports purchasing):

```python
def po_access(connection, scope, id) -> TargetProtocol:
    unit_id = PurchaseOrderService(connection, scope).unit_of(id)
    return cast(TargetProtocol, AuthorizationTarget(ScopeType.BU, unit_id, "org_unit", unit_id))

def po_write(connection, scope, id, actor: UUID | None) -> None:
    """`purchase_order.create` while draft, `purchase_order.amend` in every other status."""
```

`po_write`: inside `with tenant_transaction(cast(RlsSession, connection), scope):` (the resolver reads
grants under RLS; `vendors/documents.py:67` does the same), read `PurchaseOrderService(connection,
scope).get(id).status`; permission = `"purchase_order.create"` if `status == "draft"` else
`"purchase_order.amend"`; `actor is None` or `not AuthorizationResolver(cast(AuthorizationConnection,
connection), scope).check(IdentityId(actor), permission, po_access(connection, scope, id)).allowed` →
`ProblemError(ErrorCode.FORBIDDEN)`. Imports: `AuthorizationConnection`, `AuthorizationResolver` from
`flo.modules.identity.service`, `IdentityId` from `flo.kernel.identity`, `ErrorCode`, `ProblemError`
from `flo.kernel.errors`, `RlsSession`, `tenant_transaction` from `flo.kernel.tenancy.rls`,
`PurchaseOrderService` from `flo.modules.purchasing.service`. Comment on it:
`# ponytail: the status is read without a PO lock; a transition committing between this read and the write is judged by the earlier status. Every seeded role holding one of create/amend holds both.`

```python
register_document_access(DocumentAccess(
    "purchase_order", "purchase_order.view", "purchase_order.create", po_access,
    write_authorize=po_write, share_authorize=po_write,
))
```

`write_permission` is never consulted once `write_authorize` is set; it is filled because the field is required.

### 2. The share hook — `modules/collaboration/service.py` (operator, 30 Oct 2026)

Append to `DocumentAccess`, last:

```python
    # Runs, after the read check, when a note is created `shareable` or edited from `internal` to
    # `shareable`; it raises to refuse. None (every type but purchase_order) keeps the read rule.
    share_authorize: (
        Callable[[psycopg.Connection[tuple[object, ...]], Scope, UUID, UUID | None], None] | None
    ) = None
```

Add one private method and call it from exactly two places:

```python
def _authorize_share(self, document_type: str, document_id: UUID) -> None:
    hook = _ACCESS[document_type].share_authorize
    if hook is not None:
        hook(self.connection, self.scope, document_id, self.actor_id)
```

- `add_note`: inside the `tenant_transaction`, before the `INSERT`, `if body.visibility == "shareable": self._authorize_share(document_type, document_id)`.
- `edit_note`: bind `document_type, document_id = self.linked_document("note", id)` once and pass it to the existing `authorize` call; after the null check (207-210) and before the `note_revision` insert (211), `if (body.visibility or before.visibility) == "shareable": self._authorize_share(document_type, document_id)`. Any edit whose resulting visibility is `shareable` (a flip to shareable, or a body edit of a note already shareable) needs the PO write rule; a flip to `internal` does not.

Refusal order on `PATCH` is therefore: 404 foreign/unknown note, 403 no read, 400 no `If-Match`, 403 non-author, 409 `note_locked`, 409 `stale_version`, 422 null, **403 share**. Refusals are not audited (no refused permission check in this module is). Nothing else changes: internal notes, list, revisions and `shareable` → `internal` keep the read rule; other types are unaffected.

**Locks:** `edit_note` holds the note row lock; `po_write` only reads (`get` takes no lock, the resolver takes none), so it adds an edge to nothing. No other writer locks `note` (see What exists), and issue and change-order apply read notes without a lock (§3), so there is no cycle with E13-S05/S06/S07's award → balances → requisition → PO order.

### 3. One reader for vendor-facing notes — `modules/collaboration/service.py`

Module-level, added to `__all__`:

```python
def external_notes_for(
    connection: psycopg.Connection[tuple[object, ...]], scope: Scope,
    document_type: str, document_ids: Sequence[UUID],
) -> list[NoteRead]:
    """Internal, no authorization. Only `shareable` notes, filtered in SQL, oldest first."""
```

Inside `tenant_transaction`, `CollaborationRepository(connection, scope).execute(NOTE_SQL + " WHERE n.org_id=%(org_id)s AND n.document_type=%(type)s AND n.document_id = ANY(%(ids)s) AND n.visibility='shareable' ORDER BY n.created_at, n.id", {"type": document_type, "ids": list(document_ids)})`. No row lock. The fixed order keeps the snapshot, and so the PDF bytes, deterministic.

### 4. Notes on the vendor copy — `modules/purchasing/vendor_copy.py`, `pdf.py` (E13-S08's files)

E13-S08 ships `VendorCopy` with no notes field and freezes the `po-v1` layout ("a layout change adds
`po-v2` beside it"). So:

- `VendorCopy` gains `notes: list[str] = Field(default_factory=list)`: note **bodies only** (no author, date or id). The default keeps every stored `po-v1` snapshot validating. Add `notes` to the literal set in E13-S08's field-allowlist test.
- `vendor_copy` fills it as `[n.body for n in external_notes_for(conn, scope, "purchase_order", chain)]`, where `chain` is the snapshotted revision's id and every ancestor id: one recursive CTE over `supersedes_id` through `PurchaseOrderRepository`, the same walk as `ChangeService._root` but selecting every `id`. `vendor_copy.py` calls no other collaboration function.
- `pdf.py`: add `po-v2` = `po-v1` plus a `Notes` heading and each body drawn verbatim, in order, after the PO terms and before the standard terms; no block when `notes` is empty. `TEMPLATE_VERSION = "po-v2"`; `render` keeps `po-v1` byte-for-byte (E13-S08's golden test stays green, unedited) and dispatches on the stored version.
- `email_summary` is unchanged: notes go on the PDF only (decision 171).
- E13-S08's leak test inserts a **shareable** note `NOTELEAK2` and asserts it absent; after this story it is present by design. Change that one assertion to "the PDF text and `vendor-copy` JSON contain `NOTELEAK2`"; the other five strings stay absent.

Consequence: a note made or flipped `shareable` reaches every revision snapshotted afterwards (a change
order's new revision walks back to it) and never one already issued, whose `po_vendor_copy` row is
append-only and whose bytes `pdf_for` hash-checks (E13-S08).

### 5. Attachments never reach the vendor

`vendor_copy` and `transmission.enqueue` read no attachment, name no file and attach nothing but the
generated PDF (decisions 170, 171; E13-S09). File names are internal: none goes into `VendorCopy`, the
email context or the PDF. "Not sent until scanning is available" and the "Never sent to the vendor"
list are in-app UI (E13-S14, E13-S17). The per-file vendor mark is **E13-S25** (after this story); here
every PO file is internal.

## Plants (each fails a test above; revert after)

1. `vendor_copy` reads notes with `CollaborationService.notes_unchecked` (every visibility) → the leak test fails on `INTNOTE-7Q`.
2. Drop `AND n.visibility='shareable'` from `external_notes_for` → the leak test fails.
3. `vendor_copy` passes only the snapshotted revision's id, not the chain → the flip test fails.
4. `transmission.enqueue` also attaches the PO's uploaded files → the leak test fails on the attachment count and `INTBYTES-5W`.
5. `po_write` always checks `purchase_order.create` → the `amend`-only upload to an issued PO fails.
6. Delete the `_authorize_share` call in `add_note` → `regrant(V)`'s shareable note on a draft returns 201; the share test fails.
7. Delete the `_authorize_share` call in `edit_note` → `regrant(V)`'s flip returns 200; the share test fails.
8. `po-v2` omits the notes block → the leak test fails on `EXTNOTE-3K`.
9. Narrow the `edit_note` condition to `body.visibility == "shareable" and before.visibility != "shareable"` → `regrant(V)`'s body-only edit of its shareable note returns 200; the share test fails.

## Resolved (operator, 30 Oct 2026)

- **Vendor-facing attachment mark:** option (b) as a separate story, **E13-S25** (after E13-S11). This story keeps every PO file internal and sends none.
- **Shareable notes:** option (b), in this story: on `purchase_order`, creating a note `shareable` or flipping one to `shareable` needs the PO write rule (`purchase_order.create` while draft, `purchase_order.amend` after) through the new optional `DocumentAccess.share_authorize`; every other document type keeps E09-S10's rule.
- **Body edit of an already shareable PO note** (operator, 30 Oct 2026, was OPEN): option (b). Any `edit_note` whose resulting visibility is `shareable` runs `_authorize_share`; condition `(body.visibility or before.visibility) == "shareable"`.
