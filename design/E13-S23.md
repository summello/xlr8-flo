# E13-S23 — PO lock order: withdrawal instance-first, change-order submit award-first

**Epic** E13 · **M3** · **concurrency/S** · after **E13-S07** · tags: `concurrency` (Opus review)

> Found by Codex pre-flights 12 and 15 of E13-S07 (30 Oct 2026). Raised by the operator as its own story; part 2 added by the operator the same day.
> Starts after E13-S07 merges. Cites below are to the code as it stands before E13-S07; where E13-S07 is named (cancel, reduce, issue's `lock_award`), the contract is `design/E13-S07.md`.

## Requirements (inlined)

- **PO-007** — The lifecycle should support Draft, Approval Pending, Approved, Issued, Partially Delivered, Delivered, Accepted, Closed, Cancelled, and Superseded.
- **PO-010** — Issued POs must be immutable; changes must create a numbered, approved change order/version.
- **PO-011** — A change order must preserve the prior version, identify changed fields/lines, recalculate budget effects, and be reapproved when policy requires.

No rule changes: who may withdraw (the PO's creator), the statuses, the responses and the postings stay as they are. Only the order in which two existing commands take their locks changes.

## Problem

### 1. `PurchaseOrderService.withdraw`

`withdraw` (`apps/api/src/flo/modules/purchasing/service.py:859-876`) locks the PO (`self._row(id, lock=True)`, :862) and **then** calls `approvals.service.withdraw`, which locks the running `approval_instance` (`approvals/decisions.py:362-366`). Every other writer that ends a PO approval takes the opposite order: `decide` locks the instance (`decisions.py:226`) and the outcome adapter (`PoAdapter.on_outcome`, `purchasing/approval.py:84-95` → `settle`, service.py:878-891) then locks the PO (:880); E13-S07's cancel of an `approval_pending` PO does the same (its step 5). A creator withdrawing while an approver decides, or while E13-S07 cancels, the same PO can deadlock; Postgres aborts one side with `DeadlockDetected` (40P01), which reaches the client as a 500.

### 2. `ChangeService.submit`

`submit` (`purchasing/changes.py:512-543`) locks the PO (`self.po._row(po_id, lock=True)`, :516), then the change row (:517), then calls `approvals.service.start` (:534-540). When the published `po_change` workflow routes straight from start to end, `start` approves synchronously (`approvals/engine.py:710-740`): the adapter's `ChangeService.settle` (changes.py:571-587) calls `self._lock(ch.po_id)` (:576), which locks the **award**, the line-project balances and the requisition (changes.py:610-625) while the PO is already held. The writers that lock an issued PO's award all take it **before** the PO: `ChangeService.apply` (:595-597) and the decision path of `settle` (both through `_lock`), E13-S07's cancel and `/reduce`, and E13-S07's `issue` fix. So an auto-approving submit (PO, then award) can deadlock with E13-S07's cancel of the same PO (award, then PO).

## Design

### 1. withdraw (service.py:859-876)

Same shape as `ChangeService.withdraw` (changes.py:545-569), keeping today's checks and their order:

1. Inside the existing `tenant_transaction`: `h = self._row(id)` **unlocked** (404 for an unknown, deleted or foreign id, as today).
2. `self._creator_only(id)` (service.py:810-814, 403 unchanged).
3. `h["status"] != "approval_pending"` → the existing 409 `invalid_transition`.
4. `withdraw(document_type="po", ...)` exactly as today, holding no PO lock. It locks the running instance; the adapter's `settle` then locks the PO and moves it to `draft`.

The order is now instance → PO on every path that ends a PO approval. If a decision or a cancel ends the approval between step 1 and step 4, `withdraw` finds no running instance and raises 409 `task_closed` (decisions.py:367-368); let it through unchanged. No route, schema, permission or migration change; the route (`api/purchasing.py:168-174`) is untouched.

### 2. submit (changes.py:516)

Replace `self.po._row(po_id, lock=True)` with `self._lock(po_id)`: award, line-project balances in id order, requisition, then the PO, the order of every other writer. Everything after it is unchanged. When the workflow auto-approves, `settle`'s own `_lock` re-takes only rows this transaction already holds.

`_lock`'s unlocked `_row` still 404s first. `lock_award` raises 409 `invalid_transition` when the award is not `approved`; it cannot fire here, because a change order exists only on an `issued` PO (`create`, changes.py:431-434) and an award with a PO cannot be superseded (`SUPERSEDE_GUARDS` `po_exists`, sourcing/awards.py:859-862). No test is needed for it. E13-S07's `/reduce` already takes `_lock` before calling `submit` and needs no change.

## Acceptance

- [ ] **withdraw holds no PO lock before the instance lock** (real Postgres, no threads): patch `flo.modules.purchasing.service.withdraw` (the imported `approvals.service.withdraw`, service.py:30) with a wrapper that, before calling the original, opens a second autocommit connection and runs `SELECT 1 FROM purchase_order WHERE id=%s FOR UPDATE NOWAIT` inside `contender.transaction()`; it must return one row (`(1,)`, so a probe that sees no row cannot pass vacuously) without `LockNotAvailable`. Assert the wrapper ran once and the PO ends `draft`, the instance `withdrawn`. (Probe pattern: `tests/requisitions/test_submission_check.py:407-434`.)
- [ ] **submit takes the award before the PO** (real Postgres, no threads, workflow with an approver): patch `flo.modules.purchasing.changes.lock_award` with a wrapper that records each call and, before calling the original, runs the same `FOR UPDATE NOWAIT` probe on the PO row from a second connection; it must succeed. Assert the wrapper ran at least once during `submit` and the change ends `approval_pending`.
- [ ] **Race, withdraw vs final approve** (real Postgres, `_race` from `tests/purchasing/test_purchase_orders.py:397-409`, 5 rounds, each on a fresh `approval_pending` PO; task id and document version read before the race): exactly one call succeeds and the other returns 409 `task_closed` or `invalid_transition`; the PO is `draft` with the instance `withdrawn`, or `approved` with the instance `approved`. A deadlock raises `psycopg.errors.DeadlockDetected`, which `_race` does not catch, so it fails the test.

- [ ] `flo check --light` green.

## Plants

1. Restore `h = self._row(id, lock=True)` in `withdraw`: the first acceptance probe gets `LockNotAvailable` and fails.
2. Restore `self.po._row(po_id, lock=True)` in place of `self._lock(po_id)` in `submit`: with an approver workflow `lock_award` is never called during `submit`, so the second acceptance's "ran at least once" fails.

## Files

In scope: `apps/api/src/flo/modules/purchasing/service.py` (`withdraw` only), `modules/purchasing/changes.py` (`submit` only), tests under `apps/api/tests/purchasing/`.

Out of scope: `ChangeService.withdraw` and `approvals.withdraw_instance` (both already instance-first), `PurchaseOrderService.submit`, E13-S07's cancel, `/reduce` and `issue` (already award-first), `_post`'s balance locks for a project outside `_lock`'s set (the same on every `_apply` path; not changed here), any route, schema, migration or API client.
