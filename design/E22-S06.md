# E22-S06 — Baseline roles read the projects and master data they work against

**Epic** E22 · **M3** · **auth/S** · tags: auth, security, migration

> Operator decision, 21 Oct 2026: canvas DECISIONS **217** (closes the M2 follow-up in
> `docs/m2-decisions.md` "no baseline role holds `project.read` or `master.read`"). E09-S13 already
> gave `project.read` to Requestor and Approver; this story finishes the job for every baseline role.
> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.

## Requirements (inlined)

- **USR-003** — Access must support organization, BU/OU, module, record, and action scopes.
- **USR-005** — Server-side authorization must be evaluated for every protected request; hidden UI controls are insufficient.
- **USR-006** — Least privilege and default-deny behavior must apply to new roles and permissions.
- **USR-008** — Role, scope, and permission changes must be effective immediately or on a configured date and must be audited.
- **ACC-004** — A user cannot access another BU/OU's record by guessing an identifier or changing a request.

## Design

**Grants.** In `apps/api/src/flo/modules/identity/models.py` `BASELINE_ROLE_PERMISSIONS`, add:

| Role | Gains |
|---|---|
| `requestor` | `master.read` |
| `approver` | `master.read` |
| `sourcing-specialist` | `project.read`, `master.read` |
| `purchasing-user` | `project.read`, `master.read` |
| `vendor-manager` | `project.read`, `master.read` |

Read only: no create, update or approve permission moves. A grant applies **in the scope the role
assignment already has** (org, BU/OU or project); the existing scoped repositories and the resolver
do the narrowing, so nothing changes in `projects` or `master_data` code.

**Existing tenants.** One migration, following `20261014_0053_baseline_role_catalogue.py` and
`20261014_0062_vendor_sensitive.py`: insert the missing `role_permission` rows for every org's
**system** baseline role (`role.is_system`), `ON CONFLICT DO NOTHING`. A custom role an administrator
built is never touched. Downgrade deletes exactly the rows this migration's table names, for system
roles only. The migration number is the next free one on the milestone at merge (E22-S01 holds
`0063`); rebase `down_revision` onto the head then.

**Audit.** The migration writes one `role.permission.grant` audit row per org (system actor), naming
the role codes and permissions, so USR-010's effective-access view and the audit log explain the
change.

## Acceptance

- [ ] A seeded Requestor with a BU-scoped assignment can `GET /api/v1/projects` and `/api/v1/master/...` lists and sees only that BU's records; a project in another BU → **404** (ACC-004).
- [ ] Each of the five roles: an authorization test per role that the two reads succeed in scope and every write on projects and master data still returns 403.
- [ ] A custom (non-system) role named `requestor`-like is unchanged after the migration.
- [ ] Migration: up adds exactly the rows in the table above for every org's system roles; down removes exactly them; a data-preservation assertion that an existing unrelated grant survives up+down.
- [ ] TEN-010 isolation case for the newly readable list endpoints with a requestor of org A against org B.
- [ ] `flo check` green.

## Plants

1. Grant `project.update` to Requestor instead of `project.read`: the write-still-403 test fails.
2. Make the migration touch non-system roles: the custom-role test fails.
