# E08-S04 — Project and budget import templates end to end

**Epic** E08 · **M1** · **crud/M** · after **E08-S03**, **E07-S03** · tags: `money`

> **Conventions:** read `docs/m1-conventions.md` (authorization outcomes, scope targets, wire formats). It applies unless this packet says otherwise.

## Requirements

- **PROJ-001** — Projects must be creatable manually or through a validated import.
- **IMP-001** — The system must support robust Excel and CSV imports aligned to the application’s data model.

## Contract

Registers two concrete templates with the E08-S01 framework (version `1`), using only service entry points — **no import code reaches into a module's tables**:

**`projects`** — creates and updates projects (PROJ-001). Columns: `external_ref` (key, required), `bu_code` (code → `org_unit`), `parent_external_ref` (optional, must appear earlier in the file or already exist), `name` (required, <= 200), `description`, `department_code` (master data), `ledger_account_code` (master data), `currency` (ISO 4217), `planned_start`, `planned_end` (ISO dates), `owner_email` (optional, an existing user in the org). Create/update go through `projects.service.create_project` / `update_project` (E06-S01), so numbering, validation, audit and permissions are the ones the API uses. Project `external_ref` is stored on the project (`project.external_ref text`, unique per org when set — added in this story's this story's migration).

**`budget_allocations`** — creates allocations (BUD-001, via `budget.service.allocate`, E07-S03): `project_ref` (project `external_ref` or number), `amount` (decimal string), `currency`, `effective_date`, `reason` (required), `evidence_ref` (optional). Allocations are **never updated in place**; re-importing the same file is idempotent through a per-row `idempotency_key = "import:<batch_id-independent hash of org, template, external key, row key>"` so a re-run skips rows already posted (FIN-012). A row for a project in roll-down mode with a parent follows E06-S04's from-parent rule (the template surfaces its 409 as a row error naming the rule).

Row order matters for the `projects` template (parents before children); the validator reports a forward reference to a not-yet-defined parent as an error with the row number.

## Behaviour

1. Both templates implement `Template.validate_row` and `Template.apply_row` and register `key_columns`; the framework (E08-S02/S03) does everything else.
2. Money values are decimal strings parsed with `Decimal`; a value like `1,000.00`, `1e3` or `12.345678` (over currency precision) is a row error.
3. A user needs `project.create` / `project.update` (projects) or `budget.allocate` (allocations) at each row's scope; lacking it is a per-row error.
4. Downloadable template files contain a worked example row for each (IMP-002) and the accepted-code lists are reachable from the template description.

## Acceptance criteria

- [ ] End to end through the public endpoints: upload `projects.csv` (parent + two children), map, validate (dry-run shows 3 creates), commit atomically; the three projects exist with numbers, correct parents and depth, and `import_result` lists their ids
- [ ] Re-importing the identical file classifies all rows `skip` and creates nothing
- [ ] Changing one child's name and re-importing classifies that row `update` and updates only that project
- [ ] A child listed before its parent → row error naming the order rule
- [ ] An allocations file posts the allocations once; re-importing it posts nothing (idempotent); the ledger and `project_balance` reconcile afterwards
- [ ] A row with an inactive department code, a non-decimal amount, or a project the user cannot allocate to produces row-level errors and, in atomic mode, blocks the whole commit
- [ ] A 1,000-project file imports as a background job with visible progress (reuses E08-S03)
- [ ] Foreign-tenant project reference in `project_ref` → row error, never a cross-tenant write
- [ ] Migration up/down/data-preservation

- **`project_ref` is the project `external_ref` only** (numbers are unique only per BU, so they are ambiguous); a value that matches none is a row error.

## Pre-flight amendments 3 (Opus, 10 Oct 2026) — answers the roll-down idempotency block, authoritative

The block was right. `budget.service.allocate` stores a **direct** allocation as one entry under the caller's key (`_manual_entry`), but a **roll-down** allocation as two legs under `<key>:out` (parent debit, `entries[0]`) and `<key>:in` (recipient credit, `entries[1]`); nothing is stored under the bare key. Ruling:

1. **An allocation's identity is the credit to the recipient project.** `budget.service.entry_by_idempotency_key(connection, scope, key)` returns the entry stored under exactly `key` if one exists, otherwise the entry stored under `key + ":in"`, otherwise `None`. It never returns a `:out` leg. One query: `idempotency_key IN (%(key)s, %(key)s || ':in')`, preferring the exact match. A test covers both a direct and a roll-down allocation.
2. **`plan_row` compares that entry** (project, positive amount, currency, effective date, reason) with the row exactly as §6 says; it is the recipient's credit in both modes, so the comparison is against the recipient project and a positive amount. A funding-mode change between two imports does not create a second posting: the first allocation's entry is found under whichever key it was stored with.
3. **`apply_row` returns `("ledger_entry", <id of the entry whose project_id is the recipient>)`**, not `entries[0]` (for a roll-down that is the parent's debit). Nothing about `allocate`, the keys it writes or the ledger changes.
4. **Tests and plants:** add a roll-down re-import that classifies `skip`, and a roll-down `row_key_conflict`. Plant: make the lookup exact-match only and the roll-down re-import test fails; return `entries[0]` from `apply_row` and the `import_result` recipient test fails.

All four findings in `notes.followup` are real defects in the E08-S02/S03 framework that this story is the first to exercise. Authorized, for exactly these purposes and nothing else, each with a test:

1. **Result ids.** `ledger_entry.id` is `BIGSERIAL`; `import_result.record_id` is `uuid`. In this story's migration (`20261009_0036_*`), `ALTER TABLE import_result ALTER COLUMN record_id TYPE text USING record_id::text`. `TemplateHandler.apply_row` returns `tuple[str, UUID | int]`; `modules/imports/{handlers,commit,jobs}.py` store `str(record_id)`, and anything that surfaces a result id (`ImportReport`, generated client) carries it as a string. Downgrade: delete `import_result` rows whose `record_id` is not UUID-shaped, then convert back to `uuid`; mark that line `# irreversible: import_result rows naming integer ledger ids cannot be represented as uuid` and cover both directions in the migration test (data-preservation for UUID rows, deletion of integer rows).
2. **Amount parsing belongs to the handler.** `modules/imports/{service,validation}.py` stop rejecting a malformed mapped value at upload or mapping time for template columns whose handler declares it parses them; the handler's `plan_row` reports it as a row error. Every other upload-time check stays.
3. **Planned parents across validation slices.** `modules/imports/jobs.py` reconstructs the handler's scratch state (planned project keys and parents) from earlier `import_row` plans when a validation continues in a later slice, the same way duplicate keys are already reconstructed.
4. **Row failure labels in partial mode.** `modules/imports/{commit,jobs}.py` persist a failed row's `ProblemError` code and `checks["problem"]` label into that row's issues, not just its row number.

Nothing else in the framework changes. Finish the remaining plants (batch-independent key, recipient result) and run the full `flo check` before reporting done.
