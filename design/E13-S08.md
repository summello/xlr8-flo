# E13-S08 — Vendor-copy PDF, reproducible from the stored snapshot and template version

**Epic** E13 · **M3** · **engine/L** · after **E13-S06** · tags: `security` (Opus review)

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** canvas DECISIONS 170 (one email and one PDF, nothing else; the PDF is a simplified
> vendor copy **without chartfields** (project, department, ledger account) **and without budget
> information**; internal notes never reach it; no HTML attachment), 171 (a note marked `Sent to
> Vendor` appears on the PDF; uploaded files are never sent in M3), MASTER §7.16 (`.pdf-page`
> vendor-copy style). `design-system/pages/purchase-orders.md` §2 and §4.9; open question §7.7
> (template ownership: ships with one system template, versioned).

## Requirements (inlined)

- **PO-014** — Generated PO PDFs must be reproducible from the stored PO snapshot and template version.
- **PO-017** — Internal-only content must never be included accidentally.

## Design

**Snapshot:** at issue (E13-S05) and at each applied change order, store
`po_version(po_id, version, snapshot jsonb, template_version, pdf_sha256, created_at)`. The
**vendor-copy snapshot** is built by **one function**, `vendor_copy(po) -> VendorCopy`. It
whitelists the fields the vendor may see: number, version, dates, Bill To, Ship To, vendor snapshot,
terms, lines (description, quantity, UoM, unit price, tax, freight, line total), totals, currency,
and `Sent to Vendor` notes (from E13-S11). There are no chartfields, no budget fields, no internal
notes and no file content. `VendorCopy` is a Pydantic model with **no field** that could hold them.

**Template:** a versioned HTML/CSS template in `apps/api/src/flo/modules/purchasing/templates/po_v1.html`
using the MASTER §7.16 `.pdf-page` tokens. It is rendered to PDF by an **already-installed** library
if one exists. Otherwise this story must name the dependency in the PR body (AGENTS.md §0.6), prefer
one with no system binaries (the API image is slim, Cloud Run), and record the choice. **Check
before choosing:** `uv pip list` in `apps/api`. Rendering is deterministic: fixed fonts embedded, no
timestamps in the PDF metadata except the snapshot's own dates, so the same snapshot and template
give the **same bytes** (`pdf_sha256` equal).

**Reads:** `GET /purchase-orders/{id}/versions/{v}/pdf` (`purchase_order.view`) renders on demand
from the stored snapshot and template version and checks the hash, so it never has to store bytes in
Postgres (the 512 MB Neon ceiling). It may cache to object storage via the kernel storage port, under
an opaque key. `GET …/vendor-copy` returns the `VendorCopy` JSON and the email summary text (for the
preview UI).

## Acceptance

- [ ] **Leak test with a planted violation:** seed a PO with distinctive chartfield codes, an internal note and a budget figure; extract the PDF text and the vendor-copy JSON; assert none appear. Plant: add `ledger_account_code` to `VendorCopy` → fails.
- [ ] Reproducibility: render v1 twice → identical bytes; after a change order, v1 still renders to its original hash.
- [ ] A `Sent to Vendor` note appears; an uploaded file never does (only its name with "Not sent until scanning is available", or nothing; decision 171).
- [ ] TEN-010 and authorization; `flo check` green.

## Plants

1. Render from the live PO instead of the snapshot: the v1-after-change hash test fails.
2. Add an internal note to the whitelist: the leak test fails.
