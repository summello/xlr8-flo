# E10-S03 — Graph validation: cycle detection, unreachable steps, duplicate approvals, depth limit

**Epic** E10 · **M2** · **engine/M** · after **E10-S01** · tags: none

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` and `docs/author-traps.md`. Decisions: D-M2-3, D-M2-10.

## Requirements

- **APR-006** — Workflows must support unlimited logical levels, subject to an operational safeguard against excessive depth.
- **APR-007** — The builder must detect and prevent cycles.
- **APR-008** — The builder must warn about and prevent unintended duplicate approvals.
- **APR-012** — Publishing a workflow must validate unreachable steps, missing approvers, invalid fields, cycles, and incomplete branches.

## Contract

- `approvals.service.validate_graph(conn, scope, document_type, graph) -> ValidationReport` where `ValidationReport = {errors: [Issue], warnings: [Issue]}` and `Issue = {code, node_id?, edge_index?, detail}`.
- `GET /api/v1/workflows/{id}/versions/{version}/validation` (`workflow.read`) → 200 `ValidationReport` for the **stored** graph of that version. The builder saves the draft (`PUT`, E10-S01) and then reads its validation. A `GET` needs no `Idempotency-Key`; do not add a POST validate route (the idempotency middleware demands a key on every POST, and `IDEMPOTENCY_BYPASS_PATHS` matches exact paths only, so a path with an id can never be bypassed).
- **Publish gains the gate** (E10-S01's endpoint): body `{acknowledge_warnings: bool}`. Any error is 422 `VALIDATION_FAILED` with each issue in `errors[]` (`field` = a JSON pointer to the node or edge, `message` = `detail`) and `checks.problem = "workflow_invalid"`. Warnings without `acknowledge_warnings: true` are 409 `CONFLICT`, `checks.problem = "warnings_unacknowledged"`, listing them.
- Setting `approval.max_depth` (convention M): default 10 (D-M2-10), integer 1..50 (D-M2-3). Register it in `SETTING_DEFAULTS` and `SETTING_VALIDATORS` in `modules/org/settings.py`. The value is read at publish time with the organization's effective setting.

## Behaviour — the checks (all run every time; the report lists every issue, not the first)

| Code | Severity | Rule |
|---|---|---|
| `cycle` | error | Any directed cycle (APR-007). Report one issue per strongly connected component of more than one node (or a self-loop), naming its nodes. |
| `unreachable` | error | A node not reachable from `start`. |
| `dead_end` | error | A non-`end` node with no outgoing edge, or a node from which no `end` is reachable (APR-012, "incomplete branches"). |
| `missing_default` | error | A `condition` node without exactly one `default: true` outgoing edge; any edge from a non-condition node carrying `when` or `default`. |
| `bad_out_degree` | error | `start` or an `approval` node with other than exactly one outgoing edge (routing is linear between conditions, E10-S05). |
| `missing_approvers` | error | `approvers.type = role` naming a role code that does not exist in this organization; `users` with an id that is not a member of this organization; an empty list. |
| `invalid_field` | error | A condition leaf naming a field absent from `field_catalog(document_type)` (E10-S02), an op not allowed for that field's type, or a value of the wrong type. Unknown `custom.*` fields land here. |
| `invalid_condition` | error | A `when` that does not parse under E10-S02's grammar. |
| `too_deep` | error | The maximum number of `approval` nodes on any `start → end` path exceeds `approval.max_depth` (APR-006). |
| `duplicate_approval` | error, or warning | The same approver rule (same role code, or an overlapping user id, or two `permission` rules) appears on two `approval` nodes of one `start → end` path (APR-008). It is an **error** unless the later node has `allow_repeat: true`, in which case it is a **warning** that must be acknowledged at publish. |
| `quorum_unreachable` | error | `{"quorum": n}` on a `users` rule with fewer than `n` user ids. |

Path enumeration is exponential in the worst case: cap the graph at the E10-S01 limits (200 nodes, 400 edges) and compute depth and duplicates with a memoised DFS over the acyclic graph. Only run the path-based checks when there is no `cycle` error.

## Acceptance criteria

- [ ] One failing fixture graph per code above produces exactly that code, located at the right node or edge.
- [ ] A graph with three errors reports all three.
- [ ] Depth equal to `approval.max_depth` publishes; one more is `too_deep`; an organization setting of 3 rejects a 4-level graph; a setting of 51 or 0 is refused by the settings validator.
- [ ] A duplicate with `allow_repeat: true` publishes only with `acknowledge_warnings: true`; without it 409 `warnings_unacknowledged`.
- [ ] A clean 30-node, 12-level graph validates in under 50 ms (a timing assertion with a generous margin, marked so it can be skipped on a slow runner).
- [ ] The validation route is a `GET` and changes nothing; the report for a published version equals the one computed before it was published.

## Required tests

`apps/api/tests/approvals/test_graph_validation.py` (fixture graphs as small dicts beside each test), plus publish-gate tests through the real app in `test_workflow_definitions.py`.

## Plants

1. Skip the cycle check: the cycle test fails, and the depth test on a cyclic graph must not hang (it fails instead).
2. Count all nodes instead of approval nodes for depth: the depth-boundary test fails.
3. Treat `allow_repeat` as silencing the duplicate entirely: the warning-acknowledgement test fails.
4. Let publish ignore errors: the publish-gate test fails.
