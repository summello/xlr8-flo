# E09-S07 — Release on withdraw, cancel, expire or reduce after approval, exactly once

**Epic** E09 · **M2** · **ledger/M** · after **E09-S06** · tags: `money`

> **Conventions:** `docs/m1-conventions.md` (C: internal job triggers), `docs/m2-conventions.md` (L funding rounds and keys, M settings) and `docs/author-traps.md`. Decisions: D-M2-6 (expiry), **D-M2-15**, canvas decision 78 (withdraw until sourcing starts). Builds on E09-S05's release helper `requisitions.funding.release_live` and transition table (the rows marked E09-S07).

## Requirements

- **REQ-013** — Rejected, withdrawn, cancelled, expired, or reduced requisitions must release unused reservation exactly once.
- **FIN-011** — Failed, rejected, cancelled, expired, or reduced transactions must release unused reservations and commitments exactly once.
- **FIN-012** — Retries and duplicate submissions must not create duplicate financial effects.
- **ACC-006** — Cancelling a requisition or PO releases only its unused funds, once.
- **D-M2-6** — Requisition expiry is a per-organization setting, unset by default (`requisition.expiry_days`, never expires). When set, an approved requisition with no RFQ started within that many days of approval expires and releases its reservation exactly once.

## Design decisions (this packet)

- **"Sourcing has started" is a registry**, `requisitions.service.register_sourcing_probe(fn: Callable[[Connection, Scope, UUID], bool])`. The M3 RFQ story registers "an RFQ exists for this requisition". With no probe registered (M2), sourcing has not started. Withdraw-after-approval and expiry both consult it.
- **On a post-approval stop, the requisition-generated sub-project is abandoned** in the same transaction, through a new `projects.service.abandon_generated(conn, scope, project_id, *, reason, actor_id)` that runs the E06-S03 closing rule (it must pass: the sub-project holds nothing) and writes the project status event and audit. It is a system consequence, so it needs no `project.complete` grant. **A standalone-created project is left as it is**: its allocation stays for the operator to move or reverse. Record this in `notes.followup` next to the decision-99 question.
- **Expiry actor:** the job has no user. Ledger rows and status events carry `actor_id = 00000000-0000-0000-0000-000000000000` (the nil UUID; `ledger_entry.actor_id` has no FK to `identity`; verify `requisition_status_event` likewise and block if a FK exists), and the audit actor is `AuditActor(ActorKind.JOB, None)`.
- **Expiry age** = whole days from `decided_at` (UTC date) to today (UTC). A requisition expires when `today − decided_at::date > expiry_days`, using the effective setting for its BU/OU.
- **Reduce** is a primitive with no M2 route: `requisitions.funding.reduce_to(conn, scope, requisition_id, *, new_amount: Decimal, version: int, actor_id) -> LedgerEntry | None` releases `remaining − new_amount` from the live reservation with key `req:<id>:release:<round>:reduce:<version>`. M3's partial-award and line-cancel stories call it. E09-S08 does not, because any estimate change is material (D-M2-13) and goes through resubmit's release-and-reserve.

## Contract

- `POST /api/v1/requisitions/{id}/transitions` (E09-S05's route) now accepts, from `sourcing_in_progress`:
  - `{to: "withdrawn"}`: the requester only, with `requisition.withdraw`, and only while no sourcing probe returns true (else 409 `sourcing_started`: "Sourcing has started on REQ-00431. Ask Procurement to cancel it.");
  - `{to: "cancelled", reason}`: `requisition.cancel`, reason ≥ 10 characters. Allowed whether or not sourcing has started (M3 adds RFQ cancellation to the same transaction).
- `POST /internal/jobs/requisition-expiry`: origin secret, `Idempotency-Key` required but not replayed (convention C). **Replay contract (convention C demands one, because this job mutates business data):** each requisition expires in its own transaction under the E09-S05 lock order, only from `sourcing_in_progress`, with the deterministic release key `req:<id>:release:<round>:expired`. A second call expires nothing already expired and releases nothing twice. Response `{organizations, expired}`. The docstring says so.
- Worker: in `apps/web/worker/api-proxy.ts` `runScheduledWork`, at `:30`, hour `3` → `/internal/jobs/requisition-expiry` (beside fx-ingest and budget-reconcile). Update its test.
- Setting (convention M): `requisition.expiry_days`, default `None`, valid `None` or an integer 1..3650, in `modules/org/settings.py` `SETTING_DEFAULTS` and `SETTING_VALIDATORS`. Settable at organization or BU/OU through the existing settings routes.

## Behaviour

1. **Post-approval withdraw or cancel** (one transaction): lock `project_balance` of the requisition's project → the requisition. Check status and actor, check the probe for withdraw, `release_live(reason)`, `abandon_generated` on the sub-project if there is one (`projects.service.generated_for`), set the terminal status, write the status event (with the release entry id) and the audit.
2. **Expiry job**: enumerate organizations as `budget.reconcile.reconcile_all` does (ids only, then tenant-scoped work per organization). For each organization, select `sourcing_in_progress` requisitions whose effective `requisition.expiry_days` is set and passed, then expire each in its own transaction, with the same steps as behaviour 1 and reason `expired`. One failure is logged with the requisition id and does not stop the rest. A `# ponytail:` comment sets the ceiling: one query per requisition for the effective setting; batch by BU/OU when an organization has more than 1,000 open requisitions.
3. **`reduce_to`**: lock `project_balance` → the requisition. `new_amount` must be ≥ 0 and ≤ remaining (else 409 `ReleaseExceedsReservation`, the E07-S04 label). Equal to remaining is a no-op returning `None`.
4. **Exactly-once evidence**: every release path (E09-S05's and this story's) goes through `release_live` or `reduce_to`, which go through `budget.service.release_reservation`. Its remaining-never-below-zero rule plus the per-round keys is the guarantee. This story adds the property test that proves it across paths.

## Acceptance criteria

- [ ] Withdraw after approval by the requester: one release equal to the reservation, the generated sub-project `abandoned` with an event naming the requisition, the requisition `withdrawn`. With a test probe returning true → 409 `sourcing_started`, nothing written.
- [ ] Cancel after approval with a reason: released once, sub-project abandoned, status `cancelled`. Without a reason → 422.
- [ ] Two concurrent cancels or withdraws of one requisition: one release row, one terminal status, the other 409 `invalid_transition` or `stale_version`.
- [ ] Expiry: with `expiry_days = 30`, a requisition approved 31 days ago expires and releases once; one approved 30 days ago does not. With the setting unset, nothing expires. A BU/OU override of 10 beats an organization value of 30. Calling the job twice changes nothing the second time (every non-report table byte-identical), with the same key and with different keys.
- [ ] `reduce_to(60)` on a reservation of 100 releases 40 (key `…:reduce:<version>`). Replaying the same version releases nothing. A later cancel releases the remaining 60. Total released = 100.
- [ ] **Property test (seeded RNG, 300 runs):** random sequences of submit, return, resubmit with a changed estimate, reject-to-draft, approve, reduce, withdraw, cancel and expire, with each mutating call issued twice concurrently. In every terminal state the requisition's reservations have zero remaining, no round released more than it reserved, and the organization's reconcile reports no drift.
- [ ] Setting validation: `0`, `3651`, `"30"` and `true` are rejected with 422. `null` clears it.
- [ ] The worker calls `/internal/jobs/requisition-expiry` at 03:30 UTC and not at any other minute (worker unit test).

## Plants

1. Use the key `req:<id>:release:expired` without the round: the property test finds a double release after reject-to-draft, resubmit, approve, expire.
2. Release before locking `project_balance`: the concurrent-cancel test fails (20 runs).
3. Skip the probe check on withdraw: the `sourcing_started` test fails.
4. Compare expiry with `>=`: the 30-day boundary test fails.

## Pre-flight amendments (11 Oct 2026, Opus; binding, they override anything above)

Each item below was found by reading the code this story touches. A block on any of them is a packet defect, not an author failure.

1. **`project_status_event.actor_id` is `NOT NULL REFERENCES identity(id)`** (migration 0025). The expiry job's nil-UUID actor therefore fails on the sub-project's abandon event. `ledger_entry.actor_id` (migration 0019) and `requisition_status_event.actor_id` (E09-S05) have no foreign key, so the nil UUID is correct there. For `projects.service.abandon_generated`, write the project status event with `actor_id = requisition.requester_id` and the reason `"Abandoned because REQ-… expired"` (or `…was withdrawn`/`…was cancelled` with the real actor), and keep the true attribution in the audit row (`ActorKind.JOB`, id `None`). Record in `notes.followup`: the project event names the requester because the table's actor is a required identity.
2. **Lock order** follows E09-S05 amendment 1. A post-approval stop reads `pending_amendment_id` unlocked; if one is set, call `approvals.service.withdraw` for that instance **first** (instance → balance → requisition inside `on_outcome(WITHDRAWN)`), then take balance → requisition for the stop. Expiry has no running instance (the approved instance is closed), so it is balance → requisition.
3. **The worker test is `apps/web/src/api-proxy.test.ts`**, not a file beside `worker/api-proxy.ts`. The schedule gate is the `getUTCMinutes() === 30` block with the `hour === 16 || hour === 18 ? fx-ingest : hour === 2 ? budget-reconcile` ternary; add `hour === 3 ? "/internal/jobs/requisition-expiry"`. The test asserts each existing job still fires at its own hour and only the new one at 03:30.
4. **The ledger's label is `release_exceeds_reservation`** (409 `CONFLICT`, `checks.problem`). The packet's "ReleaseExceedsReservation" names it loosely; match on the lower-case problem.
5. **`abandon_generated` bypasses `project.complete`** but must run the same closing rule as `Lifecycle.evaluate` for `abandoned` (reserved, committed and open documents of the **sub-project**, all zero by construction). Implement it as a small function in `projects/lifecycle.py` that reuses `snapshot(..., for_update=True)` and the blocked-by check, then writes status and event. Do not call `evaluate` with a fake permission set.
