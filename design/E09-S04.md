# E09-S04 — Submission validation: fields, active master data, eligibility, funds, routing

**Epic** E09 · **M2** · **engine/L** · after **E09-S02**, **E07-S06** · tags: `money`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (G–O) and `docs/author-traps.md`. Decisions: `docs/m2-decisions.md` (**D-M2-15 reserve at submit**, D-M2-7, D-M2-12). Consumer: `design-system/pages/requisition-create.md` §5 (Funding Check) and §6 (the summary, categories and exact messages). Read §6 before writing a message.

## Requirements

- **REQ-011** — Submission must validate required fields, active master data, project eligibility, available funds, and approval routing. *(Everything except routing here; E09-S05 adds routing via `approvals.service.preview_route`, because routing needs the approval engine.)*
- **WF-002** — A status transition must validate actor, current state, required fields, approvals, and financial side effects. *(The field, eligibility and funds half; the actor and state half is E09-S05.)*
- **WF-006** — Users must receive a clear, actionable explanation when a workflow action is blocked.
- **REQ-003** — A requisition must not be created against a sub-project that was itself generated by a requisition.
- **D-M2-15 / canvas decision 33 (operator)** — A project-linked requisition reserves at submit, and **one whose estimate exceeds the funding available cannot be submitted**. There is no override. The check is authoritative only under the funding row's `FOR UPDATE` lock (FIN-006), which E09-S05's submit takes before calling this validator.

## Design decisions (this packet)

- **One validator, two callers.** `requisitions.validation.check(conn, scope, requisition_id, *, need: Decimal | None = None, lock: bool) -> SubmissionCheck`. E09-S05's submit calls it with `lock=True` inside the submit transaction, and E09-S08's resubmit calls it with `need` = the extra amount to reserve. The read-only endpoint calls it with `lock=False`; its funds figure is advisory and says so.
- **Lock order with `lock=True`:** `project_balance` row `FOR UPDATE` first, then the `requisition` row `FOR UPDATE` (the E06-S03 balance-first order every posting path uses, so submit cannot deadlock against a reservation, a transfer or a project transition). The caller must not have locked the requisition before calling.
- **Funds rule mirrors the ledger exactly**, so submission and posting can never disagree: a problem exists when `available − need < 0` **and** the requisition's BU/OU does not have `allow_negative_budget = true` (`OrgService.effective_setting`). `need` defaults to the estimate. A standalone requisition has no funds check (funding is assigned at approval, D-M2-5).
- **The needed-by date may not be in the past** (`org.service.today()`, UTC today). This is the page spec's reading of REQ-011, accepted: it closes `requisition-create.md` open question 3.
- **Category travels in the field path.** The error taxonomy is closed (convention D), and `ProblemFieldError` has only `field` and `message`, so each entry's `field` is `<category>/<field path>`. Categories: `required`, `master_data`, `project`, `lines`, `funds`, `routing`. For example `required/title`, `master_data/ledger_account_code`, `project/project_id`, `lines/3/quantity` (3 is `line_no`), `funds/estimate`, `routing/workflow`. The client maps the first segment to the label (`Required field`, `Master data`, `Project`, `Lines`, `Funds`, `Routing`) and the rest to the control.

## Contract

- `GET /api/v1/requisitions/{id}/submission-check` — `requisition.view` (record) → 200 `SubmissionCheck = {ready: bool, problems: [{category, field, message}], funding: FundingCheck | null}`, where `FundingCheck = {available, this_requisition, available_after, currency, advisory: true}`. `funding` is null for a standalone requisition. Works in any status, but `ready` is false unless the status is `draft`.
- Service export: `requisitions.service.check_submission(...)` (the validator above) and `SubmissionInvalid(problems)`, which E09-S05 converts to **422 `VALIDATION_FAILED`, `checks.problem = "submission_invalid"`, `errors = [{field: "<category>/<path>", message}]`** with `detail = "Fix N things before you submit. Nothing was submitted. Everything you entered is kept."`.

## Behaviour — the checks, in this order, every one evaluated (no early exit)

**Messages are the page spec's, verbatim, with values filled in.**

1. **Required** (`required/...`): `title` ("Enter a title"); `justification` ("Explain why it is needed"); `needed_by` ("Enter the date it is needed by"; if it is in the past, "The needed-by date is in the past"); `department_code` ("Choose a department"); `ledger_account_code` ("Choose a ledger account"); `delivery_address_id` ("Choose a delivery location"); standalone `bu_id` ("Choose a business unit"; always present by construction, kept for completeness).
2. **Master data** (`master_data/...`), for each code present: `assert_usable(conn, scope, kind, code, today)`. A failure reads "Ledger account 6140 is inactive. Choose an active account" (the reason word is `inactive`, `unknown` or `not effective yet` / `no longer effective`). The delivery address must be an effective `ship_to` address of the unit or an ancestor ("Delivery location is no longer available. Choose another"). Line `uom_code` and `category_code` are re-checked too, reported under `lines/<n>/uom_code`.
3. **Project** (`project/project_id`, project-linked only): status `active` ("The chosen project cannot take a requisition: it is <status in words>"); `is_requisition_generated` is false ("The chosen project cannot take a requisition", REQ-003); `depth_of(project) < 5` ("The chosen project is at the five-level limit, so approval could not create its sub-project. Choose a shallower project", D-M2-12); the requisition's currency equals the project's (a mismatch can only follow a direct data change, but say so: "The project's currency changed. Reopen the requisition"). Standalone: the BU/OU is active ("Choose an active business unit").
4. **Lines** (`lines/...`): at least one line ("Add at least one line"). Each line has a description, a quantity and a unit price (enforced at write, so these only fire on legacy or imported rows): "Line 3 needs a description" and so on.
5. **Funds** (`funds/estimate`, project-linked only): with `lock=True`, `budget.service.get_balance` is read **after** the `FOR UPDATE` on `project_balance` (lock before validate, FIN-006). Message: "Over the available funds by 20,000.00 USD. Reduce the estimate or ask for a budget transfer", where the amount is formatted with the currency exponent and grouping, and the code is visible.
6. Return all problems. With `lock=True` the locks are held by the caller's transaction, so E09-S05 can reserve without re-reading.

No writes happen in this story's code path, not even an audit row (the check endpoint is a read).

## Acceptance criteria

- [ ] An empty draft returns every required problem at once, each with its category prefix and the page-spec message.
- [ ] Needed-by of yesterday gives "The needed-by date is in the past". Today passes.
- [ ] An inactive ledger account, an expired `uom`, and a closed delivery address each produce a `master_data` problem naming the code.
- [ ] A requisition-generated project, a `deferred` project, and a depth-5 project each produce a `project` problem with its own message.
- [ ] Estimate 120,000 against available 100,000 gives `funds/estimate` "Over the available funds by 20,000.00 USD …". With `allow_negative_budget = true` on the BU there is no funds problem. A standalone requisition never gets one.
- [ ] `need` overrides the estimate (resubmit case): estimate 150,000 with 100,000 already reserved and `need = 50,000` against available 60,000 passes.
- [ ] `lock=True` takes the `project_balance` row lock before reading the balance (proved by a concurrent transaction that holds the row and makes the check wait), and the requisition lock after it.
- [ ] The check endpoint returns `funding` figures that equal `get_balance` and the estimate, marked `advisory: true`. A foreign-tenant id → 404; no grant → 404.
- [ ] No row in any table changes after a check (row counts and `updated_at` before and after).

## Pre-flight amendments (11 Oct 2026, Opus; binding, they override anything above)

Each item below was found by reading the code this story touches. A block on any of them is a packet defect, not an author failure.

1. **A budget lock export does not exist.** `budget.service.__all__` has `get_balance` (no lock) and the lock lives in `LedgerRepository.balance(project_id, lock=True)`, which `modules/requisitions` may not import (AGENTS.md 3.3). Add to `modules/budget/service.py` (authorized edit, with a unit test): `lock_balance(conn, scope, project_id) -> BalanceRead` that runs `LedgerRepository(conn, scope).balance(project_id, lock=True)` inside `tenant_transaction` and raises `ErrorCode.NOT_FOUND` when absent. Add it to `__all__`. E09-S05, S06, S07 and S08 call it. **Every locking caller takes `project_balance` rows in ascending project id** (decision 96 precedent).
2. **Signature.** `check_submission(conn, scope, requisition_id, *, need: Decimal | None = None, also_lock: Sequence[UUID] = (), lock: bool) -> SubmissionCheck`. With `lock=True` it locks `sorted({requisition.project_id, *also_lock})` ascending through `lock_balance`, then the requisition row. E09-S05 passes `also_lock=[held.project_id]` when a returned draft's live reservation sits on a different project (E09-S05 amendment 4).
3. **`FundingCheck` gains `already_reserved`** (the live reservation's remaining when it is on this requisition's project, else `"0.0000"`). `available` is read after the lock and already excludes the held reservation; the browser computes `available_after = available − (estimate − already_reserved)` (E09-S11 consumes it). Test: a returned draft holding 60 of a 100 estimate against available 40 shows `already_reserved 60.0000` and passes.
4. **Funds shortfall wording** uses the amount the requisition still needs (`need`), not the whole estimate, when a reservation is held.
5. **Existing helpers to call, not rewrite:** `org.service.today()`, `OrgService.effective_setting(unit_id, "allow_negative_budget")` (`.value`), `org.service.assert_usable(conn, scope, kind, code, on_date)` (raises `MasterCodeUnusable` with `.code` and `.reason`; `ProjectService.create` shows the mapping), `projects.service.depth_of(conn, scope, project_id)`. Depth rule: the parent may be at depth ≤ 4 (`ProjectService.create` refuses `depth_of(parent) >= 5`).
