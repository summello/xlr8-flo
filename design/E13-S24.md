# E13-S24 — Vendor cancellation email for a cancelled issued PO, through the outbox

**Epic** E13 · **M3** · **engine/M** · after **E13-S07**, **E13-S09** · tags: `security` (Opus review)

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** invariant 6 (every external effect through the outbox), canvas DECISIONS 170 (what

> **Writes:** no new route and no `PATCH`/`PUT`/`DELETE`. The one route it extends is a POST behind
> the idempotency middleware (`kernel/idempotency/middleware.py`, `_default_required_key`).
> **RLS:** no table and no migration. `po_transmission` and its RLS are E13-S09's.
> **Both dependencies were unmerged when this packet was written.** E13-S07 is cited from branch
> `story/E13-S07-*` (worktree `xlr8flo-m3run-E13-S07`); E13-S09 from `design/E13-S09.md`. Use the

## Requirements (inlined)

- **PO-013** — Cancelling or reducing a PO must release the unused commitment exactly once and must not erase its history.
- **PO-015** — Failed email/API/cXML transmissions must be visible, retryable, and auditable without duplicating the PO.
- **ARCH-006** — External effects such as email/API delivery must use a transactional outbox or equivalent durable handoff.

## Design

### What exists

- **E13-S07** (`purchasing/cancel.py`): a no-op stub `notify_vendor_cancelled(conn, scope, po_id)`
  (`cancel.py:51`), called once at `cancel.py:117-118`, `if status == "issued" and
  body.notify_vendor`, **after** `transition(..., "cancel", ...)` (`cancel.py:116`) and inside the
  cancel transaction, which by then holds award, balances, requisition and the PO row `FOR UPDATE`.
  `status` is the locked pre-transition status, so a cancel before issue never reaches it. A replay
  returns at `cancel.py:102-103`, before it, so it runs once per cancelled row.
  `PoCancelCreate.notify_vendor: bool = True` exists (`schemas.py:232`).
- `transition` writes `status` and `version = version + 1` (`lifecycle.py:84-88`). An issued row's
  version cannot move without a status change (`purchase_order_immutable`, migration 0084), and
  `cancelled` is terminal, so a cancelled row's `version` is fixed and is one above the version its
  issue rows carry (E13-S09 records the row's version after issue: `issue.py` passes `version + 1`,
  change apply passes `2`).
- **E13-S09** (`purchasing/transmission.py`): `po_transmission` (one row per recipient per attempt,
  `UNIQUE (org_id, po_id, version, attempt, lower(recipient_email))`), the per-recipient send
  (`_suppressed` → `address_suppressed` row, else `OutboxStore.add_email(...,
  idempotency_key=f"po_transmission:{row_id}")` and the row with its `outbox_id`), the `not_sent`
  row, the read-state expression, `GET …/transmissions`, `attention_counts`, and
  `POST /api/v1/purchase-orders/{id}/transmissions/resend` (`IssueContext`, locks only the PO row).
- Precedent for a vendor cancellation email: RFQ cancel, `sourcing/lifecycle.py:464-474`
  (`CANCELLED_TEMPLATE = "rfq-cancelled-v1"`, fixture `apps/api/templates/email/rfq_cancelled.html`).

### One send path

Reuse E13-S09's per-recipient send. If it merged inline in `enqueue`, extract it unchanged into
`_send(conn, scope, po_id, version, attempt, recipients, template, context, attachments, actor_id)`
and call it from `enqueue`, resend and this story; E13-S09's tests must stay green unmodified.

### `transmission.enqueue_cancellation(conn, scope, po_id, actor_id)`

`CANCEL_TEMPLATE = "po-cancelled-v1"` beside E13-S09's `TEMPLATE` (keep the `po-` prefix; E13-S10's
production domain gate covers "a `po` email" without saying how it recognises one, so if it merged a
list of template ids, add this one). Runs in the caller's transaction, takes **no lock**, writes
only `po_transmission` and `outbox`.

1. One scoped `SELECT number, revision, version, vendor_snapshot, recipients FROM purchase_order` for
   `po_id` (the caller holds the row).
2. Recipients: the `(recipient_name, recipient_email)` rows of the highest `attempt` on this `po_id`
   that has a row with `recipient_email IS NOT NULL` (so a recipient changed at resend carries
   forward); none → the row's `recipients`; still none → one `not_sent` row (as E13-S09 step 4) and
   return. Keep the first entry per `lower(email)`: a duplicate would hit `po_transmission`'s unique
   index and roll the cancel, release included, back. A cancel is never refused for want of a
   recipient.
3. `_send(..., version=<the row's version>, attempt=1, template=CANCEL_TEMPLATE, context=
   {"po_number": number, "revision": revision, "vendor_name": vendor_snapshot["trading_name"]},
   attachments=(), actor_id=actor_id)`. Nothing else goes in the context (Resolved: no reason). No
   attachment (Resolved: no PDF).

`notify_vendor_cancelled` gains `actor_id: UUID` (the canceller, written as `created_by`), its body
becomes the one call above, its docstring and `cancel.py`'s say E13-S24, and the call at
`cancel.py:118` passes `actor_id`. `notify_vendor=false` writes nothing.

Fixture `apps/api/templates/email/po_cancelled.html` mirroring `rfq_cancelled.html`: "Purchase order
{{ po_number }} (revision {{ revision }}) has been cancelled. Please do not supply against it."
Record in `notes.followup` that the operator must publish `po-cancelled-v1` in Resend.

### Resend on a cancelled PO (edit to E13-S09's resend)

Same route, permission, body, response and single PO lock. Changes:

- Status: `issued` → E13-S09's behaviour, unchanged; `cancelled` → resend the cancellation notice
  with `CANCEL_TEMPLATE`, the step-3 context and no attachment; any other status → 409
  `not_resendable` as before.
- Every row query in resend (the `queued` check, `max(attempt)`, the default recipients, "no rows")
  filters `version = <the locked row's version>`, not just `po_id`. On an issued row every row has
  that version, so E13-S09's behaviour is unchanged. On a cancelled row it selects only cancellation
  rows: a queued issue email does not block a cancellation resend, and a cancelled row with no
  cancellation rows (cancelled with `notify_vendor=false`) gives E13-S09's 409 `nothing_to_resend`.
- The audit `after` gains `"template": <template>`.

### Locks and transactions

`enqueue_cancellation` adds no lock to cancel's order (award, balances, requisition, PO); its inserts
take only `FOR KEY SHARE` on the PO row the transaction already holds `FOR UPDATE`, and on the
`identity` row. Resend still holds only the PO row: a cancel replay waiting on that row holds nothing
resend wants, so no cycle. Any error in the send (outbox insert, unique violation) rolls the whole
cancel back, release included; that is the ARCH-006 handoff.

### Reads

No change: E13-S09's `GET …/transmissions` lists cancellation rows with `template_version =
'po-cancelled-v1'`, and `attention_counts` counts their failures (OBS-004). The UI label is E13-S16's.

## Acceptance

- [ ] Cancel of an issued PO with two recipients: in the cancel transaction, two `po_transmission` rows on that `po_id` with `version` = the cancelled row's version, `attempt = 1`, `template_version = 'po-cancelled-v1'`, `created_by` = the canceller, and two outbox emails with that template; the issue rows are unchanged.
- [ ] Two recipients with the same email in different case → one row and one outbox email; the cancel succeeds.
- [ ] Leak: cancel with reason `REASONLEAK4`; the outbox payload, read before dispatch, has `context` keys are exactly `{po_number, revision, vendor_name}`, the payload JSON does not contain `REASONLEAK4`, and it has no `attachments` key (option A).
- [ ] `notify_vendor=false` → no new transmission row and no outbox row. Cancel of a `draft`, `approved` and `approval_pending` PO → none either.
- [ ] Retry of the cancel (same `Idempotency-Key`; and a new key with the new `If-Match`) → no second set of rows.
- [ ] Recipients carry: after an E13-S09 resend with `contact_ids` = contact X, the cancellation goes to X only.
- [ ] `_suppressed` patched to `True` → `address_suppressed` rows, no outbox email. A PO whose `recipients` are empty and whose rows have no email → one `not_sent` row, and the cancel returns 200 with its release posted.
- [ ] Atomicity: `OutboxStore.add_email` patched to raise during the cancel → the PO stays `issued` at its version, no `release` ledger entry, no transmission row, no outbox row.
- [ ] No send from the handler: with a recording fake sender, `POST …/cancel` returns with zero provider calls; one dispatcher run then makes one `po-cancelled-v1` call per recipient with key `po_transmission:{row id}`, and those rows read `sent`.
- [ ] Resend on a cancelled PO whose cancellation send is dead: attempt 2 at the cancelled version, template `po-cancelled-v1`, one outbox email per recipient; no ledger entry; status and version unchanged; audit `purchase_order.transmission.resend` with `template`.
- [ ] Resend on a cancelled PO: a queued cancellation row → 409 `transmission_queued`; a queued issue row and no queued cancellation row → 200; cancelled with `notify_vendor=false` → 409 `nothing_to_resend`. E13-S09's resend tests on issued POs pass unchanged.
- [ ] Real-Postgres concurrency: two simultaneous resends of a cancelled PO whose cancellation send is dead → exactly one 200, the other 409 `transmission_queued`; E13-S07's cancel concurrency tests still pass.
- [ ] `GET …/transmissions` on a cancelled PO lists the cancellation rows before the issue rows, each with its `template_version`.
- [ ] Resend on a cancelled PO without `purchase_order.issue` → 403; a foreign tenant's cancelled PO → 404 (added to the resend route's existing TEN-010 test). `flo check --light` green.

## Plants

1. Call the email sender directly in `enqueue_cancellation`: the no-send-from-handler test fails.
2. Put `reason` in the context: the leak test fails.
3. Drop the `version` filter from resend's `queued` check: the "queued issue row → 200" test fails.
4. Call `notify_vendor_cancelled` on every cancel, not only `issued`: the before-issue test fails.
