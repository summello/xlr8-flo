# E22-S15 — Unit-scoped grants reach the requisition lookups and out-of-office delegation

**Epic** E22 · **M3** · **security/M** · after **E22-S14**, **E09-S02** · tags: `auth`, `security`
Origin: ACC-008 automated keyboard run 2, 23 Nov 2026 (`.scratch/acc-008-run2/notes.md`, step 3). Run 1 missed it
because its database workaround gave the Requester an organization-wide role for the whole run. Operator,
23 Nov 2026: fix before the human walkthrough round.

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.

Two routers, the lookup service and their tests. No migration, no API shape change, no frontend change.

## Requirements (inlined)

- **USR-003** — Access must support organization, BU/OU, module, record, and action scopes.
- **ACC-004** — A user cannot access another BU/OU's record by guessing an identifier or changing a request.
- **ACC-008** — A complete project-to-PO workflow is operable without a mouse.
- **DECISIONS 234 / 243** (operator): a permission held at any scope admits the caller; rows narrow to where it is
  held. E22-S14 applied this to `GET /org/units`.

## The defect

`GET /api/v1/requisitions/lookups/{kind}` (`api/requisitions.py` ~161-189) is gated by `OrgCreateContext`,
`require("requisition.create", organization_target)`. A requester whose roles are granted on a business unit (the
seeded walkthrough Requester; every unit-scoped project manager) gets **403 on every kind**, so the requisition
form loads no unit, project, department, ledger account, unit of measure, delivery address or person, and **a
unit-scoped project manager cannot raise a requisition**.

The rows are already narrowed per row by point checks inside `LookupService` (`modules/requisitions/lookups.py`):
projects by `requisition.create` on each project (~61-91), units by `project_request.create` on each unit
(~93-109, D-M2-18), delivery addresses by `requisition.create` on the chosen unit (~127-140). Only the route gate is
organization-only.

## Decisions (operator, 23 Nov 2026, answering pre-flight round 1)

1. **Delivery addresses: anyone who may raise there.** Unit X's addresses are admitted to a caller holding
   `requisition.create` on X, `project_request.create` on X, or `requisition.create` on any project whose unit is X.
2. **Non-requesters: admit for what they need, reference data only.** A `requisition.view` holder may use `project`
   (narrowed to projects where they hold `requisition.view`), `delivery_address` (units where they hold
   `requisition.view`, on the unit or on a project of it) and the master-code kinds. A `master_code.substitute` holder
   may use `department` and `ledger_account`. No new access to any document.

## Ruling on pre-flight round 3 (Opus, 23 Nov 2026; no new access)

`lookups/bu` is admitted on `requisition.create` **or** `project_request.create`; its rows stay narrowed to units
where the caller holds `project_request.create` (D-M2-18), so a project-scoped requester gets **200 with no rows**.
Reason: `RequisitionForm.tsx` ~66 loads `lookup("bu")` when the form opens, so a 403 there would break the form for
the very requester this story fixes. No row is visible that was not before.

## Fix

**Route** (`api/requisitions.py` ~161-189). Replace `OrgCreateContext` with four `require_granted` dependencies
(`kernel/authz.py` ~186): `requisition.create`, `project_request.create`, `requisition.view`,
`master_code.substitute`. Then admit by kind; anything else is **403** (this is a form helper; a caller with none of
the four anywhere gets 403 as today):

| kind | admitted when the caller holds, at any scope |
|---|---|
| `project` | `requisition.create` or `requisition.view` |
| `bu` | `requisition.create` or `project_request.create` (rows unchanged: only units with `project_request.create`, D-M2-18) |
| `user` | `requisition.create` or `project_request.create` (naming sponsors; viewers and substituters do not get the member list) |
| `department`, `ledger_account` | any of the four |
| `uom`, `item_category`, `service_category` | `requisition.create`, `project_request.create` or `requisition.view` (the remaining `MASTER_KINDS`, decision 2; there is no `currency` kind) |
| `delivery_address` | `requisition.create`, `project_request.create` or `requisition.view` (then the per-unit rule below) |

Delete `OrgCreateContext` if nothing else uses it.

**Rows** (`modules/requisitions/lookups.py`), the narrowing that makes "any scope" safe:

- `project` (~61-91): a project is listed when the caller may raise in it (`requisition.create` point check, as today)
  **or** holds `requisition.view` on it. A view-only project is listed with `disabled: true` and
  `note: "view only"`, so the requisition form cannot pick it (the form already renders disabled options, as for
  generated projects) and the list filter can still filter by it. Check that `routes/requisitions/list.tsx` ~58 does
  not drop disabled rows; if it does, say so in `notes.followup` and leave the screen alone.
- `delivery_address` (~127-140): replace the single `can_raise_in_unit(bu_id)` check with **unit X is admitted** when
  the caller holds `requisition.create`, `project_request.create` or `requisition.view` on X itself, or
  `requisition.create` or `requisition.view` on a project whose `bu_id` is X (decision 1 and 2). Give
  `LookupService` what it needs to decide this without a new query per row (for example the `GrantedScopes` of those
  permissions, resolving the granted projects' units in one statement inside its transaction). An unknown or foreign
  unit is still 404 (`org.unit_chain`), and a unit the caller is not admitted to is still 404.
- `bu`, master codes and `user`: rows unchanged.

**Second gate, same class: out-of-office delegation (E22-S10).** `api/approvals.py` ~173 `DelegateContext` is
`require("approval.delegate", organization_target)`. The baseline `approver` role holds `approval.delegate`
(migration 0047 ~19), so an approver whose roles are granted on a unit (the seeded walkthrough Approver) gets 403 on
`POST /delegations` (~190) and `GET /delegations/eligible-delegates` (~202) and cannot set Approval Availability.
A delegation passes on the owner's **own** approval tasks, and `eligible_delegates`/`create_delegation`
(`modules/approvals/delegation.py` ~229, ~283) already check the delegate's eligibility per document type. Replace
`DelegateContext` on those two routes with `require_granted("approval.delegate")`; falsy → 403 as today; pass
`granted.user_id` where `context.user_id` was used. `AdminContext`, `_is_admin` (~182, organization view, revoke by
an administrator, task reassign) stay organization-only: administering everyone's delegations is an organization
act. `list` and `revoke` already use `MemberUser` and do not change.

## Acceptance

Requester cases (the original defect):

- [ ] **Unit-scoped requester:** a user holding `requisition.create` and `project_request.create` only on unit A
      (role granted with `AuthorizationTarget(ScopeType.BU, A)`), with an active project P_A under A and P_B under B:
      `lookups/project` → 200 with P_A, without P_B; `lookups/bu` → A only; `lookups/department`, `ledger_account`,
      `uom`, `item_category`, `service_category`, `user` → 200 with rows; `lookups/delivery_address?bu_id=A` → 200; `?bu_id=B` → 404 (unchanged service rule).
- [ ] **Project-scoped requester** (`requisition.create` on P_A only): `lookups/project` → P_A; `lookups/bu` → empty
      (no `project_request.create`); `lookups/department` → 200.
- [ ] **Standalone requester** (`project_request.create` only on A): `lookups/bu` → A; `delivery_address?bu_id=A` → 200
      (decision 1); `lookups/project` → 403.
- [ ] **Project-scoped requester, addresses** (`requisition.create` on P_A only): `delivery_address?bu_id=A` → 200
      (P_A's unit, decision 1); `?bu_id=B` → 404.

Non-requester cases (decision 2):
- [ ] **Unit-scoped viewer** (`requisition.view` only on A): `lookups/project` → P_A with `disabled: true`,
      `note: "view only"`; `delivery_address?bu_id=A` → 200, `?bu_id=B` → 404; `department` → 200; `user` → 403;
      `bu` → 403.
- [ ] **Code substituter** (`master_code.substitute` only, on a project): `department`, `ledger_account` → 200;
      `project`, `uom`, `item_category`, `service_category`, `delivery_address`, `user` → 403.
- [ ] **None of the four anywhere** (e.g. `record.read` only): every kind → **403**, as today.
- [ ] **Organization-wide** grants: unchanged (existing `tests/requisitions/test_lookups.py` cases green).
- [ ] **TEN-010:** a foreign tenant's project, unit or address never appears (existing
      `test_lookups_never_return_another_tenants_rows` green); route coverage keeps the lookup mapped.
- [ ] **Unit-scoped approver:** `approval.delegate` held only on unit A → `GET /delegations/eligible-delegates` 200,
      `POST /delegations` 201 for an eligible delegate; the delegation appears under `GET /delegations?view=mine`.
- [ ] **No `approval.delegate` anywhere:** both routes 403, as today. `?view=organization` still 403 for a
      non-administrator, and `POST /tasks/{id}/reassign` still needs organization `approval.admin`.
- [ ] `flo check --light` green.

## Plants

1. Restore `OrgCreateContext`: the unit-scoped requester case answers 403.
2. Admit everyone (drop the 403): the neither-permission case answers 200.
3. Pass `create` alone (drop `project_request.create` from the gate): the standalone requester gets 403 on `lookups/bu`.
5. Drop the project-under-unit arm of the address rule: the project-scoped requester's `delivery_address?bu_id=A` is 404.
6. Return view-only projects without `disabled`: the viewer case fails.
7. Admit `user` to `requisition.view`: the viewer's `user` → 403 case fails.

4. Restore `DelegateContext` on `POST /delegations`: the unit-scoped approver case answers 403.
