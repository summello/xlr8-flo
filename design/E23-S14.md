# E23-S14 — One run record per reviewer, one reviewer at a time per story

**Epic** E23 · **MT** · **chore/M** · **priority P0** (operator, 23 Oct 2026)

> MT stories start from and merge into the checked-out milestone (d9ba9c3). **No new dependency** (AGENTS.md §0.6).
> **Review: Codex only.** Operator, 23 Oct 2026: every Opus planner and reviewer sleeps until the E23 flo fixes
> (S14 to S18) are on the milestone PR and its CI is green. The concurrency tag is dropped for that reason, not
> because the story is low risk: Codex must plant every violation listed below.

## Requirement (inlined)

- **SUP-005** — Administrator and operator documentation must be updated in the same PR as the feature it describes.

## Why

Revalidated by the planner on `343f7b5` (Codex assessment, 23 Oct 2026, findings 1 and 2):

1. `agents/fleet/fleet.py` `decide()` emits one `review` action **per missing reviewer** (Codex and Opus
   on a gated story), but `launch()` names every run `STORY.STEP` (`E11-S16.review.json/.out/.exit`).
   The second launch overwrites the first record, so `busy` sees only one pid and `results[(story,
   "review")]` holds whichever was written last. When that one exits, the next tick finds the other
   verdict still missing or stale and launches it **again** while the first is still running.
   Evidence: E11-S16 got Opus reviews at 02:13, 04:32, 05:05 and 05:44 on 23 Oct, two sessions per
   round; E11-S14 the same. This doubled Opus spend on both Claude accounts.
2. Both reviewers run **in the same story worktree at the same time**. `review.sh` moves
   `reviews/*.json` to one shared `.scratch/<S>.aside` and back, and both reviewers plant and revert
   violations. AGENTS.md and project-memory already require reviewers to run sequentially. Nothing enforces it.

## Design

### 1. Run identity (`agents/fleet/fleet.py`)
- A run's name is `STORY.STEP` for every step except `review`, which is `STORY.review.REVIEWER`
  (`E11-S16.review.codex`). The record JSON gains `"reviewer"` (empty for other steps).
- `runs()` keys `busy` and `results` by `(story, step, reviewer)`; every reader in `decide()` uses the
  same key. A step with no reviewer uses `""`.
- Old `STORY.review.json` records (no reviewer field) are read as reviewer `""` and never block a new run.

### 2. One reviewer at a time per story (`agents/fleet/fleet.py`)
- `plan()` keeps at most **one** `review` action per story, and none while any review run for that
  story is busy. Order: Codex first, then Opus (Opus reads the code after Codex, never Codex's verdict:
  `review.sh` already moves verdicts aside).
- The next reviewer starts on a later tick, after the first exits.

### 3. `review.sh` defends itself
- A per-story review lock, `.scratch/<S>.review.lock`, taken before the aside move and released after
  restore. Use the process-owned lock from **E23-S15** if it has merged; otherwise a directory holding
  `pid` with a liveness check (`kill -0`) and no reclaim while the holder is alive. A second
  `review.sh` for the same story while one runs exits **75** with `review of <S> already running (pid N)`.
- The aside directory is per run (`.scratch/<S>.aside.<reviewer>`), and restoring it runs in a trap so a
  failed or killed reviewer still puts every verdict back.
- The reviewer reviews the commit recorded at launch (`.scratch/<S>.<reviewer>.sha.new`, already
  written); unchanged.

### 4. Housekeeping in the same file
- Fix the existing `ruff` findings in `agents/fleet/fleet.py` (follow-up from 21 Oct).

## Invariants
- Independent reviews are kept: no reviewer reads another's verdict; the second reviewer still runs.
- Quota and account routing are unchanged (`capacity()`, `opus_account()`).
- No change to which reviewers a story needs (`flo assign`).

## Acceptance criteria
- [ ] With fake processes (`subprocess.Popen` patched, temp state dir), `decide()` + `launch()` for a gated
      story with both verdicts missing produces **one** review action per tick, and its record is
      `STORY.review.codex.json`.
- [ ] After that fake Codex run exits 0 with a verdict, the next tick launches Opus once; while Opus is
      busy, a third tick launches nothing for that story.
- [ ] Two simultaneous review records for different reviewers on one story are both tracked in `busy`.
- [ ] `review.sh S codex` while a live holder owns `.scratch/S.review.lock` exits 75 and moves nothing.
- [ ] A reviewer killed with SIGKILL mid-run leaves every `reviews/*.json` restored by the next
      `review.sh` (or the trap) and no lock owned by a dead pid blocks the next review.
- [ ] `ruff check agents/fleet/fleet.py` is clean.
- [ ] `docs/ops/fleet-tooling.md` explains run names, sequential reviews and how to clear a review lock.
- [ ] Deployed copy: after merge, `cp agents/fleet/fleet.py ~/.claude/fleet/fleet.py` and `cmp` per
      `docs/ops/fleet-tooling.md` — the **planner** does this, not the author. Record it in `notes.followup`.

## Plants (prove each guard fails)
- Name review runs `STORY.STEP` again: the one-record-per-reviewer test fails.
- Remove the one-review-per-story filter in `plan()`: the sequential test fails.
- Remove the liveness check from the review lock: the exit-75 test fails.
