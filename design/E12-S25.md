# E12-S25 — Retrying a submit replays it instead of re-saving the draft

**Epic** E12 · **M3** · **ui/M** · after **E12-S14**, **E12-S15**, **E12-S16** · tags: `ui`
Origin: M3 epic checkpoint E12 (codex-a finding 2, 8 Nov 2026).

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (§O `If-Match`), `docs/author-traps.md`.

## Requirements (inlined)

- **ACC-002** — Retrying an approved transfer or PO issue cannot duplicate ledger entries or vendor transmission.
- AGENTS.md §3.1: every state-changing POST accepts `Idempotency-Key`; a retry with the same key replays the stored response.
- **UX-005** — errors say what happened, what was preserved and how to recover.

## Defect

Three screens save a draft, then submit it, in one button press:

| Screen | Save | Submit | File |
|---|---|---|---|
| Bid keying | `PATCH …/bids/{bid_id}` (`save()`) | `POST …/bids/{bid_id}/submit` | `apps/web/src/components/sourcing/bids/BidSheet.tsx` ~119-131 |
| Evaluation scores | `PUT …/evaluation/scores` | `POST …/evaluation/scores/submit` | `apps/web/src/components/sourcing/evaluation/Scoring.tsx` ~48-66 |
| Award | `PUT …/award/lines`, `PATCH …/award` (`save()`) | `POST …/award/submit` | `apps/web/src/components/sourcing/award/Award.tsx` ~27-48 |

Each keeps its submit key across a lost response (correct), but a retry always runs the save first. If the
submit committed and only its response was lost, the bid/scores/award is no longer a draft, so the save is
refused (409) and the stored submit response is never replayed: the user is told the submit failed when it
succeeded, and the screen is left stale. Nothing is duplicated (the server's transition guard holds); the
defect is a false failure on the most important button of each screen.

## Design

One rule for all three, no new shared abstraction unless two of them need the identical code:

- When a submit key is held (a submit was sent and no response arrived), the next press **replays the submit
  POST first, with the same key and without saving**, provided nothing the submit depends on changed since that
  save. Keep a fingerprint beside the key of **everything the submit depends on**: the saved body, plus on the bid
  sheet the evidence attachment id (uploaded separately, `BidSheet.tsx` ~92) and the submit body itself (the
  late-acceptance reason, ~127). Pre-flight 1, 8 Nov 2026. Keep the fingerprint (the RFQ editor's `submission` ref, `editor/Editor.tsx` ~41,
  is the pattern). If the form changed since, drop the key and run save + submit as a new operation.
- A response clears the key, except `409` whose problem `type` ends with `/request_in_flight` (the first attempt
  is still running; `kernel/errors/codes.py` ~141 says retry with the same key). Detect it exactly as
  `routes/sourcing/rfqs/new.tsx` ~158 does: `error?.type?.endsWith("/request_in_flight")`. The middleware raises
  it with no `checks` (`kernel/idempotency/middleware.py` ~290), so never look in `checks.problem`. That response
  and a thrown network error keep the key. Pre-flight 3, 8 Nov 2026.
- On a replayed success the screen refreshes exactly as after a first-time success.

## Acceptance

- [ ] Playwright, per screen (stub): the first submit POST is aborted (`route.abort`), the second press sends **no** PATCH/PUT and repeats the POST with the **same** `Idempotency-Key`; the stub's success is shown.
- [ ] Playwright, per screen: after an aborted submit, editing a field then pressing again sends the save and a submit with a **new** key.
- [ ] Playwright, per screen: after a definitive problem response the next press uses a new key; after a `request_in_flight` 409 (stub body `{"type": ".../request_in_flight", "status": 409}`, no `checks`) it reuses the key.
- [ ] Playwright (bid sheet): after an aborted submit, changing the evidence file or the late-acceptance reason sends a new operation, not a replay.
- [ ] Existing specs for the three screens stay green; axe unchanged; `flo check --light` green.

## Plants

1. Always save before submit again (Scoring): the no-PATCH/PUT assertion fails.
2. Clear the key in the `catch` (BidSheet): the same-key assertion fails.
