## Requirements (inlined)

- **PO-007** — The lifecycle should support Draft, Approval Pending, Approved, Issued, Partially Delivered, Delivered, Accepted, Closed, Cancelled, and Superseded.

## State machine

`status` CHECK in exactly `draft`, `approval_pending`, `approved`, `issued`, `partially_delivered`,
`delivered`, `accepted`, `closed`, `cancelled`, `superseded` and `deleted` (the E22-S02 soft delete already
stores `deleted`: `migrations/20261027_0078_purchase_order.py` CHECK is `('draft','deleted')` today; dropping it
breaks draft deletion).

| From | Action | Owner story | To |
|---|---|---|---|
| `draft` | submit | E13-S04 | `approval_pending` |
| `approval_pending` | approve / reject / withdraw | E13-S04 | `approved` / `draft` / `draft` |
| `approved` | issue | E13-S05 | `issued` |
| `issued` | change order approved | E13-S06 | `superseded` (old version) + new version `issued` |
| `draft` | delete (soft, existing `DELETE /purchase-orders/{id}`) | E13-S01 / E22-S02, moved here | `deleted` |
| `draft`, `approval_pending`, `approved` | cancel | E13-S07 | `cancelled` |
| `issued` | cancel (whole) | E13-S07 | `cancelled` |
| `issued` | close (manual, reason) | this story | `closed` |
| `issued` → `partially_delivered` → `delivered` → `accepted` | goods receipt | **M4 (E14)** | not reachable in M3 |

This story builds **one transition function** in `purchasing/lifecycle.py`:
`transition(conn, scope, po_id, action, actor_id, expected_version, reason=None)`. It runs inside the
caller's `tenant_transaction` (it opens none), locks the PO `FOR UPDATE`, checks `expected_version`
against `purchase_order.version` under the lock (409 `stale_version` on mismatch, §O), checks the table
(409 `invalid_transition` for a pair not in it, as the projects and requisitions transitions do), writes
the status with `version = version + 1` and an audit row (`purchase_order.<action>`), and is the only
writer of `purchase_order.status`. Other stories call it.

**Delete:** E22-S02's draft delete is a raw `UPDATE purchase_order SET status = 'deleted'` in
`PurchaseOrderService.delete` (`purchasing/service.py` ~583). Replace that one statement with a call to
`lifecycle.transition(..., "delete", expected_version=...)` inside the same transaction, after `_move`
returns the quantity; the route, its `If-Match` and its `Idempotency-Key` behaviour are unchanged, and
its existing tests must stay green. The audit action stays whatever E22-S02 writes today if it already
audits the delete (do not write two audit rows).

**Close route:** `POST /api/v1/purchase-orders/{id}/transitions`, body `PurchaseOrderTransitionCreate
{action: "close", reason: str (1..500, required)}` in `purchasing/schemas.py`, `If-Match` required (400 when
missing, §O), `Idempotency-Key` required (POST), CSRF as every unsafe method; permission
`purchase_order.close` checked on the PO's unit; returns the PO read with its new `ETag`. Same shape as
`api/projects.py` `transition_project`. In this story the `action` field accepts `close` only (422 for any
other value); E13-S04/S07 widen it when they add their actions.

`partially_delivered`, `delivered` and `accepted` exist in the CHECK and the enum but **no action
reaches them in M3**. A test asserts every M3 action's target set excludes them.

## Acceptance

- [ ] Every valid and invalid (from, action) pair, parametrized.
- [ ] A raw `UPDATE purchase_order SET status` outside `lifecycle.py` is caught by a test that greps `src/` for status writes (only `lifecycle.py` may write it).
- [ ] Close needs a reason and `purchase_order.close`; audited.
- [ ] TEN-010 on the close route; `flo check` green.
- [ ] Close with a stale `If-Match` is 409 `stale_version` and leaves the status; without `If-Match` 400; version increments on every transition.
- [ ] Draft delete still works through `lifecycle.transition` (existing E22-S02 delete tests green).

## Plants

1. Add a second status writer in the router: the grep test fails.
2. Allow `approved → closed`: the invalid-pair test fails.
