# E07-S07 — Same-level transfer, atomic, one transfer_group_id

**Epic** E07 · **M1** · **ledger/M** · after **E07-S05** · tags: `money`

> **Conventions:** read `docs/m1-conventions.md` (authorization outcomes, scope targets, wire formats). It applies unless this packet says otherwise.

## Requirements

- **BUD-002** — Transfers must be allowed between eligible projects at the same hierarchy level unless policy permits otherwise.
- **BUD-004** — Entries generated by one transfer must commit atomically and share one transfer identifier.

## Contract

Permission `budget.transfer` on **both** projects' scopes (giving and receiving).

- `POST /api/v1/budget/transfers` body `{from_project_id, to_project_id, amount, currency, effective_date, reason, evidence_ref?}`, `Idempotency-Key` required → 201 `TransferRead{transfer_group_id, entries:[giving, receiving]}` | 403 | 404 | 409 `InsufficientBudget` | 409 `PeriodClosed` | 409 `TransferNotEligible` | 422

## Behaviour (BUD-002, BUD-004, FIN-006)

1. **Eligibility (BUD-002):** same org; both projects `Draft` or `Active` (D-M1-11); same currency; `from != to`; **same hierarchy level** (equal `depth`) — cross-level transfers are E07-S08. Violations are a 409 `TransferNotEligible` whose `detail` states which rule failed.
2. One transaction, one new `transfer_group_id` (uuid4 from the service, deterministic from the idempotency key hash so a replay yields the same id).
3. **Deadlock-free lock order:** lock both `project_balance` rows `FOR UPDATE` in ascending `project_id` order, then validate: `giving.available - amount >= 0` unless `allow_negative_budget` (BUD-008).
4. Post two entries via `post_entry`: giving leg `entry_type=transfer, bucket=allocated, amount=-X`; receiving leg `+X`; both with the same `transfer_group_id`, `source_type='transfer'`, `source_id=transfer_group_id`, same `reason`, `effective_date`, actor. Both succeed or the transaction rolls back (BUD-004).
5. `evidence_ref` per the same rule as E07-S03 (`budget.evidence_required`).
6. Audit one `budget.transfer` row referencing the group id; legs also audit through `post_entry`.
7. The transfer cannot be undone by editing: correction is a reverse transfer (a new call); reversal of a single leg is rejected (409) — `reverse_entry` refuses entries with `entry_type='transfer'`, and a test pins it.

## Acceptance criteria

- [ ] After a transfer of 25 from A (allocated 100) to B (allocated 0): A `allocated=75`, B `allocated=25`, two ledger rows sharing one `transfer_group_id`, summing to zero across the group
- [ ] Two concurrent opposite transfers (A→B and B→A) never deadlock (run 50 iterations, both complete) and balances equal the serial result
- [ ] Two concurrent transfers each taking 60 out of A with 100 available: exactly one succeeds
- [ ] A failure injected between the two legs (monkeypatch) leaves zero rows and unchanged balances
- [ ] Different-level projects → 409 `TransferNotEligible` naming the level rule; different currencies → 409; from == to → 422
- [ ] A giving project without `budget.transfer` grant → 403 even if the receiving one is granted, and vice versa; foreign-tenant project on either side → 404
- [ ] Replayed `Idempotency-Key` → first response, same `transfer_group_id`, no second pair
- [ ] Reversing a single transfer leg through `reverse_entry` is rejected
- [ ] `project_balance` equals `SUM(amount) GROUP BY bucket` for both projects after the above

## Amendments (preflight audit — authoritative, override anything above)

- `amount` must be a **positive** decimal string (`> 0`); anything else is 422.
- `from_project_id == to_project_id` is **422** (`VALIDATION_FAILED`, label `same_project`); the other eligibility failures are 409 `TransferNotEligible`.
- **Group id and replay:** generate a random `uuid4` group id once, persist it on both legs, post the legs with keys `"<key>:out"` and `"<key>:in"`, and on replay find the legs by those keys and return them (so the replay returns the same group id). Ignore "deterministic from the idempotency key hash".
- **Statuses:** the giving project may be in any status except `abandoned`... correction: any status (residual funds may leave a completed or abandoned project); the receiving project must be `draft` or `active`. Replaces "both Draft or Active".
- Add `modules/budget/postings.py` to Files (`reverse_entry` must refuse `entry_type='transfer'`).

- **Same level means siblings (decision, closes the cousin ambiguity):** E07-S07 permits a transfer only when both projects have **equal `depth` and the same `parent_project_id`** (two root projects, both with a NULL parent, are siblings). Equal depth under *different* parents (cousins) is a cross-hierarchy transfer under BUD-003 and is rejected here with 409 `TransferNotEligible` whose `detail` says the projects have different parents and that cross-hierarchy transfers arrive with E07-S08, which lifts this restriction. Add a test for the cousin rejection, plant-verified by dropping the parent comparison. Different depth keeps its own 409 label.
