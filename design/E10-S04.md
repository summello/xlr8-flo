# E10-S04 — Approver eligibility resolution scoped to organization and BU/OU

**Epic** E10 · **M2** · **engine/M** · after **E10-S02**, **E10-S03**, **E02-S05** · tags: `auth`

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md` (H, I, K, M) and `docs/author-traps.md`. Decisions: D-M2-2, D-M2-9.

## Requirements

- **APR-004** — Approvers must be selectable only from eligible users in the relevant organization/BU/OU scope.
- **APR-019** — A user must be prevented from approving their own request where separation-of-duty policy applies.
- **USR-007** — Configurable separation-of-duty rules should prevent incompatible actions, such as requesting and finally approving the same high-value transaction.

## Contract

1. **`AuthorizationResolver.holders(permission, target) -> list[IdentityId]`** in `modules/identity/resolver.py`: every identity that holds `permission` covering `target`, using **the same recursive scope CTE as `check()`** (org grants, BU/OU grants through `authorization_scope`, project grants only while every traversed project edge permits roll-down) and the same `effective_from` rule, restricted to identities with `identity.status = 'active'`. Extract the CTE into one private SQL builder that both `check()` and `holders()` use. Two copies would drift, and that drift would be a privilege bug. Re-export through `identity.service`. Ordered by identity id, capped at 1000 rows (`# ponytail:` comment naming the cap; a group larger than 1000 is a design error for an approval step).
2. **`approvals.service.eligible_approvers(conn, scope, document_type, rule, target, requester_id, resolver) -> EligibleSet`**. Throughout, **P is the registered adapter's `approve_permission`** for `document_type` (convention I: `requisition.approve`, `project.approve` and `budget.approve`, **all three already in the shipped catalogue**; baseline holders today: `approver` holds `requisition.approve`, `project-administrator` holds `project.approve`, `budget-finance-user` holds `budget.approve`). Add `approve_permission: str` to the `DocumentAdapter` protocol here; there is **no** generic `approval.decide` permission., where `EligibleSet = {members: [Eligible], excluded: [Excluded]}`, `Eligible = {user_id, basis}` and `Excluded = {user_id, reason}`. `resolver` is typed by a **new kernel protocol** `PermissionHoldersResolver(PermissionResolver, Protocol)` in `kernel/authz.py`, adding `holders(permission, target) -> list[IdentityId]`, with `type HoldersResolverFactory = Callable[[Scope], AbstractContextManager[PermissionHoldersResolver]]`. `AuthorizationResolver` satisfies it structurally, and `api/authz_factory.py`'s `production_authorization_resolver` is passed where a `HoldersResolverFactory` is expected (the E08-S03 wiring). `approvals` never imports `modules/identity/resolver.py`. A `PermissionResolver` alone has no `holders`, so `mypy --strict` would refuse it.
   - `rule.type = permission`: members are `holders(P, target)`; basis `permission:<P>@<scope>`.
   - `rule.type = role`: users granted the role `role_code` at a scope covering `target` (same CTE, keyed on role instead of permission) **and** in `holders(P, target)`; basis `role:<code>@<scope>`. A role grant alone is not enough: holding the document type's approval permission is what makes someone eligible (convention I).
   - `rule.type = users`: the listed users that are in `holders(P, target)`; others are `excluded` with reason `not_eligible_in_scope`.
   - **Separation of duty** (APR-019, USR-007): when the effective setting `approval.separation_of_duty` (convention M, default `true`, boolean; register it in `modules/org/settings.py`) is true for the document's BU/OU, the requester is moved to `excluded` with reason `separation_of_duty`. The rule applies to every step, not only the final one (stricter than USR-007's example; recorded so it can be relaxed later by a second setting).
   - Deactivated identities never appear; a user with no role in the organization never appears.
3. **`GET /api/v1/approvals/eligible-approvers?document_type=&scope_type=org|bu&scope_id=&q=`** (`workflow.manage` at that scope) → 200 `{rows: [{user_id, email}]}`, at most 50, filtered by case-insensitive prefix on `email` when `q` is given (convention Q: `identity` has no name column, so M2 shows people by email): the builder's approver picker (APR-004). Users not eligible in that scope never appear. A foreign or unknown `scope_id` is 404.
4. **E10-S03 gains one check**, run at publish: `users` rules naming a user who does not hold the document type's P covering the definition's bound scope are `missing_approvers` errors. Role rules are checked for existence only; who holds a role changes over time (live membership, D-M2-2).

## Behaviour

- Eligibility is computed **at the moment it is asked**, never cached across requests (D-M2-2): E10-S05 and E10-S06 call it at task creation (to refuse a step with nobody eligible) and again at decision time (to decide who may act).
- The CTE refactor must not change `check()`'s results: the existing authorization suite (`tests/authz/`, `tests/isolation/`) must pass untouched.

## Acceptance criteria

- [ ] A user with `requisition.approve` granted at the organization is eligible for a document in any BU/OU; one granted at BU A is eligible in A and its child units, not in B.
- [ ] A project-scoped grant makes a user eligible for documents scoped to that project and its roll-down descendants only, matching `check()` exactly (same fixture, both functions, same answer for every user and target).
- [ ] A `role` rule excludes a user who holds the role but not P, and includes one who holds both.
- [ ] With separation of duty on, the requester is in `excluded` with `separation_of_duty`; with the BU/OU setting `false`, they are a member.
- [ ] A deactivated user and a user from another tenant never appear in `holders`, in `eligible_approvers` or in the picker.
- [ ] The picker returns only users eligible in the requested scope and honours `q`; foreign scope 404; no `workflow.manage` 403 or 404 per convention A.
- [ ] Publishing a workflow whose `users` rule names an ineligible user fails with `missing_approvers`.

## Required tests

`apps/api/tests/approvals/test_eligibility.py` (real Postgres; a fixture tree org → BU A → unit A1, BU B, and a project chain with one roll-down edge off) and a property-style test in `tests/authz/test_resolver.py` asserting `holders(p, t)` equals `{u : check(u, p, t).allowed}` over every user and target in that fixture.

## Plants

1. Give `holders()` its own copy of the CTE without the roll-down condition: the `check()`/`holders()` equivalence test fails.
2. Drop `status = 'active'`: the deactivated-user test fails.
3. Skip the separation-of-duty exclusion: the requester test fails.
4. Let a `role` rule ignore P: the role-without-permission test fails.
