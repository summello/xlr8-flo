# E22-S13 — One list-scope rule: project grants roll down in lists as in point checks

**Epic** E22 · **M3** · **security/M** · after **E22-S04**, **E22-S06** · tags: `auth`, `security`
Origin: M3 epic checkpoint E22 (codex-a finding 1 and Opus finding 1, independently, 8 Nov 2026).

## Requirements (inlined)

- **USR-003** — Access must support organization, BU/OU, module, record, and action scopes.
- **ACC-004** — A user cannot access another BU/OU's record by guessing an identifier or changing a request.
- E22-S06 amendment (operator, 22 Oct 2026, DECISIONS 234): list routes accept the read permission held at
  any scope and narrow rows to the caller's scopes; single-record GETs follow the same rule.

## Finding

Two list-narrowing implementations with different semantics landed in E22:

| | `identity.service.granted_scopes` (E22-S04) | `IdentityResolver.granted_scopes` + kernel `require_granted` (E22-S06) |
|---|---|---|
| Where | `modules/identity/service.py:705` | `modules/identity/resolver.py:171`, `kernel/authz.py:185` |
| Used by | requisitions list (`api/requisitions.py:148`), RFQ lists (`api/sourcing.py:160`, `609`) | projects list (`api/projects.py:108`), PO list (`api/purchasing.py:94`), master data (`api/master.py:31`) |
| Project grant | expands down `authorization_scope` edges with `roll_down` | direct assignments only |
| No grant anywhere | 200 with an empty page | 403 |

The point check (effective access) follows roll-down. So a user granted `project.read` on a parent project
can open a sub-project by id but does not see it in the projects list, and its POs are missing from the PO
list, while its requisitions do appear in the requisitions list.

## Decisions (operator, 8 Nov 2026)

1. **Yes: lists follow roll-down exactly as point checks.** One implementation:
   `IdentityResolver.granted_scopes` runs the roll-down CTE; the requisitions and RFQ lists move to it; the
   service-level duplicate is deleted.
2. **A caller holding the read permission nowhere gets an EMPTY 200 on every list route.**

## Design

- **One function.** The operator's "IdentityResolver" is the class `AuthorizationResolver` in
  `modules/identity/resolver.py` (~107); its `granted_scopes` (~171) today reads direct assignments only. Move the
  recursive CTE from `identity.service.granted_scopes` (~705-752) into it, unchanged in meaning, keeping
  `permission_code(permission)` and `self.scoped_params(...)` as the method uses them now. What the CTE yields,
  as the point check (`_scope_cte`, resolver.py ~55-104) sees it:
  - **Units do not roll down to units.** Every BU and OU is registered directly under the organization
    (`register_business_unit_scope`, identity/service.py ~683-689, used for both unit kinds; migration 0008 `authorization_scope_bu_parent_valid`
    forbids a `bu` parent for a `bu`), even where the org chart nests OUs. So `bu_ids` is **exactly** the
    granted BU/OU ids, nothing more, and a list narrowed by unit shows exactly the granted units' rows.
  - A unit grant covers every project beneath that unit, at any depth, whatever `roll_down` says (the point
    check only consults `roll_down` on project parents); those project ids land in `project_ids`.
  - A project grant covers a sub-project only if every project-to-project edge between them has `roll_down`.
  - An org grant sets `org_wide`; the sets may then hold anything, callers ignore them.
  It keeps returning `GrantedScopes` (`kernel/authz.py` ~43). Then **delete** `identity.service.granted_scopes`
  and its imports in `api/requisitions.py` (~18) and `api/sourcing.py` (~19); nothing may call it.
- **No grant → empty, never 403.** `kernel/authz.py` `require_granted` (~185) returns the (falsy)
  `GrantedScopes` instead of raising `FORBIDDEN`; its docstring says so. Every list route that consumes it must
  then answer an empty page for a falsy value **without running the row query** (return the empty page in the
  service before any SQL). Never turn an empty grant into `None`: in the requisitions and RFQ services `None`
  means "everything" (`requisitions/service.py` ~584 `visible`, `sourcing/service.py` ~173 `visible`), so the
  route passes `None` only when `granted.org_wide`.
- **Six list routes, one dependency.** Each takes `Depends(require_granted("<read permission>"))`:
  - `GET /api/v1/projects` (`api/projects.py` ~155, `project.read`) — already;
  - `GET /api/v1/purchase-orders` (`api/purchasing.py` ~101, `purchase_order.view`) — already;
  - `GET /api/v1/master/{kind}` and `GET /api/v1/master/currency` (`api/master.py` ~50, ~38, `master.read`) —
    already; master rows are organization-level, so any grant shows all of them (master.py ~29 comment stays).
    With no grant: `list_master` takes the `GrantedScopes` and returns `MasterPage(rows=[], next_cursor=None)`
    before its query; `currencies` returns `[]` when the grant is falsy (`list_currencies` reads a static
    table, there is no query to skip);
  - `GET /api/v1/requisitions` (`api/requisitions.py` ~133-165, `requisition.view`) — replaces `ListUser`
    (`require_member()`, ~117) and the service-function call; the service's user id comes from
    `granted.user_id` as in projects. `ListUser` stays only if another route still uses it;
  - `GET /api/v1/sourcing/rfqs` (`api/sourcing.py` ~151-165, `rfq.view`) — same move; `visible=None if
    granted.org_wide else list(granted.bu_ids)`.
  `require_member()` also refused a session whose `org_id` differs from the request scope (authz.py ~218) with
  401; `require_granted` resolves the scope from the same session (`current_scope()`), so no case is lost, but
  if an existing test expects that 401 on these two routes, keep it passing and say so in the PR.
  The requisitions and RFQ services take the `GrantedScopes` (or the same `visible` tuple built from it) exactly
  as projects and POs do; keep each service's narrowing SQL as it is apart from its input.
- **"Exactly as point checks" decides where roll-down shows (pre-flight 1, 8 Nov 2026).** A list shows a row iff
  the point check on that row would pass. Projects and project-linked requisitions are checked against their
  project scope, so a project grant (and its `roll_down` sub-projects) shows them; a standalone requisition is
  checked against its `bu_id` (requisitions/service.py list SQL `r.standalone AND r.bu_id = ANY(...)`). POs (`api/purchasing.py` ~69) and RFQs
  (`api/sourcing.py` ~97) are checked against their **business unit**, and their list SQL already narrows by
  `unit_id` (`purchasing/service.py` ~461, `sourcing/service.py` ~173-191): that stays. A project grant alone
  therefore shows **no** PO or RFQ, in the list or by id, before and after this story. This story changes no point
  check; making POs or RFQs project-visible would be a new authorization rule and is out of scope. The unit set
  they narrow by now comes from the one CTE and is exactly the granted units (see "One function").
- **Not a list, same function:** `add_evaluator` (`api/sourcing.py` ~615) asks whether *another* user may view
  an RFQ. It calls the resolver's `granted_scopes(IdentityId(body.identity_id), "rfq.view")` in place of the
  deleted service function, opening the resolver the way `eligible_evaluators` beside it does
  (`factory: HoldersResolverFactory = production_authorization_resolver`, sourcing.py ~636; the holders
  protocol extends `PermissionResolver`, which declares `granted_scopes`, authz.py ~55-79); `may_view` stays
  `granted.org_wide or unit_id in granted.bu_ids`.
- Point checks (`require`, `permits`, effective access) are untouched.
- `# ponytail:` on the CTE: a unit grant expands to every project id beneath it in Python; if an org passes ~5k
  projects under one unit, narrow in SQL with the CTE as a subquery instead.

## Acceptance

- [ ] pytest, per list route (projects, POs, master `{kind}`, requisitions, RFQs): a direct grant on unit A lists A's rows and **none** of sibling unit B's (exactly the granted units; master is organization-level, so any grant lists all its rows); no grant anywhere → **200 with an empty page** (master currency `[]`); an org grant lists everything.
- [ ] pytest, projects list: a grant on unit A lists a sub-project under A even across a non-rolling project edge (unit grants ignore `roll_down`, as the point check does), and `GET /projects/{id}` on it is 200.
- [ ] pytest, projects and requisitions lists: a read grant on a parent project lists the sub-project (and its requisitions) across a `roll_down` edge **and** not across a non-rolling edge.
- [ ] pytest, PO and RFQ lists: a project-only grant lists nothing and the by-id read of the same PO/RFQ is 403/404 as today (list ⇔ point check). The five `require_granted` routes share one parametrized test where their fixtures allow.
- [ ] pytest: for the same user, the projects list and `GET /projects/{id}` agree on every seeded project (visible in the list ⇔ 200 by id), including the rolled-down sub-project.
- [ ] pytest: `add_evaluator`'s `may_view` is unchanged for an org grant, a grant on the RFQ's unit, a grant on a sibling unit only, and no grant.

## Plants

1. Drop `AND h.roll_down` from the CTE's project branch: the non-rolling-edge case fails on the projects and requisitions lists.
2. Remove the `c.unconditional OR` so unit grants stop covering projects beneath them through non-rolling edges: the unit-grant sub-project case fails.
3. Put the 403 back in `require_granted`: the no-grant empty-200 cases fail.
4. Map a falsy grant to `visible=None` on the RFQ route: the no-grant case lists every RFQ.
