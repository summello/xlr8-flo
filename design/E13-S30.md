# E13-S30 — Issue refuses to queue a PO email the sending domain cannot send

**Epic** E13 · **M3** · **engine/M** · after **E13-S10**, **E13-S21** · tags: —
Origin: M3 Opus milestone review (finding 2, 8 Nov 2026).

> **UI authority:** `design-system/MASTER.md`, `tokens.css`, `design-system/pages/purchase-orders.md`.

## Requirements (inlined)

- **EML-001** — The sending domain must publish SPF, DKIM and DMARC, verified by an automated check before first customer send (operator narrowed: SPF and DKIM automated, DMARC manual).
- **PO-012** — Duplicate clicks, retries, worker retries, and integration retries must not issue or transmit a PO more than once unintentionally.
- **UX-005** — errors say what happened, what was preserved and how to recover.

## Finding

The EML-001 gate holds: `kernel/email.py` `po_domain_gate` refuses a `po-*` email until the latest check has
SPF and DKIM `pass`. But the dispatcher (`kernel/outbox/dispatcher.py:114`) raises `PermanentOutboxError`, so
each PO email issued before verification goes **dead**. The issue itself still commits the budget and marks
the PO issued, and the Issue dialog (`components/purchasing/issue/IssueDialog.tsx`) never reads
`po_email_allowed`, so on a new tenant the buyer is told the vendor will be emailed and learns otherwise only
from a dead row in the transmission log. When the domain later passes nothing re-sends; each PO needs a manual
Resend.

## Decision (operator, 8 Nov 2026)

(b) **Refuse at issue.** With `po_email_allowed` false the Issue dialog says "Purchase order email is held
until the sending domain is verified" and offers **issue without email** (download the PDF and send it
yourself) or **cancel**; nothing is queued, nothing goes dead.

## Design

**Server is the authority; the dialog only reflects it.**

- **One gate reading.** In `purchasing/transmission.py`, a function `po_email_allowed(conn, settings) -> bool`
  = `po_domain_gate(settings, status)(TEMPLATE) is None` with `status` from `kernel/email.py`
  `latest_domain_check(conn)` (~39; a global table, no tenant filter), the expression `sending_domain` (~475-487)
  already uses; `sending_domain` calls it. It opens **no** transaction of its own: it runs inside the caller's
  (`sending_domain`'s `tenant_transaction` ~476, `issue()`'s, and the vendor-copy wrapper's below). No second
  implementation.
  Outside production (`email_provider != "resend"`) the gate is always open (`kernel/email.py` ~62), so local
  stacks and existing tests keep issuing with email.
- **Issue body.** `POST /api/v1/purchase-orders/{id}/issue` accepts an optional body
  `PoIssue {send_email: bool = true}` (`extra="forbid"`); no body means `send_email: true`, so every existing
  caller and test keeps working (`body: PoIssue | None = None` on `issue_purchase_order`, `api/purchasing.py` ~250-258). The route
  passes `settings` (`Depends(get_auth_settings)`, as the routes at ~134 and ~475 do) and `send_email` to
  `issue()`; `issue()` gains keyword parameters `settings: Settings` and `send_email: bool = True`.
- **In `purchasing/issue.py` `issue()`**, inside the transaction, after the retry/status/version checks
  (~68-73) and **before** any write (the recipients update ~82-86, `issue_lines`, `transition`):
  - `send_email` and not `po_email_allowed` → `raise conflict("po_email_held", ...)` (the 409 helper `issue()`
    already uses for `invalid_transition`), detail
    "Purchase order email is held until the sending domain is verified. Nothing was issued." Nothing is
    written: no ledger entry, no status change, no outbox row.
  - `send_email` false → issue exactly as today **except** `enqueue_transmission` is not called; write one
    audit row through `kernel` `audit_event` (action `purchase_order.issue_without_email`, the actor, the PO) in
    the same transaction. Recipients are still resolved and stored as today; the `NO_RECIPIENTS` rule is unchanged.
    Resend is **not** available for such a PO: it refuses with `nothing_to_resend` when there are no transmission
    rows (`transmission.py` ~308), and that stays (pre-flight 1). Emailing a PO issued without email later is a
    follow-up; record it in the story's `task.json` `notes.followup` (the worktree's task packet, not a repo file).
  - A retry of the same issue (the `status == "issued"` early return, PO-012) returns before this check, as now.
- **Dialog read.** `VendorCopyRead` (`purchasing/pdf.py` ~204, already loaded by the dialog) gains
  `po_email_allowed: bool`. `pdf.py` must not import `transmission.py` (`transmission.py` ~34 imports `pdf`;
  the reverse is a cycle), and `vendor_copy_read` (~211) opens no transaction of its own (`frozen` ~170 opens and
  closes its own). So: `vendor_copy_read(conn, scope, po_id, *, po_email_allowed: bool)` only copies the value into
  both of its return paths; a new `transmission.vendor_copy(conn, scope, po_id, settings) -> VendorCopyRead`
  reads the gate as `with tenant_transaction(cast(RlsSession, conn), scope): allowed = po_email_allowed(conn,
  settings)` (the shape of `sending_domain` ~475-487), then returns `vendor_copy_read(conn, scope, po_id,
  po_email_allowed=allowed)`. `GET .../vendor-copy` (`api/purchasing.py` ~397-399) calls it, with `settings`
  from `Depends(get_auth_settings)`. The only other caller is the test helper
  `tests/purchasing/test_vendor_copy.py` ~101: pass `po_email_allowed=True` there.
- **`IssueDialog.tsx`:** held = `copy.data?.po_email_allowed === false` **or** a `409 po_email_held` came back
  from this dialog's last press. When held:
  - the dialog body shows, above the facts, a `Signal tone="warning"` (`components/ui/Signal`) labelled
    "Purchase order email is held until the sending domain is verified", followed by the sentence "Issue
    without email, then download the PDF from the order and send it to the vendor yourself." (text carries the
    meaning, A11Y-004);
  - `Dialog.Description` reads "Issuing commits the budget. No email goes to the vendor." in place of "Issuing
    sends this version to the vendor ...";
  - the primary button reads **Issue Without Email** and POSTs `{send_email: false}`; the secondary is the
    existing **Not Yet** button (the operator's "cancel": closes, nothing issued, focus returns to Issue as
    today via `onCloseAutoFocus`). No PDF link in the dialog: a PDF exists only once issued (the PDF route is
    404 before issue, `tests/purchasing/test_vendor_copy.py` ~431).
  When not held, the dialog is unchanged and POSTs no body. On a `409 po_email_held` from a plain Issue press
  (the domain lapsed after the dialog opened): set held, replace the operation key
  (`key.current = crypto.randomUUID()`: the next press is a different request body, so it is a new operation; the
  idempotency middleware stores no response of status >= 400, `kernel/idempotency/middleware.py` ~309-311, so this is
  convention, not a replay guard),
  show no generic refusal line, and move focus to the held message (wrap the `Signal` and its sentence in an element with `tabIndex={-1}` and a ref; `Signal` takes no ref).
- **After issue without email:** the issue result page (`routes/purchase-orders/issue.tsx`, `Moment`) always
  renders `IssueStage`, whose last frame says "Email queued to the vendor." (`IssueStage.tsx` ~6). The
  discriminator is the **current send**, not the list: `const emailed = currentSend(rows, id).length > 0`
  (`transmissions/recovery.ts` ~27, already computed as `current` in `Moment`). The transmissions endpoint returns
  every revision sharing the PO number (`transmission.py` ~248-260), so a list holding an earlier revision's rows
  can still mean "this revision was not emailed". Derived (an issue with email always writes attempt 1 of the
  issue template for this `po_id` in the same transaction), no new field. When `emailed` is false:
  - `IssueStage` gets a new prop `emailed: boolean` (default `true`); when false its third frame text is
    "Not emailed: send the PDF to {vendor} yourself.", the `.po-trace` span is not rendered and the third
    animation is skipped (call `onStep(3)` straight after the seal so the result block still appears; reduced
    motion already starts at step 3);
  - the result block shows, in place of the outcome line and the send table, `<p role="status">Issued without
    email. Download the PDF and send it to the vendor yourself.</p>` and a link with the detail page's markup
    (`routes/purchase-orders/detail.tsx` ~73: `className="req-link-button"`, `href={`/api/v1/purchase-orders/${id}/pdf`}`,
    `target="_blank" rel="noreferrer"`, `FilePdf` icon) labelled **Download PDF**. This link is new on this page;
    the detail page's View PDF (`HAS_PDF`, ~24) is unchanged;
  - no polling starts (`pending` is already false for an empty current send) and no recovery block renders.
  A PO issued with email renders exactly as today (pre-flight 1).
- Regenerate the client (`openapi.json`, `schema.ts`); no hand-written types.
- Follow-up, not this story: a cancel notice for a PO issued without email is still gated by the same domain
  check; record it in the story's `task.json` `notes.followup`.

## Acceptance

- [ ] pytest (real Postgres, `email_provider="resend"` settings override, no passing domain check): issue with no body → 409 `po_email_held`; afterwards the PO is still `approved`, no `ledger_entry`, no `po_transmission`, no outbox row, `recipients` unchanged.
- [ ] pytest: same state, `{send_email: false}` → 200, PO `issued`, commitment posted as in the existing issue test, **no** outbox row and no `po_transmission`, one `purchase_order.issue_without_email` audit row.
- [ ] pytest: with SPF and DKIM `pass`, issue with no body behaves exactly as today (one attempt-1 transmission queued); `{send_email: false}` also works there.
- [ ] pytest: a retried issue (same `If-Match`, PO already issued) returns the PO without the 409, held domain or not (PO-012).
- [ ] pytest: `GET .../vendor-copy` reports `po_email_allowed` false/true across the two domain states; `sending_domain` still reports the same value.
- [ ] Playwright (`po-issue.spec.ts`; stub): `po_email_allowed: false` shows the held message and **Issue Without Email**, which sends `{"send_email": false}`; **Not Yet** closes with focus back on Issue; a `409 po_email_held` on a plain Issue switches the dialog to the held state with focus on the message, and the next press carries a different `Idempotency-Key`; the result page whose transmission list is empty **or holds only another revision's rows** (different `po_id`) shows the "Issued without email" line and the Download PDF link to `/api/v1/purchase-orders/<id>/pdf`, and never the text "Email queued to the vendor."; with an attempt-1 row for this `po_id` it still shows that frame. Keyboard-only path through the held dialog; axe both themes on the held dialog and the without-email result.
- [ ] `flo check --light` green.

## Plants

1. Move the held check after `issue_lines`: the "no ledger entry" assertion fails.
2. Call `enqueue_transmission` when `send_email` is false: the "no outbox row" assertion fails.
3. Make the dialog ignore `po_email_allowed`: the Playwright held-state case fails.
4. Use `rows.length > 0` instead of the current send for `emailed`: the other-revision-rows case fails.
