# E05-S09 — Identity belongs to an organization: membership, org_id on the session, seeded first tenant

**Epic** E05 · **M1** · **security/L** · after **E05-S01** · tags: `auth`, `security`

> **Conventions:** read `docs/m1-conventions.md`. It applies unless this packet says otherwise.

## Why this story exists

The M0 release review found that the live application can never establish a tenant: `identity` is a global table with no organization link, `SessionRecord` has no `org_id`, and `TenantContextMiddleware` only binds a scope when the session carries an `org_id` (`kernel/tenancy/middleware.py`). In production every protected route therefore answers 401, and the idempotency middleware silently skips every `POST` because no tenant scope is active. Tests pass because fixtures build a scope by hand. This story connects the pieces and proves it end to end.

## Requirements

- **AUTH-001** — User profiles must link users to BU/OUs, roles, projects, locale, timezone, and notification preferences.
- **ORG-001** — An organization must support multiple Business Units and/or Operating Units, each with a unique code.
- **TEN-010** (AGENTS.md section 3.2) — `org_id` resolves from the session, never from a URL, body or header; access to another tenant's record is 404; every endpoint is in the isolation suite.

## Design decisions (confirm on review)

- **D-M1-23 One identity belongs to exactly one organization in Phase 1.** A table `identity_membership(identity_id uuid PRIMARY KEY REFERENCES identity(id), org_id uuid NOT NULL REFERENCES organization(id), created_at timestamptz NOT NULL DEFAULT now())`. The primary key on `identity_id` enforces one organization per identity; multi-organization membership is a later migration (drop the primary key, add a selected-organization claim to the session). Platform operators have no row and no tenant scope.
- **D-M1-24 The membership table carries no RLS.** Login and session resolution look an identity up before any tenant is known, exactly like `identity` itself. The row reveals only which organization an identity belongs to, and it is readable only through the session store. If a gate requires RLS on every table with an `org_id` column, add this table to that gate's documented global-table allow-list with a test that names the reason; do not weaken the gate.
- **D-M1-25 Bootstrap is a command, not an endpoint.** There is no public tenant sign-up in Phase 1. `python -m flo.modules.org.bootstrap` creates a first organization and its first administrator. It is run by the operator (as a Cloud Run job execution or locally against a disposable database), never from a request.

## Contract

**Migration** (reversible; next revision after the current head): create `identity_membership` as above, with an index on `org_id`. Backfill: none (no production identities exist). Downgrade drops the table.

**Session.** `SessionRecord` gains `org_id: UUID | None`. The store loads it with the session in one query (a join on `identity_membership`, no second round trip). The session middleware puts the record on `request.state.session`, so `authenticated_session_from_request` returns it and `TenantContextMiddleware` binds `Scope(org_id=...)`. An identity with no membership gets `org_id None`: it authenticates but every tenant route is 401, which is the existing `TenantScopeMissing` behaviour.

**Never trust a client for the organization.** No route, header or body field may name an organization for scope purposes (existing rule; add a test that a request carrying a foreign `org_id` in header, query and body is ignored).

**Bootstrap command.** `python -m flo.modules.org.bootstrap --org-name NAME --org-code CODE --admin-email EMAIL` reads the initial password from the environment variable `FLO_BOOTSTRAP_PASSWORD` or, if unset, from stdin with no echo. The password is never a command-line argument and never printed. The command, in one transaction:
1. creates the organization (through the E05-S01 org service, not raw SQL), registers its `org` authorization scope, and seeds the default organization settings that E05-S01 defines;
2. creates the administrator identity through `LocalIdentityProvider` (NIST password policy and argon2id apply, so a weak password fails with a clear message and exit code 2), inserts the `identity_membership` row, and grants the system administrator role at the organization scope (use the identity service wrappers; find the existing system role code, and if none grants the full permission set, create `org_admin` as a system role holding every permission that exists at that revision and say so in the commit body);
3. writes an audit event `org.bootstrap` (actor kind `system`);
4. is **idempotent by organization code**: running it again with the same code and the same admin email prints "already bootstrapped" and exits 0 without changing anything; the same code with a different admin email exits 3.
It prints only: the organization id, the admin email, and the next step (sign in, enroll MFA). It prints no secret.

**MFA.** Privileged roles require MFA (E02-S05). The administrator is created with MFA enrollment pending: the first sign-in lands in the enrollment flow built by E05-S10. This story does not build UI.

## Acceptance criteria

- [ ] Real end-to-end test on Postgres through the actual session middleware (no hand-built `Scope`): bootstrap organization A and an administrator, log in over HTTP with the real login route, call `GET /api/v1/org/units` with the session cookie and get 200 with organization A's data
- [ ] A second organization B with its own administrator: B's administrator requesting an id that belongs to A (a project, an org unit) gets **404**, never 403 or 200; add one case per existing id-bearing route family to `tests/isolation/` driven by real sessions (not fixtures)
- [ ] An authenticated identity with no membership gets 401 on every tenant route and 200 on `/api/v1/auth/session`-style identity routes that need no tenant
- [ ] A foreign `org_id` supplied in header, query string or JSON body changes nothing (the session's organization wins)
- [ ] With a real session, a `POST` without `Idempotency-Key` is rejected by the idempotency middleware, and a replayed key returns the first response (proving the middleware now runs with a tenant scope)
- [ ] `SessionRecord.org_id` is populated by one query (assert the query count for session resolution did not increase)
- [ ] Bootstrap: creates org, admin, membership, scope grant and audit row in one transaction; rerun is a no-op (exit 0); same code with another admin email exits 3; a 6-character password exits 2 and creates nothing; the password never appears in stdout, stderr, the audit row or the process arguments (test captures all four)
- [ ] Migration up, down, and a data-preservation assertion; the migration-chain check passes
- [ ] Plant: remove the `org_id` join from the session query and the end-to-end test fails; delete the membership row and the no-membership test fails

## Amendments (preflight audit, authoritative, override anything above)

- **D-M1-26 Organization codes live in a global registry table, not on `organization`.** `organization` has RLS keyed on `app.org_id`, so a code lookup before any tenant is known cannot read it, and it has no code column today. The same migration that creates `identity_membership` also creates `organization_code(code text PRIMARY KEY CHECK (code ~ '^[A-Z][A-Z0-9_-]{1,31}$'), org_id uuid NOT NULL UNIQUE REFERENCES organization(id), created_at timestamptz NOT NULL DEFAULT now())`. No RLS, same reasoning and the same documented allow-list entry as `identity_membership` (D-M1-24): it reveals only which id a code maps to and is readable only by the bootstrap command. `organization` itself is **not** altered and nothing is backfilled (no production organizations exist; existing test organizations simply have no registry row). The downgrade drops both tables. The command upper-cases `--org-code` before validating it.
- **Organization creation.** There is no creation function today. Add `create_organization(conn, *, name, base_currency=None) -> UUID` to `modules/org/service.py` (export it through the module's service surface). It generates the new `organization.id`, enters `tenant_transaction(conn, Scope(new_id))` first (the `organization` RLS WITH CHECK requires `app.org_id` to equal the new id), inserts the row, and returns the id. It writes no audit row itself; the bootstrap command writes the single `org.bootstrap` audit event. `--base-currency` is an optional bootstrap argument (ISO 4217 validated through the existing currency list) and defaults to NULL.
- **Default settings.** Seed no `org_setting` rows: E05-S01's defaults are resolved in code by `effective_setting`, so a brand-new organization already reads its defaults. Add a test that `effective_setting` returns its documented default for a freshly bootstrapped organization.
- **Idempotency by organization code.** Resolution order, all before any tenant scope: look the code up in `organization_code`. (a) Not found: create everything. (b) Found: read that organization's administrator by looking up the identity with `--admin-email`; if that identity has a membership in the same organization, print "already bootstrapped" and exit 0 changing nothing; otherwise exit 3. Registry insert, organization, identity, membership, role grant and audit row are one transaction, so a failed run leaves no registry row. Concurrent runs with the same code: exactly one creates, the other exits 0 or 3 (the registry primary key is the arbiter; test it with two real connections).
- **Admin role.** Use the existing system administrator role if one grants the full permission set at this revision; otherwise create `org_admin` as described above. Create it through the identity service wrappers inside the new organization's scope.
- **Files addition:** `modules/org/service.py` (the `create_organization` function only).

- **Organization scope is derived, never registered (round 2).** Delete "registers its `org` authorization scope" from step 1 of the bootstrap contract. `RoleRepository.register_scope` correctly rejects `ScopeType.ORG`; the organization scope is the session's `org_id`. Bootstrap grants the administrator role with the existing identity service `grant_role(...)` at `ScopeType.ORG` with `scope_id` = the new organization id, inside `tenant_transaction(Scope(new_id))`, exactly as organization grants are validated today. `identity/service.py` is **not** changed beyond the membership wrappers. Use `seed_baseline_roles()` in the new organization's scope to obtain the baseline roles, and grant the system administrator one; apply the `org_admin` fallback above only if none of the baseline roles holds the full permission set. Add a test that the bootstrapped administrator passes an org-scope permission check against the real resolver.
