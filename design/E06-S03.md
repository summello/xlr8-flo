# E06-S03 — Project lifecycle state machine with permission and budget-effect enforcement

**Epic** E06 · **M1** · **engine/L** · after **E06-S01** · tags: 

> **Conventions:** read `docs/m1-conventions.md` (authorization outcomes, scope targets, wire formats). It applies unless this packet says otherwise.

## Requirements

- **PROJ-012** — Status must support Draft, Approval Pending, Active, Deferred, Completed, and Abandoned.
- **PROJ-013** — Valid status transitions, permissions, and budget effects must be enforced.
- **PROJ-018** — A project with open reservations, commitments, requisitions, or POs must not close without resolution or authorized override.
- **WF-002** — A status transition must validate actor, current state, required fields, approvals, and financial side effects.
- **WF-006** — Users must receive a clear, actionable explanation when a workflow action is blocked.

## Design decisions (confirm on review)

- **D-M1-16 The project state machine.** `draft`, `approval_pending`, `active`, `deferred`, `completed`, `abandoned` (PROJ-012). The approval engine arrives in M2, so in M1 `approval_pending → active` is performed by a holder of `project.approve` directly.

  | from | to | permission | extra conditions |
  |---|---|---|---|
  | draft | approval_pending | `project.submit` | name, BU, department, ledger account, currency present |
  | approval_pending | active | `project.approve` | actor ≠ the submitter (separation of duties) |
  | approval_pending | draft | `project.approve` | `reason` required (a rejection) |
  | draft | abandoned | `project.update` | — |
  | active | deferred | `project.update` | `reason` required |
  | deferred | active | `project.update` | — |
  | active | completed | `project.complete` | closing rule below |
  | active, deferred | abandoned | `project.complete` | closing rule below, `reason` required |

  `completed` and `abandoned` are terminal. Any other pair → 409 `InvalidTransition`.
- **Budget effects (PROJ-013):** funding allocation (E07-S03) is allowed in `draft`/`active` only (D-M1-11); a `deferred` project rejects new reservations and commitments and releases/reversals still work; `completed`/`abandoned` reject all new financial postings except releases and reversals. Completion does **not** move money; leftover allocation stays until a transfer moves it.
- **Closing rule (PROJ-018):** `completed`/`abandoned` is blocked while `project_balance.reserved > 0` or `committed > 0` or `open_documents(project_id) > 0` (a hook returning 0 in M1; requisitions/POs register themselves in M2/M3). A holder of `project.close.override` may proceed with a mandatory `reason` of at least 20 characters; the override is audited with the blocking figures.

## Contract

- `POST /api/v1/projects/{id}/transitions` body `{to, reason?, override: bool=false}`, `Idempotency-Key` and `If-Match: <version>` → 200 `ProjectRead` | 403 | 404 | 409 `InvalidTransition` | 409 `StaleVersion` | 409 `ClosingBlocked` | 422
- `GET /api/v1/projects/{id}/transitions/available` → 200 list of `{to, allowed: bool, blocked_reasons: [..]}` evaluated for the caller (WF-006: say why an action is blocked, in words)

Problem details for `InvalidTransition` and `ClosingBlocked` carry a machine `code` and a human `detail` (e.g. "2 reservations totalling 40,000.0000 USD are open; release them or use an authorized override").

Migration (reversible): the next revision after the current head at story start (revision id `20260826_<next 4-digit number>`, `down_revision` = the head `python -m flo.kernel.migrate --check` validates today); stories merge one at a time, so there is no gap or fork: `project_status_event(id bigserial, org_id, project_id, from_status, to_status, actor_id, reason, override bool, blocked_by jsonb, at)` append-only by trigger, RLS; permissions `project.submit`, `project.approve`, `project.complete`, `project.close.override`.

Service guards used elsewhere: `projects.service.assert_funding_allowed(project_id)` (draft/active), `assert_commitment_allowed(project_id)` (active only), imported by `budget.service` — wire `allocate` (E07-S03), `reserve` (E07-S04) and `commit` (E07-S05) to call them in this story and update their packets' tests accordingly.

## Behaviour

1. One transaction: lock the project row `FOR UPDATE`, check `version`, validate the table above, closing rule, required fields, write the status, bump `version`, insert `project_status_event` and an audit row.
2. The actor is validated against the transition table **and** their grant at the project's scope; a hidden UI button is irrelevant.
3. Same-state transition → 409 `InvalidTransition` (no silent no-op).

## Acceptance criteria

- [ ] Every transition in the table succeeds for an authorized actor; every other (from, to) pair — all 36 minus the valid ones — returns 409 (parametrized state-machine test, AGENTS.md 3.5 `workflow`)
- [ ] A submitter cannot approve their own project; a different approver can
- [ ] Completing with 40 reserved → 409 `ClosingBlocked` with the figure in `detail`; with `project.close.override` and a 20+ char reason it succeeds and the event row records `override=true` and the blocking figures; without the permission the override flag is ignored (403)
- [ ] Two concurrent transitions with the same `If-Match` → exactly one succeeds, the other 409 `StaleVersion`
- [ ] A deferred project rejects `reserve`/`commit` and accepts `release`/`reverse`; completed rejects `allocate`
- [ ] `available` lists each target with `blocked_reasons` in plain language and is consistent with what POST would do
- [ ] Status events cannot be updated or deleted
- [ ] Foreign-tenant project → 404 on both endpoints (isolation gate entries); migration up/down/data-preservation

## Amendments (preflight audit — authoritative, override anything above)

- **Guards live in one place:** `post_entry` calls `projects.service.assert_posting_allowed(project_id, entry_type, bucket)` **after taking the balance lock** (so no per-primitive wiring is needed or allowed to drift). Rules: `allocated` bucket entries (allocation, adjustment, transfer legs) are allowed in `draft`, `active`, `deferred`; the *receiving* transfer leg and new allocation additionally require not `completed|abandoned` (a giving leg may leave any status); `reserved` and `committed` increases require `active` only; `actual` is allowed in `active` and `deferred`; `release` and `reversal` rows are always allowed. `completed` and `abandoned` therefore reject every new posting except releases, reversals and outgoing transfer legs.
- **Lock order** for both lifecycle transitions and postings: `project_balance` row `FOR UPDATE` first, then the `project` row. A transition re-reads the balance and the closing rule under that lock, so a reservation cannot slip in between the check and the status change.
- **Residual funds:** an outgoing transfer from a `completed` or `abandoned` project is allowed (E07-S07 statuses amendment), which is how leftover allocation is moved.
- Reservation is allowed in `active` only (the table above is authoritative over the `assert_commitment_allowed` wording).

- **Lock order (amendment, owed since E07-S07 review):** `post_entry` takes the `project_balance` lock and then calls `assert_posting_allowed`, which reads the project's status. A transition therefore takes the `project_balance` row `FOR UPDATE` **first**, then the project row `FOR UPDATE`, then reads status, version and the closing-rule figures, so the two paths serialize in the same order and cannot deadlock. A project with no `project_balance` row is created with one first (or the transition fails with 404 if it cannot lock one). Required tests, real Postgres: (a) a reservation posting concurrent with `completed`: exactly one outcome, either `ClosingBlocked` or the reservation rejected as posting-not-allowed, never a completed project holding a new reservation; (b) a transfer (E07-S07) into a project concurrent with its transition to `completed`: allocation left on a project does **not** block completion (the closing rule is reserved, committed and open documents only), so both serial orders are valid, and the test asserts the outcome equals one of them: either the transfer commits first and the completion then succeeds, or the completion commits first and the transfer is rejected with 409 `TransferNotEligible`; never a transfer that lands after the completion. Run it 20 times against real Postgres; (c) plant-verify (a) by moving the balance lock after the status read.

- **Closing rule applies to every terminal transition (decision, closes the draft-abandon ambiguity).** The closing rule and the override are evaluated for **every** transition into `completed` or `abandoned`, including `draft -> abandoned`. The table's permission for each row is unchanged (`draft -> abandoned` keeps `project.update`, with no `reason` required when the rule passes); a blocked `draft -> abandoned` can be overridden only by a holder of `project.close.override` with the 20-character reason, exactly like the other rows. A draft with nothing reserved, committed or open abandons without a reason. Add a test: a draft holding a reservation (planted through the ledger service) cannot be abandoned without the override.

- **Dynamic permission check (round 3 authorization).** `kernel/authz.require` takes one fixed permission, but a transition's permission depends on the locked state and the target (table above). Authorized, minimal extension: add ONE public function to `kernel/authz.py`, `permits(request: Request, permission: str, target: AuthorizationTarget) -> bool`, that resolves the request's identity and tenant scope exactly as `require.enforce` does and returns `resolver.check(...).allowed` without raising for a denial (an unauthenticated request or missing scope still raises the usual 401). Nothing else in `authz.py` changes and `require` keeps its behaviour. Both transition routes are guarded by `require("project.read", project_target)` (this gives the 401/404 concealment and satisfies the route gate); the router then builds a callable `permitted(permission) -> bool` from `permits(request, permission, target)` and passes it into the projects service, which stays free of HTTP types. The POST calls it after locking and reading the state (missing permission -> 403, never a silent downgrade; the override flag is honoured only when `permitted("project.close.override")`), and `GET .../transitions/available` calls it per target. Files addition: `kernel/authz.py` (the `permits` function only) and its unit tests under `apps/api/tests/kernel/`, including a plant (make `permits` always return True and a denial test fails). `modules/projects` must not import `identity` internals.
- **Migration revision id:** use `20261008_0025` (filename `migrations/20261008_0025_<name>.py`, `down_revision = "20261008_0024"`), per the corrected convention in `docs/m1-conventions.md`.

- **Guard receives the signed amount (round 4).** Transfer legs share `entry_type` and `bucket`, so direction is only visible in the sign. The guard signature becomes `assert_posting_allowed(project_id, entry_type, bucket, amount)` with `amount` the **signed** `Decimal` exactly as `post_entry` is about to write it; `post_entry` passes its own argument (authorized change to `modules/budget/ledger.py`: the one call site only). Rule for the `allocated` bucket: a **negative** amount (outgoing transfer leg, negative adjustment) is allowed in every status; a **positive** amount (incoming transfer leg, allocation, positive adjustment) requires a status other than `completed|abandoned`. Every other rule in "Guards live in one place" stands. Tests: an incoming transfer leg into a `completed` project is rejected by the guard itself (call `post_entry` directly, not only through the transfer service); an outgoing leg from a `completed` project succeeds; plant-verify by ignoring the sign.
