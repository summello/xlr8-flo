# E17-S02 — Notification engine: one entry point, in-app and email channels, per-event preferences

**Epic** E17 · **M4** · **engine/L** · after **E03-S06** · tags: none (ungated)

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> Invariant 6: every external effect goes through the outbox. Resend's **100/day** ceiling
> (project memory): this story changes no volume; digest batching is E17-S03.
> Back end only. The notification inbox and preferences screen is a registered **GAP**
> (`docs/ui-screen-inventory.md` §2, "Notifications and preferences").
> **RLS:** every new tenant table gets literal `ALTER TABLE <t> ENABLE ROW LEVEL SECURITY; … FORCE …; CREATE POLICY tenant_isolation ON <t> …` statements in the migration text, one block per table.

## Requirements (inlined)

- **XFN-005** — Notifications must support in-app and email channels with configurable event preferences, except mandatory security/administrative notices.
- **XFN-006** — Approval, due-date, document-expiry, failed-transmission, import/export, and material project-risk events must be eligible for notification.
- **AUTH-001** — User profiles must link users to BU/OUs, roles, projects, locale, timezone, and notification preferences. (This story owns the **notification preferences** part; locale, timezone, theme and grid defaults are E17-S06.)

## Why

Six modules call `OutboxStore.add_email` directly today (`grep -rn "add_email(" apps/api/src/flo/modules`).
None has an in-app channel and none honours a preference. One engine gives every event both
channels, one preference model and one idempotency rule.

## Design

New module `modules/notifications/` (`models.py`, `schemas.py`, `service.py`, `catalogue.py`).

### Event catalogue (`catalogue.py`, closed, code-defined)

| Event | XFN-006 class | Channels offered | Default | Email template | Emitter wired in this story |
|---|---|---|---|---|---|
| `approval.outcome` | approval | in_app, email | both on | `approval-outcome-v1` | `approvals/engine.py::notify_outcome` |
| `approval.reminder` | due-date | email | on | `approval-digest-v1` | `approvals/reminders.py`: **email gate only** (see below) |
| `vendor_document.expiry` | document-expiry | email | on | `vendor-document-expiry-v1` | `vendors/expiry.py`: **email gate only** |
| `import.finished`, `import.failed` | import/export | in_app, email | both on | `import-finished-v1`, `import-failed-v1` | `imports/service.py::notify` |
| `project.risk_high` | material project-risk | in_app | on | none (no provider template exists; email is a follow-up once the operator creates one) | `projects/risks.py::Risks.write` |
| `purchase_order.issued` | approval (decision 168: the requester is told internally) | in_app | on | none | the E13-S05 hook, if present (below) |
| `purchase_order.transmission_failed` | failed-transmission | in_app, email | both on | the template E13-S09 uses, if it emails the requester; otherwise in_app only | the E13-S09 failure path, if present |
| `export.finished`, `export.failed` | import/export | in_app, email | both on | catalogued for E15-S09 | none (E15-S09 calls `notify`) |
| `security.invitation`, `security.password_reset` | mandatory security notice | email | on, **locked** | existing | none: they stay on `IdentityOutboxStore` (identity-level, before membership) and never consult preferences |

`project.risk_high` fires when a risk is created at, or changes to, `recorded_level(score) == "high"`
(`projects/risk_indicators.py`), recipient the risk's `owner_id`, unless the owner is the actor.
Reference: the project number. No title, description or score in the notification.

**E13 hooks (M3, merged before this story).** E13-S05's packet asks for "an in-app notification row"
and E13-S09 for an internal notice on failure, but no notification table exists in M3. At story
start, `grep -rni "notif" apps/api/src/flo/modules/purchasing`: route whatever hook or table E13
left through `notify` (moving any rows E13 stored into `notification` in this story's migration and
dropping E13's table). If E13 left nothing, the two events stay catalogued without an emitter and
the gap goes in `notes.followup`.

### Tables

`notification` (RLS): `id`, `org_id`, `recipient_id uuid`, `event text` (CHECK in the catalogue),
`reference text NULL` (a document number, never free text), `link text NOT NULL` (an app-relative
path starting `/`, CHECK), `idempotency_key text NOT NULL`, `in_app bool NOT NULL`,
`email_outbox_id uuid NULL`, `created_at`, `read_at NULL`.
`UNIQUE (org_id, recipient_id, idempotency_key)`. Index `(org_id, recipient_id, created_at DESC) WHERE in_app`.
A row is written for every recipient even when both channels are off, so suppression is visible
and the unique key is the dedupe for every channel.

`notification_preference` (RLS): `org_id`, `user_id`, `event`, `in_app bool`, `email bool`,
`updated_at`. `PRIMARY KEY (org_id, user_id, event)`. No row = the catalogue default.
Preferences are per organization membership, because events are tenant data.

### Service contract (frozen once merged; E17-S03, S04, S05, E15-S09 build on it)

```python
def notify(conn, scope, *, event: str, recipients: Iterable[UUID], link: str,
           reference: str | None, context: Mapping[str, object],
           idempotency_key: str) -> int
    # Runs on the caller's connection, inside the caller's transaction. For each distinct recipient:
    # channels = preference ∩ catalogue channels; INSERT notification ... ON CONFLICT DO NOTHING;
    # only when the insert happened and email is on: emails_by_id → OutboxStore.add_email(
    #   to, template, context, idempotency_key=f"{idempotency_key}:{recipient}") and store its id.
    # Returns the number of recipients newly notified. Unknown event → ValueError (a programming error).
def channels_for(conn, scope, user_id: UUID, event: str) -> Channels   # Channels(in_app: bool, email: bool)
```

`context` goes to the email template only and is never stored on `notification`. Existing callers
keep their context and template unchanged.

**Digest sites (`approvals/reminders.py`, `vendors/expiry.py`)** keep their own outbox dedupe and
digest shape in this story; each adds one `channels_for(...).email` check before `add_email` and
skips that recipient when it is off. Turning them into engine digests with in-app entries is
E17-S03.

### API

| Method and path | Guard | Behaviour |
|---|---|---|
| `GET /api/v1/notifications` | `require_member()` (self-scoped) | The caller's in-app rows, newest first, keyset on `(created_at, id)`, `?unread=true&cursor=&page_size` (1..50). Each `{id, event, title, reference, link, created_at, read_at}`; `title` is the catalogue's fixed label (`"Approval decided"`, …). Plus `unread_count`. |
| `POST /api/v1/notifications/{id}/read` (Idempotency-Key) | `require_member()` | Sets `read_at` if null. Another user's or a foreign id → **404**. Already read → 200 unchanged. |
| `POST /api/v1/notifications/read-all` (Idempotency-Key) | `require_member()` | Marks every unread row of the caller read; returns `{marked: int}`. |
| `GET /api/v1/me/notification-preferences` | `require_member()` | Every catalogue event: `{event, label, class, channels_offered, in_app, email, locked}`. |
| `PUT /api/v1/me/notification-preferences/{event}` | `require_member()` | `{in_app: bool, email: bool}`. A channel the event does not offer set true → 422 naming it. A locked event → 422 `mandatory_notice`. Unknown event → 404. Idempotent by semantics (§C). Audited `notification.preference.set` in the current org. |

`require_member` is sanctioned here because every route reads or changes only the caller's own rows
(`docs/m2-conventions.md` §P); the service filters by `recipient_id = caller` in SQL, never after.

## Invariants

- Nothing sends from a request handler: email only via `OutboxStore.add_email` in the caller's transaction (a rolled-back decision sends nothing).
- A notification never carries an amount, comment, rationale, vendor bank data or description (AUD-006; E17-S04 hardens subjects, previews and link authorization).
- `link` is app-relative; the engine refuses an absolute URL (`ValueError`). (The imports email context keeps its absolute link for the template; `link` on the row is `/imports/<id>`.)
