# E07-S03 — Allocation command with authorization, reason, effective date and audit

**Epic** E07 · **M1** · **ledger/M** · after **E07-S02** · tags: `money`

## Requirements

- **BUD-001** — Project dashboards must provide authorized allocation, adjustment, and transfer utilities.
- **BUD-006** — Every ledger entry must link to its source document or authorized manual action.
- **BUD-007** — Manual adjustments/transfers require a reason, effective date, supporting evidence when configured, and approval when applicable.

## Contract

Permission `budget.allocate` (allocate) and `budget.adjust` (adjust), both with `reason` mandatory (BUD-007). Authorization checked server-side against the **project's scope** via the existing authz resolver (a grant at an ancestor BU/OU covers descendants).

- `POST /api/v1/projects/{project_id}/budget/allocations` body `{amount, currency, effective_date, reason, evidence_ref?}`, `Idempotency-Key` required → 201 `LedgerEntryRead` | 403 | 404 | 409 `PeriodClosed` | 409 `ParentInsufficient` | 422
- `POST /api/v1/projects/{project_id}/budget/adjustments` body `{amount (signed, non-zero), currency, effective_date, reason, evidence_ref?}`, `Idempotency-Key` required → 201 | 403 | 404 | 409 `InsufficientBudget` (a negative adjustment cannot push `available` below zero unless `allow_negative_budget`) | 409 `PeriodClosed`

Service: `modules/budget/service.py` `allocate(...)`, `adjust(...)` calling `post_entry` (E07-S02). Evidence: `evidence_ref` is stored in a new `ledger_evidence(entry_id bigint fk, org_id, ref text)` table (append-only by trigger, RLS) in migration `20260826_0020` (down `…_0019`), not on the ledger row. `budget.evidence_required` org setting (default false) makes `evidence_ref` mandatory (BUD-007 "when configured").

## Behaviour

1. `amount` arrives as a decimal **string**; the schema validator rejects JSON numbers (no float ever parsed). Allocation `amount > 0`.
2. Funding-mode interaction is E06-S04's: until it lands, `allocate` posts directly; E06-S04 adds the parent-availability check for roll-down and `ParentInsufficient` becomes live then. Leave the hook (`funding_policy.check_allocation(project, amount)` returning None) so S04 plugs in without touching this story's tests.
3. **D-M1-11: allocations are allowed on Draft and Active projects; Deferred, Completed and Abandoned projects reject allocation (409 `ProjectNotFunding`).** Until E06-S03 exists the check reads `project.status` directly through `projects.service.get_status` (a thin read stub added in this story if E06-S03 is not yet merged, replaced there).
4. The business rule "a manual action carries a reason" is already a table CHECK; the endpoint also returns 422 field errors for a missing/short (min 10 chars) reason.
5. All in one transaction with the audit row; the response includes the new balance.

## Acceptance criteria

- [ ] Allocating 100.0000 then adjusting −30.0000 yields `allocated = 70.0000` and a ledger of two entries, `bucket=allocated`
- [ ] Negative adjustment exceeding available returns 409 and writes nothing; with `allow_negative_budget=true` it succeeds
- [ ] Missing or <10-char reason → 422 with a field error; JSON number amount → 422
- [ ] Replayed `Idempotency-Key` → original response, one ledger row
- [ ] A user with `budget.allocate` on a *sibling* project only gets 403; with the grant at an ancestor BU gets 201; foreign-tenant project → 404 (isolation gate entries)
- [ ] `evidence_required=true` rejects a missing `evidence_ref` and stores it when present
- [ ] Allocation to a `Deferred` project → 409; to `Draft` → 201
- [ ] Two concurrent allocations to one project both succeed and `allocated` is the exact sum
- [ ] Migration up/down/data-preservation
