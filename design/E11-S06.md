## Requirements (inlined)

- **VEN-005** — Vendor creation, activation, scope changes, suspension, and reactivation must support approval.
- **VEN-010** — Vendor tax identifiers and other configured unique identifiers must be checked for duplicates.
- **VEN-012** — A vendor that is inactive, suspended, expired, or not approved must not be invited or selected unless policy explicitly permits an authorized override. *(This story owns the status half: only an approved, active vendor is `active`. The derived eligibility rule is E11-S11.)*

## State machine (the only way `vendor.status` changes)

| From | Action | Permission | Via approval | To on approve | To on reject |
|---|---|---|---|---|---|
| `draft` | submit | requester (own) or `vendor.edit` | yes | `active` | `rejected` |
| `rejected` | revise | `vendor.edit` | no | `draft` | — |
| `active` | change availability | `vendor.edit` | yes | `active` (new availability) | unchanged |
| `active` | suspend | `vendor.edit` | yes | `suspended` | unchanged |
| `suspended` | reactivate | `vendor.edit` | yes | `active` | unchanged |
| `active`, `suspended` | inactivate | `vendor.approve` | no (an approver's own act, audited, with a reason) | `inactive` | — |

`pending_approval` is the status **only while a create request is in approval** (submit sets it;
approve and reject leave it). For the other three requests, the vendor **stays as it is until
approved** (pages/vendors.md §2): the pending request is shown beside it, and the status does not
move. Every other transition → 409 `invalid_transition`. A state-machine test covers every cell,
valid and invalid.

## Requests are the approval documents

Table `vendor_change` (RLS): `id`, `org_id`, `vendor_id`, `kind` CHECK in `create`, `availability`,
`suspend` and `reactivate`, `payload jsonb` (for availability: `{availability, unit_ids}`), `reason
text NOT NULL` (1..500, except for create), `status` CHECK in `pending`, `approved`, `rejected` and
`withdrawn`, `requested_by`, `requested_at`, `decided_at`. At most one `pending` change per vendor
(partial unique index), or 409 `change_pending`.

`modules/vendors/approval.py` implements `DocumentAdapter` for `document_type = "vendor"` with
`document_id = vendor_change.id`. Use `approve_permission = "vendor.approve"` and
`read_permission = "vendor.view"`. Its `snapshot` target is the org (global vendor) or the first
unit by code (restricted), so `document_bu` resolves a workflow. Register it with
`register_document_type` at module import, as `budget/approval.py` does.
`on_outcome` applies the table above **inside the decision transaction**: lock the vendor row
`FOR UPDATE`, re-check it is still in the expected from-state (409 if not), apply, and audit
`vendor.status_change` with the change id.

Before starting any approval, call `approvals.service.require_workflow_for(conn, scope, "vendor",
change_id, "vendors")`: no published workflow → 409 `workflow_not_set_up`, never auto-approve.

### Submit (`POST /vendors/{id}/submit`, Idempotency-Key)

In one transaction:
1. lock the vendor
2. require `draft`
3. `contacts_complete` (E11-S02) is empty, or 422 listing the missing types
4. `answers_complete` (E11-S05) is empty, or 422 per key
5. **duplicate check** (below)
6. store the score (E11-S05 `score`)
7. insert the `vendor_change(kind='create')`, set `pending_approval`, start the approval

A score below the threshold does **not** block (decision 6h-6). It is evidence.

## Duplicate identifiers (VEN-010, decision 6h-7)

**Identifiers checked:** `vendor_sensitive.tax_id` (normalised: upper case, with spaces, dots and
hyphens stripped, compared within the same `tax_id_country`), plus any configured unique identifier.
Configured identifiers are a master kind `vendor_identifier_type` (attribute `unique: bool`) and a
table `vendor_identifier(vendor_id, type_code, value_normalised)`. The comparison lives in the
vendors **repo** (E11-S04's single door) and returns **only matching vendor ids**, never values.

- `GET /vendors/duplicate-check?tax_id=…&tax_id_country=…&identifiers[type]=…` (a live check for
  the request form, `vendor.request`): returns `{matches: [{field, vendor_id?, vendor_number?,
  trading_name?}]}`. The name and number are included **only if the caller may view that vendor**
  (`vendor.view` and its availability). Otherwise, return `{field, match: true}` only, without
  saying which vendor.
- On submit, a match against any vendor other than this one, in any status except `rejected`,
  → 409 `duplicate_identifier` with the fields, **unless** the body carries
  `{override_reason}` and the caller holds `vendor.approve` (the "vendor manager"). The override is
  stored on the change and audited as `vendor.duplicate_override`, and the approver sees it.
- Matches are rechecked inside the submit transaction after locking (a race between two
  requests with the same tax id: one passes, one gets 409; a concurrency test proves it).

## Other routes

`POST /vendors/{id}/changes` (Idempotency-Key) with `{kind, payload?, reason}` for availability,
suspend and reactivate. `POST /vendors/{id}/changes/{cid}/withdraw` by the requester while pending.
`POST /vendors/{id}/inactivate` with `{reason}`. `GET /vendors/{id}/changes` (history, newest first).

## Evidence for the decision panel

`snapshot()` returns, for a create: the score with threshold and the per-question breakdown with
weights (approvers may see them), the duplicate result (including any override reason),
`document_state` (E11-S03) and the contacts summary. For the others: the change payload, the reason,
and counts of open RFQs and issued POs for the vendor. Return 0 until E12 and E13 register; take
them through the link-graph providers when they exist, never by importing those modules.

## Acceptance

- [ ] State machine: every cell of the table, valid and invalid, as a parametrized test.
- [ ] No published vendor workflow → submit and changes return 409 `workflow_not_set_up`, and nothing is written.
- [ ] Submit refuses missing contacts and missing required answers (422) and succeeds with a below-threshold score.
- [ ] Duplicate: blocked without override; allowed with `vendor.approve` and a reason (audited); a requester without `vendor.approve` cannot override; the live check hides the vendor's identity from a caller who may not view it.
- [ ] Concurrency (real Postgres): two submits with the same tax id at once → exactly one 409.
- [ ] Availability change approved → E11-S01's `available_in` reflects it; rejected → unchanged; while pending, the vendor's availability is the old one.
- [ ] A second pending change → 409 `change_pending`.
- [ ] TEN-010 on every new route, plus an authorization test per role.
- [ ] `flo check` green.

## Plants

1. Apply the change on submit instead of on approve: the "unchanged while pending" test fails.
2. Remove the in-transaction recheck: the concurrency test sees two successes.
3. Skip `require_workflow_for`: the 409 test fails.
