# E08-S03 — Import batch record, idempotent re-import by external key, async with progress

**Epic** E08 · **M1** · **engine/M** · after **E08-S02** · tags: 

## Requirements

- **IMP-008** — Imports must be idempotent when a documented external key or batch key is reused.
- **IMP-009** — Each batch must retain uploader, time, file checksum, mapping/template version, counts, result, and resulting record identifiers.
- **IMP-012** — Large imports and exports must run asynchronously with progress, cancellation where safe, and completion/failure notification.
- **PERF-004** — Imports, complex reports, bulk exports, email delivery, and recalculation must run as background jobs with visible progress.

## Contract

Uses the existing Postgres job queue (`kernel/jobs`) and notification outbox.

Migration (reversible): the next revision after the current head at story start (revision id `20260826_<next 4-digit number>`, `down_revision` = the head `python -m flo.kernel.migrate --check` validates today); stories merge one at a time, so there is no gap or fork: `import_batch` gains `external_key text null`, `progress jsonb not null default '{}'` (`{phase, rows_done, rows_total}`), `cancel_requested bool not null default false`, `error_class text`, with `UNIQUE (org_id, template, external_key) WHERE external_key IS NOT NULL` (IMP-008).

- `POST /api/v1/imports` accepts optional `external_key` (header `X-Import-Key` or body field): re-uploading with the same (template, `external_key`) returns the **existing batch** with `200` and `Idempotent-Replay: true`, creating no second batch and no second stored object (IMP-008); a different file checksum under the same key is a 409 `ImportKeyConflict`.
- `POST /api/v1/imports/{id}/validate` and `/commit` always enqueue a job when the batch has more than 500 rows (the small-file inline path from E08-S02 stays) and return **202** with `Location: /api/v1/imports/{id}`.
- `GET /api/v1/imports/{id}` → 200 `ImportBatchRead` including `progress`, status, counts, timings.
- `POST /api/v1/imports/{id}/cancel` → 202; only valid in `validating` or `committing` **between rows/chunks**: validation cancel discards partial `import_row` data and sets `cancelled`; a commit cancel in **atomic** mode rolls the whole transaction back (nothing committed), in **partial** mode stops after the current chunk and reports what was committed. Cancelling a `committed` batch is a 409.
- `GET /api/v1/imports?status=&cursor=&page_size<=50` → 200 batch history (IMP-009: uploader, time, checksum, mapping/template version, counts, result).

## Behaviour (IMP-008, IMP-009, IMP-012, PERF-004)

1. The job processes in chunks of 500 rows, updating `progress` every chunk in its own short transaction (visible progress), and checks `cancel_requested` between chunks.
2. Jobs run under the org's tenant scope; a crash mid-run leaves the batch `failed` with `error_class` only (no message text), and **never** leaves a half-committed atomic batch (the atomic commit is one transaction, so a crash rolls it back).
3. Completion/failure sends a notification through the **outbox** (never from the handler) to the uploader: one email using the existing email port, batched into the digest rules already in place; the message names the batch, counts and a link, with no row data.
4. `IMP-009`: the batch keeps uploader, `created_at`, `file_sha256`, `template_version`, `mapping`, `counts`, status and, through `import_result`, the resulting record identifiers.
5. A worker retry of a committing job is idempotent: already-committed rows classify as unchanged and are not duplicated.

## Acceptance criteria

- [ ] Uploading twice with the same `external_key` and file returns the same batch id and one stored object; a different file under that key → 409
- [ ] A 5,000-row validate and commit run as background jobs: the POST returns 202 immediately and polling `GET` shows `rows_done` rising to `rows_total`
- [ ] Cancelling mid-validation ends in `cancelled` with no `import_row` leftovers; cancelling an atomic commit mid-run leaves zero target rows; cancelling a partial commit leaves exactly the committed chunks and states them
- [ ] A worker killed between chunks and retried finishes without duplicates (simulate by raising in the job and re-running it)
- [ ] The uploader receives exactly one outbox email on completion and one on failure; the body contains counts and a link and no row values (test inspects the outbox row)
- [ ] History lists batches with uploader, checksum, template version, counts; another tenant's batches never appear
- [ ] Foreign-tenant batch id → 404 on `GET`/`cancel` (isolation gate entries)
- [ ] Migration up/down/data-preservation
