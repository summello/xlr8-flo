# E12-S01 — RFQ draft from approved requisition lines, with the open-quantity guard

**Epic** E12 · **M3** · **engine/L** · after **E11-S01** · tags: `money` (Opus review)

> **Conventions:** `docs/m1-conventions.md`, `docs/m2-conventions.md`, `docs/author-traps.md`.
> **Decisions:** canvas DECISIONS 144 (one RFQ, several requisitions, same unit and currency) and
> 152; `design-system/pages/sourcing.md` §2 "Approved lines are the only way in"; the upstream guard
> (E09-S18, handoff 15 Oct): call `requisitions` `assert_current_upstream` before creating any RFQ.
> Back end only; the UI is E12-S12.

## Requirements (inlined)

- **SRC-001** — Sourcing users must be able to create an RFQ from approved requisition lines.
- **SRC-003** — The system must prevent sourcing more than the approved open quantity or amount unless the requisition is amended.
- **SRC-015** — All RFQs, responses, comparisons, and awards must remain linked to the requisition.
- **SRC-018** — Every expenditure line must complete RFQ sourcing before final award, PO submission, or financial effect unless a future, explicitly approved sourcing-exemption policy is introduced.
- **REQ-014** — Split sourcing and partial awards must be supported without exceeding approved quantity or amount.

## Module

New module `apps/api/src/flo/modules/sourcing/` (RFQs, bids, comparison, evaluation and awards
live here across E12). The wildcard `module-independence` contract in `.importlinter` covers it
(no per-module contract). It imports `requisitions`, `vendors`, `org` and `approvals` through their
`service` and `schemas` only.

## Data

`rfq` (RLS): `id`, `org_id`, `number` (`org.numbering`, doc type `"rfq"`, which already exists),
`title` (1..200), `status` CHECK in exactly `draft`, `published`, `closed`, `under_evaluation`,
`awarded` and `cancelled` (MASTER §2.3; only `draft` is reachable in this story), `unit_id` (the
shared BU/OU of its lines), `currency char(3)` (the shared currency), `owner_id`, `version int NOT
NULL DEFAULT 0` (0 = never published), `created_at`, `updated_at`.

`rfq_line` (RLS): `id`, `org_id`, `rfq_id`, `line_no`, `requisition_id`, `requisition_line_id`,
`requisition_version int` (the version the guard checked), `quantity NUMERIC(18,4) > 0`,
and snapshots of `description`, `uom_code`, `needed_by` and `currency` taken at creation. The
requisition line may change later through an amendment; the RFQ shows what was sourced (SRC-015).
`UNIQUE (rfq_id, requisition_line_id)`.

## The guard (SRC-003, REQ-014). Opus design decision: drafts hold quantity

`open = quantity − cancelled_qty − sourced_qty` on `requisition_line`. **A draft RFQ line counts
toward `sourced_qty` from the moment it is created**, so two buyers cannot both draft the same open
quantity. Removing a line, lowering its quantity, deleting the draft (E22-S02) or cancelling the RFQ
(E12-S09) **returns** the quantity. `sourced_qty` is never written except through the function
below.

Add to `requisitions.service`:

```
source_lines(conn, scope, changes: Sequence[LineSourcing], actor_id) -> None
# LineSourcing(requisition_id, requisition_line_id, requisition_version, delta: Decimal)
```

In the **caller's** transaction:
1. Lock every affected `requisition` row, then the `requisition_line` rows, `FOR UPDATE` in id order.
2. For each requisition, call `assert_current_upstream(conn, scope, requisition_id, requisition_version)`. It refuses a stale version, a pending amendment, an unapproved status or expired master codes.
3. For a positive delta, require `delta ≤ open`, or 409 `over_open_quantity`, with `checks` = `{line_id, open, requested}` per offending line. All or nothing.
4. Apply `sourced_qty += delta`. A negative delta never takes it below 0 (the CHECK constraint enforces this too).

Quantities are `Decimal`/`NUMERIC(18,4)`; never float.

**Same unit and currency (decision 144):** every line on one RFQ shares the requisition's business
or operating unit and currency, or 422 per line with reason `another_unit` or `different_currency`.

## API (`/api/v1/sourcing`)

| Method and path | Permission | Behaviour |
|---|---|---|
| `GET /sourcing/requisition-lines?unit_id=&currency=&q=&cursor=` | `rfq.create` | Approved lines with `open > 0` from requisitions in `sourcing_in_progress` (paged), with requested, sourced, awarded, ordered, cancelled and open (REQ-015), and `selectable` + `reason` relative to an optional `with_rfq` (unit and currency). |
| `POST /sourcing/rfqs` (Idempotency-Key) | `rfq.create` on the unit | Body `{title, lines: [{requisition_line_id, requisition_version, quantity}]}`. Creates the draft and sources the lines in **one transaction**. 201. |
| `PATCH /sourcing/rfqs/{id}/lines` (Idempotency-Key) | `rfq.edit` | Add, remove and requantify while `draft` (`source_lines` with the deltas); otherwise 409 `not_draft`. |
| `GET /sourcing/rfqs/{id}` | `rfq.view` | The draft with lines and each line's live open figure. |

Register an `rfq` node with `requisitions.links.register_link_provider`, so the requisition's Linked
Records lists its RFQs. `LinkedNode` must carry `access`, or it is omitted (fail-closed).

All writes are audited (`rfq.create`, `rfq.lines.update`).

## Acceptance

- [ ] Migrations up, down and data preservation.
- [ ] Guard: under, equal and above open (above → 409 with the figures; nothing written); several requisitions in one RFQ; a different unit and a different currency → 422 per line.
- [ ] Removing or lowering a line returns quantity; the open figure is restored exactly (Decimal equality).
- [ ] **Concurrency (real Postgres):** two RFQs drafting the last 10 units of one line at once → exactly one succeeds.
- [ ] A stale `requisition_version`, a pending amendment and an expired code each → 409 from `assert_current_upstream`; nothing written.
- [ ] The requisition's links list the RFQ; a user without `rfq.view` does not see the node.
- [ ] TEN-010: another tenant's requisition line id → 404/422, never sourced; another tenant's RFQ → 404.
- [ ] Authorization per role: requestor cannot create; sourcing-specialist can.
- [ ] `flo check` green.

## Plants

1. Validate open before taking the lock: the concurrency test sees two successes.
2. Skip `assert_current_upstream`: the stale-version test fails.
3. Let `sourced_qty` be written by a raw UPDATE in the sourcing module: the import-linter contract fails (sourcing must not import the requisitions repo).
