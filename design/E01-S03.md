# E01-S03 — API container image, slim multi-stage, non-root, health endpoints

**Epic** E01 · **M0** · **chore/M** · after **E01-S01** · tags: `security`

## Requirements

- **REL-003** — Health/readiness checks must distinguish process health from dependency readiness.

## Deliverable

The deployable artifact. Everything about hosting portability (D-02, §2.10 of the plan) rests on this image being a plain OCI container with no vendor coupling.

## Behaviour

1. Multi-stage `Containerfile`: a build stage installs dependencies into a venv; the runtime stage copies only the venv and `src/`. Target under 250 MB.
2. Runs as a **non-root** uid (1001), read-only root filesystem, no shell in the runtime stage where practical.
3. Two distinct endpoints — this is the whole point of the story:
   - `GET /healthz` → **liveness**. Returns 200 if the process is running. Touches nothing external. Must never fail because Postgres is down, or the platform will kill a healthy process during a database blip.
   - `GET /readyz` → **readiness**. Checks database connectivity and storage reachability with a short timeout, returns 200 or 503 with a per-dependency body:
     ```json
     {"status":"degraded","checks":{"database":"ok","storage":"timeout"}}
     ```
4. Neither endpoint requires authentication; neither discloses versions, hostnames, or connection strings (SEC-011).
5. `PORT` is read from the environment (Cloud Run supplies it). No hardcoded port.
6. Container honours `SIGTERM` with a graceful drain so in-flight requests finish.

## Acceptance criteria

- [ ] Image builds and `podman run` serves `/healthz` 200
- [ ] With Postgres stopped: `/healthz` still 200, `/readyz` 503 naming `database`
- [ ] Image runs as uid 1001 — `podman inspect` confirms, and `whoami` in the container is not root
- [ ] Final image is under 250 MB
- [ ] `SIGTERM` drains rather than dropping an in-flight request
- [ ] Neither endpoint's body contains a version, hostname, path, or connection string
