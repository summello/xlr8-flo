# E06-S07 — Project list and detail screens, filter/sort/group/search, saved views

**Epic** E06 · **M1** · **ui/L** · after **E06-S03**, **E04-S03** · tags: `ui`

> **Conventions:** read `docs/m1-conventions.md` (authorization outcomes, scope targets, wire formats). It applies unless this packet says otherwise.

## Requirements

- **PROJ-020** — Users must be able to filter, sort, group, search, and save project views.
- **XFN-002** — Module grids must support sorting, filtering, resizing, reordering, visibility, pinning where useful, pagination/virtualization, and saved views.

**Read first (UI story):** `design-system/MASTER.md`, then `design-system/pages/<page>.md` if one exists for projects. Tokens only; no hardcoded colour, spacing, radius or duration.

## Contract

Routes (file-based under `apps/web/src/routes/`, registered in `route-paths.ts`): `/projects` (list), `/projects/new`, `/projects/$projectId` (detail). The placeholder entries `/projects/north-plant-renewal` etc. in `route-paths.ts` are replaced by the real param route; update `tests/a11y/routes.spec.ts` accordingly.

All data comes from the **generated** OpenAPI client (`apps/web/src/api/generated`); hand-written request/response types are a rejection. Endpoints consumed: `GET/POST /api/v1/projects`, `GET/PATCH /api/v1/projects/{id}`, `GET .../transitions/available`, `POST .../transitions`, `GET .../balance`, phases/milestones/risks lists (E06-S01..S06, E07-S06). If the client lacks one of them, regenerate it; if the backend lacks one, it is a blocker, not something to stub in the UI.

## Behaviour

1. **List** uses the existing `DataGrid` (E04-S03): virtualized, server-filtered/sorted (`q`, `status`, `bu_id`, cursor), group by status or BU/OU, column visibility/order/resize/pin, **saved views** through the existing `SavedViews` (PROJ-020, XFN-002). Columns: number, name, status pill (icon + text, never colour alone), BU/OU, owner, health, allocated, available (money: tabular figures, right-aligned, currency code visible, negatives in parentheses and signed and coloured).
2. **Create** form uses the form kit (`Field`, `Combobox` for BU/OU, department and ledger account type-ahead against `/master/...` per XFN-009, `MoneyInput` is not needed here). Programmatic labels, field-level errors, an error summary, input preserved after a server validation failure (A11Y-006). Server 422 field errors map onto the matching fields.
3. **Detail** page: header (number, name, status pill, available transitions as buttons; a blocked transition is shown disabled with the server's `blocked_reasons` text beside it, not hidden), tabs for Overview, Schedule (phases, milestones), Risks, Budget. Budget tab shows the six figures from `BalanceRead` and a link to the ledger list (the dashboard drill-down is E06-S08).
4. Transitions that need a `reason` open a dialog with the reason field; `override` is offered only when the API reports `ClosingBlocked` and the user holds the permission (the permission set comes from the existing effective-access client call).
5. Loading, empty, partial and error states exist for every list and tab (UX-004). Errors state what happened, what was preserved and how to recover (UX-005).
6. Two clicks to common work; tables summarize, side sheets reveal, pages commit (progressive disclosure).

## Pre-flight amendments 3 (Opus, 10 Oct 2026) — answers the block on §6, authoritative

The block was right: `available()` evaluates each target with no reason and no override, so a reason-required edge and an overridable closure both come back `allowed: false`, and §6 then disables the very control that must open the dialog. Ruling:

1. **`allowed` means "can succeed once the required input is supplied", not "succeeds as an empty POST".** In `Lifecycle.available()`, evaluate a reason-required edge (the edge's second flag) with a placeholder reason `"x" * 20` that is never written anywhere; `override` stays `False`. A missing reason therefore never makes `allowed` false; every other problem (permission, maker-checker, missing project fields, `closing_blocked`) still does. Nothing about the transition rules changes: the `POST` path calls `evaluate()` with the real body exactly as today and still returns 422 for a missing reason.
2. **Update `test_available_matches_post`** (allowed under `docs/m1-conventions.md` C, list it in the commit body): for options whose `reason_required` is true, send the comparison `POST` with a 20-character reason; for the rest keep the empty body. The assertion that `allowed` matches the `POST` outcome and that a blocked `POST`'s `detail` appears in `blocked_reasons` stays exactly as strong. Add one test proving a reason-required edge reports `allowed: true` from `available` and still answers 422 to a `POST` without a reason.
3. **UI enabling rule (replaces the first sentence of §6):** a `reachable` control is **enabled** when `allowed` **or** `override_available`; otherwise it is disabled with its `blocked_reasons` visible beside it. An enabled control opens the reason dialog when `reason_required` or `override_available`, and submits directly otherwise. When `override_available` and not `allowed`, the dialog shows the `blocked_reasons` text, the override checkbox and the 20-character rule; it submits `override: true` and renders the server's `403` with the text preserved, as §6 already says. Plants: disable an `override_available` control and the override test fails; enable a control with `allowed: false` and `override_available: false` and the disabled-state test fails.
