# E02-S06 — Effective-access explorer endpoint and screen

**Epic** E02 · **M0** · **api/M** · after **E02-S05** · tags: `auth`

## Requirements

- **USR-010** — Administrators must be able to inspect a user's effective access and the source of inherited permissions.
- **USR-008** — Role, scope, and permission changes must be effective immediately or on a configured date and must be audited.
- **USR-009** — Deactivating a user must block new sessions without deleting historical attribution.

## Deliverable

The answer to "why can this person do that?" — a question that is unanswerable in most systems and therefore never asked until an audit. Building it as a story is the only way it gets built.

## Contract

```
GET /api/v1/admin/users/{id}/effective-access
  → 200 {
      user: {id, email, status},
      grants: [{role, role_name, scope_type, scope_id, scope_name, granted_by, granted_at}],
      permissions: [{code, allowed: true,
                     source: {via_role, via_scope_type, via_scope_id, inherited_from}}],
      denied_examples: [{code, reason: "no grant matches scope bu:17"}]
    }
POST   /api/v1/admin/users/{id}/deactivate  → 204
DELETE /api/v1/admin/users/{id}/roles/{grant_id} → 204
```

## Behaviour

1. **Every allowed permission names its source** — which role, at which scope, and if it reached the target by containment, which ancestor it was inherited from. A bare list of permission codes does not satisfy USR-010.
2. Denials are explainable too: the response includes why a notable permission is *not* held, so an administrator debugging "they cannot approve" gets an answer rather than an absence.
3. Viewing another user's effective access is itself a permission (`admin.access.read`) and is **audited** (AUD-005) — inspecting access is sensitive.
4. **Deactivation (USR-009)** revokes all sessions and blocks new ones, but **deletes nothing**. Every `created_by`, `approved_by`, and audit attribution stays intact and continues to render the user's name with a `(deactivated)` marker. A deactivated user must never be purged or anonymized by this path — that is a retention decision (E18-S08), not an administrative one.
5. **Effective dating (USR-008)** — a grant may carry `effective_from`; the resolver honours it, and the explorer shows pending grants separately from active ones.
6. The screen renders the grant list and a searchable permission table with the source column. It is read-only apart from revoke and deactivate, both of which require step-up re-auth (SEC-009).

## Acceptance criteria

- [ ] Every allowed permission shows role, scope, and inheritance path
- [ ] A permission inherited from an org-level grant names the org grant, not the target record
- [ ] Denials list a reason, not just an absence
- [ ] Viewing effective access writes an audit row naming viewer, subject, and time
- [ ] Deactivation kills existing sessions immediately and blocks new logins
- [ ] After deactivation, a record the user created still shows their name, marked deactivated
- [ ] A grant with a future `effective_from` appears as pending and grants nothing yet
- [ ] Revoke and deactivate both demand step-up re-authentication
- [ ] The screen is fully keyboard operable and passes axe
