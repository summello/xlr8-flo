# E13-S29 — ACC-008 evidence: a keyboard-only walkthrough of the project-to-PO flow

**Epic** E13 · **M3** · **docs/S** · after **E13-S27** · tags: —
Origin: M3 Opus milestone review (finding 1, 8 Nov 2026). ACC-008 is an M3 exit criterion.

## Requirements (inlined)

- **ACC-008** — A complete project-to-PO workflow is operable without a mouse. (M3 exit criterion, docs/claude-plan.md §4:
  "a complete project→requisition→RFQ→award→PO→email flow is operable without a mouse".)

## Finding

Every M3 screen has its own keyboard-only Playwright path, but all 41 e2e specs stub the API per screen
(`page.route`). Nothing drives the chain project → requisition → submit/approve → RFQ → bid → award → PO →
issue → transmission log as one flow, so a broken hand-off between screens (a redirect that drops focus, a
create that lands where the next step has no keyboard route, the missing Close control now E13-S27) passes
every spec. The CI `frontend-e2e` job has no API and no database; the `backend` job has Postgres 17.

## Decision (operator, 8 Nov 2026)

(b) **A manual walkthrough for this release.** This story writes `docs/ops/acc-008-walkthrough.md`, a
keyboard-only checklist for the local stack (`flo up`) or staging; the operator runs it and links the result
from PR #22. The full-stack CI spec (option (a): Postgres, migrated and seeded tenant, API plus built SPA, one
`e2e-live` Playwright spec with no `page.route` and no `.click()`) is a **follow-up before the first paying
customer**, recorded in the PR body, not built here.

## Design

One new file, `docs/ops/acc-008-walkthrough.md`, written from the shipped screens (read the routes and their
keyboard-only Playwright paths, do not copy the canvas). It contains:

1. **Setup:** `flo up`, migrate, bootstrap one tenant and the users the flow needs (requester, approver,
   buyer/RFQ editor, RFQ approver, PO approver/issuer) with the exact commands that exist today (`flo` and the
   bootstrap script; name them, never invent one). Mailpit as the mail stand-in; how to open it. Note that the PO
   email goes out only when the sending-domain gate allows it locally (it does: the gate applies to the `resend`
   provider only, `kernel/email.py` `po_domain_gate`).
2. **Rules for the tester:** mouse unplugged or trackpad off; only Tab, Shift+Tab, Enter, Space, Escape and the
   arrow keys; a step passes only if focus is visible at every stop and nothing needs a pointer; record the
   browser and OS.
3. **The chain, one numbered step per hand-off,** each with: the URL it starts on, the keys pressed (in words,
   e.g. "Tab to `New Requisition`, Enter"), what must be focused on arrival, and the expected result. Cover:
   create a project → create a requisition with one line on it → submit → approve (as approver, from the
   inbox) → create the RFQ from the requisition → invite a vendor and publish → key a bid → close and open the
   comparison → award → approve the award → create the PO from the award → approve the PO → issue → see the
   transmission log and the email in Mailpit → Close the PO (E13-S27's control). Include the drag-and-drop
   equivalents where a screen has drag-and-drop (name the keyboard control).
4. **Result record:** a table to fill (step, pass/fail, note), the date, tester, commit SHA, and where to
   attach it (a comment on PR #22); any failing step is filed as a story before M3 merges.
5. **Follow-up** paragraph: the automated full-stack spec (a), with the shape above, before the first paying
   customer.

Link the new file from `docs/ops/purchase-orders.md` (one line) so operators find it.
