# E13-S29 — ACC-008 evidence: a keyboard-only walkthrough of the project-to-PO flow

**Epic** E13 · **M3** · **chore/M** · after **E13-S27** · tags: —
Origin: M3 Opus milestone review (finding 1, 8 Nov 2026). ACC-008 is an M3 exit criterion.

## Requirements (inlined)

- **ACC-008** — A complete project-to-PO workflow is operable without a mouse. (M3 exit criterion, docs/claude-plan.md §4:
  "a complete project→requisition→RFQ→award→PO→email flow is operable without a mouse".)

## Finding

Every M3 screen has its own keyboard-only Playwright path, but all 41 e2e specs stub the API per screen
(`page.route`). Nothing drives the chain project → requisition → submit/approve → RFQ → bid → award → PO →
issue → transmission log as one flow, so a broken hand-off between screens (a redirect that drops focus, a
create that lands where the next step has no keyboard route, the missing Close control now E13-S27) passes
every spec. The CI `frontend-e2e` job has no API and no database; the `backend` job has Postgres 17.

## Decision (operator, 8 Nov 2026)

(b) **A manual walkthrough for this release.** This story writes `docs/ops/acc-008-walkthrough.md`, a
keyboard-only checklist for the local stack (`flo up`) or staging; the operator runs it and links the result
from PR #22. The full-stack CI spec (option (a): Postgres, migrated and seeded tenant, API plus built SPA, one
`e2e-live` Playwright spec with no `page.route` and no `.click()`) is a **follow-up before the first paying
customer**, recorded in the PR body, not built here.

**Setup (operator, 8 Nov 2026, after pre-flight 2):** a **dev seed command** (dev-only; never runnable against
Neon or production) creates the walkthrough tenant: units, master codes, five distinct people with role grants,
approval and award workflows, fixed amounts. The checklist starts from it. Reusable later by the full-stack
ACC-008 CI spec.

## Design

Three deliverables: the **seed command**, a **local same-origin harness** (the walkthrough cannot run
without one) and the **walkthrough document**. Pre-flight 1 found that `flo up` starts only Postgres, SeaweedFS
and Mailpit (`agents/scripts/flo` ~2954) and that both Vite servers register fixture plugins that answer
`POST /api/v1/auth/login` themselves (`apps/web/vite.config.ts` ~135-175, `plugins` ~179). Pre-flight 2 found
that the tenant cannot be prepared through shipped screens (no screens for units, master codes, invitations or
user grants; `award` is not offered by the workflow builder, `routes/admin/approval-workflows/list.tsx` ~72).
Staging has no second deployed environment (project memory, "Staging database"), so the local stack is the
walkthrough's place.

### 1. Seed: `python -m flo.api.walkthrough_seed` (new file `apps/api/src/flo/api/walkthrough_seed.py`)

It composes existing services in the `flo.api` layer (which may import every module's `service` and `schemas`;
`.importlinter` `layers`), the way `modules/org/bootstrap.py` `main` (~136-196) is a CLI over services. Never raw
`INSERT`s into business tables (the bootstrap's own `organization_code` insert, reached by calling `bootstrap()`,
is the one exception, because it is the shipped bootstrap).

**Guard, checked before any connection is opened; each refusal prints one line naming the reason and exits 2:**
- `DATABASE_URL`'s host (parsed with `urllib.parse.urlsplit`) is not exactly `localhost`, `127.0.0.1` or `::1`
  (this refuses every Neon host, pooled or not, and any other remote database);
- `EMAIL_PROVIDER` is not `smtp` (`Settings.email_provider`, `kernel/config.py` ~77; production is `resend`);
- `STORAGE_PROVIDER` is not `local` (`Settings.storage_provider`; production is `r2`).
A pytest plants each: a Neon-style URL (`postgresql://u:p@ep-x-pooler.eu-central-1.aws.neon.tech/db`), a remote
IP, `EMAIL_PROVIDER=resend` and `STORAGE_PROVIDER=r2` each exit 2 and **never call `psycopg.connect`**
(monkeypatch it to raise). The guard is a plain function `refuse_reason(settings) -> str | None` so the test needs
no database.

**What it creates, in one tenant, idempotent by refusal** (if the org code already exists it prints "already
seeded: use another --org-code or reset the database" and exits 3; it never edits an existing tenant):
- the organization and its administrator through `modules/org/bootstrap.py` `bootstrap()` (org name
  "Walkthrough Co", `--org-code` default `WALK`, base currency USD, admin `admin@example.com`); the administrator
  is MFA-privileged (`MFA_REQUIRED_ROLE_CODES`, `identity/models.py` ~214) and is **not** used in the chain;
- one business unit (`WALK-OPS`, "Operations") with a Bill To address on it (`OrgService.create_address`, kind
  `bill_to`; PO create needs one, as `tests/purchasing/test_purchase_orders.py` `address` ~45 shows), plus a
  delivery address if the requisition form requires one;
- the master codes a requisition line needs (at least one department and one ledger account, plus a unit of
  measure if the line form requires one), active from 2020-01-01;
- five people, each a local identity with membership in the org (`build_local_identity_provider(...)
  .create_identity`, `add_identity_membership`, as `bootstrap()` does), all sharing one password read from
  `FLO_WALKTHROUGH_PASSWORD` (prompted with `getpass` when unset; `PasswordPolicyError` exits 2 like the bootstrap),
  emails at `example.com`:
  | person | email | role grants (baseline roles, `identity/models.py` ~194), scope |
  |---|---|---|
  | Requester | `requester@example.com` | `requestor`, `project-manager` on the unit |
  | Approver | `approver@example.com` | `approver` on the unit (project, requisition and vendor approvals) |
  | Buyer | `buyer@example.com` | `sourcing-specialist`, `purchasing-user` on the unit |
  | Sourcing approver | `sourcing.approver@example.com` | the role the award workflow names, on the unit |
  | PO approver | `po.approver@example.com` | the role the PO workflow names and a role carrying `purchase_order.issue` (`api/purchasing.py` ~90), on the unit |
  None holds `organization-administrator` or `auditor`, so none needs MFA (`kernel/identity/mfa.py`
  `access_requirement` ~214-236) and the walkthrough signs in with email and password only. Where a baseline role
  lacks a permission the chain needs, grant the narrowest baseline role that carries it; never create a new role or
  permission. The table is the target; the author adjusts role names to what the services require and records each
  deviation in the doc's setup section;
- published workflows (`WorkflowService.create` / `create_version` / `publish`, as
  `tests/approvals/test_workflow_definitions.py` ~51-62 and `tests/sourcing/test_award.py` `publish_workflow` ~57
  do) for document types **`project`** (project submit requires it, `projects/service.py` ~224), `requisition`,
  `vendor` (vendor submit requires it, `vendors/changes.py` ~197), `award` (`sourcing/awards.py` ~760) and `po`;
  each one approval step naming the role of the person in the table, so the five approvals land on distinct people
  and separation of duty (`approvals/eligibility.py` ~118) never empties a step;
- one vendor, created directly by the Buyer with a document contact `vendor@example.com` (issue refuses a PO
  without a recipient, `purchasing/issue.py` ~78), submitted and approved through the vendor workflow by the Approver
  (its step names the `approver` role), so it is eligible for the RFQ;
- whatever funding the project in the chain draws on (for example an organization or unit budget), sized so a
  **50,000.00 USD** project fits; if none is needed, nothing.
It prints the org code, the five emails (never the password), the Mailpit URL and the path of the bid evidence file
(below), then exits 0.

**Proof the seed is sufficient:** a pytest (real Postgres, the worktree's test database via the usual fixtures,
with `refuse_reason` satisfied by the test settings) runs the seed's `seed(conn, settings, ...)` function and then
drives the whole chain **through the services** as the seeded people, with the fixed values below: create
project, submit, approve (Approver), create the project-linked requisition, submit, approve (Approver), create the
RFQ (Buyer), invite the vendor, publish (deadline 65 minutes ahead), key and submit the bid with a `.txt` evidence
attachment, close the RFQ by calling `sourcing/lifecycle.py` `close_due` after moving the clock or the
deadline **in the test only**, start evaluation, award, submit and approve the award (Sourcing approver), create
the PO (Buyer), submit and approve it (PO approver), issue it (PO approver). The test asserts the PO is `issued`
with one queued transmission to `vendor@example.com`. A second run against the same database exits 3 and changes
nothing.

**Bid evidence file:** commit `docs/ops/acc-008-bid-evidence.txt` (two lines of plain UTF-8; `.txt` passes
`collaboration/scan_rules.py` `BasicChecksScanner` ~36-60, bid entry refuses without evidence,
`components/sourcing/bids/BidSheet.tsx` ~75).

### 2. Harness (`apps/web/vite.config.ts`, dev only)

- `vite --mode walkthrough` (add `"walkthrough": "vite --mode walkthrough"` to `apps/web/package.json` scripts):
  turn the exported config into `defineConfig(({ mode }) => ...)`; in mode `walkthrough` **only**, `gridFixture()`
  and `formFixture()` are not registered, and `server.proxy` forwards `/api` to `http://127.0.0.1:8000`, adding
  the header `X-FLO-Origin-Secret` with the value of the `ORIGIN_SHARED_SECRET` environment variable, as the
  production Worker does (`apps/web/worker/api-proxy.ts` ~4-18; same 32-character minimum, fail at startup
  otherwise). One origin, no CORS (D-17).
- Every other mode is unchanged: the default dev server and `vite preview` keep both fixtures (the e2e suite
  depends on them) and the `test` block stays.
- A vitest (`apps/web/vite.config.test.ts`) resolves the config for mode `walkthrough` and for the default mode
  and asserts: walkthrough has the `/api` proxy with the header and neither fixture plugin (by plugin `name`,
  `xlr8flo-grid-fixture` / `xlr8flo-form-fixture`); default has both fixtures and no proxy.

### 3. `docs/ops/acc-008-walkthrough.md`

A one-line note at the top: every route and control label below is checkable by grep in `apps/web/src`.

1. **Setup (not part of the evidence).** Exact commands, each verified to exist:
   `flo up`; copy `.env.example` to `.env` (repository root), replace `MFA_ENCRYPTION_KEY` with a generated key (the
   command is in `.env.example`) and add `ORIGIN_SHARED_SECRET` of at least 32 characters; from `apps/api`, with the
   `.env` values exported: `export MIGRATIONS_DIR="$PWD/../../migrations"` then `uv run python -m
   flo.kernel.migrate` (`infra/SETUP.md` ~551-558; without it the runner looks in `/app/migrations`,
   `kernel/config.py` ~43); `FLO_WALKTHROUGH_PASSWORD=... uv run python -m flo.api.walkthrough_seed`; the API
   (`uv run uvicorn flo.api.health:app --port 8000`); the web (`npm run walkthrough` in `apps/web`); Mailpit at
   `http://localhost:8025`.
   **The jobs tick by hand:** the RFQ close and the PO email wait for it. Give the exact `curl`
   (`POST http://127.0.0.1:8000/internal/jobs/tick` with `X-FLO-Origin-Secret`, a fresh `Idempotency-Key`, and a
   matching `flo_csrf` cookie and `X-CSRF-Token`, the protocol `infra/cron-worker/jobs-tick.ts` ~13-30 uses), and
   say at which steps to run it.
   Where a person signs in, the step says which of the five (sign out, sign in as the next).
2. **Rules for the tester:** pointer off; only Tab, Shift+Tab, Enter, Space, Escape, the arrow keys and typing;
   a step passes only if focus is visible at every stop and nothing needs a pointer; the operating system's file
   dialog (bid evidence) is driven by keyboard too (on macOS, Cmd+Shift+G and type the path); record browser and OS.
3. **The chain, keyboard only, one numbered step per hand-off,** each with the person signed in, the start URL,
   the keys pressed (in words), what is focused on arrival and the expected result. **Fixed values:** project
   budget **50,000.00 USD**; requisition one line, quantity **2**, unit price **1,000.00 USD** (estimate 2,000.00,
   within the budget so submit is not refused, `requisitions/validation.py` ~225); RFQ in USD with a deadline
   **65 minutes** ahead (publish refuses a deadline under one hour, `sourcing/lifecycle.py` ~148-156); bid unit
   price **950.00 USD**, evidence `docs/ops/acc-008-bid-evidence.txt`. Steps: create the project with that budget
   (Requester) → submit it → approve it (Approver) so it is `active` (a requisition can only use an active project,
   `requisitions/lookups.py` ~61) → create the requisition (Requester) → submit → approve from the inbox (Approver)
   → create the RFQ from it (Buyer) → invite the vendor and publish → key and submit the bid (bids are keyed
   while the RFQ is published, `sourcing/bids.py` ~383, so this happens during the wait) → **wait until the
   deadline has passed**, then run the tick (the RFQ closes only through the `rfq-close` job,
   `sourcing/lifecycle.py` ~517) → start evaluation and open the comparison → award → submit the award → approve
   it (Sourcing approver) → create the PO from the award (Buyer) → submit → approve the PO (PO approver) → issue
   → run the tick → the transmission log shows the send and the email to `vendor@example.com` is in Mailpit →
   Close the PO (E13-S27). Name the keyboard equivalent wherever a screen has drag-and-drop.
4. **Result record:** a table (step, pass/fail, note), date, tester, commit SHA, to attach as a comment on PR
   #22; a failing step is filed as a story before M3 merges.
5. **Follow-up:** the automated full-stack spec (option (a)) before the first paying customer; the seed and the
   harness above are its starting point.

Link the document from `docs/ops/purchase-orders.md` (one line).

      second seed run exits 3 and changes no row count.

## Plants

1. Register `formFixture()` in the walkthrough mode: the vitest fails.
2. Drop the host check from `refuse_reason`: the Neon-URL guard test fails.
3. Remove the `vendor` workflow from the seed: the service-level chain test fails at vendor approval or RFQ
   invitation.
4. Rename one control label in the doc to a label that does not exist in `apps/web/src`: the reviewer's grep
   finds no match.
