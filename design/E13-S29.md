# E13-S29 — ACC-008 evidence: a keyboard-only walkthrough of the project-to-PO flow

**Epic** E13 · **M3** · **chore/L** · after **E13-S27** · tags: —
Origin: M3 Opus milestone review (finding 1, 8 Nov 2026). ACC-008 is an M3 exit criterion.

## Requirements (inlined)

- **ACC-008** — A complete project-to-PO workflow is operable without a mouse. (M3 exit criterion, docs/claude-plan.md §4:
  "a complete project→requisition→RFQ→award→PO→email flow is operable without a mouse".)

## Finding

Every M3 screen has its own keyboard-only Playwright path, but all 41 e2e specs stub the API per screen
(`page.route`). Nothing drives the chain project → requisition → submit/approve → RFQ → bid → award → PO →
issue → transmission log as one flow, so a broken hand-off between screens (a redirect that drops focus, a
create that lands where the next step has no keyboard route, the missing Close control now E13-S27) passes
every spec. The CI `frontend-e2e` job has no API and no database; the `backend` job has Postgres 17.

## Decision (operator, 8 Nov 2026)

(b) **A manual walkthrough for this release.** This story writes `docs/ops/acc-008-walkthrough.md`, a
keyboard-only checklist for the local stack (`flo up`) or staging; the operator runs it and links the result
from PR #22. The full-stack CI spec (option (a): Postgres, migrated and seeded tenant, API plus built SPA, one
`e2e-live` Playwright spec with no `page.route` and no `.click()`) is a **follow-up before the first paying
customer**, recorded in the PR body, not built here.

**Setup (operator, 8 Nov 2026, after pre-flight 2):** a **dev seed command** (dev-only; never runnable against
Neon or production) creates the walkthrough tenant: units, master codes, five distinct people with role grants,
approval and award workflows, fixed amounts. The checklist starts from it. Reusable later by the full-stack
ACC-008 CI spec.

## Design

Three deliverables: the **seed command**, a **local same-origin harness** (the walkthrough cannot run
without one) and the **walkthrough document**. Pre-flight 1 found that `flo up` starts only Postgres, SeaweedFS
and Mailpit (`agents/scripts/flo` ~2954) and that both Vite servers register fixture plugins that answer
`POST /api/v1/auth/login` themselves (`apps/web/vite.config.ts` ~135-175, `plugins` ~179). Pre-flight 2 found
that the tenant cannot be prepared through shipped screens (no screens for units, master codes, invitations or
user grants; `award` is not offered by the workflow builder, `routes/admin/approval-workflows/list.tsx` ~72).
Staging has no second deployed environment (project memory, "Staging database"), so the local stack is the
walkthrough's place.

### 1. Seed: `python -m flo.api.walkthrough_seed` (new file `apps/api/src/flo/api/walkthrough_seed.py`)

It composes existing services in the `flo.api` layer (which may import every module's `service` and `schemas`;
`.importlinter` `layers`), the way `modules/org/bootstrap.py` `main` (~136-196) is a CLI over services. Never raw
`INSERT`s into business tables (the bootstrap's own `organization_code` insert, reached by calling `bootstrap()`,
is the one exception, because it is the shipped bootstrap).

**Guard, checked on the raw environment before `Settings()` is constructed and before any connection is opened;
each refusal prints one line naming the reason and exits 2.** It reads `os.environ` directly, because `Settings`
(`kernel/config.py` ~175, `require_neon_transaction_pooler`) raises its own multi-line validation error on a
non-pooler Neon URL during construction, before any later check could run. Variable names carry the `FLO_`
prefix (`SettingsConfigDict(env_prefix="FLO_")`, `kernel/config.py` ~21):
- `FLO_DATABASE_URL`'s host (parsed with `urllib.parse.urlsplit`) is not exactly `localhost`, `127.0.0.1` or `::1`
  (this refuses every Neon host, pooled or not, and any other remote database);
- `FLO_EMAIL_PROVIDER` is not `smtp` (`Settings.email_provider`, `kernel/config.py` ~77; production is `resend`);
- `FLO_STORAGE_PROVIDER` is not `local` (`Settings.storage_provider`; production is `r2`).
An unset variable is refused like a wrong one (the guard does not apply `Settings`' defaults).
A pytest plants each: a pooled Neon URL (`postgresql://u:p@ep-x-pooler.eu-central-1.aws.neon.tech/db`), a
non-pooler Neon URL (`postgresql://u:p@ep-x.eu-central-1.aws.neon.tech/db`, which `Settings` itself would reject),
a remote IP, `FLO_EMAIL_PROVIDER=resend` and `FLO_STORAGE_PROVIDER=r2` each exit 2 with the guard's one line and
**never call `psycopg.connect` or construct `Settings`** (monkeypatch both to raise). The guard is a plain function
`refuse_reason(env: Mapping[str, str]) -> str | None`, called as `refuse_reason(os.environ)` first thing in
`main()`, so the test needs no database.

**What it creates, in one tenant, idempotent by refusal** (if the org code already exists it prints "already
seeded: use another --org-code or reset the database" and exits 3; it never edits an existing tenant):

### 2. Harness (`apps/web/vite.config.ts`, dev only)

- `vite --mode walkthrough` (add `"walkthrough": "vite --mode walkthrough"` to `apps/web/package.json` scripts):
  turn the exported config into `defineConfig(({ mode }) => ...)`; in mode `walkthrough` **only**, `gridFixture()`

  production Worker does (`apps/web/worker/api-proxy.ts` ~4-18; same 32-character minimum, fail at startup
  otherwise). One origin, no CORS (D-17).

  depends on them) and the `test` block stays.
- A vitest (`apps/web/vite.config.test.ts`) resolves the config for mode `walkthrough` and for the default mode
  and asserts: walkthrough has the `/api` proxy with the header and neither fixture plugin (by plugin `name`,
  `xlr8flo-grid-fixture` / `xlr8flo-form-fixture`); default has both fixtures and no proxy.
