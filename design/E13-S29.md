# E13-S29 — ACC-008 evidence: a keyboard-only walkthrough of the project-to-PO flow

**Epic** E13 · **M3** · **chore/M** · after **E13-S27** · tags: —
Origin: M3 Opus milestone review (finding 1, 8 Nov 2026). ACC-008 is an M3 exit criterion.

## Requirements (inlined)

- **ACC-008** — A complete project-to-PO workflow is operable without a mouse. (M3 exit criterion, docs/claude-plan.md §4:
  "a complete project→requisition→RFQ→award→PO→email flow is operable without a mouse".)

## Finding

Every M3 screen has its own keyboard-only Playwright path, but all 41 e2e specs stub the API per screen
(`page.route`). Nothing drives the chain project → requisition → submit/approve → RFQ → bid → award → PO →
issue → transmission log as one flow, so a broken hand-off between screens (a redirect that drops focus, a
create that lands where the next step has no keyboard route, the missing Close control now E13-S27) passes
every spec. The CI `frontend-e2e` job has no API and no database; the `backend` job has Postgres 17.

## Decision (operator, 8 Nov 2026)

(b) **A manual walkthrough for this release.** This story writes `docs/ops/acc-008-walkthrough.md`, a
keyboard-only checklist for the local stack (`flo up`) or staging; the operator runs it and links the result
from PR #22. The full-stack CI spec (option (a): Postgres, migrated and seeded tenant, API plus built SPA, one
`e2e-live` Playwright spec with no `page.route` and no `.click()`) is a **follow-up before the first paying
customer**, recorded in the PR body, not built here.

## Design

Two deliverables: a **local same-origin harness** (the walkthrough cannot run without one) and the
**walkthrough document**. Pre-flight 1, 8 Nov 2026 found that `flo up` starts only Postgres, SeaweedFS and
Mailpit (`agents/scripts/flo` ~2954) and that both Vite servers register fixture plugins that answer
`POST /api/v1/auth/login` themselves (`apps/web/vite.config.ts` ~137-170, `plugins` ~179), so no local page reaches a
real API today. Staging has no second deployed environment (project memory, "Staging database"), so the local
stack is the walkthrough's place.

### 1. Harness (`apps/web/vite.config.ts`, dev only)

- `vite --mode walkthrough` (add `"walkthrough": "vite --mode walkthrough"` to `apps/web/package.json` scripts):
  in that mode **only**, `gridFixture()` and `formFixture()` are not registered, and `server.proxy` forwards
  `/api` to `http://127.0.0.1:8000`, adding the header `X-FLO-Origin-Secret` with the value of the
  `ORIGIN_SHARED_SECRET` environment variable, as the production Worker does (`apps/web/worker/api-proxy.ts` ~4-18;
  same 32-character minimum, fail at startup otherwise). One origin, no CORS (D-17).
- Every other mode is byte-for-byte unchanged: the default dev server and `vite preview` keep both fixtures
  (the e2e suite depends on them).
- A vitest beside the existing config tests (or a new `vite.config.test.ts`) resolves the config for mode
  `walkthrough` and for the default mode and asserts: walkthrough has the `/api` proxy and neither fixture plugin;
  default has both fixtures and no proxy.

### 2. `docs/ops/acc-008-walkthrough.md`

1. **Setup (not part of the evidence; pointer allowed).** Exact commands, each verified to exist:
   `flo up`; `.env` from `.env.example` with a generated `MFA_ENCRYPTION_KEY` and an `ORIGIN_SHARED_SECRET` of at
   least 32 characters; `python -m flo.kernel.migrate` (apps/api venv); the bootstrap command
   (`python -m flo.modules.org.bootstrap --org-name … --org-code … --admin-email …`, `infra/SETUP.md` ~575); the
   API (`uvicorn flo.api.health:app --port 8000` from `apps/api` with the `.env` loaded); the web
   (`npm run walkthrough` in `apps/web`); Mailpit at `http://localhost:8025`.
   **The jobs tick by hand:** invitations, RFQ close and the PO email all wait for it. Give the exact `curl`
   (`POST http://127.0.0.1:8000/internal/jobs/tick` with `X-FLO-Origin-Secret`, a fresh `Idempotency-Key`, and a
   matching `flo_csrf` cookie and `X-CSRF-Token`, the protocol `infra/cron-worker/jobs-tick.ts` ~13-30 uses), and say
   at which steps to run it.
   **Tenant data, created through the shipped admin screens as the bootstrap administrator:** one business unit;
   the master codes a requisition line needs (department, ledger account); invite and accept five people (invitation
   emails arrive in Mailpit after a tick) and grant roles so that the requester, the requisition approver, the
   buyer (RFQ editor), the RFQ/award approver and the PO approver/issuer are **distinct** people (separation of
   duty removes a requester from their own approvers, `approvals/eligibility.py` ~118); publish workflows for
   project request, requisition, award and purchase order (governed submits fail without one,
   `approvals/service.py` ~229); one vendor created directly, with a document recipient email (issue refuses a PO
   without one, `purchasing/issue.py` ~74), submitted and approved by a person other than its creator.
   If any of these has no shipped screen, write the step as the screen that does exist; if none does, stop and write
   `notes.blocked` naming it. Never insert rows with SQL.
2. **Rules for the tester:** pointer off; only Tab, Shift+Tab, Enter, Space, Escape and the arrow keys; a step
   passes only if focus is visible at every stop and nothing needs a pointer; record browser and OS.
3. **The chain, keyboard only, one numbered step per hand-off,** each with the start URL, the keys pressed (in
   words), what is focused on arrival and the expected result. **Fixed values:** project budget **50,000.00 USD**;
   requisition one line, quantity **2**, unit price **1,000.00 USD** (estimate 2,000.00, within the budget so submit is
   not refused, `requisitions/validation.py` ~225); RFQ in USD with a deadline **5 minutes** ahead; bid unit price
   **950.00 USD**. Steps: create the project with that budget → submit it → approve it (as its approver) so it is
   `active` (a requisition can only use an active project, `requisitions/lookups.py` ~61) → create the requisition
   → submit → approve (from the inbox) → create the RFQ from it → invite the vendor and publish → key and submit the
   bid → after the deadline run the tick (the RFQ closes only through the `rfq-close` job,
   `sourcing/lifecycle.py` ~517) → open the comparison → award → approve the award → create the PO from the award →
   approve the PO → issue → run the tick → the transmission log shows the send and the email is in Mailpit → Close
   the PO (E13-S27). Name the keyboard equivalent wherever a screen has drag-and-drop.
4. **Result record:** a table (step, pass/fail, note), date, tester, commit SHA, to attach as a comment on PR #22;
   a failing step is filed as a story before M3 merges.
5. **Follow-up:** the automated full-stack spec (option (a)) before the first paying customer; the harness above
   is its starting point.
