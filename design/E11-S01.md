## Requirements (inlined)

- **VEN-001** — The system must maintain a simplified, searchable vendor list for sourcing and PO generation.
- **VEN-008** — Vendor availability must be global or restricted to selected BU/OUs.
- **VEN-009** — Global vendors may be locally disabled where policy allows, without deleting global history.
- **ORG-003** — Vendor availability must support global and BU/OU-local scope.

## Why it is first

Every vendor, RFQ and PO story builds on this table. Keep it to the record, its availability and the
list. Status *transitions* (submit, approve, suspend, reactivate) are **E11-S06**. Tax and banking
are **E11-S04**. Documents are **E11-S03**. Contacts are **E11-S02**. Eligibility, the derived
"can I use this vendor here" rule, is **E11-S11**. Do not start any of them here.

## Data (one migration, next revision after the head)

New module `apps/api/src/flo/modules/vendors/` (models, repo, schemas, service, router), with its
own import-linter contract like every other module (`service` and `schemas` are its public
surface).

`vendor`
- `id uuid`, `org_id uuid` (RLS, `tenant_isolation` policy like every tenant table)
- `number text`, unique per org, allocated by `org.numbering` with a new `"vendor"` document type.
  Add `"vendor"` to the `DocumentType` literal in `modules/org/numbering.py`, with a default format
  of `V-{seq:06}`. Numbers are never reused.
- `trading_name text NOT NULL`, `legal_name text NOT NULL`, each 1..200 chars after trim
- `status text NOT NULL` CHECK in **exactly** `draft`, `pending_approval`, `active`, `suspended`,
  `inactive`, `rejected` (MASTER §2.3; E11-S09 builds the web map from these keys). New rows are
  `draft`.
- `availability text NOT NULL` CHECK in `global`, `restricted`
- `created_by uuid`, `created_at`, `updated_at`

`vendor_unit` (where a **restricted** vendor is available): `vendor_id`, `unit_id` (FK `org_unit`),
`org_id`, PK (`vendor_id`, `unit_id`). A restricted vendor has ≥1 row. A global vendor has none, and
the service enforces both.

`vendor_local_disable` (a **global** vendor switched off in one unit): `vendor_id`, `unit_id`,
`org_id`, `disabled_by`, `disabled_at`, `reason text NOT NULL`; PK (`vendor_id`, `unit_id`).
Enabling deletes the row. History is the audit log (`vendor.local_disable`, `vendor.local_enable`,
with the reason). The vendor row is never touched, which is VEN-009's "without deleting global
history".

Indexes: `(org_id, status)`, plus `lower(trading_name)` and `lower(legal_name)` for search.

## Availability rule (Opus decision, recorded here)

A vendor is **available in unit U** when it is `global` and not locally disabled in U or any
ancestor of U, or when it is `restricted` and U or any ancestor of U is in `vendor_unit`.
Restricting to a BU therefore covers its OUs, and disabling in a BU disables it for that BU's OUs.
`service.available_in(vendor_id, unit_id) -> bool` is the one implementation. E11-S11's eligibility
calls it and never re-derives it. Walk ancestors with the existing `org_unit.parent_id` chain, as a
recursive CTE in the repo.

## Organization setting

`vendor.allow_local_disable` (bool, default `false`) in `modules/org/settings.py`: add it to
`SETTING_DEFAULTS` and `SETTING_VALIDATORS` (`_is_bool`). It resolves through the existing nearest-
unit override. Read it for the unit being disabled.

## API (all under `/api/v1`, problem details on error, foreign tenant → 404)

| Method and path | Permission | Behaviour |
|---|---|---|
| `GET /vendors?q=&status=&available_in=&cursor=&limit=` | `vendor.view` (org) | Server paging, `limit` ≤ 100, default 50. `q` matches trading name, legal name or number (case-insensitive substring), **never a tax id**. `status` repeatable. `available_in=<unit_id>` filters by the availability rule. Sorted by trading name, then id. |
| `GET /vendors/{id}` | `vendor.view` | Record plus `units` (restricted) and `disabled_in` (`[{unit_id, unit_code, by_email, at, reason}]`). |
| `POST /vendors` (Idempotency-Key) | `vendor.create` | Creates `draft`. Body: names, `availability`, `unit_ids` (required iff restricted, each a unit of this org; unknown → 422 per field). 201 with the record. |
| `PATCH /vendors/{id}` (Idempotency-Key) | `vendor.edit` | Names, and availability **only while `draft`**: after that, availability changes are an approval (E11-S06), so return 409 `availability_needs_approval`. |
| `POST /vendors/{id}/units/{unit_id}/disable` (Idempotency-Key) | `vendor.edit` **at that unit** | Body `{reason}` (1..500). 409 `not_global` if restricted; 409 `local_disable_not_allowed` if the setting is false for that unit; 409 `already_disabled`. Effective at once, no approval (decision 6h-5). |
| `POST /vendors/{id}/units/{unit_id}/enable` (Idempotency-Key) | `vendor.edit` at that unit | Deletes the row; 409 `not_disabled`. |

Every write is audited through the kernel audit writer (`vendor.create`, `vendor.update`,
`vendor.local_disable`, `vendor.local_enable`) with before/after. Use E22-S03's shared helper if it
has merged when you start; otherwise call `kernel.audit` directly, and do not add a thirteenth
module-local wrapper. The people in responses are emails (D-M2-16).

The permission codes already exist and are granted (`vendor-manager`: view, create, edit, approve;
`sourcing-specialist`: view). `tests/authz/test_catalogue_gate.py` must stay green. If you check a
code at unit scope, use the existing scoped check that requisitions use; do not invent one.

Generate the OpenAPI client after the router lands (hand-written types are a rejection).

## Acceptance

- [ ] Migration up, down and data preservation (a vendor with units and a local disable survives down→up of the *previous* revision; down drops only this story's objects).
- [ ] Create restricted without units → 422 on `unit_ids`; create global with units → 422.
- [ ] List: `q` finds by trading name, legal name and number; paging is stable across two pages with equal names; `available_in` honours the ancestor rule both ways (restricted to BU covers its OU; disabled in BU hides it in the OU).
- [ ] Local disable: refused when the setting is false (409), refused on a restricted vendor (409), refused without `vendor.edit` at that unit (403), allowed and audited otherwise. Enable reverses it. The vendor row's `updated_at` does not change on either.
- [ ] PATCH availability on a non-draft vendor → 409 `availability_needs_approval`.
- [ ] TEN-010: another tenant's vendor is 404 on GET, PATCH, disable and enable, and absent from the list.
- [ ] Authorization per role: requestor (no `vendor.view`) → 403 on list; sourcing-specialist can list but not create; vendor-manager can do all.
- [ ] Route coverage and isolation registries list every new route.
- [ ] `flo check` green.

## Plants (prove each guard fails)

1. Drop the ancestor walk (match only the exact unit): the BU-covers-OU test fails.
2. Remove the setting check: the 409 `local_disable_not_allowed` test fails.
3. Remove `org_id` from the list query's scope: TEN-010 fails (the scoped repo should make this fail to type-check, so say which).
